Chapter 22 — Project 6 — FastAPI

A frontend can display a token, but only a backend can trust one. In this project we build a production-grade Python API with FastAPI that accepts Auth0-issued access tokens, cryptographically verifies them against Auth0's public keys, and authorizes each request by scope — all without ever calling Auth0 on the hot path. We will derive, from first principles, exactly what a JWT is, why signature verification is the entire ballgame, how the JWKS endpoint distributes Auth0's public keys, why PyJWKClient caches them, and how FastAPI's dependency-injection system lets us turn "is this caller allowed?" into a one-line decorator on any route. By the end you will have a fully secured API, an interactive Swagger UI that knows how to obtain tokens, and curl and Postman recipes to prove every path works. This is the resource-server half of OAuth 2.0, done correctly.

1. Theory — First Principles of Stateless API Authorization

Before a single line of Python, we must answer one question precisely: when an HTTP request arrives at our API carrying a token, what does it mean to "verify" it, and why is that enough to trust the caller? Everything else is plumbing.

The three actors of OAuth 2.0

Our FastAPI service plays exactly one role in the OAuth 2.0 cast, and confusing the roles is the most common source of broken integrations:

  • Authorization Server (AS) — Auth0. It authenticates users, mints access tokens, and publishes its public keys. We do not build this.
  • Client — the app that obtained the token (a React SPA, a mobile app, a machine-to-machine service). We do not build this here either.
  • Resource Server (RS) — our FastAPI API. Its only job: accept a request, validate the access token attached to it, and serve or deny the resource. This chapter is entirely about being a correct Resource Server.

What an access token actually is

An Auth0 access token (for an API audience) is a JWT — a JSON Web Token. It is three Base64URL-encoded segments joined by dots: header.payload.signature. Crucially, the first two parts are not encrypted — anyone can decode and read them. The token is not a secret you keep; it is a signed claim you verify. The security comes entirely from the third segment: a digital signature produced by Auth0's private key, verifiable by Auth0's public key.

SegmentContainsExample fields
HeaderAlgorithm & key idalg: RS256, kid: "abc123", typ: "JWT"
Payload (claims)Who, for whom, when, whatiss, aud, sub, exp, iat, scope, permissions
SignatureProof the AS signed itRSA-SHA256 over header.payload

Why asymmetric (RS256) and not symmetric (HS256)

HS256 signs with a shared secret: whoever can verify can also forge. That is acceptable only when issuer and verifier are the same trusted party. With Auth0 they are not — Auth0 issues, your API verifies. So Auth0 uses RS256: it signs with a private key it never reveals, and publishes the matching public key so any number of resource servers can verify without ever being able to mint a token. This asymmetry is the foundation of decentralized, stateless trust.

The five checks that constitute "valid"

A token is trustworthy only if all of these pass. Skipping any one is a real vulnerability:

  1. Signature — verified against Auth0's public key for the matching kid. Proves authenticity and integrity.
  2. Issuer (iss) — must equal https://YOUR_TENANT/. Proves which AS minted it.
  3. Audience (aud) — must contain your API's identifier. Proves the token was meant for you, not some other API in the same tenant.
  4. Expiry (exp) / not-before (nbf) — must be currently valid. Limits the blast radius of a stolen token.
  5. Authorization (scope/permissions) — does this valid token grant the specific action this route requires?
Key

Authentication of the token (checks 1–4) answers "is this a genuine, current Auth0 token meant for me?" Authorization (check 5) answers "does it permit this operation?" A valid token is necessary but never sufficient — a read token must not delete.

2. Story-Based Explanation — The Nightclub With No Phone

Picture a nightclub, Club FastAPI. At the door stands a bouncer. Patrons arrive holding wristbands issued earlier that evening by a separate, trusted ticketing office across town — call it Auth0 Tickets Inc.

A naïve bouncer would, for every patron, phone the ticketing office and ask "is wristband #4471 real?" That works, but it is slow, and if the phone line goes down the club grinds to a halt. The clever bouncer does something better: at the start of the night he picks up a tamper-proof reference card from the office showing the exact embossing pattern genuine wristbands carry. Now he can verify any wristband by inspection — no phone call per guest. He only refreshes the reference card if he sees an embossing pattern he doesn't recognize.

That reference card is the JWKS (JSON Web Key Set): Auth0's published public keys. The embossing pattern is the RS256 signature. The bouncer verifying by inspection is your API doing local, offline JWT validation. And the rare refresh-on-unknown-pattern is exactly how PyJWKClient behaves — cache the keys, refetch only when an unfamiliar kid appears.

But the wristband alone is not the whole story. Some bands say "GENERAL", some say "VIP", some say "STAFF — backstage". The bouncer at the main door only checks the band is genuine and unexpired. The bouncer at the backstage door additionally checks it says "STAFF". That second check is the scope/permission check, and in FastAPI it becomes a tiny, reusable dependency we attach to exactly the routes that need it.

Note

The whole point of stateless verification: the bouncer never phones the office per guest. Your API never calls Auth0 per request. That is what makes JWT-based APIs scale to millions of requests with single-digit-millisecond auth overhead.

4. Real-World Analogy — The Passport and the Visa

Think of international travel. Your passport is issued by a government (the authorization server). A border officer in another country (your API) does not phone your government to verify you — that would be absurd at scale. Instead, every government distributes the security features of its passports (holograms, chip signatures) to border agencies. The officer verifies the passport locally against those known features. That distribution is the JWKS; the local check is signature verification.

But a valid passport only proves who you are. To enter the country you may also need a visa — and a tourist visa does not let you take up employment. The passport is authentication; the visa class is authorization. In our API, the JWT signature/issuer/audience checks are the passport; the scope (read:items vs delete:items) is the visa class. A genuine passport with a tourist visa correctly gets you across the border (200 on a read) but correctly gets you turned away at the work-permit desk (403 on a delete).

The exp claim is the passport/visa expiry date. The aud claim is the destination stamped on the visa — a visa for France does not admit you to Germany, just as a token minted for another API must be rejected by yours even though both came from the same Auth0 tenant.

Tip

The audience check is the one beginners most often forget — and it is a genuine privilege-escalation hole. Without it, a token your tenant issued for a low-value API would be accepted by your high-value API. Always pin audience to your API identifier.

5. Internal Working — What Happens Inside jwt.decode

To trust a library you must know what it does. Here is the exact sequence PyJWT performs when you call jwt.decode(token, key, algorithms=["RS256"], audience=..., issuer=...):

  1. Split & decode. The token string is split on dots into three parts. The header and payload are Base64URL-decoded into JSON. No crypto yet — anyone can do this.
  2. Algorithm gate. The header's alg is checked against your explicit algorithms=["RS256"] allow-list. This single line defeats the infamous alg-confusion and alg=none attacks (more in §9).
  3. Recompute the signing input. The library takes the raw base64(header) + "." + base64(payload) bytes — exactly what Auth0 signed.
  4. Verify the signature. Using the RSA public key, it computes whether the provided signature is a valid RSA-SHA256 signature of the signing input. If the token was altered by even one bit, this fails. This is the cryptographic heart of the whole system.
  5. Validate registered claims. With the signature trusted, the library checks exp (not expired, allowing optional leeway), nbf/iat, then compares aud against your expected audience and iss against your expected issuer. Any mismatch raises a specific exception.
  6. Return claims. Only if every step passes does it return the payload dict for your code to authorize against.

Where the key comes from: PyJWKClient

Step 4 needs the right public key. Auth0 may hold several keys (it rotates them). The token's header kid says which one signed it. PyJWKClient encapsulates this:

  • On first use, it HTTP-GETs https://YOUR_TENANT/.well-known/jwks.json — a JSON document listing every public key with its kid, modulus n, exponent e, and type.
  • It builds an in-memory cache mapping kid → key.
  • get_signing_key_from_jwt(token) reads the token's kid and returns the cached key. If the kid is unknown, it refetches the JWKS once (handling key rotation) before giving up.

The net effect: at most one network call per unique key, not one per request. With lifespan-cached or module-level client instances, your steady-state auth cost is pure CPU — an RSA verification, microseconds of work.

Note

The JWKS document never contains a private key. The fields n (modulus) and e (exponent) fully describe the RSA public key. You can mathematically verify signatures with them but cannot derive the private key — that is the one-way trapdoor RSA is built on.

6.2 Configuration (never hard-code tenant values)

Pull your Auth0 domain and API audience from environment variables. The issuer is your domain wrapped in https://…/ (note the trailing slash — Auth0 includes it, and a mismatch will reject every token).

# config.py
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    auth0_domain: str           # e.g. "my-tenant.us.auth0.com"
    auth0_api_audience: str      # e.g. "https://api.myapp.com"
    auth0_algorithms: str = "RS256"

    @property
    def issuer(self) -> str:
        return f"https://{self.auth0_domain}/"

    @property
    def jwks_url(self) -> str:
        return f"https://{self.auth0_domain}/.well-known/jwks.json"

    class Config:
        env_file = ".env"

settings = Settings()

6.3 The JWT verifier

This is the core. A single PyJWKClient is created once at import time (so the cache is shared across all requests). verify_jwt performs every check from §1 and raises a precise HTTPException on each failure mode.

# auth.py
import jwt
from jwt import PyJWKClient
from fastapi import Depends, HTTPException, status
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
from config import settings

# One client, created once → shared, cached JWKS for the whole process.
_jwks_client = PyJWKClient(settings.jwks_url, cache_keys=True)

# Tells FastAPI to read the "Authorization: Bearer <token>" header
# and to advertise Bearer auth in the OpenAPI schema.
bearer_scheme = HTTPBearer(auto_error=True)

def verify_jwt(
    creds: HTTPAuthorizationCredentials = Depends(bearer_scheme),
) -> dict:
    token = creds.credentials
    try:
        # 1. Resolve the right public key by the token's "kid" (cached).
        signing_key = _jwks_client.get_signing_key_from_jwt(token)

        # 2. Verify signature + iss + aud + exp in one call.
        claims = jwt.decode(
            token,
            signing_key.key,
            algorithms=[settings.auth0_algorithms],   # RS256 ONLY
            audience=settings.auth0_api_audience,       # must match our API
            issuer=settings.issuer,                     # must match our tenant
            options={"require": ["exp", "iat", "iss", "aud"]},
        )
        return claims

    except jwt.ExpiredSignatureError:
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "Token expired")
    except jwt.InvalidAudienceError:
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "Invalid audience")
    except jwt.InvalidIssuerError:
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "Invalid issuer")
    except jwt.PyJWKClientError:
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "Signing key not found")
    except jwt.InvalidTokenError:
        # Catch-all for signature failures, malformed tokens, etc.
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "Invalid token")

6.4 The scope checker (a dependency factory)

Authorization is a separate concern from authentication. require_scope is a factory: you call it with the scope a route needs, and it returns a dependency that runs after verify_jwt, inspecting the already-verified claims.

# auth.py (continued)
from typing import Callable

def require_scope(required: str) -> Callable:
    def checker(claims: dict = Depends(verify_jwt)) -> dict:
        # Auth0 puts space-delimited scopes in "scope";
        # RBAC-enabled APIs may also use a "permissions" list.
        token_scopes = set(claims.get("scope", "").split())
        token_perms = set(claims.get("permissions", []))
        granted = token_scopes | token_perms
        if required not in granted:
            raise HTTPException(
                status.HTTP_403_FORBIDDEN,
                f"Missing required scope: {required}",
            )
        return claims
    return checker
Key

Note the status codes: a bad/missing/expired token is 401 Unauthorized ("we don't know who you are"). A valid token lacking the needed scope is 403 Forbidden ("we know who you are, and you may not do this"). Getting this distinction right is both a correctness issue and a frequent interview/cert question.

7. Practical Implementation — Securing Real Routes

Now we wire the verifier into an actual API. We expose a public route (no auth), a private route (any valid token), and a scoped route (requires a specific permission).

# main.py
from fastapi import FastAPI, Depends
from auth import verify_jwt, require_scope

app = FastAPI(
    title="Auth0-Protected API",
    description="A FastAPI resource server validating Auth0 RS256 access tokens.",
    version="1.0.0",
)

# --- Public: anyone, no token needed --------------------------------
@app.get("/api/public")
def public():
    return {"message": "Anyone can see this — no token required."}

# --- Private: any authenticated caller ------------------------------
@app.get("/api/private")
def private(claims: dict = Depends(verify_jwt)):
    return {
        "message": "You presented a valid Auth0 token.",
        "subject": claims["sub"],
        "scopes": claims.get("scope", ""),
    }

# --- Scoped: valid token AND the read:items permission --------------
@app.get("/api/items")
def list_items(claims: dict = Depends(require_scope("read:items"))):
    return {"items": ["alpha", "beta", "gamma"], "owner": claims["sub"]}

# --- Scoped write: requires delete:items ----------------------------
@app.delete("/api/items/{item_id}")
def delete_item(item_id: str,
                claims: dict = Depends(require_scope("delete:items"))):
    return {"deleted": item_id, "by": claims["sub"]}

Run it:

uvicorn main:app --reload --port 8000
# Swagger UI:  http://localhost:8000/docs
# ReDoc:       http://localhost:8000/redoc

7.1 Making Swagger obtain tokens for you

By default HTTPBearer lets testers paste a token into Swagger's "Authorize" box. To let Swagger run the full Authorization Code + PKCE flow against Auth0, configure OpenAPI's OAuth2 settings:

# main.py — let Swagger drive the Auth0 login flow
app = FastAPI(
    title="Auth0-Protected API",
    swagger_ui_init_oauth={
        "clientId": "YOUR_SPA_CLIENT_ID",
        "usePkceWithAuthorizationCodeGrant": True,
        "scopes": "openid profile read:items delete:items",
        "additionalQueryStringParams": {
            "audience": "https://api.myapp.com",   # forces a JWT access token
        },
    },
)
Warn

The audience query param is essential. Without it, Auth0 may return an opaque access token (not a JWT) usable only against /userinfo. Passing your API identifier as the audience forces Auth0 to mint a verifiable RS256 JWT for your API.

Key architectural properties that fall out of stateless JWT validation:

  • Horizontal scaling is free. Because each replica verifies tokens with its own cached keys and no session store, you can add or kill instances at will. No sticky sessions, no shared Redis for auth.
  • Auth0 is off the hot path. A traffic spike to your API does not spike traffic to Auth0. The JWKS endpoint is hit a handful of times per process lifetime.
  • Run with multiple workers. In production use gunicorn -k uvicorn.workers.UvicornWorker -w 4 main:app. Each worker has its own cache — acceptable, since JWKS is tiny and fetched rarely.
  • Resilience. If Auth0's JWKS endpoint is briefly unreachable, already-cached keys keep serving traffic. Only first-ever startup or a key rotation depends on reachability.
Tip

For very large fleets, warm the JWKS cache at startup in a lifespan handler so the first real user request never pays the fetch latency, and so a misconfigured tenant fails fast on boot rather than on first traffic.

Defense-in-depth checklist

  • Always HTTPS. A bearer token is a password-equivalent; never transmit it over plaintext.
  • Explicit algorithm allow-list. Never derive the algorithm from the token. This is non-negotiable.
  • Validate iss and aud every time. They are cheap and they close real holes.
  • Short token lifetimes + refresh tokens at the client. Limits the value of a stolen access token.
  • Treat scope absence as deny. Default to 403; never "allow if unsure".
  • Consider revocation needs. JWTs are valid until exp; if you need instant revocation, keep lifetimes very short or add a fast denylist check for high-risk operations.
Danger

The single most dangerous shortcut is calling jwt.decode(token, options={"verify_signature": False}) "just to read the claims." Any code path that trusts an unverified token is a full authentication bypass. Decode-without-verify is only ever acceptable for non-security display (and even then, label it loudly).

10. Performance Considerations

  • JWKS caching is the whole game. A naïve implementation that fetches JWKS on every request adds a network round-trip (tens to hundreds of ms) to every call and can rate-limit you out of Auth0. With PyJWKClient's cache, steady-state auth cost is one RSA verify — typically well under a millisecond.
  • RSA verification is CPU work, not I/O. RS256 verification is cheap but not free. At extreme throughput, profile it; it parallelizes across workers/cores.
  • Reuse one client instance. Creating a new PyJWKClient per request throws away the cache and re-fetches. Define it once at module scope (as we did) or in lifespan.
  • Async I/O for the rest. FastAPI shines with async def handlers; verification itself is sync/CPU, but everything downstream (DB, upstream calls) should be async so a slow dependency doesn't block the event loop.
  • Decode order matters. Resolve the signing key (cache lookup) before the expensive verify; PyJWT already orders cheap checks (alg gate) before the RSA math.
  • Avoid per-request object churn. Compile the settings once; don't rebuild the issuer/audience strings on every call.

11. Common Mistakes

  1. Forgetting the trailing slash in issuer. Auth0's iss is https://tenant/. Comparing against https://tenant (no slash) rejects every token.
  2. Omitting audience. Without it you accept tokens minted for other APIs in the same tenant — a privilege-escalation hole.
  3. Not passing the audience to the client. If the client doesn't request your API as audience, Auth0 returns an opaque token your verifier can't decode. Symptom: "Invalid token / not enough segments".
  4. Letting the token pick the algorithm. Passing algorithms=jwt.get_unverified_header(token)["alg"] reopens alg-confusion. Hard-code ["RS256"].
  5. Creating a new PyJWKClient per request. Destroys caching; hammers Auth0; adds latency.
  6. Using 403 for missing tokens (or 401 for missing scopes). 401 = unauthenticated; 403 = authenticated-but-forbidden. Mixing them confuses clients and breaks retries.
  7. Treating absence of a claim as permission. Always default to deny.
  8. Installing plain PyJWT without [crypto]. RS256 silently unavailable → "Algorithm not supported" at runtime.
  9. Reading permissions but not scope (or vice versa). Client-credentials tokens use scope; RBAC-enabled user tokens may use permissions. Check both.
  10. Logging the full Authorization header. Leaks live tokens into log aggregators.
Warn

"Not enough segments" and "Invalid header padding" almost always mean you received an opaque token, not a JWT. The fix is on the client side: request your API's identifier as the audience.

12. Best Practices

  • Externalize all tenant config (domain, audience) to environment variables; fail fast at startup if missing.
  • One verifier dependency, reused everywhere. Keep verify_jwt and require_scope in a single auth.py; never inline JWT logic in routes.
  • Model scopes after actions, not roles: read:items, create:orders, delete:users. Map roles→scopes inside Auth0, keep the API checking concrete permissions.
  • Document security in OpenAPI. Because we use HTTPBearer/OAuth2 security schemes, Swagger shows a lock icon per protected route and an Authorize button — self-documenting and testable.
  • Return precise errors (401 vs 403, with a clear WWW-Authenticate header where appropriate) but never leak why a signature failed in a way that helps an attacker.
  • Warm the cache in lifespan for predictable latency and boot-time validation.
  • Write tests against forged, expired, wrong-audience, and wrong-scope tokens — not just the happy path. The failure paths are where security lives.
  • Pin dependency versions and track PyJWT/cryptography CVEs.

13. Interview Questions (with model answers)

Q1. Why does a FastAPI resource server not need to call Auth0 on every request?

Model answer: Auth0 access tokens are self-contained, RS256-signed JWTs. The API verifies them locally using Auth0's public keys, fetched once from the JWKS endpoint and cached. Because verification is offline cryptography, there is no per-request call to Auth0 — only an occasional JWKS fetch (first use or key rotation). This is what makes the design horizontally scalable and resilient.

Q2. What exactly do you validate in a token, and why each?

Model answer: Signature (authenticity/integrity, via the public key matching the header kid), issuer (it came from our tenant), audience (it was minted for our API, preventing cross-API replay), expiry/nbf (it is currently valid), and then scope/permissions for the specific action (authorization). The first four are authentication; the last is authorization.

Q3. RS256 vs HS256 for a third-party-issued token — which and why?

Model answer: RS256. HS256 uses a shared secret, so any verifier could also forge tokens — unacceptable when Auth0 issues and we only verify. RS256 is asymmetric: Auth0 signs with a private key it never shares, and we verify with the public key, which cannot mint tokens. Trust is distributed without distributing forgery power.

Q4. How would you mitigate the algorithm-confusion attack?

Model answer: Never trust the token header's alg. Pass an explicit algorithms=["RS256"] allow-list to jwt.decode. This prevents both alg=none and the RS256→HS256 trick where an attacker signs an HS256 token using the public key as the secret.

Q5. 401 vs 403 — when each?

Model answer: 401 Unauthorized when authentication fails — no token, malformed, expired, bad signature, wrong issuer/audience. 403 Forbidden when authentication succeeds but the token lacks the required scope/permission for that action.

Q6. What is the JWKS endpoint and what does it contain?

Model answer: /.well-known/jwks.json publishes the tenant's set of public signing keys, each with a kid and the RSA parameters (n, e). The verifier matches the token's header kid to a key to check the signature. It never contains private keys.

Q7. How do you handle Auth0 rotating its signing keys?

Model answer: Tokens carry the kid of the key that signed them. When a token's kid is not in the cache, PyJWKClient refetches the JWKS once and finds the new key. Old tokens remain verifiable as long as their key is still published. No code change or downtime is required for rotation.

Q8. Can a JWT be revoked before it expires?

Model answer: Not natively — a signed JWT is valid until exp. Mitigations: keep lifetimes short, and for high-risk operations consult a fast denylist/introspection. Long-lived JWTs trade revocation for scalability; pick lifetimes accordingly.

14. Certification Tips

  • Know the resource-server role. The cert frequently asks who validates tokens (the API/RS) versus who issues them (Auth0/AS). Don't confuse the API with the client.
  • Access token vs ID token. APIs validate access tokens (audience = API). ID tokens (audience = client) are for the client, not the API. A common trap question.
  • Audience drives token format. Requesting an API audience yields a JWT; no audience yields an opaque token good only for /userinfo. Memorize this cause/effect.
  • RBAC settings. Enabling "Add Permissions in the Access Token" puts a permissions array in the token; "RBAC" must be on for the API. Know where in the Auth0 dashboard these live (Applications → APIs → your API → RBAC Settings).
  • Scopes vs permissions. Scopes are requested by the client; granted permissions reflect what RBAC actually allows. The cert tests whether you know a requested scope can be denied.
  • Always RS256 for SPA/native/M2M. The cert expects asymmetric signing as the default and HS256 as the exception.
  • Issuer format includes the trailing slash and the https:// scheme — exact-match questions appear.

17. Mini Project — A Multi-Tenant Notes API with Ownership

Combine authentication, authorization, and data-level access control — the trio real APIs need.

# notes.py
from fastapi import FastAPI, Depends, HTTPException, status
from pydantic import BaseModel
from auth import verify_jwt, require_scope

app = FastAPI(title="Notes API")

class Note(BaseModel):
    id: int
    owner: str        # the "sub" of the user who created it
    text: str

DB: dict[int, Note] = {}
_next_id = 1

@app.post("/notes", status_code=201)
def create_note(text: str, claims: dict = Depends(require_scope("create:notes"))):
    global _next_id
    note = Note(id=_next_id, owner=claims["sub"], text=text)
    DB[_next_id] = note
    _next_id += 1
    return note

@app.get("/notes")
def my_notes(claims: dict = Depends(require_scope("read:notes"))):
    # Authorization is not enough — also enforce OWNERSHIP at the data layer.
    return [n for n in DB.values() if n.owner == claims["sub"]]

@app.delete("/notes/{note_id}", status_code=204)
def delete_note(note_id: int, claims: dict = Depends(require_scope("delete:notes"))):
    note = DB.get(note_id)
    if note is None:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Not found")
    if note.owner != claims["sub"]:
        # Valid token, valid scope — but not YOUR note.
        raise HTTPException(status.HTTP_403_FORBIDDEN, "Not your note")
    del DB[note_id]

The lesson: scopes answer "may this kind of action happen?"; ownership answers "may this caller act on this specific object?" Production APIs need both. A user with delete:notes still must not delete another user's note — that is an object-level (IDOR) check the token alone cannot make.

Danger

Skipping the ownership check is the #1 vulnerability in real APIs: Broken Object Level Authorization (BOLA/IDOR), top of the OWASP API Security list. A correct scope does not imply a right to a specific record.

19.1 The verifier in one screen

_jwks = PyJWKClient("https://TENANT/.well-known/jwks.json")  # once, module scope

def verify(creds = Depends(HTTPBearer())):
    key = _jwks.get_signing_key_from_jwt(creds.credentials)   # cached
    return jwt.decode(
        creds.credentials, key.key,
        algorithms=["RS256"],                # RS256 only
        audience="https://api.myapp.com",     # your API id
        issuer="https://TENANT/",             # trailing slash!
        options={"require": ["exp","iat","iss","aud"]},
    )

20. Key Takeaways

  • Your API is a Resource Server. Its job is to verify Auth0-issued access tokens locally and authorize each request — never to issue tokens or authenticate users.
  • Verification, not lookup. RS256 + JWKS lets you trust tokens by cryptographic inspection, with no per-request call to Auth0. That is the source of scalability and resilience.
  • Five checks, all mandatory: signature, issuer, audience, expiry, and scope. Skipping any is a real vulnerability; audience and issuer are the most-forgotten.
  • Cache the keys, share one client. PyJWKClient turns auth into microseconds of CPU. A fresh client per request is the classic performance and rate-limit mistake.
  • Authentication ≠ authorization. A valid token (401 gate) still needs the right scope (403 gate) — and for specific records, an ownership check the token cannot make.
  • Hard-code the algorithm allow-list. algorithms=["RS256"] closes the alg=none and algorithm-confusion attacks in one line.
  • FastAPI dependencies make it clean. verify_jwt and require_scope are reusable, testable, and self-documenting — they put a lock icon and Authorize button right in Swagger.
  • Force a JWT with the audience param; an opaque token means the client forgot to request your API. That single param resolves the most common "not enough segments" error.
Key

If you remember one sentence from this chapter: a resource server trusts a token by verifying its RS256 signature against cached public keys and checking iss/aud/exp, then authorizes by scope and ownership — all locally, all stateless. Master that and you can secure any framework, not just FastAPI.
