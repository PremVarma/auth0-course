Chapter 28 — Security Masterclass

Every other chapter in this course taught you how to make authentication work. This one teaches you how to make it fail safely under attack — which is a completely different skill. An attacker does not care that your login page is pretty; they care about the one redirect parameter you forgot to validate, the JWT verifier that trusts the token's own alg header, the refresh token sitting in localStorage where any injected script can read it. In this masterclass we map the OWASP Top 10 onto identity, dissect the canonical OAuth and JWT attacks down to the byte level, build a STRIDE threat model for a real auth system, and write the defensive code — in Spring Boot, Node, React, Next.js, FastAPI, plus curl and Postman — that turns each theoretical attack into a non-event. We explain why each defense works before we show how to deploy it, because a defense you don't understand is a defense you'll eventually disable to "fix a bug."

1. Theory — First Principles of Attacking Identity

Security is not a feature you add; it is a property that emerges (or fails to emerge) from how your system handles trust boundaries. A trust boundary is any line across which data changes its trustworthiness — the browser/server line, the network/application line, the user/token line. Every vulnerability in this chapter lives exactly on such a boundary, where the code on one side assumed something about data that the code on the other side did not guarantee.

Three first-principles ideas govern everything that follows:

  1. The attacker controls every input you do not explicitly control. The redirect URI in the query string, the alg field inside a JWT header, the Origin header, the state value coming back — if you did not generate it and verify it, treat it as hostile. This is the single mindset that prevents most identity bugs.
  2. Authentication is a claim; authorization is a decision. A token is just a claim ("I am Jane"). Whether Jane may delete invoice 482 is a decision your server must make on every request. Broken Access Control — OWASP's #1 risk — happens when systems treat the claim as the decision.
  3. Cryptographic verification must be a server-side decision, never a client-asserted fact. "Is this signature valid?" must be answered by code you wrote using a key you chose with an algorithm you pinned. The instant you let the token tell you how to verify it, you have lost.

Key

A secure auth system assumes each layer will eventually be breached and is designed so that no single breach yields account takeover. Short-lived access tokens limit the blast radius of token theft; refresh-token rotation limits the blast radius of refresh-token theft; MFA limits the blast radius of credential theft. Security is the art of shrinking blast radii.

2. Story-Based Explanation — The Night Helios Got Owned (Twice)

It is 2:14 a.m. and you are the on-call engineer at Helios Analytics. PagerDuty fires: customer accounts are exporting data they shouldn't have. By sunrise you have reconstructed two separate, very ordinary attacks that together took over a finance admin's account.

Attack one — the redirect. A phishing email sent the admin a link to the real Helios login URL — except the redirect_uri pointed at helios.attacker-cdn.com. Helios's Authorization Server had a sloppy allow-list that matched on prefix, so https://helios.app.evil.com passed. After a legitimate login, the authorization code was delivered straight to the attacker, who exchanged it for tokens. The admin saw nothing wrong; they logged into the real site.

Attack two — the storage. Even with tokens, the attacker wanted persistence. Helios's SPA stored the refresh token in localStorage. A months-old XSS in a third-party charting widget let the attacker read it and mint fresh access tokens for weeks. Because refresh-token rotation was off, the stolen token never changed.

Neither bug was exotic. Neither required breaking cryptography. Each was a trust boundary the team assumed was safe: "the redirect comes from our own login, surely it's fine"; "localStorage is our own domain, surely it's private." The rest of this chapter is the set of habits that would have turned both 2 a.m. pages into nothing at all: strict exact-match redirect allow-lists, PKCE, refresh-token rotation with reuse detection, and tokens kept out of JavaScript's reach entirely.

Note

Real breaches are rarely Hollywood. They are a forgotten validation plus a default left on. The attacker's job is to find the one boundary you trusted without verifying. Your job, learned here, is to verify every boundary by reflex.

4. Real-World Analogy — The Hotel Key-Card System

A modern hotel is the perfect mental model for token security, because hotels solved these problems decades ago in the physical world.

  • The room key card = access token. It is short-lived (expires at checkout), scoped (opens your room and the gym, not the safe room), and it carries no password — losing it doesn't reveal your identity. This is exactly why we use short-lived, scoped access tokens instead of sending the password on every request.
  • Your ID at the front desk = refresh token / login. Stronger, rarer to present, kept safe. You only show it to get new key cards. If a key card is stolen, the thief cannot make new ones without your ID. That is refresh-token separation.
  • Re-coding the lock on each issue = refresh-token rotation. Good hotels invalidate the previous card whenever they print a new one. Hand back an old card and the lock blinks red — that red blink is reuse detection, and it tells the desk something is wrong.
  • The "is this really our card?" check = signature verification. The lock trusts the hotel's secret coding, not whatever is printed on the plastic. A card that says "master key" in Sharpie still won't open the door — that is refusing to trust the token's self-described alg.
  • Tailgating through the door behind a guest = session fixation / CSRF. Strong authentication at the desk is useless if anyone can slip through an unlocked side door. That is why we re-issue session IDs on login and require anti-CSRF tokens.
  • Calling the desk to confirm a suspicious request = MFA. Even with a valid-looking ID, the desk calls your registered phone before changing the room on file. Phishing-resistant MFA is the call you cannot fake from across the world.
Tip

When you're unsure whether a design is safe, translate it into the hotel. "We store the master ID in the room's mini-bar" (localStorage) sounds obviously wrong the moment it's physical. The hotel test is a surprisingly reliable security smell-detector.

5. Internal Working — Anatomy of the Canonical Attacks

5.1 JWT alg:none and algorithm confusion

A JWT is three Base64URL parts: header.payload.signature. The header self-describes the algorithm. Two classic attacks abuse a verifier that believes that header:

  • alg:none: The attacker sets {"alg":"none"}, edits the payload ("role":"admin"), and drops the signature entirely. A naive library that "supports" none accepts it because the token says no signature is needed.
  • RS256 → HS256 confusion: Your server verifies RS256 with a public key. The attacker re-signs the token as HS256 using that public key as the HMAC secret. If your verifier picks the algorithm from the header and feeds it the RSA public key (which is, by definition, public), the HMAC check passes. You authenticated the attacker with your own public key.

The fix is identical for both: the verifier must pin the expected algorithm(s) and never derive it from the token. Below, a deliberately broken verifier vs. a correct one.

// ❌ VULNERABLE — algorithm taken from the token header
jwt.verify(token, key); // many libs infer alg from header → alg-confusion / none

// ✅ SAFE — algorithm pinned by the server, key resolved from trusted JWKS
jwt.verify(token, publicKey, {
  algorithms: ['RS256'],          // pin! reject HS256, none, everything else
  issuer:   'https://YOUR_TENANT.us.auth0.com/',
  audience: 'https://api.helios.app',
});

5.2 The OAuth mix-up attack

When a client supports multiple identity providers, an attacker who controls one (malicious) IdP can trick the client into sending an authorization code minted by the honest IdP to the attacker's token endpoint, or vice-versa, because the client forgets which IdP a given response came from. The defense (RFC 9207) is the authorization server returning an iss parameter in the response, and the client verifying that the response's issuer matches the one it started the flow with — plus binding the per-flow state to the chosen provider.

5.3 Session fixation

The server hands an anonymous visitor a session ID. The attacker tricks the victim into authenticating using that same, attacker-known session ID (e.g., by planting it via a crafted link). After login, the server keeps the ID — now the attacker holds an authenticated session. The fix is one line of discipline: regenerate the session identifier at the moment of privilege change (login, MFA step-up). The pre-login ID becomes worthless.

5.4 Replay attacks

An attacker captures a valid message (a signed request, an OIDC id_token) and re-sends it. Signatures alone don't help — the replay is genuinely signed. Defenses bind the message to a single use or moment: short exp, a server-generated nonce the response must echo (OIDC nonce), and a unique jti the server records and refuses to accept twice within the token's lifetime.

5.5 Where tokens leak

   Token leakage channels (each is a separate trust boundary):
     • URL / query string  → ends up in browser history, Referer, server logs
     • localStorage        → readable by ANY script ⇒ XSS = token theft
     • Referer header      → leaks token to third-party resources
     • verbose logs / APM  → tokens printed in error traces
     • browser back/cache  → cached pages with embedded tokens

6. Code Walkthrough — Reading Attacks and Defenses

6.1 Exact-match redirect validation (defeats Attack One)

# FastAPI authorization-server side: never prefix/substring match redirect_uri
from urllib.parse import urlparse

ALLOWED_REDIRECTS = {
    "https://helios.app/callback",
    "https://app.helios.com/auth/callback",
}

def validate_redirect_uri(uri: str) -> bool:
    # ✅ exact string membership — NOT startswith(), NOT 'in', NOT regex prefix
    return uri in ALLOWED_REDIRECTS
# "https://helios.app.evil.com/callback" is NOT in the set → rejected

Why exact match? Prefix matching (startswith("https://helios.app")) accepts https://helios.app.evil.com. Suffix matching accepts https://evil.com/helios.app/callback. Substring is worse still. Only full-string equality has no parsing ambiguity for an attacker to exploit.

6.2 PKCE on the client (defeats stolen-code reuse)

// PKCE: a per-request secret the client keeps, proving it started the flow
import crypto from 'node:crypto';
const b64url = (b) => b.toString('base64url');

const verifier  = b64url(crypto.randomBytes(32));          // keep secret, client-side
const challenge = b64url(crypto.createHash('sha256')
                          .update(verifier).digest());      // sent in /authorize

// /authorize?...&code_challenge=CHALLENGE&code_challenge_method=S256
// /token  body includes code_verifier=VERIFIER
// AS recomputes SHA256(verifier) and compares to the stored challenge.
// A thief who steals only the CODE cannot complete /token without VERIFIER.

6.3 Anti-CSRF + state on the callback (defeats login CSRF / forced login)

// Generate per-flow state, bind to the user's session, verify on return
const state = crypto.randomBytes(16).toString('hex');
req.session.oauthState = state;            // server-side, tied to this session
// ...redirect to /authorize?...&state=STATE

// On /callback:
if (req.query.state !== req.session.oauthState) {
  return res.status(400).send('state mismatch — possible CSRF');
}
delete req.session.oauthState;             // single use

6.4 Constant-time secret comparison (defeats timing side-channels)

import { timingSafeEqual } from 'node:crypto';
function safeEqual(a, b) {
  const ba = Buffer.from(a), bb = Buffer.from(b);
  if (ba.length !== bb.length) return false;   // length leak acceptable here
  return timingSafeEqual(ba, bb);              // no early-exit on first diff byte
}
// '===' on secrets leaks how many leading bytes matched via response time.
Warn

Notice every defense above is small. The hard part is never the code — it is remembering that the boundary exists. That is what threat modeling (Section 16/STRIDE below) systematizes so you don't rely on memory.

7. Practical Implementation — Hardened Verification Across Stacks

7.1 Spring Boot — resource server with pinned alg, issuer, audience

// application.yml
// spring.security.oauth2.resourceserver.jwt.issuer-uri:
//   https://YOUR_TENANT.us.auth0.com/

@Configuration
@EnableWebSecurity
public class SecurityConfig {

  @Value("${spring.security.oauth2.resourceserver.jwt.issuer-uri}")
  String issuer;

  @Bean
  JwtDecoder jwtDecoder() {
    // Loads JWKS from issuer; algorithm comes from the JWKS key type (RS256),
    // NOT from the attacker-controlled token header.
    NimbusJwtDecoder decoder =
        JwtDecoders.fromIssuerLocation(issuer);

    OAuth2TokenValidator<Jwt> withIssuer =
        JwtValidators.createDefaultWithIssuer(issuer);      // iss + exp + nbf
    OAuth2TokenValidator<Jwt> audience = new AudienceValidator("https://api.helios.app");
    decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(withIssuer, audience));
    return decoder;
  }

  @Bean
  SecurityFilterChain chain(HttpSecurity http) throws Exception {
    http
      .authorizeHttpRequests(a -> a
        .requestMatchers("/api/admin/**").hasAuthority("SCOPE_admin:all")  // authZ decision
        .anyRequest().authenticated())
      .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
      .csrf(c -> c.disable());  // OK only for stateless Bearer APIs; KEEP csrf on cookie/session apps
    return http.build();
  }
}

class AudienceValidator implements OAuth2TokenValidator<Jwt> {
  private final String aud;
  AudienceValidator(String aud) { this.aud = aud; }
  public OAuth2TokenValidatorResult validate(Jwt jwt) {
    return jwt.getAudience().contains(aud)
        ? OAuth2TokenValidatorResult.success()
        : OAuth2TokenValidatorResult.failure(
            new OAuth2Error("invalid_token", "missing audience", null));
  }
}

7.2 Next.js (App Router) — tokens in HttpOnly cookies, never in JS

// app/api/auth/callback/route.js  (server-side; tokens never reach the browser JS)
import { cookies } from 'next/headers';

export async function GET(req) {
  // ...exchange code (+ PKCE verifier from secure cookie) for tokens...
  const { access_token, refresh_token, expires_in } = await exchange(req);

  const jar = await cookies();
  jar.set('access_token', access_token, {
    httpOnly: true,                 // ✅ unreachable by document.cookie / XSS
    secure: true,                   // ✅ HTTPS only
    sameSite: 'lax',                // ✅ blocks cross-site CSRF on top-nav GETs
    path: '/',
    maxAge: expires_in,
  });
  jar.set('refresh_token', refresh_token, {
    httpOnly: true, secure: true, sameSite: 'strict', path: '/api/auth/refresh',
  });
  return Response.redirect(new URL('/dashboard', req.url));
}

7.3 React — what NOT to do, and the safe pattern

// ❌ NEVER: token reachable by any injected script
localStorage.setItem('access_token', token);   // XSS = total compromise

// ✅ Keep access token in memory (module variable / context), refresh via
//    an HttpOnly cookie hit to your backend-for-frontend. On reload it's gone
//    from memory and silently re-acquired from the cookie-backed session.
let inMemoryToken = null;
export const setToken = (t) => { inMemoryToken = t; };
export const getToken = () => inMemoryToken;

7.4 FastAPI — replay defense with a jti denylist

import time, jwt   # PyJWT
from fastapi import Header, HTTPException

_seen_jti: dict[str, float] = {}   # use Redis with TTL in production

def verify(token: str = Header(..., alias="Authorization")):
    raw = token.removeprefix("Bearer ")
    claims = jwt.decode(
        raw, key=PUBLIC_KEY,
        algorithms=["RS256"],                 # pinned
        issuer="https://YOUR_TENANT.us.auth0.com/",
        audience="https://api.helios.app",
        options={"require": ["exp", "iat", "jti"]},
    )
    jti, exp = claims["jti"], claims["exp"]
    if jti in _seen_jti:                        # replay!
        raise HTTPException(401, "token replay detected")
    _seen_jti[jti] = exp                        # remember until it expires
    return claims

Principles encoded in this diagram: (1) the SPA never touches a raw token — a Backend-for-Frontend holds them in HttpOnly cookies; (2) every hop re-verifies rather than trusting upstream ("zero trust" between services, each with its own aud); (3) Auth0's Attack Protection (brute-force, breached-password, bot detection, suspicious-IP throttling) sits in front of the credential boundary; (4) all anomaly signals flow to a SIEM so A09 (logging/monitoring) is real, not aspirational; (5) signing keys live in a KMS/HSM and rotate, so a leaked key has a bounded blast radius.

Key

The architectural rule of thumb: tokens live where script cannot reach, secrets live where humans cannot copy, and every boundary re-verifies instead of trusting the boundary before it.

9. Security Analysis — STRIDE Threat Model of the Login System

STRIDE is Microsoft's mnemonic for the six classes of threat. Applied to an auth system, it forces you to enumerate attacks systematically instead of relying on whatever you happen to remember at 2 a.m.

STRIDEThreat in authConcrete attackPrimary mitigation
Spoofing identityPretend to be another userCredential stuffing, phishing, alg-confusion forgeryMFA, breached-password detection, pinned-alg JWT verify
TamperingAlter tokens/requestsEdit JWT payload, IDOR on object IDsSignature verify, server-side authZ on every object
RepudiationDeny an action happenedNo audit trail of who exported dataImmutable, signed audit logs to SIEM
Information disclosureLeak secrets/tokensToken in URL/localStorage/logs, verbose errorsHttpOnly cookies, log scrubbing, generic errors
Denial of serviceExhaust the auth pathLogin flood, JWKS-fetch hammeringRate limiting, WAF, caching JWKS
Elevation of privilegeGain rights you lackTrusting client-sent role, broken scope checkServer-derived roles, least privilege, deny by default

The discipline is to walk the data-flow diagram (Section 8), draw the trust boundaries, and ask all six STRIDE questions at each boundary. The browser→BFF boundary alone yields spoofing (stolen cookie), tampering (CSRF), and info disclosure (XSS reading tokens) — each with a named mitigation above. A threat model is "done" when every boundary × every applicable STRIDE letter has either a control or an accepted, documented risk.

Danger

The most expensive STRIDE letter in identity is E — Elevation of Privilege, because it is Broken Access Control (OWASP A01). Always test: can a normal user reach /api/admin/*? Can user A read user B's object by changing an ID? If you only test one thing in this chapter, test horizontal and vertical privilege escalation.

10. Performance Considerations — Fast and Secure Are Not Enemies

  • JWKS caching: Verifying RS256 needs the issuer's public key. Fetching JWKS on every request adds latency and a DoS amplification path. Cache keys by kid with a sane TTL (e.g., 10 min) and refresh on cache-miss of an unknown kid (handles rotation). This makes verification a few microseconds of local crypto, not a network round-trip.
  • Local vs. introspection: Stateless JWT verification is O(1) local crypto — fast. Token introspection (calling the AS to ask "is this token still valid?") is a network call but gives instant revocation. Choose per route: short-lived access tokens make local verification safe; introspect only the high-value endpoints.
  • Replay jti store: A denylist must be fast and bounded. Use Redis with a TTL equal to the token's remaining lifetime so the set self-cleans; never an unbounded in-memory map (memory DoS).
  • Argon2/bcrypt cost: Password hashing is intentionally slow to resist cracking, but too slow becomes a login-flood DoS. Tune work factor to ~100–250 ms on your hardware, and put rate limiting in front so the slow path can't be weaponized.
  • Constant-time compares add negligible cost; never trade them away for speed.
Tip

Performance security trade-offs are usually false dilemmas: cache the public keys, keep tokens short-lived, and you get both fast verification and bounded revocation lag. The only real cost is thinking about TTLs.

11. Common Mistakes

  • Trusting hdr.alg: Letting the library infer the algorithm from the token. Always pin.
  • Skipping aud/iss checks: A token valid for service X gets accepted by service Y. Verify audience on every service.
  • Prefix/regex redirect matching: helios.app.evil.com slips through. Exact match only.
  • Tokens in localStorage: Turns any XSS into account takeover. Use HttpOnly cookies or in-memory.
  • No refresh-token rotation: A stolen refresh token works forever. Rotate + detect reuse.
  • Trusting client-supplied roles/scopes: The client says role=admin and you believe it. Derive authorization server-side from verified claims.
  • No session regeneration on login: Session fixation. Regenerate the ID on every privilege change.
  • Verbose error messages: "user not found" vs "wrong password" enables user enumeration. Return one generic failure.
  • Disabling CSRF on cookie-auth apps: CSRF disable is only safe for stateless Bearer APIs. Cookie/session apps need anti-CSRF tokens or strict SameSite.
  • Logging tokens: Access/refresh tokens in APM traces or access logs. Scrub before logging.
  • No rate limiting on login/MFA: Enables credential stuffing and OTP brute force. Rate-limit and lock progressively.
  • Long-lived access tokens: Big blast radius on theft. Keep access tokens minutes, not days.

12. Best Practices

  1. Pin algorithms, verify iss/aud/exp/nbf on every token, every service.
  2. Use Authorization Code + PKCE for every interactive client (SPA, native, web). Never the implicit flow.
  3. Exact-match redirect URIs in the allow-list; no wildcards in production.
  4. Keep tokens out of JavaScript: HttpOnly + Secure + SameSite cookies via a BFF, or in-memory access tokens.
  5. Rotate refresh tokens with automatic reuse detection (revoke the whole family on reuse).
  6. Short-lived access tokens (minutes); revoke/introspect high-value paths.
  7. Enforce MFA, prefer phishing-resistant factors (passkeys/WebAuthn, FIDO2) over SMS OTP.
  8. Enable Auth0 Attack Protection: brute-force, breached-password, suspicious-IP throttling, bot detection.
  9. Deny by default in authZ; derive roles/scopes server-side; test privilege escalation explicitly.
  10. Set strong headers: Content-Security-Policy, Strict-Transport-Security, Referrer-Policy: no-referrer, X-Content-Type-Options: nosniff.
  11. Manage keys in KMS/HSM, rotate signing keys, never commit secrets; scan repos and CI.
  12. Log security events to a SIEM with anomaly alerting; make repudiation impossible.
  13. Keep dependencies patched (A06); pin and audit your JWT/crypto libraries.
  14. Threat-model with STRIDE before shipping and after every architecture change.

13. Interview Questions (with Model Answers)

Q1. Why is it dangerous to let the JWT library pick the algorithm from the token header?

Model answer: Because the header is attacker-controlled. Two attacks follow: alg:none (the attacker drops the signature and the verifier accepts an unsigned token) and RS256→HS256 confusion (the attacker re-signs with your public key as an HMAC secret; a verifier that picks HS256 from the header and uses the RSA public key as the secret validates the forgery). The fix is to pin the expected algorithm(s) server-side and resolve the key from a trusted JWKS by kid, ignoring the header's claimed algorithm.

Q2. A SPA stores its access and refresh tokens in localStorage. What's wrong and what would you do?

Model answer: localStorage is readable by any JavaScript, so a single XSS becomes full account takeover and (with the refresh token) long-term persistence. I'd move to a Backend-for-Frontend that holds tokens in HttpOnly+Secure+SameSite cookies so script can't read them, keep the access token in memory only if a pure-SPA pattern is required, enable refresh-token rotation with reuse detection, add a strict CSP to reduce XSS, and set short access-token lifetimes to bound the blast radius.

Q3. Explain how PKCE and state defend the authorization-code flow, and what each one does not protect.

Model answer: PKCE binds the token exchange to the client that started the flow: the client sends code_challenge=SHA256(verifier) and later proves possession with code_verifier, so a stolen authorization code is useless without the verifier — this defeats code interception/injection. state is a per-flow, session-bound nonce verified on the callback; it defeats CSRF / forced-login and login-CSRF. PKCE does not stop CSRF on the callback (that's state's job), and state does not stop code theft (that's PKCE's job) — you need both, plus exact-match redirect URIs.

Q4. What is refresh-token rotation with reuse detection, and why is it stronger than a long-lived refresh token?

Model answer: On each refresh the AS issues a new refresh token and invalidates the previous one. If a previously-used (and thus revoked) refresh token is presented again, that signals theft: the AS revokes the entire token family and forces re-authentication. A long-lived refresh token, once stolen, works indefinitely and invisibly; rotation turns the thief's reuse into a detectable, self-revoking event, shrinking the blast radius from "forever" to "until the next legitimate refresh."

Q5. Map Broken Access Control to a concrete identity bug and the test you'd run.

Model answer: BAC (OWASP A01) shows up as IDOR and missing scope/role checks — e.g., GET /api/invoices/482 returns the invoice without verifying it belongs to the caller, or a normal user reaching /api/admin/*. I test both horizontal escalation (user A requests user B's object ID) and vertical escalation (non-admin hits admin routes). The fix is server-side, deny-by-default authorization on every object and route, deriving identity from the verified token rather than from any client-supplied ID or role.

Q6. How would you make MFA phishing-resistant?

Model answer: SMS/TOTP can be phished or relayed in real time (AiTM proxies). Phishing-resistant MFA uses WebAuthn/FIDO2 passkeys, where the authenticator signs a challenge bound to the origin; a proxy on a look-alike domain gets the wrong origin and the signature won't validate. I'd also enable step-up auth for sensitive actions and bind sessions to device signals so a relayed cookie alone isn't enough.

14. Certification Tips

  • Know Auth0 Attack Protection by name: Brute-Force Protection, Suspicious IP Throttling, Breached Password Detection, and Bot Detection — what each defends and where it's configured (Dashboard → Security → Attack Protection).
  • Flows: The exam expects you to know that public clients (SPA/native) must use Authorization Code + PKCE, that the implicit flow is deprecated, and why.
  • Token validation: Be able to list the claims a resource server must validate: signature, iss, aud, exp, nbf, and (for OIDC) nonce/azp.
  • Refresh tokens: Know rotation, reuse detection, and absolute/inactivity lifetimes as tenant settings.
  • MFA: Recognize factor types and that WebAuthn/passkeys are phishing-resistant; know Adaptive MFA / step-up triggers.
  • Mapping: Expect scenario questions that ask you to pick the control for a described attack (e.g., "users report tokens being reused" → enable rotation + reuse detection).
  • Storage: The "correct" answer for SPA token storage on the exam is HttpOnly cookies / not localStorage — memorize the rationale (XSS).
Note

Certification questions love the word "best." When asked the "best" MFA, "best" token storage, or "best" flow, choose the option that minimizes blast radius and removes attacker-controlled trust: passkeys, HttpOnly cookies, Auth Code + PKCE.

15. Hands-On Exercises

  1. Forge and fail: Craft an alg:none token (header {"alg":"none"}, payload {"role":"admin"}, empty signature) and send it to a protected endpoint. Confirm a 401. Then temporarily remove the algorithms pin and observe the danger — re-pin immediately.
  2. Redirect bypass: Implement a validate_redirect_uri with startswith(), prove https://helios.app.evil.com passes, then switch to exact match and prove it's rejected.
  3. PKCE by hand: Generate a verifier/challenge pair with the snippet in 6.2 and run a full authorize→token exchange against your Auth0 tenant with curl. Then retry the token exchange without the verifier and confirm it fails.
  4. Rotation trap: Enable refresh-token rotation in your tenant, capture RT2, use it once, replay it, and confirm the family is revoked.
  5. CSP lab: Add a Content-Security-Policy header, attempt an inline-script "XSS," and watch the browser block it.
  6. Brute-force demo: Run the curl loop from 7.5 against a test app and observe rate-limiting kick in.

16. Assignment — A STRIDE Threat Model

Take the Helios architecture from Section 8 and produce a written threat model:

  1. Draw the data-flow diagram and mark every trust boundary (browser↔BFF, BFF↔Auth0, BFF↔microservices, service↔datastore).
  2. For each boundary, enumerate the applicable STRIDE threats with a concrete attack and a named mitigation (use the Section 9 table as a template).
  3. Identify the three highest-risk items (likelihood × impact) and write the specific code or config change that closes each.
  4. List every place a token could leak in your design and the control preventing it.
  5. Define your token lifetimes (access, refresh inactivity, refresh absolute) and justify each against blast radius.

Deliverable: a 2–4 page document plus the diagram. This is exactly the artifact a security reviewer or interviewer will ask you to produce.

17. Mini Project — "Harden Helios"

Build a small but realistic hardened app and a test suite that proves the hardening:

  • BFF (Node/Next or FastAPI): Authorization Code + PKCE login against Auth0, tokens in HttpOnly+Secure+SameSite cookies, anti-CSRF on state-changing routes, refresh via a server endpoint with rotation.
  • Resource server (Spring Boot or FastAPI): pinned-alg JWT verification with iss/aud/exp checks, deny-by-default authorization, a /api/admin/* route guarded by scope, and a jti replay denylist in Redis.
  • Headers: CSP, HSTS, Referrer-Policy, X-Content-Type-Options on every response.
  • Attack-suite (Postman/curl): automated tests that send alg:none, a tampered payload, a missing-audience token, an evil redirect_uri, a state-less callback, and a replayed jti — each asserting the correct rejection.
  • Tenant config: enable rotation + reuse detection, brute-force protection, breached-password detection, and MFA (passkey).

Done means: every request in your attack-suite returns the expected 4xx, every legitimate flow works, and you can explain — per the STRIDE table — which boundary each test exercises.

20. Key Takeaways

  • Attackers exploit trusted boundaries, not broken crypto. Most identity breaches are a forgotten validation plus a default left on. Verify every input you didn't generate.
  • Never let the token tell you how to verify it. Pin the algorithm; resolve keys from a trusted JWKS; check iss/aud/exp/nbf — this kills alg:none and algorithm confusion.
  • Authentication is a claim; authorization is a decision. Broken Access Control (OWASP A01 = STRIDE Elevation) is the #1 risk; make a server-side, deny-by-default decision on every route and object, and test horizontal + vertical escalation.
  • Code + PKCE + exact-match redirects + state together close the redirect/CSRF/code-theft family. Each defends a different boundary; you need all of them.
  • Keep tokens out of JavaScript and out of URLs. HttpOnly cookies or in-memory only; this turns XSS from "account takeover" into "annoyance."
  • Rotate refresh tokens with reuse detection and keep access tokens short — security is the discipline of shrinking blast radius at every layer.
  • Prefer phishing-resistant MFA (passkeys/WebAuthn) and enable Auth0 Attack Protection to defeat credential stuffing, brute force, and bots at the credential boundary.
  • Threat-model with STRIDE before you ship, log everything to a SIEM, and treat every breach as inevitable — design so that no single failure is fatal.
Key

If you internalize one sentence from this chapter: trust nothing the attacker can touch, verify on every boundary, and design so that any single control failing still leaves the attacker locked out. That is defense in depth, and it is the whole game.
