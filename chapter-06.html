Chapter 6 — OAuth Grant Types: Client Credentials, Device, Refresh, Implicit, Password

In Chapter 5 you mastered the Authorization Code flow with PKCE — the grant for apps where a human logs in through a browser. But the real world has machines talking to machines at 3 a.m., smart TVs with no keyboard, mobile apps that must stay logged in for months, and legacy systems that predate modern redirects. OAuth 2.0 answers each of these with a different grant type. This chapter dissects all five remaining grants from first principles: why each exists, exactly how the bytes flow, where each one is dangerous, which ones the OAuth 2.1 working group has deprecated and why, and how to wire every one of them up in Auth0 with real, runnable code. By the end you will be able to look at any application and name the correct grant in seconds — the single most-tested skill on the Auth0 certification and in system-design interviews.

1. Theory — First Principles: What Is a "Grant" and Why Are There Many?

Strip OAuth 2.0 down to one sentence and it says: "How can a client obtain an access token, without being handed the resource owner's password?" An access token is just a string the client presents to an API ("Resource Server") to prove it is allowed to do something. The whole protocol is the choreography of getting that string safely.

A grant type (the spec also calls it an "authorization grant") is the specific method by which a client proves it deserves a token. Why is one method not enough? Because the security properties available to a client depend entirely on what kind of thing the client is:

  • Can it keep a secret? A backend server can store a client secret in an environment variable no attacker can read. A single-page app shipped to the browser cannot — its source is public. A native CLI on a laptop cannot either.
  • Is a human present? A nightly billing job has no user. A login page has one. A smart TV has a human, but no convenient way for them to type.
  • Is there a browser / redirect channel? Authorization Code needs the user-agent to follow a redirect. A device with no browser (or a daemon with no UI) cannot use redirects at all.

From these three axes the OAuth designers derived a family of grants. Four "core" grants appear in RFC 6749 (Authorization Code, Implicit, Resource Owner Password Credentials, Client Credentials), one is added by RFC 8628 (Device Authorization), and the Refresh Token "grant" (RFC 6749 §6) is a special grant used only to mint new access tokens from a previously issued refresh token. We covered Authorization Code in Chapter 5; this chapter covers the other five.

Key

A grant type is not a feature you pick for taste — it is dictated by your client's trust profile: (1) can it hold a secret, (2) is a user present, (3) is a browser redirect available. Get those three answers and the correct grant falls out automatically.

The two "shapes" of token requests

Every OAuth grant ends with an HTTP POST to the token endpoint (/oauth/token in Auth0). What differs is the grant_type form parameter and the credentials presented alongside it:

2. Story-Based Explanation — Five Doors Into the Same Building

Imagine "CinemaCloud", the booking platform you will build in your capstone. It is one company, but its software wears many hats. Picture each piece of software as a different visitor trying to get into the secured back-office building, where a guard (the Authorization Server) hands out colour-coded badges (tokens).

Mira, the nightly accountant (Client Credentials). Every midnight a billing service totals the day's ticket sales and pushes invoices to the payments API. There is no human watching. The service walks up to the guard, shows its own company ID card (a client secret it alone possesses) and says "I am the billing robot, give me my badge." No user is involved — the robot is acting as itself. The guard checks the card and issues a badge scoped to create:invoices.

Tom, watching the lobby TV (Device flow). CinemaCloud has a smart-TV app for browsing trailers and signing in to see your watchlist. The TV has no keyboard — typing a password with a remote is misery. So the TV shows a short code: "Go to cinema.cloud/activate on your phone and enter WDJB-MJHT." Tom pulls out his phone, logs in there comfortably, approves the TV, and seconds later the TV lights up — authenticated, without ever touching a password on the TV itself.

Priya, who never wants to log in again (Refresh tokens). Priya uses the CinemaCloud mobile app daily. Forcing her to type her password every hour would be torture, but keeping a long-lived access token would be dangerous if her phone is stolen. The compromise: she gets a short-lived badge (access token, ~15 min) plus a special renewal voucher (refresh token). When the badge expires, the app silently swaps the voucher for a fresh badge — and, with rotation, gets a brand-new voucher each time, so a stolen old voucher becomes useless.

Ravi, the legacy ghost (Implicit). Years ago, before browsers could safely do cross-origin POSTs, CinemaCloud's old single-page dashboard used the Implicit flow — the token was thrown straight back in the URL fragment. It worked, but tokens leaked into browser history and logs. Ravi's flow is the building's old fire-escape door: still bolted shut for emergencies-of-the-past, but the company has a sign on it reading "DEPRECATED — use the front door (Auth Code + PKCE)."

Sam, the impatient insider (ROPC). An internal admin tool, built by Sam in a hurry, just collects the username and password in its own form and sends them to the guard directly: "Here, log this person in." It works, but Sam's tool now sees the password — defeating the entire reason OAuth exists. The guard grudgingly allows it for trusted first-party tools, but security keeps trying to shut it down.

Note

One building (your tenant), one guard (the Authorization Server), but five doors. Each door exists because a real visitor couldn't use the others. Memorise the visitor, not the door, and you'll never confuse the grants.

5. Internal Working — What the Server Actually Does

5.1 Client Credentials internals

When Auth0 receives grant_type=client_credentials, it: (1) authenticates the client — either by verifying the client_secret against the stored hash, or by validating a private-key JWT (client_assertion) signed by the client's private key; (2) looks at the requested audience to find the target API; (3) computes the granted scopes by intersecting the API's "permissions" granted to this M2M application with any requested scope; (4) mints a signed JWT access token whose sub equals the client_id (there is no user, so the subject is the machine), with no refresh token (machines just ask again). Notice: no id_token is ever issued — Client Credentials is pure OAuth authorization, never authentication of a person.

5.2 Device flow internals

The device endpoint creates a record linking three things: a long, secret device_code (kept by the device), a short, human-friendly user_code (shown on screen), and a pending status. The device then polls the token endpoint. The server replies authorization_pending until the user approves on the second device, then flips the record to approved and the next poll returns tokens. The interval field tells the device how fast it may poll; polling faster earns a slow_down error that increases the interval. The device_code expires (default ~15 min via expires_in) so an unapproved session cannot linger forever.

5.3 Refresh token rotation internals

A refresh token belongs to a token family — a chain identified internally so the server can reason about lineage. With rotation enabled, each successful refresh consumes the presented token and issues a new one (RT1 → RT2 → RT3 …). The old token is marked used. If a used token is ever presented again (classic sign of theft — both the legitimate client and an attacker hold copies), Auth0 triggers automatic reuse detection: it revokes the entire family, forcing a fresh login. This converts a stolen refresh token from a permanent backdoor into, at most, a brief window before the next legitimate rotation slams the door.

   Token family lifecycle with rotation + reuse detection
   ---------------------------------------------------------
   issue RT1 ──refresh──▶ RT2 ──refresh──▶ RT3  (RT1,RT2 now "used")
                                            │
        attacker replays RT1 ───────────────┘
        server sees "used" token reused  ==>  REVOKE FAMILY
        legitimate client's RT3 also dies ==>  must re-authenticate
Note

Reuse detection is intentionally blunt — it kills the whole family, even the legitimate session, because the server cannot tell the thief from the victim. A forced re-login is a small price for closing a stolen-token backdoor.

5.4 Implicit internals (and why it's structurally weak)

Implicit skips the authorization code entirely. The /authorize endpoint, after login, redirects with the access token in the URL fragment (#access_token=...). The fragment is chosen because it is never sent to servers — but it is readable by any JavaScript on the page, lands in browser history, and can leak via the Referer header. Crucially there is no client authentication and no second leg: whoever first reads the fragment owns the token. There is also no refresh token (issuing one in the open would be reckless), so sessions die quietly or rely on silent iframe re-auth.

5.5 ROPC internals

ROPC is the most "direct" grant: the app collects the user's raw username and password and POSTs them to the token endpoint with its own client credentials. The server checks the password against the connection's user store and returns tokens. Because the password flows through the application, every protection layered on the hosted login page — MFA prompts, anomaly/brute-force detection, bot protection, SSO, consent screens, passwordless — is bypassed. ROPC only works against database connections, never against social or enterprise identity providers (you cannot POST a Google password to Auth0).

7. Practical Implementation — Real Code in Real Stacks

7.1 Client Credentials in Spring Boot (WebClient)

// build.gradle: spring-boot-starter-oauth2-client + webflux
// application.yml registers the M2M client; Spring manages the token cache.
spring:
  security:
    oauth2:
      client:
        registration:
          cinema-m2m:
            authorization-grant-type: client_credentials
            client-id: ${AUTH0_M2M_CLIENT_ID}
            client-secret: ${AUTH0_M2M_CLIENT_SECRET}
            provider: auth0
        provider:
          auth0:
            token-uri: https://YOUR_TENANT.us.auth0.com/oauth/token

// --- config: attach the audience (Auth0 needs it) & an authorized WebClient ---
@Configuration
class M2MConfig {
  @Bean
  WebClient cinemaApiClient(ReactiveClientRegistrationRepository regs,
                            ReactiveOAuth2AuthorizedClientService svc) {
    var manager = new AuthorizedClientServiceReactiveOAuth2AuthorizedClientManager(regs, svc);
    // Auth0 requires the custom `audience` parameter on the token request:
    manager.setContextAttributesMapper(req -> Mono.just(
        Map.of("audience", "https://api.cinema.cloud")));
    var oauth = new ServerOAuth2AuthorizedClientExchangeFilterFunction(manager);
    oauth.setDefaultClientRegistrationId("cinema-m2m");
    return WebClient.builder().filter(oauth).build();
  }
}

// --- usage: token is fetched, cached, and refreshed automatically ---
@Service
class BillingClient {
  private final WebClient client;
  BillingClient(WebClient cinemaApiClient){ this.client = cinemaApiClient; }

  public Mono<String> postInvoice(Invoice inv) {
    return client.post().uri("https://api.cinema.cloud/invoices")
        .bodyValue(inv)
        .retrieve().bodyToMono(String.class);  // Authorization: Bearer ... added for you
  }
}

7.2 Device flow in Node.js (CLI polling)

import fetch from 'node-fetch';
const DOMAIN = 'YOUR_TENANT.us.auth0.com';
const CLIENT_ID = 'YOUR_NATIVE_CLIENT_ID';
const form = o => new URLSearchParams(o);

async function deviceLogin() {
  // 1. request device + user codes
  const dc = await (await fetch(`https://${DOMAIN}/oauth/device/code`, {
    method: 'POST',
    body: form({ client_id: CLIENT_ID, scope: 'openid profile offline_access',
                 audience: 'https://api.cinema.cloud' })
  })).json();

  console.log(`\n  Go to: ${dc.verification_uri_complete}`);
  console.log(`  Or visit ${dc.verification_uri} and enter code: ${dc.user_code}\n`);

  // 2. poll the token endpoint until the user approves
  let interval = dc.interval;
  while (true) {
    await new Promise(r => setTimeout(r, interval * 1000));
    const res = await fetch(`https://${DOMAIN}/oauth/token`, {
      method: 'POST',
      body: form({ grant_type: 'urn:ietf:params:oauth:grant-type:device_code',
                   device_code: dc.device_code, client_id: CLIENT_ID })
    });
    const data = await res.json();
    if (res.ok) return data;                        // { access_token, refresh_token, id_token }
    if (data.error === 'authorization_pending') continue;
    if (data.error === 'slow_down') { interval += 5; continue; }
    throw new Error(data.error_description || data.error); // expired_token / access_denied
  }
}
deviceLogin().then(t => console.log('Logged in! access_token:', t.access_token.slice(0,20) + '…'));

7.3 Refresh tokens in React (Auth0 SPA SDK does rotation for you)

// main.jsx — enable refresh-token rotation in a SPA safely
import { Auth0Provider } from '@auth0/auth0-react';

<Auth0Provider
  domain="YOUR_TENANT.us.auth0.com"
  clientId="YOUR_SPA_CLIENT_ID"
  authorizationParams={{
    redirect_uri: window.location.origin,
    audience: 'https://api.cinema.cloud',
    scope: 'openid profile offline_access'   // offline_access => refresh token
  }}
  useRefreshTokens={true}                     // use rotating refresh tokens...
  useRefreshTokensFallback={false}            // ...not legacy silent-iframe auth
  cacheLocation="memory"                      // safest; localStorage only if you must
>
  <App />
</Auth0Provider>

// In a component: the SDK silently rotates the refresh token under the hood.
import { useAuth0 } from '@auth0/auth0-react';
function useApi() {
  const { getAccessTokenSilently } = useAuth0();
  return async (url) => {
    const token = await getAccessTokenSilently(); // refreshes if expired
    return fetch(url, { headers: { Authorization: `Bearer ${token}` } });
  };
}

7.4 Refresh tokens in FastAPI (server-side confidential client)

import time, httpx
from fastapi import FastAPI

DOMAIN = "YOUR_TENANT.us.auth0.com"
CID, CSECRET = "YOUR_CLIENT_ID", "YOUR_CLIENT_SECRET"
app = FastAPI()
_store = {"access_token": None, "refresh_token": "SAVED_RT", "exp": 0}

async def get_access_token() -> str:
    if _store["access_token"] and time.time() < _store["exp"] - 30:
        return _store["access_token"]                       # still valid
    async with httpx.AsyncClient() as c:
        r = await c.post(f"https://{DOMAIN}/oauth/token", data={
            "grant_type": "refresh_token",
            "client_id": CID, "client_secret": CSECRET,
            "refresh_token": _store["refresh_token"],
        })
    r.raise_for_status()
    tok = r.json()
    _store["access_token"] = tok["access_token"]
    _store["exp"] = time.time() + tok["expires_in"]
    if "refresh_token" in tok:                               # ROTATION: persist new RT!
        _store["refresh_token"] = tok["refresh_token"]
    return _store["access_token"]
Warn

The single most common refresh-token bug: forgetting to persist the rotated refresh token. If rotation is on and you keep using the old one, the very next refresh triggers reuse detection and logs the user out. Always overwrite your stored token with the new refresh_token from the response.

Pattern: Backend-For-Frontend (BFF). The modern best practice for browser apps is to not store refresh tokens in JS at all. A small server (the BFF / Next.js route handlers) runs Authorization Code + PKCE, holds the refresh token in an HttpOnly cookie-backed session, and proxies API calls. The browser never touches a token. SPAs that cannot deploy a BFF fall back to useRefreshTokens with in-memory storage and rotation.

M2M at scale. Cache the Client Credentials token (it has no refresh token — you just request a new one near expiry). For high-security M2M, replace the shared client_secret with Private Key JWT (client_assertion) or, between cloud workloads, mTLS / workload identity federation so there is no long-lived secret to leak.

Key

In production: humans + browser ⇒ Authorization Code + PKCE (refresh tokens for staying logged in); humans + no keyboard ⇒ Device flow; no human ⇒ Client Credentials. Refresh tokens are an add-on to user flows, never a standalone login method. Implicit and ROPC appear in production only as legacy you are migrating off.

Why OAuth 2.1 removes Implicit and ROPC

OAuth 2.1 (the consolidation of OAuth 2.0 best practices) omits the Implicit grant and the Resource Owner Password Credentials grant entirely and mandates PKCE for all Authorization Code uses. Implicit is removed because PKCE made code flow safe even for public clients, eliminating Implicit's only reason to exist while removing its token-in-URL risk. ROPC is removed because it is fundamentally incompatible with the goal of OAuth (apps shouldn't see passwords) and with modern protections like MFA, passwordless, and federated login.

10. Performance Considerations & Token Lifetimes

  • Cache Client Credentials tokens. A token endpoint round-trip is ~100–300 ms and counts against rate limits. Fetch once, reuse until ~30 s before expires_in, then refetch. Never request a fresh M2M token per API call.
  • Pick lifetimes deliberately. Short access tokens (5–15 min) limit the blast radius of a leak but mean more refreshes. Long ones reduce traffic but linger if stolen. Standard balance below.
  • Device polling. Respect interval. Polling faster only earns slow_down and wastes requests; it never speeds up approval.
  • Refresh storms. If many clients share a token lifetime they may all refresh at once. Stagger by adding jitter, or refresh proactively at a random point in the token's life rather than exactly at expiry.
  • JWT vs. opaque. JWT access tokens validate locally via cached JWKS (microseconds, no network) — far faster than introspecting an opaque token per request.

11. Common Mistakes

  • Using Client Credentials to "log in a user." It has no user — sub is the client. There is no id_token. If you need to know who the human is, you need a user flow.
  • Embedding a client secret in a SPA or mobile app. Public clients have no secret. Use PKCE.
  • Not persisting the rotated refresh token — guarantees reuse-detection logout on the next refresh.
  • Requesting Client Credentials tokens on every request instead of caching — rate-limit pain and latency.
  • Forgetting audience on the M2M request. Without it Auth0 issues an opaque token for the userinfo endpoint, not a JWT for your API — and validation fails confusingly.
  • Forgetting offline_access scope — then wondering why no refresh token came back.
  • Choosing Implicit because "it's simpler." It is deprecated and insecure; Auth Code + PKCE is now just as easy with the SDKs.
  • Using ROPC against social/enterprise connections — impossible; ROPC only works with database connections.
  • Ignoring slow_down in device polling — leads to throttling and a stuck device.
  • Treating refresh tokens as a login method. You must first obtain one through a real user flow (Auth Code, Device, or ROPC).

12. Best Practices

  • Default to Authorization Code + PKCE for anything with a user and a browser. Reach for other grants only when that one genuinely cannot apply.
  • Always enable refresh-token rotation with reuse detection for public clients (SPA, mobile).
  • Scope M2M apps minimally. One M2M client per consumer, each granted only the exact API permissions it needs.
  • Prefer Private Key JWT / mTLS over shared secrets for high-value M2M.
  • Keep access tokens short and let refresh tokens do the "stay logged in" work.
  • Store refresh tokens server-side or in HttpOnly cookies (BFF). If you must store in a SPA, use in-memory + rotation, never localStorage if avoidable.
  • Show the app name and requested scopes on device-flow consent so users can spot phishing.
  • Revoke refresh tokens on logout and on suspected compromise (and rely on rotation to auto-revoke families).
  • Plan to retire Implicit and ROPC. Inventory where they are used and migrate to redirect flows.
  • Always set and validate audience so tokens are bound to the intended API.

13. Interview Questions (With Model Answers)

Q1. When would you use the Client Credentials grant?

A. For machine-to-machine access where no user is involved — a backend service, daemon, or cron job calling an API as itself. The client authenticates with its own credentials (secret or private-key JWT) and receives an access token whose subject is the client. No id_token and no refresh token are issued.

Q2. Why is the Implicit flow deprecated?

A. It returns the access token in the URL fragment, where it leaks via browser history, the Referer header, and JavaScript/XSS. It performs no client authentication and no code-for-token exchange, so whoever reads the fragment owns the token, and it cannot safely issue refresh tokens. PKCE made Authorization Code safe for public clients, removing Implicit's only advantage while eliminating its risks. OAuth 2.1 drops it.

Q3. Explain refresh token rotation and reuse detection.

A. Each time a refresh token is used, the server invalidates it and issues a new one (RT1→RT2→…), all part of one token "family." If a previously-used token is presented again — a sign that both a legitimate client and a thief hold copies — the server revokes the entire family, forcing re-authentication. This turns a stolen refresh token from permanent access into a brief window.

Q4. Why is ROPC discouraged even though it "works"?

A. The application collects and transmits the user's plaintext password, which violates OAuth's core goal (apps shouldn't see credentials) and bypasses MFA, anomaly/brute-force detection, bot protection, SSO, consent, and passwordless. It also only works against database connections. It is acceptable only for trusted first-party legacy apps and is removed in OAuth 2.1.

Q5. A smart TV app needs login but has no keyboard. Which grant and why?

A. Device Authorization (RFC 8628). The TV shows a short user code and a verification URL; the user authenticates on a phone/PC; the TV polls the token endpoint until approval. It avoids painful on-device typing and keeps credentials off the constrained device.

Q6. Does Client Credentials return an ID token?

A. No. ID tokens assert a user's identity; Client Credentials has no user. It returns only an access token (authorization), never authentication of a person.

Q7. How do you stop a refresh token from being a permanent backdoor if stolen?

A. Rotation + reuse detection, short absolute and idle lifetimes, HttpOnly/server-side storage, binding to the client, and revocation on logout. Combined, a stolen token is either short-lived, useless after the next legitimate rotation, or triggers a family revocation.

Q8. Why must M2M token requests include audience in Auth0?

A. The audience identifies the target API (Resource Server). It tells Auth0 which API's permissions to grant and to mint a JWT for that API. Omitting it yields an opaque token meant for /userinfo, which your API cannot validate as a JWT.

Q9. PKCE vs. client secret — when each?

A. Client secret is for confidential clients that can keep it private (backend servers). PKCE is for public clients (SPAs, native/mobile) that cannot, replacing the secret with a per-request code verifier/challenge so an intercepted authorization code is useless.

Q10. Is the Refresh Token flow a way to log a user in?

A. No. It only mints new tokens from an existing refresh token. The user must first authenticate via a real flow (Authorization Code, Device, or ROPC) that issued the refresh token in the first place.

14. Certification Tips

Exam

The Auth0 / OIDC exams love "given this app type, pick the grant" questions. Burn the decision tree (next section) into memory.

  • Map app type → grant cold: Regular Web App = Auth Code; SPA = Auth Code + PKCE; Native/Mobile = Auth Code + PKCE (or Device for no-keyboard); M2M = Client Credentials.
  • Know that Client Credentials issues no ID token and no refresh token — a frequent trap answer.
  • Remember the exact device grant_type URN: urn:ietf:params:oauth:grant-type:device_code.
  • Know that offline_access scope is what triggers a refresh token.
  • Implicit and ROPC are deprecated / not recommended / removed in OAuth 2.1 — expect a question whose correct answer is "don't use it."
  • ROPC works only with database connections, not social/enterprise IdPs.
  • Recognise device-flow polling errors: authorization_pending, slow_down, expired_token, access_denied.
  • Refresh token rotation + automatic reuse detection is the recommended SPA pattern.

20. Key Takeaways

Key

1. A grant type is dictated by three questions: can the client hold a secret, is a user present, is a browser redirect available? Answer those and the grant is decided.

Key

2. Client Credentials = machine-to-machine. No user, no ID token, no refresh token; the client authenticates as itself. Always send audience; cache the token.

Key

3. Device flow = users on input-constrained devices (TVs, CLIs). Show a user code, defer login to a second device, poll the token endpoint respecting interval.

Key

4. Refresh tokens keep users logged in without re-prompting. Always enable rotation + reuse detection, persist the new token, and store it as securely as possible (BFF / HttpOnly / in-memory).

Key

5. Implicit (token in URL, no client auth) and ROPC (app sees the password) are deprecated/discouraged and removed in OAuth 2.1. Treat them only as legacy to migrate off — to Authorization Code + PKCE.

Key

6. Default everywhere a human logs in through a browser: Authorization Code + PKCE, with short access tokens and rotating refresh tokens. Everything in this chapter is the exception you reach for when that default can't apply.
