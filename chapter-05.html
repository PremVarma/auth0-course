Chapter 5 — Authorization Code Flow and PKCE

The Authorization Code flow is the single most important grant in OAuth 2.0 — it is the flow that powers "Log in with Google," every Auth0-protected web app, every mobile login, and most of the secure enterprise integrations you will ever build. In this chapter we rebuild it from first principles: why a "code" exists at all, how the browser redirect dance works, why the state parameter stops CSRF, and how PKCE (Proof Key for Code Exchange) closed a dangerous interception hole so that even apps that cannot keep a secret — single-page apps and mobile apps — can use this flow safely. By the end you will be able to draw the full sequence diagram from memory, run it by hand with curl and Postman, and implement it correctly in Node, React, Next.js, Spring Boot, and FastAPI.

1. Theory — First Principles: Why a "Code" at All?

OAuth 2.0 is a delegated authorization framework. Its core job is to let a client (your application) obtain an access token so it can call an API (a resource server) on behalf of a user, without the user ever handing their password to the client. The Authorization Code grant is the canonical way to do this when a human is sitting in front of a browser.

Start from the problem. We have four parties:

Role (OAuth term)Who it isWhat it must NOT see
Resource OwnerThe end user (a human)—
ClientYour app (web/SPA/mobile/server)The user's password
Authorization ServerAuth0 (issues tokens)—
Resource ServerYour APIThe user's password

The naive design would be: the user logs in at Auth0, and Auth0 immediately sends the access token back to the client. But how does it send it back? The only transport available after a browser login is an HTTP redirect — and redirect URLs are visible in the browser address bar, in server logs, in the Referer header, and in browser history. Putting a long-lived, bearer access token in a redirect URL is like writing your house key on a postcard. This is exactly the weakness of the now-deprecated Implicit flow.

The Authorization Code flow solves this with indirection: instead of returning the valuable token through the insecure front channel (the browser redirect), Auth0 returns a short-lived, single-use authorization code. The code is useless on its own. The client then exchanges that code for tokens over a back channel — a direct, server-to-server, TLS-protected HTTPS POST that no browser, log, or attacker on the redirect path can read. This separation of "front channel" (browser, untrusted) and "back channel" (server-to-server, trusted) is the central idea of the whole flow.

Key

The authorization code is a one-time, short-lived bearer of intent, not a credential. Its only purpose is to be redeemed — exactly once, within ~30–60 seconds — for the real tokens over a secure back channel.

Front channel vs. back channel is worth memorizing:

  • Front channel: data travels through the user-agent (the browser) via redirects and query strings. Fast and works without server-side cooperation, but everything is visible to the user and to anything sitting on the redirect path. Used to deliver the code.
  • Back channel: a direct HTTPS call from the client's backend to Auth0's /oauth/token endpoint. Invisible to the browser. Used to deliver the client_secret and receive the tokens.

2. Story-Based Explanation — The Coat-Check Ticket

Imagine a fancy hotel. You (the user) arrive with a valuable coat (your identity and permissions). A valet (the client app) wants to fetch your car later, but you would never hand the valet the actual car keys to keep.

So the hotel desk (Auth0) does something clever. After you prove who you are at the desk, they don't hand the valet the keys. They hand the valet a numbered ticket (the authorization code). Anyone could glance at that ticket number, but it is worthless by itself — you cannot drive a car with a paper number.

When the valet actually needs the car, they walk to a private back office (the back channel), show the ticket plus their own staff badge (the client_secret), and only then does the hotel produce the keys (the tokens). The ticket is torn up immediately — it can never be used again.

Now the twist that gives us PKCE. Some valets are freelancers with no staff badge — a phone app or a browser SPA cannot keep a secret, because anyone can decompile the app or read the JavaScript. For these badge-less valets, an attacker who steals the ticket could walk into the back office and claim the keys. PKCE fixes this: when the freelance valet first gets the ticket, they whisper a secret password (the code_verifier) and hand over only a scrambled fingerprint of it (the code_challenge) to the desk. Later, to redeem the ticket, they must say the original password out loud. A thief who copied the ticket never heard the password, so the scrambled fingerprint won't match, and the desk refuses. The badge problem is solved without ever needing a badge.

Note

Hold this analogy in your head for the rest of the chapter: ticket = code, back office = token endpoint, staff badge = client_secret, whispered password = code_verifier, scrambled fingerprint = code_challenge.

3.3 Why PKCE matters — the interception attack it blocks

  WITHOUT PKCE (public client):
     legit app --/authorize--> Auth0 --redirect code--> [OS hands URL to wrong app]
                                                              |
                                          MALICIOUS APP grabs the code
                                                              |

                              (client_id is public, no secret needed -> attacker wins)

  WITH PKCE:
     MALICIOUS APP grabs the code, but never saw the verifier
                              POST /oauth/token (code, client_id, code_verifier=???)
                                                              |
                              Auth0: SHA256(wrong) != stored challenge --> 400 ✓ BLOCKED

4. Real-World Analogy — Wiring Money vs. Mailing Cash

Think about how banks move money. You would never mail an envelope of cash (that is the Implicit flow — the token flies through the open browser). Instead the sending bank gives you a reference number (the authorization code) and the actual money moves bank-to-bank over a secured wire (the back channel token exchange). The reference number alone can't be spent.

PKCE is the one-time PIN your bank texts you. The reference number plus the PIN proves it is really you completing the transfer. Someone who shoulder-surfed the reference number on your screen still can't move the money, because they never received the PIN on your phone. The code_verifier is that PIN: generated fresh, known only to the legitimate client, and required to complete the exchange.

Tip

The state parameter is a different safeguard: it is the tracking number you wrote down before you started. When the confirmation comes back, you check that the tracking number matches what you sent. If it doesn't, someone forged the response — you reject it. That is CSRF protection.

5. Internal Working — Endpoint by Endpoint, Parameter by Parameter

5.1 The /authorize request (front channel)

This is a plain browser navigation (an HTTP GET). Auth0's authorization endpoint for a tenant dev-xyz.us.auth0.com is https://dev-xyz.us.auth0.com/authorize. The query parameters:

ParameterRequired?Meaning
response_type=codeYesAsks for the Authorization Code grant (vs. token = implicit).
client_idYesPublic identifier of your Auth0 Application.
redirect_uriYesWhere Auth0 sends the code. Must exactly match a registered callback.
scopeYesWhat you want, e.g. openid profile email offline_access. openid triggers OIDC and an id_token; offline_access requests a refresh token.
audienceAuth0-specificThe API identifier you want an access token for. Without it you may get an opaque token instead of a JWT for your API.
stateYes (practically)Opaque random value echoed back; binds the response to this browser session (CSRF defense).
nonceOIDCRandom value embedded in the id_token to prevent replay of ID tokens.
code_challengePKCEBASE64URL(SHA-256(verifier)).
code_challenge_methodPKCEAlways S256 for production (never plain).

5.2 What Auth0 does with the code

When Auth0 generates the code, it stores server-side a small record bound to it: the client_id, the exact redirect_uri, the granted scopes, the user's identity, the nonce, and — if PKCE was used — the code_challenge and method. The code itself is an opaque, high-entropy string. It typically expires in about 30–60 seconds and is marked single-use the moment it is redeemed.

5.3 The /oauth/token exchange (back channel)

A POST with Content-Type: application/x-www-form-urlencoded. Auth0 performs these checks in order:

  1. Does the code exist and is it unexpired and unused? (else invalid_grant)
  2. Does the supplied redirect_uri exactly match the one used at /authorize? (binding check)
  3. For confidential clients: is the client_secret (or private-key-JWT) valid?
  4. For PKCE: does BASE64URL(SHA-256(code_verifier)) equal the stored code_challenge?
  5. All pass → issue access_token (+ id_token if openid, + refresh_token if offline_access), and burn the code.

5.4 How the PKCE math actually works (S256)

code_verifier  : a cryptographically random string, 43-128 chars,
                 from the set [A-Z a-z 0-9 - . _ ~]  (unreserved URL chars)

code_challenge : BASE64URL-ENCODE( SHA-256( ASCII(code_verifier) ) )
                 (BASE64URL = base64 with '+'->'-', '/'->'_', no '=' padding)

Verification at token endpoint:
   BASE64URL( SHA-256( received_verifier ) )  ==  stored_challenge ?

SHA-256 is a one-way hash: given the challenge you cannot reverse it to find the verifier. So even if the attacker captures the /authorize request (and thus the challenge) and the code, they still cannot produce a verifier that hashes to the challenge. That is the entire security argument.

6. Code Walkthrough — Generating PKCE Values

Before any framework, do it by hand so the magic disappears.

Node.js — generate verifier + challenge

import crypto from "node:crypto";

// 1) verifier: 32 random bytes -> base64url is 43 chars (within 43-128 limit)
function base64url(buf) {
  return buf.toString("base64")
    .replace(/\+/g, "-")
    .replace(/\//g, "_")
    .replace(/=+$/, "");
}

const codeVerifier  = base64url(crypto.randomBytes(32));
const codeChallenge = base64url(
  crypto.createHash("sha256").update(codeVerifier).digest()
);
const state = base64url(crypto.randomBytes(16));  // CSRF token
const nonce = base64url(crypto.randomBytes(16));  // OIDC replay guard

console.log({ codeVerifier, codeChallenge, state, nonce });
// Store codeVerifier + state + nonce in the user's session BEFORE redirecting.

Python (FastAPI) — same primitives

import secrets, hashlib, base64

def b64url(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

code_verifier  = b64url(secrets.token_bytes(32))           # 43 chars
code_challenge = b64url(hashlib.sha256(code_verifier.encode()).digest())
state          = secrets.token_urlsafe(16)
nonce          = secrets.token_urlsafe(16)

Java (Spring Boot) — same primitives

import java.security.MessageDigest;
import java.security.SecureRandom;
import java.util.Base64;

SecureRandom rng = new SecureRandom();
byte[] v = new byte[32];
rng.nextBytes(v);
String codeVerifier = Base64.getUrlEncoder().withoutPadding().encodeToString(v);

byte[] digest = MessageDigest.getInstance("SHA-256")
        .digest(codeVerifier.getBytes(java.nio.charset.StandardCharsets.US_ASCII));
String codeChallenge = Base64.getUrlEncoder().withoutPadding().encodeToString(digest);
Warn

Use a cryptographically secure RNG (crypto.randomBytes, secrets, SecureRandom) — never Math.random(), random.random(), or java.util.Random. Predictable verifiers defeat the entire point of PKCE.

7. Practical Implementation — Five Stacks

7.1 curl — the flow by hand

Step 1: build the authorize URL and open it in a browser (front channel). After login Auth0 redirects to your callback with ?code=...&state=....

# --- Step 1: authorize URL (paste into a browser) ---
AUTH0_DOMAIN="dev-xyz.us.auth0.com"
CLIENT_ID="abc123"
REDIRECT_URI="http://localhost:3000/callback"
AUDIENCE="https://api.myapp.com"

# (compute these with the Node/Python snippet from section 6)
CODE_CHALLENGE="E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM"
STATE="random-state-xyz"

echo "https://$AUTH0_DOMAIN/authorize?\
response_type=code&\
client_id=$CLIENT_ID&\
redirect_uri=$REDIRECT_URI&\
scope=openid%20profile%20email%20offline_access&\
audience=$AUDIENCE&\
state=$STATE&\
code_challenge=$CODE_CHALLENGE&\
code_challenge_method=S256"

Step 2: take the code from the redirect and exchange it (back channel). Public client uses code_verifier; confidential client adds client_secret.

# --- Step 2: exchange the code for tokens ---
curl --request POST \
  --url "https://$AUTH0_DOMAIN/oauth/token" \
  --header "content-type: application/x-www-form-urlencoded" \
  --data "grant_type=authorization_code" \
  --data "client_id=$CLIENT_ID" \
  --data "code_verifier=THE_ORIGINAL_VERIFIER" \
  --data "code=PASTE_AUTH_CODE_HERE" \
  --data "redirect_uri=$REDIRECT_URI"
# Confidential client instead/also sends:  --data "client_secret=YOUR_SECRET"

# Response:
# { "access_token":"eyJ...", "id_token":"eyJ...",
#   "refresh_token":"v1.M...", "token_type":"Bearer", "expires_in":86400 }

7.2 Node.js (Express) — confidential client, manual exchange

import express from "express";
import crypto from "node:crypto";
import session from "express-session";

const app = express();
app.use(session({ secret: "change-me", resave: false, saveUninitialized: true }));

const DOMAIN = "dev-xyz.us.auth0.com";
const CLIENT_ID = process.env.CLIENT_ID;
const CLIENT_SECRET = process.env.CLIENT_SECRET;
const REDIRECT_URI = "http://localhost:3000/callback";
const b64url = b => b.toString("base64").replace(/\+/g,"-").replace(/\//g,"_").replace(/=+$/,"");

app.get("/login", (req, res) => {
  const verifier  = b64url(crypto.randomBytes(32));
  const challenge = b64url(crypto.createHash("sha256").update(verifier).digest());
  const state = b64url(crypto.randomBytes(16));
  // persist server-side, tied to THIS session
  req.session.verifier = verifier;
  req.session.state = state;

  const url = new URL(`https://${DOMAIN}/authorize`);
  url.search = new URLSearchParams({
    response_type: "code",
    client_id: CLIENT_ID,
    redirect_uri: REDIRECT_URI,
    scope: "openid profile email offline_access",
    audience: "https://api.myapp.com",
    state,
    code_challenge: challenge,
    code_challenge_method: "S256",
  }).toString();
  res.redirect(url.toString());
});

app.get("/callback", async (req, res) => {
  const { code, state } = req.query;
  if (state !== req.session.state) return res.status(403).send("Bad state (CSRF?)");

  const r = await fetch(`https://${DOMAIN}/oauth/token`, {
    method: "POST",
    headers: { "content-type": "application/x-www-form-urlencoded" },
    body: new URLSearchParams({
      grant_type: "authorization_code",
      client_id: CLIENT_ID,
      client_secret: CLIENT_SECRET,        // confidential client
      code,
      code_verifier: req.session.verifier, // PKCE proof (good even for confidential)
      redirect_uri: REDIRECT_URI,
    }),
  });
  const tokens = await r.json();
  if (tokens.error) return res.status(400).json(tokens);

  req.session.tokens = tokens;             // keep tokens server-side, NOT in browser JS
  delete req.session.verifier; delete req.session.state;
  res.send("Logged in! Tokens stored server-side.");
});

app.listen(3000);

// main.jsx — @auth0/auth0-react handles PKCE + state + token storage for you
import { Auth0Provider } from "@auth0/auth0-react";
import { createRoot } from "react-dom/client";
import App from "./App";

createRoot(document.getElementById("root")).render(

      audience: "https://api.myapp.com",
      scope: "openid profile email",
    }}
    useRefreshTokens={true}            // refresh-token rotation for SPAs
    cacheLocation="memory">            // safest: in-memory, not localStorage
    <App />
  </Auth0Provider>
);
// App.jsx
import { useAuth0 } from "@auth0/auth0-react";

export default function App() {
  const { loginWithRedirect, logout, user, isAuthenticated, getAccessTokenSilently } = useAuth0();
  if (!isAuthenticated) return <button onClick={() => loginWithRedirect()}>Log in</button>;

  async function callApi() {
    const token = await getAccessTokenSilently();
    const res = await fetch("https://api.myapp.com/me", {
      headers: { Authorization: `Bearer ${token}` },
    });
    console.log(await res.json());
  }
  return (
    <>
      <p>Hi {user.name}</p>
      <button onClick={callApi}>Call API</button>
      <button onClick={() => logout()}>Log out</button>
    </>
  );
}

8. Production Architecture — Where Tokens Should Live

The biggest architectural decision is token storage, and it follows directly from client type.

  PATTERN A — "Backend for Frontend" (BFF)  [RECOMMENDED for web]
  ----------------------------------------------------------------
   Browser  --cookie(HttpOnly,Secure,SameSite)-->  Your Server  --Bearer-->  API
                                                       |
                                                  holds tokens
                                                  (never sent to browser JS)
   Auth Code + PKCE runs on the server. XSS cannot read an HttpOnly cookie.

  PATTERN B — Pure SPA  [only if no backend]
  ----------------------------------------------------------------
   Browser (Auth0 SPA SDK) holds access token in MEMORY
        + refresh-token rotation, short token lifetimes
   Auth Code + PKCE runs in the browser. Acceptable, but XSS = total compromise.

  PATTERN C — Native / Mobile
  ----------------------------------------------------------------
   App uses system browser (ASWebAuthenticationSession / Custom Tabs)
        + Auth Code + PKCE + claimed https redirect (App Links / Universal Links)
   Tokens in OS secure storage (Keychain / Keystore).
Key

In 2026 the consensus best practice for web apps is the BFF pattern: run the flow server-side, store tokens server-side, and give the browser only an encrypted HttpOnly session cookie. SPAs that hold tokens in JavaScript are a fallback, not the goal.

9. Security Analysis — Threats and Mitigations

ThreatHow it worksMitigation in this flow

Danger

PKCE protects the code exchange; it does not protect tokens after they are issued. If your SPA stores an access token in localStorage and you have an XSS bug, the attacker reads the token directly — PKCE never enters the picture. Defense in depth (CSP, BFF, short lifetimes, refresh rotation) is still required.

10. Performance Considerations

  • Extra round trip: Auth Code adds one back-channel POST vs. Implicit. This happens once per login, costs tens of milliseconds, and is irrelevant compared to the security gain. Never optimize it away.
  • PKCE hashing cost: a single SHA-256 over ≤128 bytes — microseconds. Negligible.
  • JWKS caching: your API validates the access-token signature using Auth0's public keys from /.well-known/jwks.json. Cache them (most SDKs do, ~10 min) so you don't fetch keys on every request — that is the real hot path, not the login.
  • Silent token renewal: SPAs renew via refresh-token rotation (getAccessTokenSilently) rather than full redirects, avoiding page reloads.
  • Session affinity: if you store the code_verifier/state in server session, ensure your load balancer uses sticky sessions or a shared session store (Redis), or the callback may hit a node that doesn't have the verifier.

11. Common Mistakes

  1. redirect_uri mismatch. A trailing slash, http vs https, or a different port breaks the exact match. Auth0 returns Callback URL mismatch. Register the exact URI in the Application settings.
  2. Not validating state. Generating it but not comparing it on return leaves you open to CSRF. Compare and reject mismatches.
  3. Reusing one code_verifier for every login. It must be fresh per request; a static verifier is no better than no PKCE.
  4. Using code_challenge_method=plain. Sends the verifier in cleartext at /authorize. Always use S256.
  5. Putting client_secret in a SPA or mobile app. It will be extracted. SPAs/mobile are public clients — PKCE only.
  6. Storing tokens in localStorage "because it's easy." Readable by any XSS. Prefer memory or HttpOnly cookies via a BFF.
  7. Forgetting audience. Without it Auth0 may issue an opaque access token your API cannot validate as a JWT.
  8. Trying to redeem a code twice. Codes are single-use; the second attempt fails (and Auth0 may revoke the issued tokens as an anomaly).
  9. Letting the verifier/state get lost between requests (e.g., stateless server with no sticky sessions). The callback then can't find them.

12. Best Practices

  • Use Authorization Code + PKCE for every client type — confidential clients too. PKCE adds defense in depth at zero cost (OAuth 2.1 makes this the default).
  • Always S256, never plain.
  • Generate state, nonce, and code_verifier with a CSPRNG; bind them to the session; verify on return; then discard.
  • Register an exact allowlist of redirect URIs; no wildcards in the path.
  • Prefer the BFF pattern for web; tokens stay server-side behind HttpOnly cookies.
  • For SPAs: in-memory tokens, short access-token TTLs, refresh-token rotation, a strict Content-Security-Policy.
  • For mobile: system browser (not embedded WebView), claimed https redirects (App Links/Universal Links), tokens in OS secure storage.
  • Use an official Auth0 SDK rather than hand-rolling — it gets PKCE, state, nonce, and renewal right.
  • Request the least scopes needed; add offline_access only when you truly need refresh tokens.

13. Interview Questions (with Model Answers)

Q1. Why does the Authorization Code flow return a code instead of a token directly?

A. Because the response travels through the browser (front channel), where URLs leak into history, logs, and the Referer header. A code is short-lived and single-use, useless without a back-channel exchange, so leaking it is far less damaging than leaking a long-lived access token. The real tokens move over a direct server-to-server TLS call.

Q2. What problem does PKCE solve, and for whom?

A. The authorization-code interception attack on public clients (SPAs, mobile) that cannot hold a secret. A malicious app could claim the redirect, grab the code, and — since the client_id is public — redeem it. PKCE binds the code to a per-request secret (code_verifier) that the attacker never saw, so the exchange fails for them.

Q3. Walk me through S256.

A. The client generates a random code_verifier, computes code_challenge = BASE64URL(SHA-256(verifier)), sends the challenge + method at /authorize. At /oauth/token it sends the original verifier; the server re-hashes it and checks it equals the stored challenge. SHA-256 is one-way, so the challenge can't be reversed to forge a verifier.

Q4. How does state differ from nonce?

A. state is an OAuth CSRF defense for the authorization response — a random value you send and verify on return to ensure the callback belongs to the session that started it. nonce is an OIDC defense embedded inside the id_token to prevent ID-token replay. State protects the round trip; nonce protects the ID token.

Q5. Is PKCE a replacement for the client secret?

A. For public clients, yes — it provides proof of possession without a stored secret. For confidential clients, no — you still send the secret (or use private-key-JWT); PKCE is added on top as defense in depth. OAuth 2.1 recommends PKCE for all clients.

Q6. Why is the Implicit flow deprecated?

A. It returned the access token directly in the redirect fragment, exposing it to leakage and offering no way to safely deliver refresh tokens. Auth Code + PKCE gives SPAs the same browser-only capability with far better security, so Implicit is removed in OAuth 2.1.

Q7. Where should an SPA store its access token?

A. Ideally nowhere reachable by JavaScript: use a BFF with HttpOnly cookies. If pure SPA, in memory with refresh-token rotation and a strict CSP. Avoid localStorage/sessionStorage because XSS can read them.

Q8. What stops an attacker who steals the code from also stealing tokens, even with a confidential client?

A. The token endpoint also requires the client_secret (server-only) and rechecks the redirect_uri; with PKCE it also requires the verifier. Multiple independent factors must all match, and the code is single-use and short-lived.

14. Certification Tips

  • Memorize the parameter sets: /authorize uses response_type=code, client_id, redirect_uri, scope, state, code_challenge, code_challenge_method; /oauth/token uses grant_type=authorization_code, code, redirect_uri, code_verifier, and (confidential) client_secret.
  • The exam loves the mapping client type → flow: Regular Web App = Auth Code (confidential); SPA = Auth Code + PKCE (public); Native = Auth Code + PKCE (public); M2M = Client Credentials.
  • Know that Auth0 calls registered callbacks "Allowed Callback URLs" and they must match exactly.
  • Remember audience is the Auth0-specific parameter that makes Auth0 issue a JWT access token for your API.
  • Be ready to identify S256 vs plain and why plain is discouraged.
  • Know the error codes: invalid_grant (bad/expired/used code or PKCE mismatch), access_denied (user declined), callback URL mismatch.

19. Cheat Sheet

AUTHORIZE  GET https://TENANT/authorize
  response_type=code
  client_id=...        redirect_uri=...(exact match)
  scope=openid profile email offline_access
  audience=https://api.myapp.com
  state=RANDOM         (verify on return)
  nonce=RANDOM         (OIDC, check in id_token)
  code_challenge=BASE64URL(SHA256(verifier))
  code_challenge_method=S256

TOKEN      POST https://TENANT/oauth/token   (x-www-form-urlencoded)
  grant_type=authorization_code
  code=AUTH_CODE       redirect_uri=...(same as above)
  code_verifier=ORIGINAL_RANDOM        (public + recommended for all)
  client_id=...        client_secret=... (confidential only)

PKCE       verifier  : 43-128 chars [A-Za-z0-9-._~], CSPRNG
           challenge : base64url(sha256(verifier)), method S256

CLIENT TYPE -> FLOW
  Regular Web App   = Auth Code (confidential)      [secret + PKCE]
  SPA               = Auth Code + PKCE (public)     [no secret]
  Native / Mobile   = Auth Code + PKCE (public)     [no secret, system browser]
  Machine-to-Machine= Client Credentials            [secret, no user]

ERRORS
  invalid_grant   = bad/expired/reused code OR PKCE mismatch
  access_denied   = user declined consent
  callback mismatch = redirect_uri not in Allowed Callback URLs

STORAGE
  Web  -> BFF + HttpOnly Secure SameSite cookie  (BEST)
  SPA  -> in-memory + refresh rotation + CSP
  Mobile -> OS Keychain / Keystore

20. Key Takeaways

Key

The code is a one-time ticket, not a credential. Front channel delivers the code; back channel exchanges it for tokens. This split is the heart of the Authorization Code flow.

Key

PKCE replaces the client secret for apps that can't keep one. A fresh per-request code_verifier, sent only at the back-channel exchange and verified against the SHA-256 code_challenge, defeats code interception. Always use S256.

Key

state stops CSRF, nonce stops ID-token replay, exact redirect_uri matching stops open-redirect token theft. Each parameter closes a specific hole — none is optional.

Key

Use Auth Code + PKCE for every client type (OAuth 2.1 default), prefer the BFF pattern for web apps, keep tokens out of JavaScript, request least scopes, and let an official Auth0 SDK handle the moving parts.
