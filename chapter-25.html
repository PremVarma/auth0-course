Chapter 25 — Project 9 — Mobile Authentication

A phone is a hostile place to store a secret. There is no server you control, the binary ships to every attacker who wants it, and a stolen device is a stolen vault. Yet mobile is where most of your users live. This chapter builds native authentication with Auth0 from first principles: why the Authorization Code flow with PKCE is the only correct grant for a public client, why you must open the system browser and never an embedded webview, how the OS hands the redirect back to your app through deep links / app links, where tokens actually live (the iOS Keychain and Android Keystore), how biometric unlock gates that storage, and how refresh token rotation keeps a long-lived session safe on a device you do not trust. Our primary code is React Native with react-native-auth0, backed by native Swift and Kotlin snippets so you understand what the SDK does for you. By the end you will be able to ship mobile auth that survives a security review, explain every decision in a senior interview, and answer the certification's mobile questions cold.

1. Theory — Why Mobile Auth Is Different (First Principles)

Everything about mobile auth flows from one uncomfortable fact: a native app is a public client. To understand why that single classification dictates every later decision, we have to define the term precisely.

In OAuth 2.0, a client is the application requesting access on behalf of a user. Clients come in two kinds:

  • A confidential client can keep a secret. It runs on a server you control. It can hold a client_secret in an environment variable that no end user ever sees. When it talks to the token endpoint it proves "I really am this app" by presenting that secret.
  • A public client cannot keep a secret. A native mobile app, a single-page app, a desktop app — anything whose code is fully delivered to the user's device — falls here. Whatever secret you compile into the binary can be extracted with a decompiler in minutes. There is no hiding place.
Key

A native app is a public client. It has no client secret, because any secret you ship is already compromised. This is not a limitation to work around — it is the premise that the entire mobile flow is designed to respect.

The consequence: you cannot use a secret to prove identity, so you must prove control of the request another way

If a public client can't present a secret, how does the authorization server know that the app redeeming an authorization code is the same app that started the login? It can't, with secrets. So OAuth's answer for public clients is PKCE (Proof Key for Code Exchange, pronounced "pixy"), defined in RFC 7636. PKCE replaces the static secret with a fresh, per-request secret that never has to be stored: the app invents a random value at the start of each login, sends only its hash up front, and reveals the original value when it redeems the code. We dissect the math in §5. For now, hold the shape: no permanent secret; a one-time proof per login.

The second consequence: you have no controlled redirect URI — you have a deep link

On the web, after login the browser redirects to https://yourapp.com/callback — a URL your server owns. A mobile app is not a web server; it has no URL. So the operating system provides a mechanism to route a URL into a specific installed app: custom URL schemes (myapp://callback) and the more secure universal links (iOS) / app links (Android), which use real https:// URLs that the OS verifies belong to your app. The redirect at the end of the OAuth dance lands on one of these, and the OS wakes your app. §3 and §7 make this concrete.

The third consequence: where do tokens live on a device you don't trust?

The server-side world stores sessions in a database behind a firewall. On a phone there is no firewall and the device may be lost, jailbroken, or rooted. The tokens (access token, ID token, and the prized long-lived refresh token) must rest in the platform's hardware-backed secure storage — the iOS Keychain and the Android Keystore — never in plain files, never in UserDefaults/SharedPreferences, never in AsyncStorage. And because a long-lived refresh token on a device is dangerous, we use refresh token rotation: each use burns the old token and issues a new one, so a stolen-and-replayed token can be detected and the whole family revoked.

Those three consequences — PKCE instead of a secret, deep links instead of a server redirect, hardware-backed storage with rotation instead of a database session — are mobile authentication. The rest of this chapter is detail on each.

2. Story-Based Explanation — Priya Builds "TrailMate"

Priya is shipping TrailMate, a hiking app, to iOS and Android with a React Native codebase. Watch her make — and nearly miss — every key decision.

Day 1 — the tempting shortcut. Priya's first instinct is to drop a username/password form right inside the app and POST it to Auth0's /oauth/token endpoint with the Resource Owner Password grant. It's one screen, no browser, feels native. Her security lead stops her: "Now your app sees the user's raw password. If your app is the thing handling the password, you've thrown away every benefit of delegating to an IdP — no SSO, no social login, no enterprise federation, and you're one bug away from leaking credentials. The password grant is deprecated for exactly this reason. Use the browser."

Day 2 — webview vs. system browser. Priya tries an embedded WKWebView so the login "stays inside the app." It works in the demo. But the security lead points out three problems: the user can't tell a real Auth0 page from a phishing page rendered in your webview (no address bar), the webview can't share the system browser's session so SSO breaks, and Apple/Google increasingly reject apps that put third-party login in embedded webviews. She switches to ASWebAuthenticationSession on iOS / Custom Tabs on Android — the OS-blessed in-app browser that shares cookies with Safari/Chrome.

Day 3 — the redirect vanishes. Login succeeds in Auth0, the browser tries to redirect to com.trailmate://callback... and nothing happens. The app never wakes. She forgot to register the URL scheme in Info.plist / AndroidManifest.xml and to add the callback URL to her Auth0 Application's Allowed Callback URLs. Once registered, the OS catches the redirect and hands control back to TrailMate with the authorization code.

Day 4 — "stay logged in." Users hate re-logging-in. Priya requests the offline_access scope to get a refresh token, and stores it. The security lead's last lesson: "Don't put that in AsyncStorage — it's plaintext on a rooted phone. Put it in the Keychain/Keystore, gate it behind Face ID, and turn on refresh token rotation in Auth0 so a stolen token self-destructs on replay." Priya does all three. TrailMate ships, passes the pen test, and Priya can explain every line in her next interview.

Note

Every wrong turn Priya took is a real, common mistake — and each correct turn is a rule the certification tests. Keep her four days in mind; the chapter follows the same arc.

4. Real-World Analogy — The Hotel, the Notary, and the Single-Use Coat Check

Mobile auth has a lot of moving parts; anchor each in something physical.

PKCE = the single-use coat-check ticket you tear in half

Imagine you check your coat but you're worried someone will steal your claim ticket. So you tear a unique ticket in half: you keep one half (code_verifier) and hand the attendant the other half (code_challenge) when you drop the coat. When you return, you present your half; the attendant matches the torn edges. A thief who grabs your coat ticket (the authorization code) off the floor still can't claim the coat, because they don't hold the matching torn half. The verifier never sat on a public counter — it stayed in your pocket the whole time. That is exactly PKCE: the challenge goes up front in the open redirect; the verifier is revealed only at redemption, over a direct back-channel.

System browser = the hotel's official front desk, not a clerk who follows you to your room

You give your passport to the front desk (the system browser, an institution you can see and trust, with a sign over it — the URL bar). You would never hand your passport to a stranger in the hallway who claims to work for the hotel and offers to "process it in your room" (an embedded webview inside the app, with no sign, who could be anyone and is standing in your private space watching). The front desk also remembers you for the rest of your stay (the shared SSO session cookie), so you don't re-prove yourself at the spa and the gym.

Keychain/Keystore = the in-room safe bolted to the wall, opened by your fingerprint

Your room key card (the tokens) doesn't get left on the nightstand (AsyncStorage). It goes in the safe (Keychain/Keystore) that is physically bolted into the building's structure (the Secure Enclave / Trusted Execution Environment — a separate chip even the main OS can't read out of), and the safe only opens to your fingerprint (biometric unlock). Steal the whole room and you still can't crack the bolted safe.

Refresh token rotation = a hotel key that reprograms itself every time you tap it

Each time you tap your key card on your door, the lock issues you a fresh card and invalidates the old one. If a pickpocket copies your card and taps it, the lock sees a card that was already replaced — it knows a copy exists, alarms, and disables your room entirely until you check in again at the front desk. The attacker's copy and your real card both die. That is reuse detection.

Tip

If you can retell the "torn coat-check ticket" story for PKCE and the "self-reprogramming hotel key" story for rotation, you can answer the two hardest mobile interview questions on the spot.

5. Internal Working — PKCE, Deep Links, and Secure Enclaves Under the Hood

5.1 PKCE, step by step with the actual math

  1. Generate the verifier. The app creates a cryptographically random string, 43–128 characters, from the unreserved URL set ([A-Z a-z 0-9 - . _ ~]). This is the code_verifier. It stays in memory on the device; it is never sent in the front-channel (the browser redirect).
  2. Derive the challenge. Compute code_challenge = BASE64URL( SHA-256( ASCII(code_verifier) ) ) and set code_challenge_method=S256. (A "plain" method exists where challenge = verifier, but you must always use S256 — plain offers no protection if the front channel leaks.)
  3. Front-channel. The app opens the browser to /authorize carrying the challenge (the hash). Even if malware reads the redirect URL, it sees only the hash — and SHA-256 is one-way, so it can't recover the verifier.
  4. Back-channel. After the user authenticates, the app receives the authorization code via the deep link and POSTs it to /oauth/token together with the original code_verifier.
  5. Server proof. Auth0 hashes the received verifier and checks it equals the challenge it stored at step 3. Match → it knows the redeemer is the same party that started the flow → it issues tokens. No secret was ever needed.
Why this defeats the attack

The threat PKCE kills is authorization-code interception: on mobile, another malicious app could register the same custom URL scheme and intercept the redirect, stealing the code. Without PKCE, that stolen code could be redeemed for tokens. With PKCE, the thief has the code but not the in-memory code_verifier, so redemption fails.

5.2 How a deep link actually routes back into your app

Two mechanisms, with very different security:

Custom URL schemeUniversal Link (iOS) / App Link (Android)
Looks likecom.trailmate://callbackhttps://trailmate.com/callback
OwnershipAny app can claim the same schemeOS verifies you own the domain (file on your server)
VerificationNone — collision possibleiOS fetches /.well-known/apple-app-site-association; Android fetches /.well-known/assetlinks.json
Interception riskHigher (mitigated by PKCE)Very low — only the verified app opens it
Recommended forAcceptable with PKCE; common in samplesProduction — strongest binding of redirect to your app

When the browser issues the final 302 to your redirect URI, the OS looks at the scheme/host. For a custom scheme it dispatches to whatever app registered it; for a verified universal/app link it checks the association file it downloaded at install time and dispatches only to your app. Either way your app receives the URL in a platform callback (iOS application(_:open:) / SceneDelegate, or Android an Intent with ACTION_VIEW), from which the SDK extracts code and state.

5.3 Where the Keychain and Keystore get their hardware

On modern iPhones the Secure Enclave is a separate coprocessor with its own boot ROM and keys that the main CPU and OS can never read. Keychain items can be bound to it and to a biometric "access control" so the OS only releases the secret after a successful Face ID/Touch ID check. On Android the Keystore backs keys in a Trusted Execution Environment (TEE) or a dedicated StrongBox secure element; keys can be marked setUserAuthenticationRequired(true) so they're usable only just after a biometric/credential unlock. In both, the raw key material never enters your app's address space — you ask the secure hardware to encrypt/decrypt on your behalf.

5.4 Refresh token rotation internals

With rotation enabled, each refresh token is single-use and linked into a family. Redeeming RTn returns a new access token plus RTn+1 and immediately invalidates RTn. Auth0 keeps a small grace window for in-flight network retries. If a previously-used token is presented again, Auth0 concludes the token was leaked and revokes the entire family, forcing a fresh interactive login. This converts the worst property of refresh tokens (long-lived, replayable) into a self-tripping alarm.

6. Code Walkthrough — react-native-auth0, Line by Line

The SDK hides the choreography of §3 behind a few calls. Let's read what each one does.

Install and configure

# React Native
npm install react-native-auth0
cd ios && pod install && cd ..   # iOS native deps

You configure two values from your Auth0 Native application: the tenant domain and the client ID. There is deliberately no client secret — remember, a native app is a public client.

// App.tsx — wrap your tree in the provider
import { Auth0Provider } from 'react-native-auth0';

export default function Root() {
  return (
    <Auth0Provider
      domain="your-tenant.us.auth0.com"
      clientId="YOUR_NATIVE_CLIENT_ID">
      {/* no clientSecret — public client */}
      <App />
    </Auth0Provider>
  );
}

Login — one call that performs the entire §3 flow

import { useAuth0 } from 'react-native-auth0';

function LoginButton() {
  const { authorize, user, error } = useAuth0();

  const onLogin = async () => {
    await authorize({
      // request a refresh token (long-lived session) + standard OIDC claims
      scope: 'openid profile email offline_access',
      audience: 'https://api.trailmate.com',   // so the access token works on YOUR API
    });
    // Under the hood, authorize() did ALL of this for you:
    //   1. generated code_verifier + code_challenge (S256)
    //   2. opened the SYSTEM BROWSER (ASWebAuthSession / Custom Tab)
    //   3. built /authorize URL with state, nonce, PKCE challenge
    //   4. caught the deep-link redirect with the code
    //   5. POSTed code + code_verifier to /oauth/token (no secret)
    //   6. validated id_token signature + nonce, stored tokens securely
  };

  return <Button title="Log in" onPress={onLogin} />;
}
Key

The single most important options here: offline_access asks for a refresh token (without it you get no long-lived session), and audience tells Auth0 to mint an access token for your API rather than an opaque token only usable at /userinfo. Omit audience and your API calls will fail validation.

Reading the session, refreshing, and logging out

function Profile() {
  const { user, getCredentials, clearSession } = useAuth0();

  const callApi = async () => {
    // getCredentials() returns a VALID access token, transparently using the
    // stored refresh token to renew it if it has expired. You never touch the RT.
    const { accessToken } = await getCredentials();
    await fetch('https://api.trailmate.com/trails', {
      headers: { Authorization: `Bearer ${accessToken}` },
    });
  };

  const onLogout = async () => {
    // Opens the browser to /v2/logout to clear the SSO session AND
    // wipes the locally stored tokens from the Keychain/Keystore.
    await clearSession();
  };

  return user ? (<View>{/* ... */}</View>) : null;
}

7. Practical Implementation — Wiring the Deep Link and Storage

The SDK can't register your URL scheme for you — the OS requires it in native config. This is the step beginners most often miss, so do it carefully.

7.1 Auth0 dashboard

  1. Create an Application of type Native (not Regular Web, not SPA).
  2. In Allowed Callback URLs and Allowed Logout URLs, add the platform-specific URLs the SDK expects (shown below).
  3. Enable Refresh Token Rotation and set a reasonable Refresh Token Expiration (absolute + inactivity) under the Application's Grant / Refresh Token settings.

7.2 iOS — register the callback (Info.plist) and (optionally) universal links

<!-- ios/TrailMate/Info.plist : register the custom scheme so the OS routes

7.4 Storing tokens securely + biometric gate (React Native)

The SDK already stores credentials in the Keychain/Keystore. To require biometrics before those tokens are released, enable Local Authentication:

import Auth0 from 'react-native-auth0';

const auth0 = new Auth0({ domain, clientId });

// Require Face ID / Touch ID / device passcode before credentials are returned.
auth0.credentialsManager.requireLocalAuthentication(
  'Unlock TrailMate',        // iOS prompt title
  'Cancel',                  // cancel button
  'Authenticate',            // fallback title (Android)
  'Use device passcode',     // fallback
  /* LAPolicy */ undefined,
);

// Now getCredentials() will trigger the biometric prompt and, on success,
// release a valid (auto-refreshed) access token from secure storage.
const { accessToken } = await auth0.credentialsManager.getCredentials();

8. Production Architecture — Mobile + BFF + API

A real mobile system is not just the app and Auth0. It includes your APIs, and increasingly a Backend-For-Frontend (BFF). Here's how the pieces fit and what each is responsible for.

                                      |  + refresh (rotation)
   +-------------+   deep link   +----+-------+
   |  System     |<------------- |  Native /  |
   |  Browser    |-------------> | React      |   stores tokens in
   +-------------+   /authorize  | Native App |   Keychain/Keystore,
                                 +-----+------+   biometric-gated
                                       | Bearer access_token (JWT)
                                       v
                         +-------------------------+   verifies JWT
                         |   Your Resource API     |   sig (JWKS) + iss
                         |   (validates access tok)|   + aud + exp + scope
                         +-------------------------+

Two valid architectures

Direct (app holds tokens)BFF / Token Handler (server holds tokens)
Where the refresh token livesOn the device (Keychain/Keystore)On your server; device gets only a session cookie/short token
Access token reaches APIApp sends Bearer directlyBFF attaches token server-side

For mobile specifically, the direct model is the standard and is considered safe because native apps have real hardware-backed storage (unlike browsers/SPAs, where the BFF pattern is now preferred). Use a BFF on mobile only when policy demands tokens never touch the device.

Architecture tip

Always set an audience so you receive a JWT access token your API can verify offline against Auth0's JWKS. Your API should validate signature, iss, aud, exp, and required scope/permissions on every request — never trust the app to enforce authorization.

9. Security Analysis — The Threat Model of a Phone in an Attacker's Hand

Reason about mobile security by enumerating the threats and the control that stops each.

ThreatWhat the attacker doesControl that stops it
Authorization-code interceptionMalicious app registers your custom scheme, grabs the code from the redirectPKCE — code is useless without the in-memory verifier; universal/app links make interception even harder
Credential theft / phishingApp or a fake page captures the user's passwordSystem browser (real URL bar, app can't read the page) instead of an embedded webview
Token theft from storageReads tokens off a lost/rooted/jailbroken deviceKeychain/Keystore, hardware-backed, ...ThisDeviceOnly, biometric-gated
Refresh-token replaySteals an RT and reuses it for long-term accessRefresh token rotation + reuse detection → family revocation
Shoulder-surf / unattended unlockUses an already-unlocked phoneBiometric unlock required to release tokens for sensitive actions
Token leakage in transit/logsSniffs traffic or reads logsTLS everywhere; never log tokens; certificate pinning for highest-risk apps
CSRF / mix-up on the redirectInjects a forged authorization responsestate parameter checked on return; nonce checked in the ID token
Danger

Never use the Resource Owner Password (ROPG) grant in a mobile app. It makes your app handle the raw password, defeats SSO/social/MFA-by-redirect, and is deprecated. If you ever see grant_type=password in a mobile codebase, treat it as a finding.

Danger

Never store tokens in AsyncStorage, UserDefaults, SharedPreferences, plist files, or a JS variable that persists to disk. On a rooted/jailbroken device these are plaintext. Tokens belong only in the Keychain/Keystore.

Defense in depth

Layer controls: PKCE + system browser + hardware storage + rotation + biometrics + short access-token lifetime + jailbreak/root detection for high-risk apps. No single control is sufficient; the combination is what survives a determined attacker with physical access.

10. Performance & UX Considerations

On mobile, "performance" is mostly about perceived latency and battery, not raw throughput.

  • Silent refresh beats re-login. A short access-token lifetime (e.g., minutes) keeps blast radius small, but you don't want the user re-authenticating constantly. The refresh token lets the SDK renew the access token silently in the background — the user never sees a browser. Tune access-token TTL to balance security (shorter) vs. refresh frequency (longer).
  • Refresh proactively, not reactively. Renew slightly before expiry (the SDK does this) so an API call never has to wait on a refresh round-trip. Reactive refresh (only after a 401) adds a visible stall.
  • Cache the user profile locally. The decoded ID token already contains name, email, picture; render from it instead of calling /userinfo on every screen.
  • Biometric prompts cost time and goodwill. Don't prompt on every screen. Gate app open and sensitive actions (payments, settings), not routine reads. Over-prompting trains users to tap through.
  • Cold start. On launch, read tokens from secure storage and check expiry locally before any network call — instant "logged-in" UI, refresh in the background.
  • Keep tokens small. Every API call ships the access token; bloated custom claims slow every request and can blow header size limits. Reference large data, don't embed it.
  • Network resilience. The rotation grace window matters on flaky mobile networks — a dropped response shouldn't immediately trip reuse detection. The SDK handles retries; don't roll your own naive retry that double-spends a refresh token.
Tip

The ideal returning-user experience: app opens → Face ID → tokens released from Keychain → access token still valid (or silently refreshed) → home screen, no browser, sub-second. That flow is the gold standard reviewers look for.

11. Common Mistakes

Mistake 1

Using an embedded webview for login. Breaks SSO, enables phishing, and gets apps rejected from the App Store / Play Store. Always use ASWebAuthenticationSession (iOS) / Chrome Custom Tabs (Android) — which the SDK does for you.

Mistake 2

Using the Resource Owner Password grant to "keep it native." Your app should never see the raw password. Use the browser-based Authorization Code + PKCE flow.

Mistake 3

Storing tokens in AsyncStorage / plaintext. Use the Keychain/Keystore. The SDK's CredentialsManager already does; don't second-guess it by copying tokens elsewhere.

Mistake 4

Trying to embed a client secret in the app. Native apps are public clients — there is no secret to use. If a tutorial tells you to ship a secret, it's wrong for mobile.

Mistake 5

Forgetting offline_access, then wondering why there's no refresh token and the user is logged out after the access token expires.

Mistake 6

Forgetting audience, then receiving an opaque token that your own API can't validate as a JWT.

Mistake 7

Not registering the URL scheme / callback URL. Login works in the browser but never returns to the app. Check Info.plist / manifest placeholders and the dashboard's Allowed Callback URLs.

Mistake 8

Rolling your own refresh logic that races and double-spends a rotated token, tripping reuse detection and logging users out. Let the SDK serialize refreshes.

Mistake 9

Treating logout as "just delete the local token." That leaves the SSO session in the system browser, so the next login skips credentials. Call clearSession() to clear both.

12. Best Practices

  • Authorization Code + PKCE, always. It's the only correct grant for a public mobile client. Let the SDK generate verifier/challenge with S256.
  • System browser only. Never embed a webview for login. This is also an App Store / Play Store compliance requirement for third-party identity.
  • Request offline_access + an audience so you get a refresh token and a verifiable JWT access token for your API.
  • Store every token in the Keychain/Keystore, bound to ThisDeviceOnly, and gate release behind biometrics for app-open and sensitive actions.
  • Enable refresh token rotation + reuse detection in the dashboard, with sensible absolute and inactivity lifetimes.
  • Prefer universal links / app links over bare custom schemes in production for the strongest redirect binding.
  • Keep access tokens short-lived and refresh proactively in the background; cache profile from the ID token to avoid extra calls.
  • Validate on the API (signature/iss/aud/exp/scope) — never trust the client to enforce authorization.
  • Log out via clearSession() to clear both local tokens and the browser SSO session; revoke the refresh token server-side where appropriate.
  • For high-risk apps add certificate pinning and jailbreak/root detection as defense in depth.

13. Interview Questions (with Model Answers)

Q1. Why can't a mobile app use a client secret, and what replaces it?

Model answer: A native app is a public client — its binary ships to every user, so any embedded secret can be extracted by decompiling. Therefore it can't prove its identity to the token endpoint with a secret. PKCE replaces the static secret with a fresh per-login proof: the app generates a random code_verifier, sends only SHA-256(verifier) (the challenge) in the front-channel /authorize request, and reveals the verifier when redeeming the code. The server hashes the verifier and matches it to the challenge, proving the redeemer started the flow — no permanent secret needed.

Q2. Why must you use the system browser instead of an embedded webview?

Model answer: Three reasons. Security: an embedded webview has no address bar, so users can't tell a real IdP page from a phish, and the host app can read the page (including the password). SSO: the system browser shares a session cookie across apps, so the user gets single sign-on; a webview is isolated and breaks it. Compliance: Apple and Google reject apps that put third-party login in embedded webviews. The correct primitives are ASWebAuthenticationSession on iOS and Chrome Custom Tabs on Android.

Q3. Walk me through how the redirect gets back into the app.

Model answer: The app registers a redirect URI — either a custom scheme (com.app://callback) or a verified universal/app link (https://app.com/callback). After authentication the browser issues a 302 to that URI. The OS matches the scheme/host and dispatches the URL into the registered app via a platform callback or Intent. For universal/app links the OS first verified domain ownership through an association file (apple-app-site-association / assetlinks.json), so only your app can receive it — that's why they're preferred over custom schemes.

Q4. Where do you store tokens on mobile, and why not AsyncStorage?

Model answer: In the iOS Keychain and Android Keystore, which are hardware-backed (Secure Enclave / TEE / StrongBox), can be bound to the device, and gated behind biometrics. AsyncStorage / UserDefaults / SharedPreferences are effectively plaintext and are readable on a rooted or jailbroken device, so they must never hold tokens — especially the long-lived refresh token.

Q5. Explain refresh token rotation and reuse detection.

Model answer: Each refresh token is single-use; redeeming it returns a new access token and a new refresh token, invalidating the old one. Tokens are linked in a family. If a previously-used (already-rotated) refresh token is presented again, Auth0 concludes it leaked and revokes the entire family, forcing a fresh interactive login. This turns a long-lived, replayable credential into a self-tripping alarm — a stolen-and-replayed token gets both the attacker and the victim logged out, surfacing the breach.

Q6. How does biometric unlock relate to token security — does Face ID protect the token?

Model answer: Biometrics don't authenticate to Auth0; they gate local release of tokens from secure storage. The Keychain/Keystore item is bound to a biometric access-control policy, so the OS only decrypts and returns the token after a successful Face ID/Touch ID (or device credential) check. It protects against an attacker with physical access to an unlocked-but-not-biometrically-verified device, and adds a presence check before sensitive actions.

Q7. Direct token storage on device vs. a BFF — when would you choose each on mobile?

Model answer: Direct is the standard for mobile because native apps have genuine hardware-backed secure storage plus rotation, so holding tokens on the device is acceptable. A BFF (token-handler) keeps the refresh token entirely off the device, giving the app only a session reference; you'd choose it for the highest-risk apps or strict policies that forbid tokens on the client, at the cost of running an extra service. (Note: for SPAs/browser apps the BFF pattern is now generally preferred precisely because browsers lack good secure storage.)

Q8. A user reports login opens the browser, they sign in, but the app never comes back. Diagnose.

Model answer: The redirect isn't being routed back. Check (1) the URL scheme is registered in Info.plist / Android manifest placeholders, (2) the exact callback URL is in the Auth0 Application's Allowed Callback URLs, and (3) for universal/app links the association file is reachable and correct. Mismatches between the configured scheme/callback and what the SDK sends are the usual cause.

14. Certification Tips

Exam focus

Mobile questions cluster tightly around grant choice, browser choice, and storage. Lock these in:

  • Native app = public client = Authorization Code + PKCE. If an answer mentions a client secret for a native app, it's wrong. If it mentions Implicit or ROPG for mobile, it's wrong.
  • PKCE uses S256 (SHA-256), with code_challenge_method=S256; "plain" exists but isn't recommended.
  • System browser, not webview — know the names: ASWebAuthenticationSession (iOS), SFSafariViewController (older), Chrome Custom Tabs (Android). Webview = wrong answer.
  • Application type in the dashboard must be "Native."
  • offline_access scope is required to receive a refresh token.
  • Refresh token rotation is the recommended setting for public clients; know that reuse detection revokes the whole family.
  • Secure storage: Keychain (iOS), Keystore (Android). Recognize these as the correct answer for "where to store tokens."
  • Custom scheme vs. universal/app links: know that links require a domain-association file and provide stronger binding.
  • The SDKs to recognize: react-native-auth0, Auth0.swift, Auth0.Android.

15. Hands-On Exercises

  1. Create a Native app + run login. Spin up a fresh React Native app, add react-native-auth0, create a Native Auth0 application, wire the callback URLs, and complete one login. Confirm the system browser (not a webview) opens.
  2. Compute PKCE by hand. Generate a random 64-char verifier, compute BASE64URL(SHA-256(verifier)) with a CLI (openssl), and confirm you get a valid 43-char challenge. This makes §5.1 concrete.
  3. Inspect the /authorize URL. Use a proxy or device logs to capture the outbound /authorize request and verify it contains code_challenge, code_challenge_method=S256, state, nonce, and no secret.
  4. Break and fix the redirect. Temporarily change the URL scheme to something wrong, observe the "browser opens but app never returns" symptom, then fix it — so you'll recognize the failure instantly in the future.
  5. Add a biometric gate. Enable requireLocalAuthentication and confirm getCredentials() triggers Face ID / fingerprint before returning a token.
  6. Trip reuse detection (lab only). With rotation on, manually replay a previously-used refresh token against /oauth/token and observe the family revocation and forced re-login.

17. Mini Project — "QuickAuth" React Native App

Build a small but correct app that demonstrates the whole chapter: login via system browser with PKCE, silent refresh, biometric-gated token release, an authenticated API call, and proper logout.

The core screen

// QuickAuth.tsx
import React from 'react';
import { View, Text, Button, Alert } from 'react-native';
import { useAuth0, Auth0Provider } from 'react-native-auth0';

const API = 'https://api.quickauth.example.com';

function Home() {
  const { authorize, clearSession, getCredentials, user, isLoading } = useAuth0();

  if (isLoading) return <Text>Loading…</Text>;

  const login = () =>
    authorize({
      scope: 'openid profile email offline_access',  // refresh token
      audience: API,                                  // JWT for our API
    }).catch(e => Alert.alert('Login failed', String(e)));

  const callApi = async () => {
    try {
      // Triggers biometric prompt (if configured), auto-refreshes if needed.
      const { accessToken } = await getCredentials();
      const res = await fetch(`${API}/me`, {
        headers: { Authorization: `Bearer ${accessToken}` },
      });
      Alert.alert('API says', JSON.stringify(await res.json()));
    } catch (e) {
      Alert.alert('Call failed', String(e));
    }
  };

  return (
    <View style={{ padding: 24, gap: 12 }}>
      {user ? (
        <>
          <Text>Hello, {user.name}</Text>
          <Button title="Call protected API" onPress={callApi} />
          <Button title="Log out" onPress={() => clearSession()} />
        </>
      ) : (
        <Button title="Log in" onPress={login} />
      )}
    </View>
  );
}

export default function App() {
  return (
    <Auth0Provider domain="your-tenant.us.auth0.com" clientId="YOUR_NATIVE_CLIENT_ID">
      <Home />
    </Auth0Provider>
  );
}

Minimal API that validates the access token (Node/Express)

import express from 'express';
import { auth } from 'express-oauth2-jwt-bearer';   // validates JWT via JWKS

const app = express();
// Verifies signature (JWKS), iss, aud, exp on EVERY request.
app.use(auth({
  audience: 'https://api.quickauth.example.com',
  issuerBaseURL: 'https://your-tenant.us.auth0.com/',
}));

app.get('/me', (req, res) => {
  // req.auth.payload holds verified claims — trust these, not the client.
  res.json({ sub: req.auth.payload.sub, scope: req.auth.payload.scope });
});

app.listen(3000);

Acceptance checklist

  • Login opens the system browser (verify the URL bar appears), not a webview.
  • A refresh token is issued (request includes offline_access) and stored in secure storage.
  • getCredentials() triggers a biometric prompt and returns a valid token after expiry without a visible re-login.
  • The API rejects a request with no/expired/invalid token and accepts a valid one.
  • clearSession() logs out of both the app and the browser SSO session.
Production note

This mini project uses defaults for clarity. Before shipping: enable refresh token rotation, set short access-token TTLs, configure biometric requirement on the CredentialsManager, prefer universal/app links, and validate required scopes/permissions per endpoint on the API.

20. Key Takeaways

Key

A native app is a public client with no secret. Everything else follows: use Authorization Code + PKCE (S256), never a client secret, never the Implicit or password grants.

Key

Open the system browser, never an embedded webview. It prevents phishing, preserves SSO, and is required by App Store / Play Store policy. The SDK uses ASWebAuthenticationSession / Custom Tabs for you.

Key

The redirect comes home via a deep link. Register the URL scheme (and prefer verified universal/app links), and add the callback URL in the dashboard — or login opens but never returns.

Key

Tokens live only in the Keychain/Keystore, hardware-backed and biometric-gated. AsyncStorage and friends are plaintext on a rooted/jailbroken device and must never hold tokens.

Key

Refresh token rotation turns a long-lived credential into a tripwire. Single-use, family-linked, with reuse detection revoking the whole family — combined with short access-token TTL and silent refresh for a seamless, safe session.
