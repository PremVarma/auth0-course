Chapter 26 — Project 10 — Capstone: Cinema Booking Platform

This is the chapter where everything you have learned stops being a list of features and becomes a system. We are going to design and build CineVerse, a real cinema booking platform: customers browse showtimes and book seats from a Next.js app, staff scan tickets at the door from a mobile-friendly React app, admins manage screens and pricing from a back-office, and behind the gateway a polyglot fleet of microservices — Spring Boot, Node, and FastAPI — quietly talk to one another over HTTP and Kafka. The hard part is never "show a login button." The hard part is making one identity flow correctly across three front-ends, an API gateway, six services, a Kafka bus, and a Redis cache — with the right person allowed to do the right thing, every token verified, every seat locked exactly once, and every event carrying proof of who caused it. Auth0 sits at the center of all of it. By the end you will be able to draw this architecture on a whiteboard in an interview and defend every arrow.

1. Theory — First Principles of a Multi-App, Multi-Service Identity System

Up to now you have integrated Auth0 into single applications. A capstone is different in kind, not just degree. The moment you have more than one front-end and more than one back-end service, three new questions appear that a single app never forces you to answer:

  1. Where does identity live? Each app cannot have its own user database — then "Jane" is three different people. Identity must be centralized in one authority (Auth0) and referenced everywhere by a stable identifier (the sub claim).
  2. How does proof of identity travel? A user authenticates once in the browser, but the booking service needs to know who they are, and so does the payment service that booking calls. Proof must propagate — as an access token on the wire, and as identity metadata on async events.
  3. Who is allowed to do what, and who decides? A customer may book a seat; only staff may mark a ticket "used"; only an admin may change prices. The decision must be expressible (RBAC permissions), enforceable at every hop (the gateway and each service), and impossible to forge (signed tokens).

The foundational principle is the token boundary. There are exactly two kinds of token in OAuth 2.0 / OIDC, and confusing them is the most common architecture bug in junior designs:

TokenFormatAudiencePurposeWho validates it
ID tokenJWT (OIDC)the client app"who is the user" — proves a login happenedthe front-end / SDK
Access tokenJWT (Auth0 default)an API (the aud claim)"this bearer may call this API" — authorizes a requestevery back-end service

Rule, memorize it: ID tokens never leave the client; access tokens never decide UI. A front-end uses the ID token to render "Hi, Jane" and the access token to call the API. A back-end ignores ID tokens entirely and validates only access tokens. Every service in CineVerse is an OAuth 2.0 resource server: it does nothing but verify the signature, issuer, audience, expiry, and scopes/permissions of the access token it receives.

The two flavors of trust

There are two distinct trust relationships in the system, and they use two different OAuth grants:

  • User-to-service (delegated): a human logs in via the Authorization Code flow + PKCE. The token says "acting on behalf of user auth0|abc."
  • Service-to-service (autonomous): the booking service calls the payment service with no human present. It uses the Client Credentials grant (M2M). The token says "I am the booking service" — there is no user.
Key

A capstone is the discipline of keeping one identity (Auth0) authoritative while it flows through many trust boundaries. Every boundary either re-validates the token it received or mints a new token appropriate to the next hop. There is no "trusted internal network" — we assume zero trust, so even service-to-service calls carry and verify tokens.

2. Story-Based Explanation — A Friday Night at CineVerse

It is 7:42 p.m. on a Friday. Maya opens the CineVerse customer app on her phone to book three seats for the 8:15 showing of a blockbuster. She is one of forty people doing the exact same thing this minute. Follow her identity through the system and you will understand the whole architecture.

  1. Maya taps Log in. The Next.js app redirects her to Auth0's Universal Login. She authenticates (she has an account; if not, she'd sign up here). Auth0 redirects back with an authorization code; the app exchanges it for an ID token (to greet her) and an access token scoped to the CineVerse API.
  2. She picks seats H4, H5, H6 and taps Hold. The app sends the access token to the API gateway. The gateway checks the token is valid and forwards to the Booking Service (Spring Boot).
  3. Booking calls Redis: SET seat:screen3:H4 maya-lock NX EX 120 — "lock this seat for Maya, but only if nobody else holds it, and auto-expire in 120 seconds." Two of her three seats lock; H6 was grabbed half a second earlier by someone else. She sees H6 turn red instantly. This is the seat-lock race, and Redis settles it atomically.
  4. Maya re-picks H7 and pays. Booking, with no user in the loop now, fetches an M2M token and calls the Payment Service (Node). It also publishes a Kafka event booking.confirmed stamped with Maya's sub, so downstream services know whose booking it was.
  5. The Notification Service (FastAPI) consumes that event, reads the sub, looks up her email, and sends her tickets — each a QR code containing a signed ticket ID.
  6. At 8:09 Maya reaches the door. Raj, an usher, logs into the staff app (he has the staff role) and scans her QR. The staff app calls Booking's POST /tickets/{id}/redeem. Booking checks Raj's token carries redeem:tickets, flips the ticket to used, and publishes ticket.redeemed. If Raj's friend tries the same QR, it's already used — denied.
  7. Meanwhile the cinema manager, Dana (the admin role), is in the back-office adjusting Saturday's pricing. Her token carries write:pricing, which Maya's and Raj's tokens do not. Same Auth0 tenant, same login UI — three completely different sets of powers.

One identity provider. One Maya. Six services. Three apps. Every action gated by a token, every token signed by Auth0, every event traceable to a human or a service. That is the whole game.

Note

Notice the two seams where things go wrong in real systems: the seat race (concurrency, solved by Redis) and the identity-on-events problem (async, solved by stamping the sub into the Kafka message). We will spend real time on both.

4. Real-World Analogy — The Cinema as a Building

Forget code for a moment and picture a physical multiplex, because the architecture maps onto it one-to-one.

  • Auth0 is the box office that issues wristbands. You show ID once at one window. They give you a tamper-evident wristband (the token) printed with what you're entitled to: a customer's plain band, a staff member's "all-doors" band, a manager's master band. Nobody inside the building re-checks your ID — they check your wristband, because forging it is infeasible (it's cryptographically signed).
  • The API gateway is the turnstile at the entrance. It does a fast, coarse check: is this a real wristband, not expired, issued by our box office? If yes, you're in the building. It does not decide which specific screen you may enter.
  • Each microservice is a specific door (Screen 3, the projection booth, the manager's office). The door checks not just that your wristband is real, but that it grants this door specifically (the fine-grained permission).
  • The Redis seat-lock is the velvet rope a host throws over a seat the instant you say "I'll take it" — held for two minutes, then released if you don't show your ticket.
  • Kafka is the staff radio network. When a booking confirms, a message goes out over the radio — "row H, screen 3, booked by guest #4471" — and every relevant department (concessions, ushers, the email desk) hears it. The radio call always says who it's about, so departments don't have to ask.
  • M2M tokens are the internal staff keycards. When the booking desk phones the payment desk, the payment desk doesn't ask "which customer?" — it verifies the caller is the booking desk via its keycard.

The whole reason this building works at scale is that identity is established once at the door and trusted everywhere via an unforgeable token. That is exactly what Auth0 gives a distributed system.

5. Internal Working — How a Request Is Actually Authorized

Let's trace, mechanically, what happens when a service receives Authorization: Bearer eyJ.... There is no magic; it is five deterministic checks.

5.1 Anatomy of the access token

// Decoded payload of a CineVerse access token (RS256-signed JWT)
{
  "iss": "https://cineverse.eu.auth0.com/",   // issuer — must be OUR tenant
  "sub": "auth0|6612ab...",                     // the stable user id
  "aud": ["https://api.cineverse.com"],         // audience — must be OUR api
  "iat": 1718800000,
  "exp": 1718803600,                            // expiry — must be in the future
  "azp": "Cust0merAppClientId",                 // authorized party (the client)
  "scope": "openid profile book:seats",
  "permissions": ["book:seats", "read:bookings"], // RBAC permissions (Auth0)
  "https://cineverse.com/roles": ["customer"]   // custom claim added by an Action
}

5.2 The five validation steps every service performs

   incoming JWT
        │
        ▼
   ┌──────────────────────────────────────────────────────────┐
   │ 1. SIGNATURE  fetch JWKS (cached), pick key by `kid`,     │
   │               verify RS256 signature → not forged         │
   │ 2. ISSUER     iss == https://cineverse.eu.auth0.com/      │
   │ 3. AUDIENCE   aud contains https://api.cineverse.com      │
   │ 4. EXPIRY     exp > now  (and nbf <= now if present)       │
   │ 5. AUTHZ      required permission ∈ token.permissions      │
   └──────────────────────────────────────────────────────────┘
        │ all pass                       │ any fail
        ▼                                ▼
   handle request (sub is trusted)   401 (1-4) / 403 (5)

Steps 1–4 are authentication (is this a genuine, current token for us?). Step 5 is authorization (may this specific token do this specific thing?). A failure in 1–4 is a 401 Unauthorized; a failure in 5 is a 403 Forbidden. Getting that distinction right is a classic interview tell.

5.3 Why JWKS instead of a shared secret?

Auth0 signs tokens with an RSA private key it never shares. Services verify with the matching public key, published at https://your-tenant/.well-known/jwks.json. This is asymmetric (RS256), and it's the right choice for a distributed system: a leaked verification key cannot mint tokens, and key rotation is automatic (services pick the new key by its kid header). Never use HS256 (shared secret) across multiple services — one compromised service can then forge tokens for all of them.

Warn

Always pin both iss and aud. A token validly signed by your tenant but minted for a different API (different aud) must be rejected — otherwise a token meant for your low-privilege analytics API could be replayed against your high-privilege booking API. This is the "confused deputy" / audience-confusion attack.

// app/api/bookings/route.ts — server route that calls the gateway WITH the token
import { getAccessToken } from '@auth0/nextjs-auth0';

export async function POST(req: Request) {
  // getAccessToken returns the API access token (aud = cineverse api),
  // refreshing it via the refresh token if it has expired.
  const { accessToken } = await getAccessToken({
    authorizationParams: { audience: process.env.AUTH0_AUDIENCE },
  });

  const body = await req.json();
  const res = await fetch('https://gw.cineverse.com/bookings', {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${accessToken}`,   // delegated user token
      'Content-Type': 'application/json',
    },
    body: JSON.stringify(body),
  });
  return new Response(await res.text(), { status: res.status });
}
Tip

The access token is obtained and attached on the server side of Next.js, never exposed to the browser JavaScript. The browser holds only an encrypted, http-only session cookie. This is the single most important front-end security decision: tokens never touch localStorage.

6.2 Booking Service — Spring Boot resource server

# application.yml — Spring Security validates the JWT for us
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://cineverse.eu.auth0.com/
          audiences: https://api.cineverse.com    # enforce aud (Spring Boot 3.4+)
// SecurityConfig.java — map Auth0 "permissions" claim to Spring authorities
@Configuration
@EnableMethodSecurity   // turns on @PreAuthorize
public class SecurityConfig {

  @Bean
  SecurityFilterChain api(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(j ->
            j.jwtAuthenticationConverter(converter())));
    return http.build();
  }

  // Auth0 puts RBAC in a "permissions" array, not "scope". Map it.
  private JwtAuthenticationConverter converter() {
    var perms = new JwtGrantedAuthoritiesConverter();
    perms.setAuthoritiesClaimName("permissions");
    perms.setAuthorityPrefix("");                 // use raw "book:seats"
    var conv = new JwtAuthenticationConverter();
    conv.setJwtGrantedAuthoritiesConverter(perms);
    return conv;
  }
}
// BookingController.java — fine-grained authz + identity from the token
@RestController
@RequestMapping("/bookings")
public class BookingController {

  private final BookingService bookings;
  BookingController(BookingService b) { this.bookings = b; }

  @PostMapping
  @PreAuthorize("hasAuthority('book:seats')")     // step 5: RBAC
  public ResponseEntity<BookingDto> create(
        @AuthenticationPrincipal Jwt jwt,          // the verified token
        @RequestBody BookSeatsRequest req) {

    String userSub = jwt.getSubject();             // trusted: "auth0|6612ab"
    BookingDto dto = bookings.book(userSub, req);  // sub is the owner
    return ResponseEntity.status(201).body(dto);
  }

  @PostMapping("/tickets/{id}/redeem")
  @PreAuthorize("hasAuthority('redeem:tickets')")  // ONLY staff have this
  public TicketDto redeem(@PathVariable String id,
                          @AuthenticationPrincipal Jwt jwt) {
    return bookings.redeem(id, jwt.getSubject());
  }
}

6.3 The Redis seat lock (atomic, expiring)

// SeatLockService.java — one atomic SET NX EX per seat
@Service
public class SeatLockService {
  private final StringRedisTemplate redis;
  SeatLockService(StringRedisTemplate r) { this.redis = r; }

  /** returns true only if WE won the lock for this seat */
  public boolean tryLock(String screen, String seat, String userSub) {
    String key = "seat:" + screen + ":" + seat;
    Boolean won = redis.opsForValue()
        .setIfAbsent(key, userSub, Duration.ofSeconds(120)); // SET k v NX EX 120
    return Boolean.TRUE.equals(won);
  }

  /** release only if WE still own it — Lua makes check+del atomic */
  private static final String UNLOCK =
    "if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end";

  public void release(String screen, String seat, String userSub) {
    redis.execute(new DefaultRedisScript<>(UNLOCK, Long.class),
        List.of("seat:" + screen + ":" + seat), userSub);
  }
}

6.4 M2M call — Booking → Payment (Client Credentials)

// PaymentClient.java — fetch an M2M token, cache it, call Payment
@Component
public class PaymentClient {
  private final WebClient http = WebClient.create();
  private volatile String cachedToken; private volatile Instant expiry = Instant.MIN;

  private synchronized String token() {
    if (Instant.now().isBefore(expiry.minusSeconds(60))) return cachedToken; // reuse
    var resp = http.post().uri("https://cineverse.eu.auth0.com/oauth/token")
       .bodyValue(Map.of(
          "grant_type", "client_credentials",
          "client_id", System.getenv("M2M_CLIENT_ID"),
          "client_secret", System.getenv("M2M_CLIENT_SECRET"),
          "audience", "https://payments.cineverse.com"))    // Payment's audience
       .retrieve().bodyToMono(TokenResp.class).block();
    cachedToken = resp.access_token();
    expiry = Instant.now().plusSeconds(resp.expires_in());
    return cachedToken;
  }

  public ChargeResult charge(String bookingId, long amountCents) {
    return http.post().uri("https://payments.cineverse.com/charge")
       .header("Authorization", "Bearer " + token())          // M2M, no user
       .bodyValue(Map.of("bookingId", bookingId, "amount", amountCents))
       .retrieve().bodyToMono(ChargeResult.class).block();
  }
}

6.7 The Action that injects roles into the token

// Auth0 Action (Login flow) — add roles + a stable custom claim
exports.onExecutePostLogin = async (event, api) => {
  const ns = 'https://cineverse.com/';
  const roles = event.authorization?.roles || [];
  api.accessToken.setCustomClaim(`${ns}roles`, roles);
  api.idToken.setCustomClaim(`${ns}roles`, roles);
  // tighten: never let a customer self-assign staff perms
  if (roles.includes('admin')) {
    api.accessToken.setCustomClaim(`${ns}tenant_admin`, true);
  }
};

7. Practical Implementation — Wiring the Tenant

Here is the exact Auth0 object model you create in the dashboard (or via the Management API / Terraform) before any code runs. Doing this in the right order saves hours of "invalid audience" debugging.

  1. Create the API (Applications → APIs). Identifier (audience): https://api.cineverse.com. Signing: RS256. Enable RBAC and Add Permissions in the Access Token.
  2. Define permissions on that API: book:seats, read:bookings, cancel:bookings, redeem:tickets, read:schedule, write:pricing, manage:screens.
  3. Create roles (User Management → Roles) and attach permissions:
    • customer → book:seats, read:bookings, cancel:bookings
    • staff → redeem:tickets, read:schedule
    • admin → all of the above + write:pricing, manage:screens
  4. Create three SPA/Regular Web Apps (customer Next.js = Regular Web App; staff + admin = SPA or Regular). Set callback/logout URLs. Authorization Code + PKCE.
  5. Create a second API for payments: https://payments.cineverse.com with permission charge:create and a refund permission.
  6. Create M2M applications: a "Booking→Payment" machine app, authorized for the Payments API with charge:create. Repeat for any other service-to-service edge.
  7. Add the post-login Action (section 6.7) and deploy it to the Login flow.
  8. (Optional, B2B) If each cinema chain is a separate tenant-within-tenant, enable Organizations and require organization on login so a token is scoped to one chain.

8. Production Architecture — Hardening for Real Traffic

8.1 Refresh-token strategy

Customers should not be bounced to login mid-booking. Use refresh token rotation with automatic reuse detection: every refresh issues a new refresh token and invalidates the old; if an old one is replayed, Auth0 revokes the whole family (a stolen token is detected and killed). For the customer web app, refresh tokens live encrypted server-side in the session; for native/PWA staff scanners, store them in secure OS storage, never in JS-readable storage.

8.2 Where each check lives

   GATEWAY          → coarse: valid token? right issuer/audience? (401)
   SERVICE          → fine:   does token carry THIS permission?   (403)
   DOMAIN LOGIC     → ownership: is sub the OWNER of this booking? (403)

The gateway should not be the only place you check — it's a defense-in-depth layer, not the authority. Each service re-validates the token (JWKS is cached locally) and enforces its own permissions, because a misconfigured gateway must not become a single point of bypass. The third layer is the one juniors forget: even with read:bookings, Jane must not read Bob's booking. That is an object-level check (the dreaded OWASP API #1, BOLA) that only your domain code can do, because only it knows who owns the row.

8.3 Identity propagation on Kafka

Async events lose the HTTP request context, so identity must be put into the message. Two patterns:

  • Claims in the payload (simplest): include actor: { sub, roles } in the event body. Good enough when producers are trusted services inside your boundary.
  • Signed token in a header (strongest): attach the short-lived access token (or a dedicated event JWT) as a Kafka header so consumers can verify it, not just trust it. Use when the bus crosses trust boundaries.

8.4 JWKS caching and resilience

Cache the JWKS in every service (TTL ~10 min) and refresh on an unknown kid. If Auth0 is briefly unreachable, services keep validating with the cached keys — login stops, but in-flight requests with valid tokens still work. Set sensible token lifetimes: short access tokens (e.g. 1 hour) limit blast radius; longer-lived refresh tokens keep UX smooth.

10. Performance Considerations

  • Validate tokens locally, not over the network. RS256 verification against a cached JWKS is microseconds. Never call Auth0 per request to "check" a token — that adds latency and a hard dependency. JWTs are self-contained on purpose.
  • Cache the M2M token. Client-credentials tokens are valid for hours. Fetching one per outbound call would hammer the token endpoint and hit rate limits. Cache it and refresh ~60s before expiry (section 6.4).
  • Keep tokens lean. Every claim adds bytes to every request header. Put only what services need (permissions, a roles claim). Don't dump the whole user profile into the token.
  • Redis for hot, ephemeral state. Seat locks and session lookups are sub-millisecond. Use short TTLs so abandoned holds free themselves with no cleanup job.
  • Kafka decouples slow work. Sending a ticket email takes seconds; doing it inline would block the booking response. Publishing an event returns in ~1ms and lets Notification scale independently on consumer lag.
  • Connection pooling to Auth0. Reuse HTTP clients for the token endpoint and JWKS; cold TLS handshakes dominate otherwise.
  • Right-size token lifetime. Too short = constant refresh round-trips; too long = larger theft window. One hour for access tokens is a sane default.
Note

The single biggest perf mistake teams make with Auth0 is treating token validation like a remote call. It is not — that's the whole point of a signed, stateless JWT. The only network calls should be: login (once), refresh (occasionally), JWKS fetch (rarely, cached), and M2M token fetch (hourly, cached).

11. Common Mistakes

  • Using the ID token to call APIs. The ID token's aud is the client, not your API; services will reject it. Always request and send the access token (set audience at login).
  • Forgetting to enable RBAC / "add permissions to access token" on the API — then the permissions claim is missing and every @PreAuthorize denies.
  • Trusting roles sent by the client. A front-end can lie. Roles must come from the signed token (injected by an Action), never from a request body or header.
  • Skipping the ownership check (BOLA). "Authenticated" is not "authorized to see this object."
  • No idempotency on payment. A retried request double-charges. Pass an idempotency key.
  • Releasing a Redis lock without ownership check. A naive DEL can delete a lock another user just acquired; use the Lua compare-and-delete (section 6.3).
  • HS256 across services. Shared secret = any service can forge tokens. Use RS256.
  • Tokens in localStorage. One XSS and the attacker has the user's session.
  • Dropping identity at the Kafka boundary. Consumers can't answer "who did this?" because the producer didn't stamp the sub.
  • One M2M app for everything. Leak it once and every service edge is compromised. One app per edge.

12. Best Practices

  • One identity authority. Auth0 owns identity; services own data. The only user key services store is the sub.
  • Zero trust internally. Every hop validates a token, including service-to-service. There is no "safe" internal network.
  • Least privilege per token. Customers get customer perms, staff get staff perms, each M2M app gets exactly one API's scopes.
  • Defense in depth: coarse check at the gateway, fine check at the service, ownership check in domain logic.
  • RS256 + JWKS + caching everywhere; pin iss and aud.
  • Refresh-token rotation with reuse detection.
  • Stamp identity onto events so the async world stays traceable and auditable.
  • Idempotency keys on every mutating, money-touching, or non-replayable operation.
  • Externalize config (issuer, audience, secrets) — never hard-code; manage secrets in a vault.
  • Infrastructure as code: define APIs, roles, permissions, and M2M apps in Terraform/Deploy-CLI so the tenant is reproducible and reviewable.

13. Interview Questions (with model answers)

Q1. Walk me through how a single user identity flows from the browser to a downstream payment service.

Model answer: The browser does Authorization Code + PKCE with Auth0 and receives an ID token (for UI) and an access token whose aud is our API. The app sends only the access token to the gateway. The gateway and the Booking service each verify it (signature via JWKS, iss, aud, exp, and the required permission). Booking then needs to call Payment with no user present, so it uses the Client Credentials grant to get an M2M token whose aud is the Payments API, and calls Payment with that. The user's identity (sub) is carried forward in the booking record and stamped onto the Kafka event, so even async consumers know who acted. Two grant types, two audiences, one identity authority.

Q2. Why not validate tokens by calling Auth0 on every request?

Model answer: JWTs are self-contained and signed; you verify them locally with the cached public key in microseconds. Calling Auth0 per request adds latency, creates a hard runtime dependency on the IdP, and will hit rate limits. The only remote calls should be login, occasional refresh, the rarely-refreshed JWKS fetch, and the hourly M2M token fetch.

Q3. A customer's token is valid and has read:bookings. They request another customer's booking. What happens?

Model answer: If you only checked the permission, you'd leak it — that's BOLA (OWASP API #1). The permission grants the ability to read bookings in general; it does not grant access to a specific object. Domain logic must compare the row's owner to jwt.sub and return 403/404 if they differ. Authentication, then permission, then ownership.

Q4. How do you prevent two users from booking the same seat under load?

Model answer: Two layers. First, an atomic Redis SET seat NX EX 120 as a short hold — only one caller wins, and abandoned holds expire on their own. Second, a database unique constraint on (showing_id, seat) as the durable source of truth, so even if Redis fails, the DB rejects the second confirm. The lock is for UX (instant feedback); the constraint is for correctness.

Q5. Why RS256 over HS256 in a microservices system?

Model answer: HS256 is symmetric — every verifier needs the signing secret, so any compromised service can forge tokens for all. RS256 is asymmetric: Auth0 signs with a private key it never shares; services verify with the public key from JWKS. A leaked verification key can't mint tokens, and rotation is automatic via the kid header.

Q6. How does identity survive an async Kafka boundary?

Model answer: HTTP request context is gone, so the producer must put identity into the message — minimally an actor.sub field, or, across trust boundaries, a signed token in a Kafka header that consumers verify. Otherwise consumers can't audit or authorize, and "who did this?" becomes unanswerable.

Q7. Where would you enforce that only staff can redeem tickets?

Model answer: The redeem:tickets permission belongs only to the staff and admin roles in Auth0, so it never appears in a customer's token. The Booking endpoint declares @PreAuthorize("hasAuthority('redeem:tickets')"). Even if a customer crafts a request, their token lacks the permission and gets a 403. The gateway can pre-filter too, but the service is the authority.

14. Certification Tips

  • Know ID vs access token cold. The exam loves "which token calls an API?" — always the access token; the ID token authenticates the user to the client.
  • Client Credentials = no user. Expect questions on which grant a backend job uses (Client Credentials) vs an interactive web app (Authorization Code + PKCE).
  • RBAC switches: remember you must enable RBAC and "Add Permissions in the Access Token" on the API for the permissions claim to appear.
  • Actions vs Rules/Hooks: Actions are the current extensibility model; know that custom claims must be namespaced (a URL prefix) or Auth0 strips them.
  • Refresh token rotation + reuse detection is the recommended SPA/native pattern — be ready to name it.
  • Audience is mandatory to receive a JWT access token for your API; without it you get an opaque token. Common exam trap.
  • Organizations are the B2B construct for isolating multiple business customers in one tenant — recognize the use case.
  • JWKS / RS256 is the default and recommended signing algorithm; know the public/private split.

15. Hands-On Exercises

17. Mini Project — The Walk-Up Kiosk

Build a fourth surface: a self-service kiosk in the lobby that lets a guest buy a ticket without a personal login, while still being fully governed.

  • Device identity: the kiosk is a machine, so it authenticates with its own M2M (or Device-Authorization) client. It is not a person; its token carries a kiosk scope, not customer permissions.
  • Guest booking: the kiosk creates an anonymous booking — the sub on the event is the kiosk client, with a guest reference (phone/email entered at the screen) in the payload, not in identity.
  • Payment: the kiosk calls Booking, which calls Payment over the existing M2M edge — no new privileged path.
  • Ticket delivery: Notification consumes booking.confirmed as usual; if there's no sub-linked email, it prints the QR at the kiosk instead.
  • Constraint: a kiosk token must not be able to call /refund, /pricing, or read other people's bookings. Prove it with the same break-it-on-purpose tests from section 15.

The lesson: a non-human surface is still an identity in Auth0 — it just gets a machine credential and a tightly scoped token, slotting into the exact same validation pipeline as every human.

20. Key Takeaways

Key

One identity authority, many trust boundaries. Auth0 is the single source of identity; every front-end and service references the same user by sub and trusts only Auth0-signed tokens. That is what turns ten apps into one system.

Key

Two tokens, two grants, two audiences. ID token for UI, access token for APIs; Authorization Code + PKCE for humans, Client Credentials for services; each token's aud pins it to exactly one API.

Key

Authorize in three layers. Coarse at the gateway (valid token), fine at the service (right permission), object-level in domain logic (right owner). Skipping the third is the classic BOLA breach.

Key

Distributed correctness lives outside Auth0 too. Redis settles the seat race atomically, a DB constraint guarantees it durably, idempotency keys stop double-charges, and Kafka carries the sub so the async world stays auditable.

Key

Validate locally, trust nothing internally, grant least privilege. RS256 + cached JWKS makes verification fast and dependency-free; zero-trust hops and per-edge M2M apps keep the blast radius small when something leaks.
