Phase 6 · Hands-On Auth0

Chapter 14 — Hands-On Auth0: Actions, Custom Claims, M2M and Management API

Up to now you have learned the theory of OAuth, OIDC, JWTs and the Auth0 platform. This chapter is where you finally make Auth0 do work for you. You will write a real post-login Action that injects a user's roles and permissions into their ID and access tokens as namespaced custom claims; test it and decode the resulting token; stand up a machine-to-machine (M2M) application; obtain a Management API token via the client-credentials grant; and then drive the Management API from curl, Postman and code to create users and assign roles. Along the way you will learn the crucial difference between user_metadata and app_metadata, how to bulk import and export users, and how to safely promote configuration from a development tenant to production. By the end you will be able to automate identity the way real backend engineers do.

1. Theory — First Principles

Auth0 is, at its core, an identity pipeline. A user (or a machine) presents credentials, Auth0 authenticates them, and then it emits tokens — signed JSON Web Tokens that your applications and APIs trust. Everything in this chapter is about shaping that pipeline and programming Auth0 from the outside.

There are exactly two ways to influence Auth0 at runtime, and you must understand the distinction from first principles:

  • Inbound extensibility — Actions. Code that Auth0 runs inside its own pipeline, at well-defined moments (a "trigger") such as right after a user logs in. Actions cannot reach out and change Auth0's configuration; they can only enrich the request flowing through them — most importantly, by adding claims to the tokens about to be minted.
  • Outbound extensibility — the Management API. A REST API you call to read and mutate the tenant's configuration: users, roles, connections, clients, rules, email templates. This is how you create users, assign roles, rotate secrets, and export data programmatically.

Why custom claims must be namespaced. The OpenID Connect specification reserves a set of standard claim names (sub, iss, aud, exp, email, name...). To prevent your private claims from ever colliding with a future standard claim — and to make it unambiguous that you defined them — Auth0 requires that any non-standard claim you add to an OIDC token be a fully-qualified URI, e.g. https://myapp.example.com/roles. Auth0 silently drops any non-namespaced custom claim. This is not Auth0 being fussy; it is enforcing OIDC §5.1, which says private claims SHOULD be collision-resistant.

Why machines need their own identity (M2M). The Authorization Code flow assumes there is a human at a browser to consent and type a password. A nightly batch job, a backend service, or a CLI has no human. For these, OAuth defines the client-credentials grant: the application authenticates as itself using a client ID + secret and receives an access token whose subject is the application, not a person. The Management API is itself just an Auth0 API (audience https://YOUR_TENANT/api/v2/), so to call it you obtain an M2M token scoped to it.

Key

Actions enrich tokens inside the pipeline; the Management API changes configuration from outside. Custom claims must be namespaced URIs or Auth0 drops them. Machines authenticate with the client-credentials grant, not a user login.

2. Story-Based Explanation

Imagine you have just joined "CineBook", a cinema-booking startup. The login screen already works (Chapter 13). But on day one the lead engineer hands you two tickets:

"Our React app needs to hide the Admin menu unless the logged-in user is an admin — but the token doesn't say what role the user has. Fix it."
"Our nightly cron imports 5,000 partner users from a CSV and assigns them the partner role. Right now an intern does it by hand in the dashboard. Automate it."

The first ticket is an Action problem. The role lives in Auth0, but it is not in the token, so the front-end is blind. You will write a post-login Action that copies the user's roles into a namespaced claim. After deploying it, the React app reads token['https://cinebook.com/roles'] and shows the Admin menu only to admins. No backend change, no redeploy — just a small piece of code running inside Auth0's login pipeline.

The second ticket is a Management API problem. There is no human in a nightly cron, so you create an M2M application called "CineBook Importer", authorize it for the Management API with the scopes create:users and update:users, and your cron exchanges its client secret for a token. With that token it loops over the CSV, calls POST /api/v2/users and POST /api/v2/users/{id}/roles, and the intern is freed forever. Better still, for 5,000 users you switch to the bulk import job so you do not hit rate limits.

These two tickets are the whole chapter. Every concept below exists to solve one of them well, securely, and in production.

4. Real-World Analogy

Think of an airport.

  • The Action is the gate agent's stamp machine. As you walk through the boarding gate (the login pipeline), the agent looks up your booking and stamps your boarding pass with "Priority", "Lounge access", "Seat 3A". The stamp travels with you on the pass (the token). The agent cannot change the airline's database — they can only stamp the pass in front of them, at that one moment.
  • The Management API is the airline's back-office system. Staff there create passenger records, upgrade tickets, and assign frequent-flyer tiers. They never stand at the gate; they change the underlying data that the gate agent will later read.
  • The M2M app is a service account badge. The automated check-in kiosk is not a person, so it carries its own badge (client ID + secret) to talk to the back office.
  • user_metadata vs app_metadata: user_metadata is the "meal preference" you yourself filled in — harmless if you change it. app_metadata is your "frequent-flyer tier" — if passengers could edit that, everyone would be Platinum. So only the airline writes it.
Note

A namespaced custom claim is exactly the stamp on the boarding pass: it is information the airport vouches for, carried by the traveller, and trusted downstream because it is signed.

5. Internal Working

5.1 How an Action executes

An Action is a Node.js (currently Node 18/20 LTS on the Auth0 runtime as of 2026) module that exports an onExecutePostLogin(event, api) function. When a login completes, Auth0 spins up a short-lived, sandboxed serverless container, injects the event (read-only facts about this login: the user, the client, the request, the connection) and the api (the levers you can pull: set claims, deny access, redirect, etc.), and runs your function. Actions in a flow run in sequence, top to bottom, sharing nothing except what you explicitly write. Each Action has a hard execution budget (a few seconds) — exceed it and the login fails.

5.2 Why roles are not in the token by default

Auth0's RBAC stores roles and permissions in its database, associated with the user. Tokens are deliberately lean — Auth0 will only auto-include permissions in the access token if you enable "Add Permissions in the Access Token" on the API. Roles are never auto-included. So the canonical pattern is: read event.authorization.roles (populated when RBAC is enabled) and copy it into a namespaced claim yourself.

5.3 How the Management API token is verified

When your M2M app calls /oauth/token, Auth0 verifies the client secret, confirms the app is authorized for the requested audience (the Management API), intersects the requested scopes with the scopes granted to that app, and mints a signed JWT whose aud is the Management API and whose scope claim lists the granted permissions. The Management API then, on every request, validates that JWT's signature (RS256, via the tenant's JWKS), expiry, audience, and required scope before performing the operation.

  Token lifetime & caching (M2M)
  ------------------------------
  t0   request token  -->  { expires_in: 86400 }   (default 24h)
  t0..t+86400s   REUSE the same token (cache it!)
  t+86400s       token expired -> request a NEW one
  Anti-pattern: requesting a fresh token on EVERY call
                = wasted /oauth/token quota + latency

6. Code Walkthrough — The Post-Login Action

Here is the complete, runnable post-login Action that solves ticket #1. Create it in the Auth0 Dashboard under Actions → Library → Build Custom → Login / Post Login, paste the code, then add it to the Login flow.

/**
 * Post-Login Action: add roles + permissions as namespaced custom claims.
 * Trigger: post-login
 */
exports.onExecutePostLogin = async (event, api) => {
  // 1) A namespace MUST be a URI you control. It does NOT need to resolve.
  //    Convention: your app's https URL. NEVER use an auth0.com domain
  //    (Auth0 forbids namespaces under its own domains).
  const namespace = 'https://cinebook.com';

  // 2) Roles are populated by Auth0 ONLY when RBAC is enabled on the API.
  const roles = event.authorization?.roles ?? [];

  // 3) Add the same claim to BOTH tokens:
  //    - id_token  -> consumed by the front-end (UI decisions)
  //    - access_token -> consumed by your API (authorization decisions)
  api.idToken.setCustomClaim(`${namespace}/roles`, roles);
  api.accessToken.setCustomClaim(`${namespace}/roles`, roles);

  // 4) Optionally surface a non-sensitive user_metadata value to the UI.
  const theme = event.user.user_metadata?.theme;
  if (theme) {
    api.idToken.setCustomClaim(`${namespace}/theme`, theme);
  }

  // 5) Surface a tenant/plan flag stored in app_metadata (user cannot edit it).
  const plan = event.user.app_metadata?.plan ?? 'free';
  api.accessToken.setCustomClaim(`${namespace}/plan`, plan);
};

Line-by-line, why each line exists:

  • namespace — a URI you own. It is a label, not a URL that gets fetched. Using https://cinebook.com guarantees no collision with OIDC standard claims.
  • event.authorization?.roles — the optional chaining (?.) protects against logins where authorization context is absent (e.g. an M2M token has no user). Defaulting to [] means the claim is always present and always an array — predictable for the consumer.
  • setting both tokens — the front-end reads the ID token to render UI; your API must never trust the ID token for authorization and instead reads the access token. Putting roles in both keeps each layer self-sufficient.
  • user_metadata.theme — safe to expose because it is a user preference, not a security decision.
  • app_metadata.plan — an authorization-relevant flag; it lives in app_metadata precisely because the user must not be able to edit it.
Warn

event.authorization.roles is empty unless RBAC is enabled on the API the user is logging in for (API → Settings → "Enable RBAC"). If your roles claim is always [], that toggle is the first thing to check.

7. Practical Implementation — Test the Action & Inspect the Token

7.1 Test inside the dashboard

The Action editor has a Run tab with a mock event. Edit the mock so event.authorization.roles = ["admin"] and click Run — the console shows the claims your code set. This is a fast unit test before you touch a real login.

7.2 Get a real token and decode it

Trigger a real login from your app (or use the Try button on a connection). Then decode the JWT. You can paste it into jwt.io, but here is a CLI way that never sends your token to a website:

# Decode the PAYLOAD of a JWT locally (base64url -> JSON). Read-only, no verify.
TOKEN="eyJhbGciOi...your.jwt.here"
echo "$TOKEN" | cut -d '.' -f2 | tr '_-' '/+' \
  | awk '{ l=length($0)%4; if(l){ for(i=0;i<4-l;i++) $0=$0"=" } print }' \
  | base64 -d 2>/dev/null | python3 -m json.tool

You should see your namespaced claims in the decoded payload:

{
  "iss": "https://your-tenant.us.auth0.com/",
  "sub": "auth0|6650f0c1a2b3c4d5e6f7a8b9",
  "aud": ["https://api.cinebook.com", "https://your-tenant.us.auth0.com/userinfo"],
  "exp": 1718900000,
  "https://cinebook.com/roles": ["admin"],
  "https://cinebook.com/plan": "pro"
}

7.3 Read the claim in a React front-end

import { useAuth0 } from '@auth0/auth0-react';

const NAMESPACE = 'https://cinebook.com';

function AdminMenu() {
  const { user, isAuthenticated } = useAuth0();
  // ID-token claims are flattened onto `user` by the SDK.
  const roles = (isAuthenticated && user?.[`${NAMESPACE}/roles`]) || [];
  if (!roles.includes('admin')) return null;
  return <a href="/admin">Admin</a>;
}

7.4 Enforce the claim in a Spring Boot resource server (the real gate)

UI hiding is cosmetic; the API must enforce. Map the namespaced claim to Spring authorities:

@Bean
SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
  http
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/admin/**").hasAuthority("ROLE_admin")
        .anyRequest().authenticated())
    .oauth2ResourceServer(o -> o.jwt(j -> j.jwtAuthenticationConverter(rolesConverter())));
  return http.build();
}

private JwtAuthenticationConverter rolesConverter() {
  JwtAuthenticationConverter conv = new JwtAuthenticationConverter();
  conv.setJwtGrantedAuthoritiesConverter(jwt -> {
    List<String> roles =
        jwt.getClaimAsStringList("https://cinebook.com/roles");
    return roles == null ? List.of()
        : roles.stream()
               .map(r -> new SimpleGrantedAuthority("ROLE_" + r))
               .collect(Collectors.toList());
  });
  return conv;
}

8. Production Architecture — M2M, Management API & Tenants

8.1 Create the M2M application & get a token

Dashboard → Applications → Create Application → Machine to Machine, then authorize it for "Auth0 Management API" and tick only the scopes you need (least privilege). Then exchange the secret for a token:

curl --request POST \
  --url 'https://YOUR_TENANT.us.auth0.com/oauth/token' \
  --header 'content-type: application/json' \
  --data '{
    "grant_type": "client_credentials",
    "client_id": "YOUR_M2M_CLIENT_ID",
    "client_secret": "YOUR_M2M_CLIENT_SECRET",
    "audience": "https://YOUR_TENANT.us.auth0.com/api/v2/"
  }'
# -> { "access_token": "eyJ...", "expires_in": 86400, "token_type": "Bearer" }

8.2 Call the Management API — create user & assign role (curl)

MGMT_TOKEN="eyJ...from step 8.1..."
BASE="https://YOUR_TENANT.us.auth0.com/api/v2"

# Create a user in the Username-Password-Authentication db connection
USER=$(curl -s --request POST --url "$BASE/users" \
  --header "authorization: Bearer $MGMT_TOKEN" \
  --header 'content-type: application/json' \
  --data '{
    "connection": "Username-Password-Authentication",
    "email": "partner1@example.com",
    "password": "A-Str0ng-Passw0rd!",
    "email_verified": false,
    "app_metadata": { "plan": "partner" }
  }')

USER_ID=$(echo "$USER" | python3 -c 'import sys,json;print(json.load(sys.stdin)["user_id"])')

# Assign a role (get the role id once from GET /roles)
curl -s --request POST --url "$BASE/users/$USER_ID/roles" \
  --header "authorization: Bearer $MGMT_TOKEN" \
  --header 'content-type: application/json' \
  --data '{ "roles": ["rol_ABC123partner"] }'

8.4 Doing it from a backend (Node.js, with token caching)

import { ManagementClient } from 'auth0';

// The SDK fetches AND caches the M2M token for you (renews before expiry).
const mgmt = new ManagementClient({
  domain: 'YOUR_TENANT.us.auth0.com',
  clientId: process.env.M2M_CLIENT_ID,
  clientSecret: process.env.M2M_CLIENT_SECRET,
  // audience defaults to the Management API
});

export async function onboardPartner(email) {
  const { data: user } = await mgmt.users.create({
    connection: 'Username-Password-Authentication',
    email,
    password: crypto.randomUUID() + 'Aa1!',
    app_metadata: { plan: 'partner' },
  });
  await mgmt.users.assignRoles(
    { id: user.user_id },
    { roles: ['rol_ABC123partner'] }
  );
  return user.user_id;
}

8.5 FastAPI / Python equivalent

import os, time, httpx

_token_cache = {"value": None, "exp": 0}
TENANT = os.environ["AUTH0_TENANT"]      # e.g. your-tenant.us.auth0.com
BASE   = f"https://{TENANT}/api/v2"

async def mgmt_token() -> str:
    if _token_cache["value"] and time.time() < _token_cache["exp"] - 60:
        return _token_cache["value"]            # reuse cached token
    async with httpx.AsyncClient() as c:
        r = await c.post(f"https://{TENANT}/oauth/token", json={
            "grant_type": "client_credentials",
            "client_id": os.environ["M2M_CLIENT_ID"],
            "client_secret": os.environ["M2M_CLIENT_SECRET"],
            "audience": f"https://{TENANT}/api/v2/",
        })
    r.raise_for_status()
    data = r.json()
    _token_cache.update(value=data["access_token"],
                        exp=time.time() + data["expires_in"])
    return data["access_token"]

async def create_user(email: str) -> str:
    tok = await mgmt_token()
    async with httpx.AsyncClient() as c:
        r = await c.post(f"{BASE}/users",
            headers={"authorization": f"Bearer {tok}"},
            json={"connection": "Username-Password-Authentication",
                  "email": email, "password": "A-Str0ng-Passw0rd!1"})
    r.raise_for_status()
    return r.json()["user_id"]

8.6 Promoting config to production — tenants & environments

A "tenant" is an isolated Auth0 instance. The production pattern is one tenant per environment: cinebook-dev, cinebook-staging, cinebook-prod. You never click around in prod. Instead you treat tenant configuration as code using the auth0-deploy-cli or the Terraform Auth0 provider, and promote tested config forward.

# Export the dev tenant to versioned YAML/JSON (config-as-code)
a0deploy export --format yaml \
  --output_folder ./tenant-dev \
  --config_file dev.config.json

# Review the diff in git, then import into staging/prod
a0deploy import --input_file ./tenant-dev/tenant.yaml \
  --config_file prod.config.json

   DEV tenant            STAGING tenant           PROD tenant
   (free play)            (test like prod)        (locked down)
       |                       ^                        ^
       | a0deploy export       | a0deploy import        | a0deploy import
       v                       |                        |
   git repo (tenant.yaml) -----+------------------------+
   - Actions code               keyword replace per env:
   - clients, APIs, conns       client secrets, callback URLs, namespaces
   (secrets EXCLUDED from git, injected from a vault)
Tip

Use keyword replacement in the deploy CLI so the same tenant.yaml produces different callback URLs and audiences per environment, and inject secrets from a vault at deploy time — never commit a client secret to git.

10. Performance Considerations

  • Cache the M2M token. It is valid ~24h. Requesting a new one per call wastes latency and burns your /oauth/token quota. The official SDKs cache automatically; if you hand-roll, cache with a 60s safety margin (see 8.5).
  • Keep Actions fast. Every Action runs on the critical login path — its latency is added to every user's login. Avoid network calls inside an Action; if you must, set tight timeouts and fail open or closed deliberately.
  • Respect Management API rate limits. The Management API is rate-limited (per tenant, returned in X-RateLimit-Remaining headers). For more than a handful of users, use the bulk import job, not a loop of POST /users.
  • Don't bloat tokens. Large claim arrays inflate every request that carries the token. Put only what the consumer needs; fetch the rest from your DB by sub.
  • Use search wisely. GET /users?q=... uses Lucene over an eventually-consistent index. For exact-by-email use GET /users-by-email, which is strongly consistent.

10.1 Bulk import (the right way for 5,000 users)

# 1) users.json: an array of user objects matching the import schema
# 2) Kick off an async import job (assign a connection_id, not a name)
curl -s --request POST --url "$BASE/jobs/users-imports" \
  --header "authorization: Bearer $MGMT_TOKEN" \
  --form users=@users.json \
  --form connection_id="con_XXXXXXXX" \
  --form upsert=true \
  --form send_completion_email=false
# -> returns { "id": "job_abc", "status": "pending" }

# 3) Poll the job until status = "completed"
curl -s --url "$BASE/jobs/job_abc" \
  --header "authorization: Bearer $MGMT_TOKEN"

10.2 Bulk export

# Export all users of a connection as a gzipped JSON file (async job).
curl -s --request POST --url "$BASE/jobs/users-exports" \
  --header "authorization: Bearer $MGMT_TOKEN" \
  --header 'content-type: application/json' \
  --data '{
    "connection_id": "con_XXXXXXXX",
    "format": "json",
    "fields": [{"name":"user_id"},{"name":"email"},{"name":"app_metadata"}]
  }'
# Poll the returned job id; when done it gives a signed download "location" URL.
Note

Bulk export cannot export password hashes via this endpoint. To migrate hashes out of Auth0 you must open a support request; this is a deliberate security control.

11. Common Mistakes

  1. Forgetting the namespace. api.idToken.setCustomClaim('roles', ...) silently does nothing for OIDC tokens. Always use a URI.
  2. Expecting roles without RBAC. event.authorization.roles is empty unless RBAC is enabled on the API.
  3. Not adding the Action to the flow. Deploying an Action only saves it to the Library — you must drag it onto the Login flow and click Apply.
  4. Putting roles in user_metadata. Users can edit user_metadata via the self-service Management endpoints — instant privilege escalation. Use app_metadata / RBAC.
  5. Requesting a Management token on every request. Cache it.
  6. Authorizing on the ID token in the API. The API must use the access token and validate aud.
  7. Looping POST /users for thousands of users. You will hit rate limits; use the import job.
  8. Shipping the M2M client secret to the browser. Client credentials are confidential — backend only.
  9. Hardcoding role IDs across tenants. Role IDs differ per tenant; resolve them at deploy time or via GET /roles.
  10. Editing config directly in prod. Promote via export/import so changes are reviewed and reproducible.

12. Best Practices

  • One namespace per app, defined once as a constant, reused in Action and consumers.
  • Always default arrays (?? []) so claim consumers never special-case "missing".
  • Set roles in both ID and access tokens — UI from ID, enforcement from access.
  • Least-privilege M2M apps, one per responsibility, with rotation.
  • Cache and proactively refresh the Management token (60s margin).
  • app_metadata for authorization, user_metadata for preferences — never mix.
  • Idempotent imports using upsert=true so re-runs are safe.
  • Config as code with a0deploy/Terraform; secrets from a vault; keyword replacement per environment.
  • Separate tenants per environment; never test in prod.
  • Pin role assignment to role IDs resolved per tenant, not hardcoded strings.

13. Interview Questions (with Model Answers)

Q1. Why must custom claims be namespaced in Auth0?

Model answer: OIDC reserves standard claim names; private claims should be collision-resistant (OIDC §5.1). Auth0 enforces this by requiring custom claims to be URIs and silently dropping non-namespaced ones, so your data never clashes with current or future standard claims and is unambiguously yours.

Q2. An Action sets roles but the API still sees none. Walk me through debugging.

Model answer: (1) Is RBAC enabled on the API so event.authorization.roles is populated? (2) Is the claim namespaced? (3) Is the Action actually in the Login flow and applied? (4) Is the API reading the access token (not ID) and the right namespace? (5) Decode a fresh token to confirm the claim is present.

Q3. Difference between an Action and the Management API?

Model answer: An Action runs inside Auth0's pipeline to enrich the in-flight login/token; it cannot change tenant config. The Management API is an external REST API you call to read/mutate config (users, roles, clients). Actions = inbound enrichment; Management API = outbound administration.

Q4. How does a backend authenticate to the Management API?

Model answer: Via the client-credentials grant: an M2M app exchanges its client ID + secret at /oauth/token with audience = the Management API, receiving an access token scoped to the granted Management permissions. The token is cached and reused until near expiry.

Q5. user_metadata vs app_metadata — and a security implication?

Model answer: user_metadata is user-editable preferences; app_metadata is app-controlled and users cannot edit it. Authorization data (roles, plan, flags) must live in app_metadata or RBAC; putting it in user_metadata lets a user escalate their own privileges via the self-service profile update endpoint.

Q6. You must import 100k users from a legacy DB. Approach?

Model answer: Use the bulk users-imports job in batches, with upsert=true for idempotency, mapping fields to the import schema. If the legacy passwords use a supported hash, import the hashes so users keep their passwords; otherwise enable custom-database "lazy migration" to migrate on first login. Avoid per-user POSTs (rate limits).

Q7. How do you promote Auth0 config to production safely?

Model answer: Separate tenants per environment; treat config as code with a0deploy or Terraform; export dev to versioned files, review the diff in git, use keyword replacement for per-env values, inject secrets from a vault, and import into staging then prod. No manual prod edits.

Q8. Why is the M2M secret more dangerous than an ID token?

Model answer: An ID token is short-lived and scoped to one user/session. The M2M secret is a long-lived credential that can mint tokens able to administer the whole tenant (create users, change roles). Leaking it is a full administrative compromise; hence vault storage, rotation, and backend-only use.

  • Know the trigger names cold: onExecutePostLogin, onExecuteCredentialsExchange (M2M), onExecutePreUserRegistration, onExecutePostUserRegistration.
  • The exam tests that custom claims must be namespaced URIs and that roles need RBAC enabled.
  • Remember the API objects: api.idToken.setCustomClaim, api.accessToken.setCustomClaim, api.access.deny, api.redirect.sendUserTo, api.user.setAppMetadata.
  • Management API auth is client-credentials with audience = https://TENANT/api/v2/; tokens carry scopes like read:users, create:users.
  • app_metadata = not user-editable; user_metadata = user-editable. Expect a question contrasting them.
  • Bulk operations are asynchronous jobs you poll; upsert makes imports idempotent.
  • Config promotion uses auth0-deploy-cli / Terraform across separate tenants per environment.

20. Key Takeaways

  • Actions enrich; the Management API administers. One runs inside the pipeline, the other is called from outside.
  • Custom claims must be namespaced URIs or Auth0 drops them — this prevents collisions with OIDC standard claims.
  • Roles need RBAC enabled to populate event.authorization.roles; copy them into both ID and access tokens.
  • Machines use the client-credentials grant; the Management API is just an audience you request a token for.
  • Cache the Management token (~24h) — never refetch per call.
  • app_metadata holds authorization data (user-uneditable); user_metadata holds preferences (user-editable).
  • Use bulk import/export jobs for volume; upsert=true makes them idempotent.
  • Promote config as code across separate tenants per environment; never click around in production.
  • A JWT is signed, not encrypted — never put secrets or sensitive PII in a claim.
