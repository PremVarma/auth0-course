Chapter 18 — Project 2 — Next.js + Auth0

In Chapter 17 you secured a single-page React app where every line of code ran in the browser. Next.js changes the game completely: now your code runs in two places at once — on a Node.js server and in the browser — and the boundary between them is exactly where authentication gets subtle, powerful, and occasionally dangerous. This chapter builds a production-grade Next.js 15 App Router application with @auth0/nextjs-auth0 v4, from npm install to a deployed protected dashboard that calls an external API with a real access token. You will learn to wire login/logout, run auth in middleware, read sessions inside Server Components, protect Route Handlers, and reason about the SSR-vs-RSC distinction that trips up even experienced engineers in interviews.

1. Theory — First Principles: Why Next.js Auth Is Different

To understand Next.js authentication you must first internalise one idea: your code executes in two trust domains. In a classic React SPA (Chapter 17) the browser is the only runtime. The browser is untrusted — the user controls it, can read every byte of JavaScript, and can inspect every network request. That is why an SPA must use the Authorization Code flow with PKCE and store tokens in memory: there is no safe place to keep a secret.

Next.js introduces a server runtime you control. The server is trusted: only you can read its environment variables, only you can read files on its disk, and the user never sees the code that runs there. This single fact unlocks a fundamentally safer authentication model: the Backend-For-Frontend (BFF) pattern.

The Backend-For-Frontend (BFF) pattern

In the BFF model, the Next.js server — not the browser — talks to Auth0. The server performs the Authorization Code exchange using a confidential client (one that can keep a client_secret), receives the tokens, and stores them in an encrypted, HttpOnly session cookie. The browser never touches a raw access token or refresh token. JavaScript in the browser literally cannot read an HttpOnly cookie, so an XSS bug cannot exfiltrate the session.

Key

SPA auth (Ch.17) keeps tokens in browser memory because there is no trusted server. Next.js auth keeps tokens in an encrypted HttpOnly cookie managed by a trusted server. This is the single most important conceptual difference, and the reason Next.js auth is considered more secure by default.

Why a dedicated SDK exists

The @auth0/nextjs-auth0 SDK exists to implement the BFF correctly. Doing it by hand means implementing: the PKCE-protected redirect, state and nonce validation (CSRF + replay protection), ID-token signature verification against Auth0's JWKS, cookie encryption with a rotating key, automatic refresh-token rotation, and a way to read that session from both Server Components and Route Handlers. The SDK gives you all of this behind a tiny surface area.

The three runtimes you must keep straight

RuntimeWhere it runsTrusted?Auth role
MiddlewareEdge / server, before the request reaches a routeYesMounts auth routes, refreshes/attaches the session cookie, gatekeeps
Server Components (RSC)Server only, render-timeYesRead session, fetch data with the access token, never send tokens to the client
Client ComponentsBrowserNoRead non-sensitive user profile via a provider/hook; never see raw tokens

2. Story-Based Explanation — The Hotel With a Concierge

Picture two hotels.

Hotel SPA (Chapter 17) has no front desk. When you arrive, the hotel hands you the master key card and says, "Hold onto this; show it whenever you want into a room." You carry the key everywhere. If a pickpocket bumps into you (an XSS attack), they can lift the key from your pocket. The hotel trusts you to guard it, because there is nobody else to hold it.

Hotel Next.js has a concierge at a locked desk. When you arrive you authenticate with the concierge once. The concierge keeps your master key in a vault behind the desk and hands you only a numbered coat-check ticket (the encrypted session cookie). Whenever you want into a room, you give the concierge your ticket; the concierge fetches the master key from the vault, opens the door for you, and hands the key right back into the vault. A pickpocket who steals your ticket gets a useless stub — it is meaningless without the concierge, the vault, and the encryption key.

In this analogy:

  • The concierge is the Next.js server (middleware + Server Components + Route Handlers).
  • The vault is the encrypted session cookie + the AUTH0_SECRET that decrypts it.
  • The coat-check ticket is the cookie the browser holds — opaque, HttpOnly, useless on its own.
  • The master key is the access token, which the browser never holds directly.
Note

The whole point of the BFF "concierge" is that the dangerous object (the access token) stays server-side. The browser only ever holds a reference. This is why we say Next.js auth has a smaller attack surface than SPA auth.

4. Real-World Analogy — The Embassy Visa Stamp

Think of your Next.js server as a national embassy operating on foreign soil (the public internet). Auth0 is the home country's passport office.

  • A citizen (the user) shows up at the embassy. The embassy doesn't issue passports itself — it phones the passport office (Auth0) to verify identity. That phone call is the Authorization Code exchange, done over a secure line using the embassy's confidential credentials (the client_secret).
  • Once verified, the embassy issues a day-pass with a tamper-proof stamp (the encrypted session cookie). The citizen carries the day-pass; the embassy keeps the citizen's real passport in its safe (the server-side session / access token).
  • When the citizen wants a service from a partner ministry (the external API), the embassy presents the citizen's passport (the access token) on their behalf. The citizen never carries the passport into the ministry themselves.
  • Middleware is the security checkpoint at the embassy gate that checks the day-pass on every entry and quietly renews it before it expires (silent token refresh).
Tip

The reason embassies — and BFFs — exist is delegation under control. The user delegates the holding of credentials to a party that can guard them better than the user can. That is the BFF thesis in one sentence.

5. Internal Working — What the SDK Actually Does

Let's lift the hood on @auth0/nextjs-auth0 v4. Understanding the mechanics is what separates "I followed a tutorial" from "I can debug this in production."

5.1 The mounted auth routes

The SDK's middleware automatically mounts these endpoints — you do not create files for them:

RoutePurpose
/auth/loginStarts the Authorization Code + PKCE flow; redirects to Auth0 /authorize.
/auth/logoutClears the session cookie and redirects to Auth0 logout (kills the SSO session).
/auth/callbackReceives the code, exchanges it for tokens, validates, sets the cookie.
/auth/profileReturns the user profile JSON (used by client-side useUser()).
/auth/access-tokenReturns a fresh access token to server-trusted callers; refreshes if needed.
/auth/backchannel-logoutReceives OIDC Back-Channel Logout tokens from Auth0 to terminate sessions.

5.2 The session cookie internals

The session is a stateless, encrypted cookie by default (no database required). The SDK uses the AUTH0_SECRET to derive an encryption key, then seals the tokens and profile into a JWE (JSON Web Encryption) using authenticated encryption (AES-256-GCM). Because it's authenticated encryption, any tampering with the cookie invalidates it — the server detects modification and rejects it.

  AUTH0_SECRET  ----derive---->  encryption key
                                      |
   { user, idToken, accessToken,      |  AES-256-GCM
     refreshToken, expiresAt }  --encrypt-->  appSession=eyJ...   (the cookie)
                                      |
   on each request: decrypt, check expiry, maybe refresh, re-encrypt
Warn

Because the session is stateless, large sessions produce large cookies. Browsers cap a single cookie near ~4 KB; the SDK chunks if needed, but bloated sessions (huge custom claims, many scopes) hurt performance. Keep custom claims lean.

5.3 Automatic token refresh

When you request the access token (via getAccessToken() or auth0.getSession() with a near-expiry token), the SDK checks expiresAt. If the access token is expired or about to expire and a refresh token is present (you enabled offline_access scope and rotation in Auth0), the SDK silently calls Auth0's /oauth/token with grant_type=refresh_token, gets a new access token, rotates the refresh token, and re-seals the cookie — all server-side, invisible to the user.

Danger

The application in Auth0 MUST be a Regular Web Application, not a Single Page Application. A SPA has no client_secret and cannot perform the confidential-client token exchange the SDK relies on. Choosing the wrong app type is the #1 setup error.

6.3 The client instance — lib/auth0.ts

// lib/auth0.ts
import { Auth0Client } from "@auth0/nextjs-auth0/server";

// One shared instance for the whole app. Reads env vars automatically.
export const auth0 = new Auth0Client({
  // You can override env here, e.g. force a specific audience/scope:
  authorizationParameters: {
    scope: process.env.AUTH0_SCOPE,
    audience: process.env.AUTH0_AUDIENCE,
  },
});

6.4 Middleware — middleware.ts (project root)

// middleware.ts  (must live at the project root, NOT in /app)
import type { NextRequest } from "next/server";
import { auth0 } from "./lib/auth0";

export async function middleware(request: NextRequest) {
  // This single call:
  //  1. Mounts /auth/login, /auth/logout, /auth/callback, etc.
  //  2. Decrypts the session cookie on every request.
  //  3. Silently refreshes the access token if it is near expiry.
  //  4. Re-attaches the (possibly rotated) session cookie to the response.
  return await auth0.middleware(request);
}

export const config = {
  matcher: [
    /*
     * Run on everything EXCEPT static assets & images, so we don't
     * waste cycles decrypting cookies for /favicon.ico etc.
     * IMPORTANT: the /auth routes MUST be matched, so do not exclude them.
     */
    "/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)",
  ],
};
Warn

If your matcher accidentally excludes /auth/*, login silently 404s. The matcher must include the auth routes. A common bug is copying a matcher that excludes api — that breaks the SDK's mounted routes.

6.6 Login / logout links — app/page.tsx

Login and logout are plain anchors to the SDK-mounted routes. No client JS, no button handler required.

// app/page.tsx  (a Server Component by default)
import { auth0 } from "@/lib/auth0";

export default async function Home() {
  const session = await auth0.getSession();

  if (!session) {
    return (
      <main>
        <h1>Welcome</h1>
        {/* These are the SDK's mounted routes. Plain links. */}
        <a href="/auth/login">Log in</a>
      </main>
    );
  }

  return (
    <main>
      <h1>Hello, {session.user.name}</h1>
      <a href="/auth/logout">Log out</a>
    </main>
  );
}

7. Practical Implementation — Sessions, Protected Pages & APIs

7.1 Reading the session in a Server Component (the protected dashboard)

// app/dashboard/page.tsx  — a PROTECTED Server Component
import { auth0 } from "@/lib/auth0";
import { redirect } from "next/navigation";

export default async function Dashboard() {
  // Runs ON THE SERVER. The cookie was decrypted by middleware.
  const session = await auth0.getSession();

  // Defense-in-depth: even with middleware, re-check at the page level.
  if (!session) {
    redirect("/auth/login?returnTo=/dashboard");
  }

  return (
    <main>
      <h1>Dashboard</h1>
      <p>Signed in as <strong>{session.user.email}</strong></p>
      {/* session.user contains ID-token claims only — safe to render. */}
      <pre>{JSON.stringify(session.user, null, 2)}</pre>
    </main>
  );
}

7.2 Calling an external API with the access token (Server Component)

// app/dashboard/orders/page.tsx
import { auth0 } from "@/lib/auth0";
import { redirect } from "next/navigation";

export default async function Orders() {
  const session = await auth0.getSession();
  if (!session) redirect("/auth/login?returnTo=/dashboard/orders");

  // getAccessToken() returns a VALID token, refreshing it if needed.
  // It throws if no token is available (e.g. wrong audience/scope).
  const { token } = await auth0.getAccessToken();

  const res = await fetch("https://my-api.example.com/orders", {
    headers: { Authorization: `Bearer ${token}` },
    // RSC fetch is cached by default — opt out for per-user data:
    cache: "no-store",
  });

  if (!res.ok) {
    // 401 here usually means audience/scope mismatch, not a Next.js bug.
    throw new Error(`API responded ${res.status}`);
  }

  const orders: Array<{ id: string; total: number }> = await res.json();

  return (
    <ul>
      {orders.map((o) => (
        <li key={o.id}>{o.id} — ${o.total}</li>
      ))}
    </ul>
  );
}
Key

The access token is fetched and used entirely on the server. It is never serialized into the HTML sent to the browser, never placed in a prop passed to a Client Component, and never logged. This is the whole security advantage of RSC over SPA — guard it jealously.

7.3 Protecting a Route Handler (your own API endpoint)

// app/api/profile/route.ts
import { auth0 } from "@/lib/auth0";
import { NextResponse } from "next/server";

export async function GET() {
  const session = await auth0.getSession();

  if (!session) {
    return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
  }

  // Optional: call a downstream API on the user's behalf
  const { token } = await auth0.getAccessToken();
  const upstream = await fetch("https://my-api.example.com/me", {
    headers: { Authorization: `Bearer ${token}` },
    cache: "no-store",
  });

  const data = await upstream.json();
  return NextResponse.json({ user: session.user, data });
}

7.4 A Server Action that mutates with the token

// app/dashboard/actions.ts
"use server";
import { auth0 } from "@/lib/auth0";

export async function createOrder(formData: FormData) {
  const session = await auth0.getSession();
  if (!session) throw new Error("Unauthorized");

  const { token } = await auth0.getAccessToken();
  await fetch("https://my-api.example.com/orders", {
    method: "POST",
    headers: {
      Authorization: `Bearer ${token}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ item: formData.get("item") }),
  });
}

Production checklist

  • Custom domain for Auth0 (auth.yourapp.com) so cookies and branding stay first-party and refresh tokens are not blocked by third-party-cookie restrictions.
  • Rotate AUTH0_SECRET via your secrets manager; never commit .env.local.
  • Set APP_BASE_URL to the real HTTPS origin in each environment; add matching Allowed Callback URLs (https://yourapp.com/auth/callback) and Allowed Logout URLs in the Auth0 dashboard.
  • Enable refresh token rotation + absolute/inactivity expiry on the Auth0 application.
  • Back-Channel Logout configured so a logout from Auth0 (or admin revoke) terminates the Next.js session server-side.
  • Stateless vs stateful sessions: default stateless cookies scale horizontally with zero infra; switch to a stateful store (Redis) only if you need server-side revocation lists or sessions too big for a cookie.

9. Security Analysis

ThreatHow Next.js + SDK mitigates it
XSS token theftTokens live in an HttpOnly encrypted cookie + server memory. JS cannot read them, so an XSS payload cannot exfiltrate the access/refresh token.
CSRF on loginThe state parameter is generated, cookied, and validated on callback. A forged callback without the matching state is rejected.
ID-token replay / forgeryThe nonce is validated and the ID token's signature is verified against Auth0's JWKS before any session is created.
Cookie tamperingAES-256-GCM authenticated encryption — any modified byte invalidates the cookie; the server rejects it.
Token leakage to clientNever pass session.accessToken as a prop to a Client Component or into serialized JSON — it would ship to the browser. Keep token use server-side.
Open redirectThe SDK validates returnTo against your app's origin; do not bypass it with user-supplied absolute URLs.
Stolen refresh tokenRotation invalidates the old token on each use; reuse detection (automatic in Auth0) revokes the family.
Danger

The single most dangerous mistake in Next.js auth is leaking the access token across the server→client boundary. Anything you return from a Server Component as a prop to a "use client" component, or put in a Route Handler JSON response, is sent to the browser. Returning the access token there silently re-creates the SPA attack surface you were trying to avoid.

10. Performance Considerations

  • Cookie decryption cost: middleware decrypts the session on matched requests. Scope your matcher tightly so static assets don't pay the cost.
  • Don't double-fetch the session: calling getSession() repeatedly in one render is cheap (it reads the already-decrypted request), but avoid redundant getAccessToken() calls — each may trigger a refresh network round-trip when near expiry.
  • RSC fetch caching: Next.js caches fetch by default. For per-user authorized data, set cache: "no-store" (or revalidate: 0) so User A never sees User B's cached response.
  • Edge vs Node runtime: the SDK's crypto runs in both, but heavy refresh logic and large sessions favour the Node runtime. Choose deliberately per route.
  • Session size: bloated custom claims grow the cookie, increasing every request's payload. Keep the ID token lean; fetch heavy profile data from your own API instead.
  • Streaming & Suspense: wrap slow authorized fetches in <Suspense> so the shell streams immediately while the protected data resolves.

11. Common Mistakes

  1. Using a SPA application type in Auth0. The SDK needs a Regular Web App with a client_secret. SPA → callback fails or no token exchange.
  2. v3 routes in a v4 project. v4 mounts /auth/*, not /api/auth/*. Old links break login.
  3. Forgetting middleware.ts at the project root. Without it the /auth/* routes never mount and the session never refreshes.
  4. Matcher excludes the auth routes. Login 404s silently.
  5. Requesting an access token without an audience. You get an opaque token (or only an ID token) and your API returns 401. Set AUTH0_AUDIENCE.
  6. Missing offline_access scope but expecting refresh — there is no refresh token, so the session dies when the access token expires.
  7. Passing the access token to a Client Component — re-introduces the XSS attack surface.
  8. Relying on middleware alone for authorization. Middleware is a first gate, not the last; re-check getSession() in the page/handler (defense in depth).
  9. Caching per-user fetches. Forgetting cache: "no-store" can serve one user's data to another.
  10. Mismatched APP_BASE_URL / callback URLs across environments → Callback URL mismatch error.

12. Best Practices

  • Centralise the Auth0Client in one lib/auth0.ts and import it everywhere — never instantiate twice.
  • Use middleware plus per-route getSession() checks (defense in depth), and redirect("/auth/login?returnTo=...") for protected pages.
  • Keep all token usage server-side; expose only the user profile to the client via useUser().
  • Always set cache: "no-store" on authorized, per-user fetches.
  • Request the minimum scopes and a specific audience; enable offline_access only when you genuinely need refresh.
  • Use a custom Auth0 domain in production to keep auth first-party.
  • Validate API access on the API side too — the API must independently verify the JWT (audience, issuer, signature, scopes). Never trust that "Next.js already checked."
  • Centralise authorization rules (RBAC/scope checks) in a small helper rather than scattering if statements.
  • Log auth failures without logging tokens.

13. Interview Questions (with Model Answers)

Q1. Why is Next.js auth considered more secure than SPA auth?

Model answer: Next.js has a trusted server runtime, enabling the BFF pattern. Tokens are stored in an encrypted HttpOnly cookie and held in server memory; the browser never holds raw access/refresh tokens. JavaScript can't read HttpOnly cookies, so an XSS bug can't exfiltrate the session — unlike an SPA that must keep tokens in JS-readable memory.

Q2. What's the difference between reading auth in a Server Component vs a Client Component?

Model answer: A Server Component calls auth0.getSession() / getAccessToken() directly on the server and may use the access token to call APIs — the token never reaches the browser. A Client Component uses useUser() via <Auth0Provider> and can only see the non-sensitive user profile, never tokens.

Q3. What does the middleware actually do?

Model answer: auth0.middleware() mounts the /auth/* routes, decrypts the session cookie per request, silently refreshes the access token when near expiry (rotating the refresh token), and re-attaches the updated cookie to the response. It can also gatekeep protected paths.

Q4. Why must the Auth0 application be a Regular Web App, not a SPA?

Model answer: The SDK performs a confidential-client Authorization Code exchange requiring a client_secret, which only a Regular Web App has. A SPA is a public client with no secret, so it can't do the server-side token exchange.

Q5. How do you call a protected external API from Next.js?

Model answer: On the server, call auth0.getAccessToken() (configured with the API's audience and scopes), then fetch the API with an Authorization: Bearer header and cache: "no-store". The token is acquired and used entirely server-side.

Q6. What is the SSR vs RSC consideration for auth?

Model answer: Both run on the server, but RSC (Server Components) render to a serialized tree that's streamed to the client — so you must never include a token in that tree. SSR'd Client Components (those marked "use client" but server-rendered for the first paint) hydrate in the browser and must only receive profile data, never tokens. The rule: token logic stays in pure server contexts (RSC, Route Handlers, Server Actions).

Q7. How does silent token refresh work and what enables it?

Model answer: Requesting offline_access yields a refresh token stored in the session. When the access token nears expiry, the SDK calls /oauth/token with grant_type=refresh_token server-side, rotates the refresh token, and re-seals the cookie — no user interaction. Rotation + reuse detection mitigates stolen refresh tokens.

Q8. Where is the session stored and what are the trade-offs?

Model answer: By default it's a stateless encrypted cookie — no DB, scales horizontally for free, but can't be revoked server-side and is size-limited (~4 KB, chunked). A stateful store (e.g. Redis) enables instant revocation and large sessions at the cost of infrastructure.

14. Certification Tips

  • Know that web apps use the Authorization Code flow (with PKCE) and are confidential clients; SPAs are public clients. The exam tests this distinction repeatedly.
  • Memorise that the session cookie is HttpOnly + Secure + SameSite and what each flag prevents.
  • Be able to map OIDC params: state = CSRF, nonce = replay, code_verifier/challenge = PKCE.
  • Understand refresh token rotation and reuse detection — likely a scenario question.
  • Know Allowed Callback URLs and Allowed Logout URLs must exactly match (scheme + host + path).
  • Recognise that the API must validate the JWT independently (audience, issuer, signature) — auth at the app does not exempt the resource server.
  • Back-Channel Logout and OIDC single logout concepts appear in advanced questions.

Show answer key
  1. BFF (Backend-For-Frontend). Tokens stay server-side in an encrypted HttpOnly cookie; the browser never holds raw tokens, so XSS can't steal them.
  2. Authorization Code flow (with PKCE).
  3. It needs a client_secret for the confidential-client token exchange; SPAs are public clients with no secret.
  4. /auth (v3 used /api/auth).
  5. Any of: /auth/login, /auth/logout, /auth/callback, /auth/profile, /auth/access-token, /auth/backchannel-logout.
  6. At the project root (same level as app/), not inside app/.
  7. Mounts /auth/* routes; decrypts the session cookie; silently refreshes the access token near expiry (rotating refresh token); re-attaches the updated cookie to the response (and can gatekeep).
  8. AES-256-GCM authenticated encryption — any modification invalidates it.
  9. AUTH0_SECRET; a 32-byte (64-hex-char) random value.
  10. Without an audience you get an ID token / opaque token unsuitable for the API, which returns 401.
  11. offline_access.
  12. await auth0.getSession().
  13. useUser() from @auth0/nextjs-auth0, with <Auth0Provider> in the layout.
  14. Exposes the user profile claims; never exposes access or refresh tokens.
  15. const { token } = await auth0.getAccessToken(); then fetch with Authorization: Bearer + cache:"no-store".
  16. So one user's authorized response isn't cached and served to another user.
  17. RSC output and SSR'd client components are serialized/sent to the browser — keep all token logic in pure server contexts (RSC/Route Handlers/Server Actions) and never pass tokens to client components.
  18. Defense in depth — middleware is a first gate, not the last; the page/handler must independently verify authorization.
  19. CSRF on the authorization request/callback.
  20. Replay of an ID token (binds the token to the request).
  21. On near-expiry, the SDK calls /oauth/token with grant_type=refresh_token server-side, rotates the refresh token, re-seals the cookie — invisibly.
  22. Each refresh issues a new refresh token and invalidates the old one; if an old (stolen) token is reused, Auth0 detects it and revokes the whole token family.
  23. Stateless cookie: no infra, scales free, but no server-side revocation + size-limited. Stateful store: instant revocation + large sessions, but needs infrastructure.
  24. Leaking the access/refresh token across the server→client boundary (as a prop to a client component or in a Route Handler JSON body).

20. Key Takeaways

Key
  • Next.js runs in two trust domains; the trusted server enables the BFF pattern — the defining security advantage over SPAs.
  • Tokens live in an encrypted HttpOnly cookie and server memory; the browser holds only an opaque reference. XSS can't steal what JS can't read.
  • Use a Regular Web Application (confidential client) in Auth0 — never a SPA — for the v4 SDK.
  • middleware.ts at the root mounts /auth/*, decrypts the session, and silently refreshes tokens. It's a first gate, not the last — re-check in pages/handlers.
  • Read the session with auth0.getSession() on the server; use useUser() for profile-only data on the client.
  • Acquire access tokens with getAccessToken() (correct audience/scope) and call external APIs entirely server-side with cache:"no-store".
  • The cardinal sin is leaking a token across the server→client boundary — that silently rebuilds the SPA attack surface.
  • In production: custom Auth0 domain, rotating refresh tokens, exact callback/logout URLs, and an API that independently validates every JWT.
