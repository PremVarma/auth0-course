Chapter 23 — Project 7 — GraphQL Authentication

REST gave you a comfortable mental model: one URL is one resource, one HTTP verb is one action, so you bolt a middleware in front of the route and you are secured. GraphQL deliberately demolishes that model. There is one endpoint, one HTTP verb (POST), and a client can ask for any shape of data it likes in a single request — including data it is not allowed to see. The gateway-guard pattern collapses, because there is no longer a gate per resource; there is a single door behind which lives an entire graph. This chapter rebuilds authentication and authorization for that graph from first principles. We will put the Auth0-verified principal into the GraphQL context, validate Auth0-issued JWTs in Apollo Server, and then enforce access at three depths — the operation, the type, and the individual field — using both imperative checks in resolvers and declarative schema directives like @auth and @hasPermission. By the end you will be able to defend why a query and a mutation need different authorization philosophies, and ship a GraphQL API that is as locked down as any REST service you have built.

1. Theory — First Principles: Why GraphQL Breaks Gateway Auth

Start from the two questions every secured system must answer, the same pair we have used all course long:

  • Authentication (AuthN) — Who are you? Proving the caller's identity. In our stack this is done once, by validating an Auth0-issued JWT access token. GraphQL changes nothing about this step; a JWT is a JWT no matter what protocol carries it.
  • Authorization (AuthZ) — What may you do? Deciding whether this caller may perform this operation on this data. This is where GraphQL is genuinely different from REST, and where most teams get it dangerously wrong.

To see why it is different, you must understand what a GraphQL request actually is. A REST request is addressed: GET /invoices/482 names exactly one resource and one action. The server can inspect the URL and the verb before running any business logic and decide allow/deny. That is why REST security lives in middleware — the middleware has everything it needs from the request line.

A GraphQL request is not addressed. It is a document. The client POSTs a query like { me { email invoices { total } } } to a single endpoint (conventionally /graphql). The server cannot know what data will be touched until it parses and executes that document, walking a tree of resolvers. There is no URL that says "invoices" and no verb that says "read." The authorization decision therefore cannot live at the door — it must live inside the graph, attached to the schema itself.

ConceptRESTGraphQL
EndpointsMany (one per resource)One (/graphql)
HTTP verb carries intentYes (GET/POST/PUT/DELETE)No (almost always POST)
What is requested is knowable from the request lineYesNo — only after parsing the query
Natural place for AuthZRoute middleware / gatewayResolver / schema directive / field level
Over-fetching riskLow (server picks the shape)High (client picks the shape)
Authentication mechanismJWT / sessionIdentical — JWT / session

The crucial first-principles takeaway: AuthN is unchanged; AuthZ moves from the perimeter into the resolution layer. The Auth0 part of this chapter (validating a JWT against your tenant's JWKS) is exactly what you learned for REST APIs. The new work is wiring the result of that validation — the principal — into a place every resolver can reach, and then enforcing fine-grained rules there.

Key

In REST you guard routes. In GraphQL you guard the graph. Authentication still happens once at the edge (validate the Auth0 JWT). Authorization must happen at the operation, type, and field level — because a single query can reach data that spans many "resources" at once.

2. Story-Based Explanation — The Restaurant With One Waiter

Picture two restaurants owned by the same company.

Restaurant REST is a food court. Every dish has its own counter — the pizza counter, the sushi counter, the dessert counter. A security guard stands at each counter checking your wristband. If your band does not grant dessert, the dessert guard simply refuses you. Adding security is easy: hire one guard per counter. This is route middleware.

Restaurant GraphQL is a single table where you hand one waiter a written order: "the steak, my account balance, the chef's secret recipe, and the other table's bill." The waiter takes one order slip and fetches everything in one trip. There is exactly one waiter and one door. If you put a guard at the door, the guard can check that you are a customer at all (authentication) but cannot tell, from the door, that your slip secretly asked for the chef's recipe and a stranger's bill. The dangerous items are inside the order.

So the company rewrites the rule: the waiter must read each line of the slip and apply policy line by line. "Steak — allowed. Your balance — allowed, it's yours. Secret recipe — denied, staff only. Other table's bill — denied, not yours." The order still succeeds for the allowed lines; the forbidden lines come back as errors or nulls. That is field-level authorization, and the waiter is your resolver layer.

Now extend the story. Some slips are not requests for food but instructions: "cancel table 5's order," "comp this meal," "fire the kitchen." Those are mutations. The company decides that any instruction — anything that changes the restaurant's state — must be checked before the waiter acts, and that the bar for instructions is higher than for merely reading the menu. Reading is permissive; commanding is strict. Hold that distinction; it is the spine of Section 13's interview answers and the reason mutations and queries get different default postures.

Note

The "one waiter, one door" image explains the single most asked GraphQL-security question: "If everything goes through one endpoint, how do you secure individual fields?" Answer: you don't secure the door — you make the waiter (resolvers + directives) enforce policy per line of the order.

4. Real-World Analogy — The Office Building vs. The Open-Plan Library

A REST API is an office building. Each room (route) has a door with a badge reader. Want the finance room? Badge in at the finance door. Security is physical and per-room; the building's architecture is the access-control list.

A GraphQL API is an open-plan library where you fill out a single request form and a librarian fetches a stack of materials for you in one trip. There are no walls between sections, so you cannot put a badge reader on a room — there are no rooms. Instead:

  • The front desk (context builder) checks your membership card once — that's authentication, the Auth0 JWT.
  • The librarian (resolvers/directives) reads your form item by item and applies the rules: public shelves for anyone, the rare-books cage only for researchers, your own borrowing history only for you.
  • Restricted items can be silently omitted from the stack (return null) or refused out loud (return an error) — a deliberate design choice we examine in Section 9.

The analogy also explains the N+1 cost of fine-grained auth (Section 10): if checking each form line requires the librarian to walk to a back office and phone HR ("is this person really a researcher?"), a form with 100 lines triggers 100 phone calls. The fix is to phone HR once when you check the membership card and write the answer on a sticky note (the principal in context) the librarian can glance at for free.

Note

Why the analogy matters for interviews: when asked "how is GraphQL auth different?" the strongest answer is structural, not syntactic — REST's architecture enforces access (rooms with doors); GraphQL's architecture is a single open space, so access control must be data-driven and pushed into resolution.

5. Internal Working — How Apollo Builds Context and Resolves Fields

To secure GraphQL correctly you must understand the execution machinery, because authorization hooks into specific phases. A GraphQL request passes through these stages:

  1. HTTP receive. The server receives a POST with a JSON body { query, variables, operationName } and HTTP headers including Authorization: Bearer <token>.
  2. Context construction. Before any resolver runs, Apollo invokes your context function once per request. This is the single, perfect place to authenticate: read the header, verify the JWT against Auth0's JWKS, and return a context object containing the principal. If the token is missing or invalid you have a choice — throw here (reject the whole request) or set user = null and let resolvers decide (recommended, because public fields should still work for anonymous callers).
  3. Parse. The query string is lexed and parsed into an Abstract Syntax Tree (AST). Syntax errors are rejected here, before any auth or business logic.
  4. Validate. The AST is validated against the schema (do the requested fields exist? are types correct?). Custom validation rules can run here — e.g. query-depth and complexity limits, which are themselves a security control (Section 10).
  5. Execute. Apollo walks the AST top-down, calling a resolver for every requested field. Each resolver receives four arguments: (parent, args, contextValue, info). contextValue is the object your context function returned — the same instance is shared by every resolver in this request, which is exactly why the principal belongs there.

The four resolver arguments — the load-bearing one is context

ArgumentWhat it isRole in auth
parentResult of the parent field's resolver (e.g. the User object when resolving User.ssn)Holds the owning record — used for ownership checks (is parent.id === context.user.sub?)
argsArguments passed to the field ({ id: "5" })Identifies the target resource for the policy decision
contextPer-request shared object from your context functionCarries the authenticated principal — the heart of GraphQL auth
infoAST + execution metadata (field name, path, schema)Used by directives/plugins to read field-level config and the selection set

How a schema directive actually intercepts a field

A directive like @hasPermission(permission: "read:reports") is not magic. At server startup you transform the schema: you walk every field, look for the directive in info/the field's AST, and if present you wrap the original resolver in a new function that runs the check first, then calls the original. This is the same decorator pattern you would use in any language. The directive is just declarative sugar over "wrap this resolver with a guard." Understanding this demystifies the whole feature: a directive is a compile-time resolver wrapper.

Key

The context function runs once per request, before resolution, and its return value is handed to every resolver as the third argument. That single fact is the entire architecture: authenticate in context, authorize in resolvers/directives that read context.user.

6. Code Walkthrough — From JWT Verification to a Populated Principal

We build the spine piece by piece using Node.js with Apollo Server 4 (the current major line in 2026). Alternatives are noted in Section 7. First, the JWT verifier. We never hardcode a secret: Auth0 signs access tokens with RS256 (asymmetric), so we fetch the public signing keys from the tenant's JWKS endpoint and cache them.

// auth.js — verify an Auth0 access token (RS256) using the tenant JWKS
import { jwtVerify, createRemoteJWKSet } from 'jose';

// Auth0 publishes rotating public keys here. createRemoteJWKSet
// caches them in memory and refreshes on key rotation automatically.
const JWKS = createRemoteJWKSet(
  new URL(`https://${process.env.AUTH0_DOMAIN}/.well-known/jwks.json`)
);

export async function verifyToken(token) {
  // jwtVerify checks: signature (against JWKS), exp/nbf, iss, aud.
  const { payload } = await jwtVerify(token, JWKS, {
    issuer:   `https://${process.env.AUTH0_DOMAIN}/`,   // must match `iss`
    audience: process.env.AUTH0_AUDIENCE,               // your API identifier
    // algorithms intentionally pinned — never accept "none" or HS256 here:
    algorithms: ['RS256'],
  });
  return payload; // { sub, scope, permissions, ... }
}

Why each guard matters: the audience check ensures the token was minted for your API and not some other Auth0 application in the same tenant; the issuer check binds it to your tenant; pinning algorithms to RS256 defeats the classic "alg:none" and "HS256 with the public key as secret" attacks. Skipping any of these is a real, exploited vulnerability — not theory.

Next, turn the verified payload into a principal and place it on the context.

// principal.js — shape the raw JWT payload into something resolvers like
export function toPrincipal(payload) {
  if (!payload) return null;
  // Auth0 puts API permissions in `permissions` when RBAC is enabled,
  // and OAuth scopes in the space-delimited `scope` string.
  const scopes = (payload.scope || '').split(' ').filter(Boolean);
  return {
    sub: payload.sub,                         // stable user id, e.g. auth0|abc
    scopes,
    permissions: payload.permissions || [],   // e.g. ["read:reports"]
    // helpers the resolvers/directives will call:
    has(perm)  { return this.permissions.includes(perm); },
    hasScope(s){ return this.scopes.includes(s); },
    isAdmin()  { return this.permissions.includes('admin:all'); },
  };
}

Finally, the context function that ties them together. Note the deliberate choice: a missing/invalid token does not throw — it yields user: null, so public fields still work and resolvers decide what requires login.

// context.js
import { verifyToken } from './auth.js';
import { toPrincipal } from './principal.js';

export async function buildContext({ req }) {
  const header = req.headers.authorization || '';
  const token  = header.startsWith('Bearer ') ? header.slice(7) : null;

  let user = null;
  if (token) {
    try {
      const payload = await verifyToken(token);
      user = toPrincipal(payload);
    } catch (err) {
      // Invalid token (expired, wrong aud, bad signature) → stay anonymous.
      // Do NOT leak the reason to the client; log it server-side.
      console.warn('Token rejected:', err.code || err.message);
    }
  }
  return { user };   // <-- handed to EVERY resolver as the 3rd argument
}
Warn

Do not return the raw JWT payload as your principal. Map it to a small, intentional shape. Leaking the entire token into context tempts resolvers to trust arbitrary claims, and couples your business logic to Auth0's exact claim layout — which makes provider migration painful and auditing harder.

7. Practical Implementation — Operation, Type, and Field Authorization

Now we enforce the three depths. We will show both styles — imperative checks in resolvers (explicit, easy to debug) and a declarative custom directive (DRY, self-documenting in the schema). Production systems usually combine them.

7.1 The schema (with directive definitions)

# schema.graphql
# Declare custom directives so the schema is the source of truth for policy.
directive @auth on FIELD_DEFINITION | OBJECT
directive @hasPermission(permission: String!) on FIELD_DEFINITION

type Query {
  publicStats: Stats                                   # anonymous OK
  me: User @auth                                       # any logged-in user
  users: [User!]! @hasPermission(permission: "read:users")  # admin-ish
  report(id: ID!): Report @hasPermission(permission: "read:reports")
}

type Mutation {
  updateProfile(name: String!): User @auth
  deleteUser(id: ID!): Boolean @hasPermission(permission: "delete:users")
}

type User {
  id: ID!
  email: String! @auth          # only logged-in callers see emails
  ssn: String @hasPermission(permission: "read:pii")  # field-level PII guard
}

type Report { id: ID! title: String! body: String! }
type Stats  { totalUsers: Int! }

7.2 Imperative resolver checks (the explicit style)

// Small reusable guards — these throw the right GraphQL errors.
import { GraphQLError } from 'graphql';

function requireUser(ctx) {
  if (!ctx.user) {
    throw new GraphQLError('Not authenticated', {
      extensions: { code: 'UNAUTHENTICATED', http: { status: 401 } },
    });
  }
  return ctx.user;
}
function requirePermission(ctx, perm) {
  const user = requireUser(ctx);
  if (!user.has(perm)) {
    throw new GraphQLError('Forbidden', {
      extensions: { code: 'FORBIDDEN', http: { status: 403 } },
    });
  }
  return user;
}

export const resolvers = {
  Query: {
    publicStats: () => ({ totalUsers: 42 }),         // no guard: public
    me: (_p, _a, ctx) => getUser(requireUser(ctx).sub),
    users: (_p, _a, ctx) => { requirePermission(ctx, 'read:users'); return listUsers(); },
    report: (_p, { id }, ctx) => {
      requirePermission(ctx, 'read:reports');
      return getReport(id);
    },
  },
  Mutation: {
    deleteUser: (_p, { id }, ctx) => {
      requirePermission(ctx, 'delete:users');
      return removeUser(id);
    },
  },
  User: {
    // FIELD-level ownership check: you see your own ssn; admins see all.
    ssn: (parent, _a, ctx) => {
      const user = requireUser(ctx);
      if (user.sub !== parent.id && !user.isAdmin()) {
        throw new GraphQLError('Forbidden', { extensions: { code: 'FORBIDDEN' } });
      }
      return parent.ssn;
    },
  },
};

7.3 The declarative custom directive (the DRY style)

This is the centerpiece the chapter promised: a real @hasPermission directive implemented as a schema transform that wraps resolvers.

// directives.js — implement @auth and @hasPermission via schema mapping
import { mapSchema, getDirective, MapperKind } from '@graphql-tools/utils';
import { defaultFieldResolver, GraphQLError } from 'graphql';

export function authDirectiveTransformer(schema) {
  return mapSchema(schema, {
    [MapperKind.OBJECT_FIELD]: (fieldConfig) => {
      const authDir = getDirective(schema, fieldConfig, 'auth')?.[0];
      const permDir = getDirective(schema, fieldConfig, 'hasPermission')?.[0];
      if (!authDir && !permDir) return fieldConfig;          // no guard, leave it

      const original = fieldConfig.resolve || defaultFieldResolver;
      fieldConfig.resolve = async (parent, args, ctx, info) => {
        if (!ctx.user) {
          throw new GraphQLError('Not authenticated', {
            extensions: { code: 'UNAUTHENTICATED' } });
        }
        if (permDir && !ctx.user.has(permDir.permission)) {
          throw new GraphQLError('Forbidden', {
            extensions: { code: 'FORBIDDEN' } });
        }
        return original(parent, args, ctx, info);   // delegate to real resolver
      };
      return fieldConfig;
    },
  });
}

7.4 Wiring it all into Apollo Server 4

// server.js
import { ApolloServer } from '@apollo/server';
import { startStandaloneServer } from '@apollo/server/standalone';
import { makeExecutableSchema } from '@graphql-tools/schema';
import { readFileSync } from 'node:fs';
import { resolvers } from './resolvers.js';
import { authDirectiveTransformer } from './directives.js';
import { buildContext } from './context.js';

let schema = makeExecutableSchema({
  typeDefs: readFileSync('./schema.graphql', 'utf8'),
  resolvers,
});
schema = authDirectiveTransformer(schema);   // apply directive wrappers

const server = new ApolloServer({ schema });

const { url } = await startStandaloneServer(server, {
  listen: { port: 4000 },
  context: buildContext,                      // runs per request (Section 6)

8. Production Architecture — Where Auth Lives at Scale

A single Apollo process is fine for a tutorial. In production you usually face a federated graph or a graph behind a gateway, and you must decide where token validation and policy enforcement live.

                  ┌──────────────────────────────────────┐
   Client ──JWT──▶│  API Gateway / Apollo Router         │
                  │  • validate Auth0 JWT once (RS256)   │
                  │  • inject claims as signed headers   │
                  │  • depth/complexity limits           │
                  └───────────────┬──────────────────────┘
                                  │  trusted internal headers
                                  │  (x-user-sub, x-permissions)
            ┌─────────────────────┼─────────────────────┐
            ▼                     ▼                     ▼
     ┌────────────┐       ┌────────────┐        ┌────────────┐
     │ Users      │       │ Billing    │        │ Reports    │
     │ subgraph   │       │ subgraph   │        │ subgraph   │
     │ field auth │       │ field auth │        │ field auth │
     └────────────┘       └────────────┘        └────────────┘
       Each subgraph re-checks fine-grained authZ on its own fields.

Two architectural rules earn their keep:

  • Validate the JWT once, at the edge (gateway/router), then propagate verified claims to subgraphs as signed/trusted internal headers. Re-verifying the full JWT at every subgraph wastes CPU and JWKS round-trips. But — and this is critical — subgraphs must trust only the gateway (network isolation / mTLS), otherwise a caller could forge those headers directly.
  • Authorize fine-grained access at the subgraph that owns the data. The gateway knows who you are; only the Billing subgraph knows whether this invoice is yours. Coarse, declarative checks (role/scope present?) can live at the gateway via Apollo Router's @authenticated and @requiresScopes; ownership checks must live with the data.

For RBAC, enable it in the Auth0 dashboard (API → RBAC Settings → "Add Permissions in the Access Token") so the permissions claim arrives populated. Keep permission strings stable and resource-oriented (read:reports, delete:users) — they become a public contract between Auth0 and your graph.

Tip

Cache the JWKS aggressively (the jose remote key set does this for you), but allow refresh on key rotation. A cold JWKS fetch on every request adds latency and a hard dependency on Auth0's availability to your hot path.

Throw vs. null: the philosophical security choice

When a caller requests a forbidden field, you can throw a ForbiddenError (loud — the whole field errors, partial data returns for the rest) or return null (quiet — the field is simply empty). Throwing is honest and debuggable; returning null avoids confirming the field even exists, reducing information disclosure. Choose deliberately per field: for existence-sensitive data (does this user even have an SSN on file?) prefer null; for clear policy boundaries prefer an explicit FORBIDDEN error so clients can react correctly.

Danger

The #1 GraphQL breach pattern is BOLA: authentication passes (the JWT is valid) but the resolver never checks ownership, so any logged-in user can read any record by guessing IDs. A valid token is not authorization. Always compare the target resource's owner against context.user.sub.

10. Performance Considerations — Auth Without N+1

Fine-grained authorization can quietly destroy performance because it runs per field, per row. A query returning 500 users, each with an authorized ssn field, runs the guard 500 times. If each guard hits the database or calls Auth0, you have built an N+1 catastrophe.

  • Authenticate once, authorize from memory. The principal (permissions, scopes, roles) is decoded from the JWT in the context function — a single operation. Every subsequent permission check is an in-memory array lookup, not a network call. This is the entire reason the principal lives in context.
  • Batch ownership lookups with DataLoader. When ownership checks need data ("is report 999 owned by this user?"), use a per-request DataLoader to coalesce the lookups into one batched query, deduplicated and cached for the request's lifetime.
  • Push authorization into the data query. The cheapest field-level check is the one you never make: filter at the database (WHERE owner_id = $sub) so unauthorized rows never enter the resolver. This converts authorization into a query predicate.
  • Bound the work before it starts. Query depth and complexity limits cap how many resolvers (and thus how many auth checks) a single request can trigger — a performance and security control.
  • Cache JWKS. Asymmetric verification is fast (microseconds), but fetching keys is a network call; cache it (Section 8).
// DataLoader keeps ownership checks O(1 batched query) per request.
import DataLoader from 'dataloader';
function makeLoaders() {
  return {
    reportOwner: new DataLoader(async (ids) => {
      const rows = await db.reports.findOwners(ids);  // ONE query for all ids
      const map = new Map(rows.map(r => [r.id, r.owner_id]));
      return ids.map(id => map.get(id) ?? null);
    }),
  };
}
// build a fresh loader set per request inside buildContext:
//   return { user, loaders: makeLoaders() };
Key

The performance secret of GraphQL auth: do the expensive work (token verification) once in context; make every per-field check a cheap in-memory comparison; batch any unavoidable DB ownership lookups with DataLoader.

11. Common Mistakes

  1. Guarding only the gateway, not the graph. Putting auth middleware in front of /graphql and assuming you're done. It checks authentication, not field-level authorization.
  2. Confusing authentication with authorization. "The JWT is valid" only proves identity. BOLA happens when you stop there.
  3. Trusting client-supplied IDs without ownership checks. report(id) with no owner comparison is an IDOR by construction.
  4. Verifying tokens without pinning the algorithm or checking aud/iss. Opens algorithm-confusion and cross-API token reuse.
  5. Throwing on missing token in context. Breaks legitimately public fields; set user = null and let resolvers decide.
  6. Leaking the raw JWT payload as the principal. Couples business logic to Auth0's claim layout and invites trusting arbitrary claims.
  7. Per-field DB/Auth0 calls for authorization. N+1 by design; authorize from the in-memory principal.
  8. Leaving introspection and verbose errors on in production. Hands attackers the schema map and internal hints.
  9. Treating queries and mutations identically. Mutations change state and deserve stricter, default-deny posture.
  10. Putting permission logic in the client. Clients can hide a button, never enforce a rule. The server is the only authority.
Warn

Mistakes #1, #2, and #3 are the same root cause expressed three ways: assuming the perimeter is enough. In GraphQL the perimeter only authenticates — authorization must reach every field.

12. Best Practices

  • Authenticate once in context, authorize everywhere in resolution. One verification, many cheap checks.
  • Default-deny mutations. Every state-changing operation requires an explicit permission; reads may be more permissive.
  • Make the schema the policy source of truth. Declarative @auth/@hasPermission directives put access rules where reviewers can see them.
  • Layer coarse + fine checks. Operation/type directives for "has permission?"; resolver logic for "owns this row?".
  • Pin RS256 and validate aud/iss/exp. Non-negotiable JWT hygiene.
  • Centralize guard helpers. requireUser/requirePermission avoid copy-paste drift.
  • Filter at the data layer when possible. The unauthorized row that never loads is the most secure row.
  • Disable introspection and mask errors in prod; add depth/complexity/rate limits.
  • Use stable, resource-oriented permission strings (read:reports) defined in Auth0 RBAC.
  • Test authorization, not just authentication. Write tests that confirm a valid-but-unauthorized token is rejected per field.

13. Interview Questions (with Model Answers)

Q1. Why can't you secure a GraphQL API the way you secure REST?

Model answer: REST exposes many endpoints; the resource and action are knowable from the URL and HTTP verb before business logic runs, so route middleware can decide allow/deny. GraphQL has one endpoint and one verb; what data is touched is only knowable after parsing the query and walking resolvers. Authentication still happens once at the edge (validate the JWT), but authorization must move into the resolution layer — at the operation, type, and field level — because a single query can span many resources.

Q2. Where do you put the authenticated user, and why there?

Model answer: In the per-request context object. Apollo runs the context function once before resolution and passes its return value to every resolver as the third argument. Verifying the JWT there means one verification per request, and every resolver gets the principal for free as an in-memory object — avoiding per-field network calls.

Q3. What is BOLA and how does it manifest in GraphQL?

Model answer: Broken Object-Level Authorization: the caller is authenticated but the resolver never checks that they own the requested object, so node(id) or report(id) lets anyone read others' data by guessing IDs. Fix: compare the resource's owner (from parent/a loader) against context.user.sub, or filter by owner in the data query.

Q4. How do you implement field-level authorization without an N+1 problem?

Model answer: Decode permissions once from the JWT into context; per-field checks become in-memory array lookups. For ownership checks that need data, batch with DataLoader so all checks in a request collapse into one query; better still, push the predicate into the SQL/data query so unauthorized rows never load.

Q5. How should mutations be treated differently from queries?

Model answer: Mutations change state, so they default-deny and require explicit, often higher-privilege permissions; they should also be idempotent/validated and audited. Queries are reads and can be more permissive, often gated only at sensitive fields. Treating them identically either over-restricts reads or under-protects writes.

Q6. What is a schema directive and how does @hasPermission work internally?

Model answer: A directive is declarative metadata on schema elements. @hasPermission is implemented as a schema transform that, at startup, wraps each annotated field's resolver in a guard that checks context.user for the required permission before delegating to the original resolver. It's the decorator pattern applied to resolvers.

Q7. How do you validate an Auth0 access token, and which checks are mandatory?

Model answer: Fetch the tenant JWKS, verify the RS256 signature, and check iss (your tenant), aud (your API identifier), and exp/nbf. Pin the algorithm to RS256 to defeat alg-confusion. Cache JWKS for performance.

Tip

In senior interviews, anchor every answer to the structural insight: "one endpoint means authorization can't live at the perimeter." It signals you understand the model, not just the syntax.

14. Certification Tips

  • RS256 vs HS256: Auth0 APIs sign access tokens with RS256 by default; the certification expects you to verify via JWKS, not a shared secret.
  • RBAC switches: Know that "Enable RBAC" and "Add Permissions in the Access Token" (API settings) are what populate the permissions claim. Exam questions probe why permissions is empty — answer: those toggles are off.
  • Scopes vs permissions: Scopes (scope claim) are what the client requested and was granted; permissions are what the user actually has via RBAC. Both can gate access; know the difference.
  • Audience matters: A token without your API's audience is an ID token or for another API — reject it. This is a frequent distractor.
  • Token vs session: APIs (including GraphQL) use bearer access tokens; web apps use sessions. Don't mix them up.
  • Custom claims namespacing: Non-standard claims added via Actions must be namespaced (a URL prefix) or Auth0 strips them — relevant if you push roles/permissions through an Action.

19. Cheat Sheet

  GRAPHQL + AUTH0 — QUICK REFERENCE
  ─────────────────────────────────────────────────────────
  AUTHENTICATE (once, in context):
    header → Bearer token → jwtVerify(token, JWKS, {iss,aud})
    pin algorithms: ['RS256']   |   cache JWKS
    success → context.user = { sub, permissions, scopes }
    failure → context.user = null   (do NOT throw here)

  AUTHORIZE (in resolution):
    OP-level    @hasPermission("read:reports") on Query/Mutation
    TYPE-level  @auth on an OBJECT or its key fields
    FIELD-level resolver checks parent.owner === user.sub

  GUARD LADDER (every field):
    authenticated? → has permission? → owns the resource?

  MUTATIONS: default-deny + explicit permission + audit
  QUERIES:   permissive, lock down sensitive fields only

  ERRORS:
    UNAUTHENTICATED (no/invalid token)  → 401-equivalent
    FORBIDDEN       (valid but not allowed) → 403-equivalent
    mask details in prod; log server-side

  PERF: verify once · check in-memory · DataLoader · filter in DB
  HARDEN: disable introspection · depth/complexity limits · rate limit
  AUTH0: enable RBAC + "Add Permissions in Access Token"

20. Key Takeaways

  • AuthN is unchanged; AuthZ moves inward. Validating an Auth0 JWT is identical to REST; the difference is that authorization must live in the resolution layer, not at the perimeter.
  • One endpoint, one waiter. A single query can reach many resources, so you guard the graph (operation, type, field), not the door.
  • The principal lives in context. Verify the token once per request; every resolver reads the principal for free.
  • Three rungs on every field: authenticated? → authorized (coarse permission)? → owns the resource (fine ownership)?
  • Directives are resolver wrappers. @auth/@hasPermission are declarative sugar over the decorator pattern; combine them with imperative ownership checks.
  • Mutations default-deny; queries default-permissive. Writes change state and earn stricter posture and auditing.
  • BOLA is the cardinal sin. A valid token is not authorization — always compare the resource owner to context.user.sub.
  • Pin RS256, validate iss/aud/exp, cache JWKS, disable introspection, and bound query depth/complexity.
  • Performance: verify once, check in memory, batch with DataLoader, filter in the database.
Key

If you remember one sentence from this chapter: in GraphQL you authenticate at the edge and authorize inside the graph — operation, type, and field — because the single endpoint means the perimeter can prove who you are but never what each line of your query is allowed to touch.
