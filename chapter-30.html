Chapter 30 — Interview Preparation

You have spent twenty-nine chapters building a real mental model of identity: how OAuth 2.0 delegates access, how OpenID Connect layers identity on top of it, how a JWT is signed and verified, how Auth0 stitches it all together with Actions, Organizations, and the Management API. An interview is a different skill. It is not "do you know the answer" — it is "can you reason out loud, from first principles, under mild pressure, and convince a senior engineer that you would not blow up their production auth on a Friday night." This chapter turns your knowledge into interview performance. We will drill conceptual Q&A, scenario questions, system-design whiteboards (design SSO; design auth for microservices), security deep-dives, and live debugging — each answered the way a strong candidate answers: define the term, state the trade-off, name the failure mode, then give the concrete Auth0 mechanism. We close with a full mock-interview script you can rehearse against a friend or a mirror.

1. Theory — What an Interview Actually Measures

Before drilling questions, understand the thing being scored. An identity/auth interview is rarely a memory test. The interviewer is sampling four dimensions, and every question is a probe into one of them:

SignalWhat it meansHow they probe it
Conceptual depthDo you understand why a mechanism exists, not just its name?"Why does OAuth even have an authorization code step?"
Trade-off reasoningCan you pick between two valid options and justify it?"Local JWT validation vs. token introspection — which and why?"
Security instinctDo you reach for the safe default and spot the foot-gun?"Where do you store the access token in a browser?"
Operational maturityHave you actually run this in production?"A token validates locally but the API still 401s — debug it."

The single biggest differentiator between a junior and a senior answer is the trade-off sentence. A junior says "use PKCE." A senior says "use Authorization Code with PKCE for any public client — SPA, mobile, native — because a public client cannot keep a secret, so PKCE substitutes a per-request, dynamically generated proof (the code verifier) for the static client secret, which closes the authorization-code-interception attack." Same recommendation, vastly more signal.

The first-principles chain you must own cold

Almost every conceptual question reduces to one chain. Memorize the chain, not the answers:

  1. Authentication (AuthN) = proving who you are. Output: an identity (the id_token in OIDC).
  2. Authorization (AuthZ) = deciding what you may do. Output: a grant (the access_token in OAuth).
  3. OAuth 2.0 = a delegation framework. It lets a user grant an app limited access to an API without sharing their password. It says nothing about identity.
  4. OpenID Connect (OIDC) = a thin identity layer on top of OAuth 2.0. It standardizes the id_token (a JWT) and the /userinfo endpoint, so "log in with X" becomes interoperable.
  5. JWT = the container format for those tokens: a signed, base64url-encoded, self-describing claim set. It is not encryption; it is a tamper-evident envelope.
  6. Session = the persistence of an authenticated state over time — a cookie at the IdP (SSO session) and/or at your app (app session).
Key

If you can fluently explain why OAuth alone is not authentication ("OAuth gives you a valet key to an API; it never promises the holder is the user"), you have already passed the bar most candidates fail. OIDC exists precisely because people misused OAuth for login and got it subtly wrong.

2. Story-Based Explanation — Two Candidates, One Question

The interviewer asks the same question to two candidates: "How does login with Auth0 work?"

Priya (junior signal) says: "You add the Auth0 SDK, call loginWithRedirect(), the user types their password, and then you get a token you put in the header." Accurate-ish, but it's a list of API calls. It shows she has used a quickstart. It does not show she understands the protocol, so the interviewer cannot trust her with a novel problem.

Sam (senior signal) says: "It's an OIDC Authorization Code flow with PKCE. My SPA redirects the browser to Auth0's /authorize endpoint with a generated code challenge. Auth0 authenticates the user — that establishes an SSO session as a cookie on the Auth0 domain — and redirects back to my callback with a short-lived, single-use authorization code. My app then POSTs that code plus the original code verifier to /oauth/token. Auth0 checks the verifier matches the challenge, and returns an id_token (who the user is) and an access_token (what they can call). I validate the ID token's signature against Auth0's JWKS, then send the access token as a Bearer header to my API, which validates it independently. The reason the code is exchanged server-side-style rather than returned directly is to keep the actual tokens out of the browser URL and history."

Same product, same SDK. But Sam named the flow, the endpoints, the security reason for each step, and the validation responsibilities. That is the gap this chapter closes. The trick is not knowing more — it's narrating the why at every hop.

Tip

When you don't know an exact detail, narrate your reasoning anyway: "I'd expect Auth0 to rotate the refresh token here, because reuse detection requires a one-time-use token — let me reason about what happens if it didn't." Interviewers reward visible thinking over confident silence.

4. Real-World Analogy — The Hotel

Map every confusing token concept onto a hotel, and the vocabulary stops being abstract:

The killer follow-up: "Why does the door not phone the desk every time?" Answer: performance and decoupling. The hologram (signature) lets the door decide locally in microseconds; phoning the desk (introspection) is only worth it when instant revocation matters more than latency. That single analogy lets you reason about JWT vs. opaque tokens, local validation vs. introspection, and access-token lifetime all at once.

5. Internal Working — What Happens Beneath the SDK

Interviewers love to peel back the SDK. Be ready to explain each layer.

5.1 Anatomy of a JWT

A JWT is three base64url segments joined by dots: header.payload.signature. It is signed, not encrypted — anyone can read the payload, but no one can alter it without breaking the signature.

eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6ImFiYzEyMyJ9   ← header
.eyJzdWIiOiJhdXRoMHwxMjMiLCJhdWQiOiJodHRwczovL2FwaSIsImV4cCI6MTcwMH0   ← payload
.SflKxwRJ...signature...                                     ← signature

HEADER  { "alg":"RS256", "typ":"JWT", "kid":"abc123" }   // which key signed it
PAYLOAD { "iss":"https://tenant.auth0.com/",             // issuer
          "sub":"auth0|123",                              // subject (user id)
          "aud":"https://api.example.com",                // audience (your API)
          "exp":1700000000, "iat":1699996400,             // expiry / issued-at
          "scope":"read:orders write:orders",
          "azp":"client_id..." }
SIGNATURE = RS256( base64url(header) + "." + base64url(payload), privateKey )

5.2 How an API verifies a token (the exact checklist)

This is the most testable internal in the whole chapter. A correct verifier does all of these — skipping any one is a security bug:

  1. Parse the header, read kid (key ID).
  2. Fetch the public key from the issuer's JWKS endpoint https://tenant.auth0.com/.well-known/jwks.json matching that kid (cache it!).
  3. Verify the signature with that key using the algorithm in alg — but pin the expected algorithm (RS256) to defeat alg:none and HS/RS confusion attacks.
  4. Check exp (not expired) and optionally nbf/iat with small clock skew.
  5. Check iss equals your exact issuer URL.
  6. Check aud contains your API's identifier — this stops a token minted for App B being replayed at API A.
  7. Check scope/permissions for the specific operation.

5.3 Why RS256 over HS256

HS256 is symmetric: the same secret signs and verifies, so every service that verifies could also forge tokens. RS256 is asymmetric: Auth0 holds the private key (signs), and every API holds only the public key (verifies). A leaked verifier key cannot mint tokens. For any multi-service architecture, RS256 is the default. HS/RS confusion is the classic exploit: an attacker re-signs a token with HS256 using your public key as the HMAC secret; a naive library that trusts the header's alg accepts it. Defense: explicitly require RS256.

Danger

Never let the token's own alg header choose the verification algorithm. Always pass the expected algorithm to your JWT library. "Trusting the header" is the root of both alg:none and HS/RS confusion attacks — a guaranteed follow-up in any security round.

6. Code Walkthrough — The Snippets You'll Be Asked to Write

You may be asked to "write a middleware that validates an Auth0 token" on a shared editor. Have these memorized in at least one stack. Comments are the narration the interviewer wants to hear.

Node.js / Express — resource server validating an access token

const { auth, requiredScopes } = require('express-oauth2-jwt-bearer');

// Validates: RS256 signature via JWKS, exp, iss, aud — in one middleware.
const checkJwt = auth({
  audience: 'https://api.example.com',          // MUST match token aud
  issuerBaseURL: 'https://tenant.auth0.com/',   // MUST match token iss
  tokenSigningAlg: 'RS256',                      // pin algorithm — no alg:none
});

app.get('/orders',
  checkJwt,                                      // 1) authenticate the token
  requiredScopes('read:orders'),                // 2) authorize the operation
  (req, res) => {
    const userId = req.auth.payload.sub;         // trustworthy: signature-verified
    res.json({ orders: getOrdersFor(userId) });
  });

Java Spring Boot — resource server (Spring Security)

// application.yml
// spring.security.oauth2.resourceserver.jwt:
//   issuer-uri: https://tenant.auth0.com/
//   audiences: https://api.example.com

@Configuration
@EnableMethodSecurity
public class SecurityConfig {
  @Bean
  SecurityFilterChain filter(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a
          .requestMatchers("/public").permitAll()
          .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt());  // validates sig+iss+aud+exp via JWKS
    return http.build();
  }
}

@RestController
class OrderController {
  @GetMapping("/orders")
  @PreAuthorize("hasAuthority('SCOPE_read:orders')")  // scope-based authz
  List<Order> list(@AuthenticationPrincipal Jwt jwt) {
    return service.forUser(jwt.getSubject());          // sub = Auth0 user id
  }
}

FastAPI — verifying the JWT manually (shows you know the internals)

import jwt                       # PyJWT
from jwt import PyJWKClient
from fastapi import Depends, HTTPException, Header

ISSUER  = "https://tenant.auth0.com/"
AUDIENCE = "https://api.example.com"
jwks = PyJWKClient(f"{ISSUER}.well-known/jwks.json")   # caches keys

def verify(authorization: str = Header(...)):
    token = authorization.removeprefix("Bearer ").strip()
    key = jwks.get_signing_key_from_jwt(token).key      # match by kid
    try:
        return jwt.decode(token, key,
                          algorithms=["RS256"],          # pin algorithm
                          audience=AUDIENCE, issuer=ISSUER)  # check aud + iss
    except jwt.PyJWTError:
        raise HTTPException(401, "invalid token")

@app.get("/orders")
def orders(claims: dict = Depends(verify)):
    return {"user": claims["sub"]}

7. Practical Implementation — A 5-Minute Preparation Drill

Knowing answers is not the same as retrieving them under pressure. Build the recall with this repeatable drill, run daily for two weeks before an interview:

  1. The 60-second flow. Out loud, with no notes, narrate Authorization Code + PKCE end to end. Time yourself. Repeat until smooth.
  2. The whiteboard sprint. Draw diagram 3.3 (microservices auth) from memory in under 2 minutes, narrating each box.
  3. The trade-off table. For five pairs — JWT vs opaque, localStorage vs httpOnly cookie, RS256 vs HS256, access vs refresh token, RBAC vs ABAC — say the one-sentence "use X when Y because Z."
  4. The debug script. Pick one failure (401 with a valid-looking token) and recite the diagnostic ladder (audience → issuer → algorithm → clock skew → scopes → JWKS cache).
  5. The STAR story. Have one real (or course-project) story: "I integrated Auth0 into X, hit problem Y, fixed it by Z, learned W."

The goal is automaticity: the structures should fall out of your mouth so your conscious attention is free for the novel twist the interviewer adds.

8. Production Architecture — The Two Design Questions You Must Nail

8.1 "Design Single Sign-On for our suite of products"

Structure your answer in this order: requirements → protocol choice → session model → logout → edge cases.

  • Clarify first. "How many apps? Same company or third parties? Web only or mobile too? Do you need enterprise federation (SAML/OIDC to customer IdPs)?" Asking this is itself a strong signal.
  • Protocol. Use OIDC with Auth0 as the central IdP. Each app is a separate OIDC client. The shared SSO session lives as a cookie on the Auth0 tenant domain.
  • Session model. First login authenticates and sets the IdP cookie. Subsequent apps do a silent /authorize (prompt=none); because the IdP cookie is valid, the user is bounced back with a code, no password prompt. Each app then mints its own app session.
  • Logout. Distinguish app logout (kill local session) from Single Logout (kill the IdP session via Auth0's /v2/logout and propagate via OIDC back-channel logout / session-management to sibling apps).
  • Enterprise twist. For B2B, add Organizations + Connections so each customer brings their own IdP; Auth0 federates upstream and still issues your standard tokens downstream.

8.2 "Design authentication & authorization for a microservices platform"

  • Authenticate at the edge. An API gateway / BFF validates the Bearer JWT once (signature, aud, iss, exp). Internal services trust the edge but still authorize their own resources by scope/permission.
  • Identity propagation. Don't forward the raw user token blindly to every hop; mint a short-lived internal token or pass a signed, scoped identity header. This limits the audience and blast radius.
  • Service-to-service. Use the client credentials grant (M2M) — no user present. Each service is its own Auth0 client with its own scopes.
  • Token strategy. JWT for stateless, low-latency validation; add introspection or a short TTL + revocation list only where instant revocation matters.
  • Authorization model. RBAC for coarse roles; push fine-grained, relationship-based checks (Auth0 FGA / ReBAC) to a dedicated authorization service when ownership graphs get complex.
Key

In any design round, the phrase interviewers wait for is "it depends, and here's the axis it depends on." Name the trade-off axis (latency vs. revocation freshness, simplicity vs. flexibility) and you've shown senior judgment even before picking a side.

9. Security Analysis — The Questions That Separate Seniors

QuestionThe answer that wins
Where do you store tokens in a browser?Best: never expose them — use the BFF pattern (token stays server-side, browser gets an httpOnly Secure SameSite cookie). If the SPA must hold one, keep it in memory, never localStorage (any XSS reads it). Refresh via silent auth or rotating refresh tokens.
Why is the Implicit flow deprecated?It returned tokens in the URL fragment — leaking to history, logs, referrers — and had no client authentication. Authorization Code + PKCE replaced it: the token never appears in the redirect, and PKCE binds the code to the requester.
What is refresh-token rotation / reuse detection?Each refresh issues a new refresh token and invalidates the old one. If an old (already-used) token is presented, Auth0 detects theft and revokes the whole family — turning a stolen token into a self-defeating one.
How do you prevent CSRF in OAuth?The state parameter: a random value sent to /authorize and verified on callback, binding the response to this browser's request. For OIDC also use nonce to bind the ID token to the request.
What's a confused-deputy / audience attack?A token minted for API A replayed against API B. Defense: every API strictly validates aud equals its own identifier.
How do you revoke a stateless JWT?You can't truly revoke a signed JWT before exp. Mitigations: short access-token TTL (5–15 min), refresh-token revocation, a denylist of jti, or switch to introspection for high-risk operations.
Danger

If you ever say "store the JWT in localStorage so it survives refresh," expect an immediate follow-up on XSS. The correct senior reflex is: localStorage is XSS-readable; prefer in-memory + silent refresh, or the BFF pattern with httpOnly cookies.

10. Performance Considerations — Latency the Interviewer Cares About

  • Cache the JWKS. Fetching the public key on every request adds a network round-trip and can rate-limit you. Cache keys by kid and refresh on rotation/miss. This is the single most common performance question.
  • Local JWT validation is microseconds; introspection is a network call. Default to local validation; reserve introspection for revocation-critical paths.
  • Right-size token lifetime. Short access tokens (good for security) mean more refreshes (more traffic). Balance: short access TTL + longer rotating refresh tokens.
  • Keep tokens lean. A bloated token (huge custom claims, full permission lists) inflates every request header and can blow past header-size limits. Put large/volatile data behind a lookup keyed by sub, not in the token.
  • Silent auth uses an iframe / refresh token, not a full redirect. Know that getAccessTokenSilently avoids a page reload but still hits Auth0 when the cached token expires.
   per-request cost:
   local JWT verify  ▏▎ ~50µs (cached JWKS)
   introspection     ▏▔▔▔▔▔▔▔▔▔▔▔▔ ~20–100ms (network)
   choose local unless you need instant revocation

11. Common Mistakes — In the Interview and In the Code

Interview-behavior mistakes

  • Jumping to the SDK call instead of naming the protocol. Lead with the flow and the why.
  • Conflating authentication and authorization. The fastest way to lose senior credibility.
  • Saying "OAuth is for login." OAuth is delegation; OIDC is login. Get this exactly right.
  • Not asking clarifying questions in design rounds. Diving straight into a solution signals juniority.
  • Confident silence when stuck. Narrate your reasoning; partial credit is real.

Technical mistakes interviewers fish for

  • Validating signature but forgetting aud and iss checks.
  • Letting the token's alg header pick the algorithm (alg:none / HS-RS confusion).
  • Storing tokens in localStorage.
  • Using the ID token to call an API — it's for the client; APIs validate the access token.
  • Treating an expired token as a server bug rather than triggering a refresh.
  • Using HS256 across many services (any verifier can forge).
Warn

The ID-token-vs-access-token mix-up is the most common real-world Auth0 bug and a favorite interview trap. ID token = "who is this user" (for your front end). Access token = "what may this caller do" (for your API). Send the access token to APIs.

12. Best Practices — Your Default Recommendations

  • Always use Authorization Code + PKCE for public clients; client credentials for M2M.
  • Always validate signature + iss + aud + exp, and pin the algorithm to RS256.
  • Prefer the BFF pattern for browser apps; otherwise in-memory tokens + silent refresh, never localStorage.
  • Short access-token TTL + rotating refresh tokens with reuse detection.
  • Cache JWKS by kid; refresh on rotation.
  • Use state (CSRF) and nonce (ID-token binding) on every authorize request.
  • Keep tokens lean; enrich claims via Auth0 Actions, not by stuffing the token.
  • Centralize identity (one IdP), distribute authorization (each service owns its checks).
  • In answers, always pair a recommendation with its trade-off and failure mode.

13. Interview Questions — With Model Answers

Conceptual

Q1. What's the difference between authentication and authorization, and which Auth0 token represents each?
Model: Authentication proves who you are (output: OIDC id_token). Authorization decides what you may do (output: OAuth access_token). The ID token is for the client to know the user; the access token is sent to the API as a Bearer credential. Confusing them — e.g., sending the ID token to an API — is a classic bug.

Q2. Why does OAuth need OIDC on top of it for login?
Model: OAuth 2.0 only delegates access to resources; possession of an access token does not prove the holder is the user, nor in a standard way tell you who they are. People hacked login on top of OAuth and got it subtly wrong (e.g., trusting /userinfo-style endpoints insecurely). OIDC standardizes identity: a signed id_token with defined claims (sub, iss, aud, nonce) and a discovery document, making "log in with X" interoperable and verifiable.

Q3. Walk me through verifying a JWT.
Model: Read kid from the header, fetch the matching public key from the issuer's JWKS (cached), verify the signature with a pinned RS256 algorithm, then check exp/nbf with small skew, iss equals my issuer, aud contains my API id, and the required scope. Skipping aud allows cross-API replay; trusting the header's alg allows alg:none.

Scenario

Q4. Your SPA needs to call your API. What flow, where do tokens live, how do you refresh?
Model: Authorization Code + PKCE (SPA is a public client). Tokens in memory (or the BFF pattern with httpOnly cookies). Refresh via silent auth / rotating refresh tokens with reuse detection. Never localStorage.

Q5. A backend cron job must call your API with no user present. How?
Model: Client credentials grant. Register an M2M application in Auth0, grant it the needed API scopes, and have the job exchange client_id/secret for an access token at /oauth/token.

System design

Q6. Design SSO for five internal apps. (See §8.1.) Model skeleton: clarify scope → OIDC with Auth0 as central IdP → shared IdP session cookie + silent prompt=none per app → per-app sessions → single logout via back-channel → Organizations for B2B federation.

Q7. Design auth for microservices. (See §8.2.) Model skeleton: authenticate JWT at the gateway, propagate scoped identity inward, each service authorizes its own resources, client credentials for service-to-service, JWT + short TTL with introspection only where revocation is critical.

Security

Q8. How would you handle logout so a stolen token can't keep working?
Model: Short access-token TTL limits the window; revoke the refresh token (and its rotation family) on logout; for high-risk paths use introspection or a jti denylist; kill the IdP session via /v2/logout and propagate single logout. Acknowledge honestly that a stateless JWT can't be revoked before expiry — that limitation drives the short-TTL design.

Q9. Explain a real attack against JWTs and its defense.
Model: alg:none (strip the signature) and HS/RS confusion (re-sign with HS256 using the public key as the HMAC secret). Both exploit libraries that trust the token's own alg. Defense: always pin the expected algorithm; never derive it from the header.

Debugging

Q10. The token validates in jwt.io but my API returns 401. Walk me through debugging. (See §15 ladder.) Model: Almost always aud mismatch (no audience requested, so you got an opaque/ID token, or the wrong API id), then iss trailing-slash mismatch, then algorithm pinning, then clock skew, then missing scope, then a stale JWKS cache after key rotation.

Tip

End every model answer with one sentence of trade-off or failure mode. It converts a "correct" answer into a "senior" answer.

14. Certification Tips — Mapping Interview Prep to the Auth0 Exam

The Auth0 Certified Developer / Lab exams reward the same fundamentals, but phrased as product features. Bridge your interview knowledge to exam vocabulary:

  • Flows: Know which grant maps to which app type — Regular Web App (Auth Code), SPA (Auth Code + PKCE), Native (Auth Code + PKCE), M2M (Client Credentials). The exam loves "which flow for which client."
  • Tokens: ID token (OIDC, for the client) vs. access token (OAuth, for the API) vs. refresh token (rotation). Audience and issuer validation are exam staples.
  • Customization: Actions (post-login, machine-to-machine) for adding claims, MFA, and gating; the older Rules/Hooks are deprecated — say Actions.
  • Connections: Database, Social, Enterprise (SAML/OIDC), Passwordless. Know Universal Login is the recommended, hosted, customizable login.
  • B2B: Organizations, member roles, organization-specific connections, invitations.
  • Operations: Management API vs. Authentication API; tenants and environments (dev/staging/prod) and how to promote config.
  • Exam strategy: Eliminate answers that violate a security default (localStorage, implicit flow, HS256 across services) — they're almost always wrong.
Note

If a multiple-choice option recommends storing tokens in localStorage, using the implicit flow, or trusting the token's alg header, it is a distractor. The exam, like a good interviewer, scores secure defaults.

15. Hands-On Exercises — The Debugging Ladder

Debugging questions are pure operational signal. Internalize this diagnostic ladder and practice reciting it for each symptom.

Symptom A: valid-looking token, API returns 401

   1. aud      → did you request audience? token aud == API identifier?
   2. iss      → exact match incl. trailing slash (https://t.auth0.com/)?
   3. alg      → API pinned to RS256? token actually RS256?
   4. exp/skew → expired? server clock drift > allowed skew?
   5. scope    → token missing the required permission?
   6. JWKS     → key rotated? cache stale → refetch by kid
   7. token    → are you sending the ACCESS token, not the ID token?

Symptom B: CORS error on the token or API call

CORS is a browser enforcement, not an auth failure. Diagnose: is the request origin in Auth0's Allowed Web Origins / Allowed Origins (CORS)? Does your API return the right Access-Control-Allow-Origin and handle the preflight OPTIONS? A 401 disguised as CORS often means the failed response simply lacks CORS headers — fix the auth, the "CORS error" disappears.

Symptom C: redirect/callback error (callback URL mismatch)

The exact redirect_uri sent to /authorize must be listed in the application's Allowed Callback URLs — character-for-character, including scheme, port, and trailing slash. Also confirm state round-trips (CSRF) and, for OIDC, that nonce matches.

Exercise tasks

  1. Deliberately request a token without an audience, call your API, observe the 401, and explain why (you got an opaque token / wrong aud).
  2. Decode a real token on jwt.io and read off iss, aud, exp, scope aloud.
  3. Rotate your signing key in Auth0 (or simulate) and confirm your JWKS cache refetches.
  4. Trigger a callback-URL-mismatch on purpose and fix it.

17. Mini Project — The Mock Interview Script

Rehearse this end-to-end with a partner. Italics are coaching notes, not spoken.

Interviewer: Tell me how a user logs into a single-page app with Auth0.

You: It's an OIDC Authorization Code flow with PKCE because the SPA is a public client that can't keep a secret. The app generates a code verifier and its SHA-256 challenge, redirects the browser to Auth0's /authorize with the challenge and a state value. Auth0 authenticates the user, which sets the SSO session cookie on the Auth0 domain, and redirects back to my callback with a one-time authorization code. My app POSTs that code plus the original verifier to /oauth/token; Auth0 confirms the verifier hashes to the challenge and returns an ID token and an access token. I validate the ID token against the JWKS and send the access token as a Bearer header to my API. (Named flow, endpoints, why PKCE, what each token is for.)

Interviewer: Why PKCE and not just a client secret?

You: A browser app ships its source to the user, so any embedded secret is public. PKCE replaces the static secret with a per-request dynamic proof: only the client that generated the verifier can redeem the code, which closes the authorization-code-interception attack. (Trade-off + named attack.)

Interviewer: Where do you store the tokens?

You: Ideally I don't expose them to the browser at all — the BFF pattern keeps tokens server-side and gives the browser an httpOnly, Secure, SameSite cookie, so XSS can't read a token and CSRF is mitigated by SameSite plus a token. If the SPA must hold one, in memory only — never localStorage, which any XSS can read — and I refresh via silent auth with rotating refresh tokens. (Safe default first, fallback second, named threats.)

Interviewer: Now the API gets a token but returns 401 even though jwt.io shows it's valid. Debug it.

You: I'd walk the ladder. Most likely the aud: did the SPA request the API's audience? If not, you get a token whose audience isn't my API and validation fails. Next the iss — a missing trailing slash breaks the exact match. Then algorithm pinning, clock skew on exp, a missing scope, and finally a stale JWKS cache after key rotation. And I'd confirm I'm sending the access token, not the ID token. (Systematic, ranked by likelihood.)

Interviewer: How would you do service-to-service calls behind that API?

You: Client credentials grant — no user present. Each service is its own M2M client with least-privilege scopes, exchanging its credentials for a short-lived access token. I authenticate the JWT at the edge once and propagate a scoped internal identity inward rather than forwarding the user's token everywhere, to limit audience and blast radius. (Correct grant + propagation reasoning.)

Interviewer: Last one — how do you revoke access immediately if an account is compromised?

You: Honestly, a stateless JWT can't be un-signed before it expires, so step one is short access-token TTLs — minutes, not days — to bound the window. Then I revoke the refresh token and its whole rotation family so no new tokens can be minted, kill the IdP session, and for the most sensitive endpoints add token introspection or a jti denylist so revocation is enforced in real time at the cost of a lookup. (Names the limitation, then layers mitigations with trade-offs.)

Tip

Notice the pattern in every answer: name it → explain why → state the trade-off or threat. Drill that three-beat rhythm until it's automatic and you'll sound senior on questions you've never seen.

Show answer key
  1. ID token (OIDC) carries identity claims about the user.
  2. The access token — it represents authorization to call the API.
  3. OAuth solves delegated authorization (access); OIDC adds standardized authentication/identity (the ID token).
  4. Authorization Code + PKCE. A SPA ships its code publicly, so any embedded secret is exposed; it's a public client.
  5. The authorization-code-interception attack — only the client that created the verifier can redeem the code.
  6. iss, aud, exp (and the algorithm pin) — issuer match, audience match, not expired, correct/expected algorithm.
  7. To prevent a token minted for another API being replayed against this one (confused-deputy / audience attack).
  8. alg:none and HS/RS confusion attacks (trusting the token's own alg header).
  9. HS256 is symmetric, so every verifier could also forge tokens; RS256 keeps the private signing key only at the IdP, verifiers hold only the public key.
  10. Not in localStorage — it's readable by any XSS. Prefer in-memory or the BFF pattern.
  11. Backend-for-Frontend: tokens stay server-side; the browser gets an httpOnly cookie. Neutralizes token theft via XSS.
  12. CSRF protection: a random value bound to the request and verified on callback.
  13. Binds the ID token to the original request, preventing ID-token replay/injection (OIDC).
  14. It returned tokens in the URL fragment (leaking to history/logs) and lacked client auth; replaced by Auth Code + PKCE.
  15. Client credentials grant.
  16. Each refresh invalidates the prior token; presenting an already-used token signals theft and revokes the whole family.
  17. No — a signed JWT is valid until exp. Use short TTLs, refresh revocation, a jti denylist, or introspection.
  18. Avoids a network round-trip per request and rate limits; refetch on a kid miss or key rotation.
  19. The IdP/SSO session (cookie on the Auth0 domain, shared) authenticates once; each app maintains its own app session.
  20. aud mismatch (often no audience requested) and iss mismatch (trailing-slash); also sending the ID token instead of the access token.
  21. Latency vs. revocation freshness (local is fast but can't see instant revocation; introspection is current but a network call).
  22. The exact redirect_uri must be in Allowed Callback URLs — scheme, host, port, path, trailing slash, character-for-character.

19. Cheat Sheet — One-Glance Recall

  TOKENS        id_token = WHO (OIDC, for client)
                access_token = WHAT (OAuth, for API, Bearer header)
                refresh_token = mint new access tokens (rotate + reuse-detect)

  FLOWS         SPA / mobile / native ........ Auth Code + PKCE
                regular web app .............. Auth Code
                machine-to-machine ........... Client Credentials
                (implicit & password grant ... deprecated)

  VALIDATE JWT  signature(JWKS by kid) + iss + aud + exp + scope
                PIN alg = RS256   (never trust token's alg header)

  STORE TOKENS  best: BFF (httpOnly cookie) > in-memory > NEVER localStorage

  CSRF/REPLAY   state = CSRF on /authorize ; nonce = bind id_token (OIDC)

  REVOCATION    short access TTL + refresh revocation + jti denylist
                (stateless JWT can't be un-signed before exp)

  DEBUG 401     aud → iss(/) → alg → exp/skew → scope → JWKS → wrong token

  DESIGN SSO    central IdP (OIDC) + shared IdP cookie + silent prompt=none

20. Key Takeaways

  • Interviews score reasoning, not recall. The trade-off sentence is what separates junior from senior answers.
  • Own the first-principles chain: AuthN→AuthZ, OAuth(delegation)→OIDC(identity), JWT(container), session(persistence).
  • ID token = who; access token = what. Never send the ID token to an API. This is the most common trap.
  • JWT validation = signature + iss + aud + exp + scope, with the algorithm pinned to RS256. Forgetting aud or trusting the header's alg are the classic bugs.
  • Auth Code + PKCE for public clients; client credentials for M2M. Implicit and password grants are dead.
  • Token storage: BFF > in-memory >> localStorage (XSS-readable).
  • Design SSO = central IdP + shared session + silent auth + single logout. Design microservices auth = authenticate at the edge, authorize per service, M2M between services.
  • Debug 401s with a ladder: aud → iss → alg → exp/skew → scope → JWKS → wrong token.
  • Rehearse out loud. Automaticity in the structures frees your mind for the novel twist — that is what gets the offer.
Key

Every strong answer follows the same three beats: name the mechanism, explain why it exists, state its trade-off or failure mode. Master that rhythm and you can sound senior even on a question you have never seen — which is exactly what an interview is designed to test.
