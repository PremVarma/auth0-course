Chapter 20 — Project 4 — Spring Authorization Server + Auth0

Up to now you have treated Auth0 as the authorization server — the single thing that mints tokens for your whole world. In this project we flip that assumption on its head and build something more sophisticated: your own OAuth 2.1 / OpenID Connect authorization server, on Java 21 with Spring Authorization Server, that issues first-party tokens to your internal clients and federates upstream to Auth0 so your users can still log in with everything Auth0 brings — social, enterprise SSO, MFA, passkeys, Actions. You will learn precisely when running your own AS alongside a managed IdP is the right call (and when it is reckless over-engineering), how token relay through an API gateway keeps every hop verifiable, how dynamic and static client registration actually work, and how to combine a first-party auth server with Auth0 connections so that one user identity flows cleanly from the browser, through your AS, up to Auth0, and back down into your microservices. By the end you will be able to draw the full topology on a whiteboard in an interview and defend every arrow.

1. Theory — First Principles: Why Two Authorization Servers?

An OAuth 2.0 / OpenID Connect Authorization Server (AS) is the component that authenticates a resource owner (your user) and issues tokens — an access token (a bearer credential for calling APIs), an ID token (a signed assertion of who logged in), and optionally a refresh token (a long-lived credential to get new access tokens). Auth0 is, fundamentally, a managed, multi-tenant authorization server. So the obvious question is: if Auth0 is already an AS, why on earth would you build a second one?

The answer comes from separating four responsibilities that beginners tend to collapse into one:

ResponsibilityQuestion it answersWho is best at it
User authenticationIs this human really Jane?Auth0 (social, enterprise, MFA, passkeys, breach detection)
Token issuance & shapeWhat claims/scopes/audiences go in the token, in what format, signed by which key?You — if you have non-negotiable requirements Auth0 cannot fully express
Client governanceWhich apps may request tokens, with which grants and redirect URIs?Either — but your AS can own first-party clients tightly
Consent & policy at issuanceShould this token be issued right now, given device, risk, contracts?Your AS, when policy is too proprietary or fast-changing to externalize

The key insight is that authentication and token issuance are separable. OpenID Connect was deliberately designed so that an AS can itself be a relying party of another AS. This is called federation (also "brokering" or "chaining"). Your Spring Authorization Server can delegate the "is this really Jane?" question upstream to Auth0, receive the proof, and then mint its own tokens for your internal ecosystem. You get Auth0's best-in-class login experience and total control over the tokens your services actually consume.

Key

An authorization server can be a client of another authorization server. "Federating to Auth0" means your Spring AS performs an OIDC login against Auth0 the same way a normal web app would — then it stops being a client and becomes an issuer, signing brand-new tokens for your own clients.

The default position: do NOT build your own AS

Before the seduction of building, internalize the senior-engineer default: you almost never need your own authorization server. Auth0 already issues compliant tokens, runs custom logic via Actions, supports custom claims, organizations, fine-grained authorization, and rotates signing keys for you. Running an AS means owning key management, token revocation, consent storage, client metadata, security patching, and 24/7 availability of the single most attackable component in your stack. Build one only when a concrete, written requirement forces it. Section 11 lists the legitimate triggers.

2. Story-Based Explanation — Northwind's Two-Speed Problem

You are the platform lead at Northwind Logistics. The company has two very different identity worlds glued into one product:

  1. The customer-facing portal. Shippers and drivers log in. They want Google login, "Sign in with Apple," passkeys, and the occasional enterprise SSO when a big freight customer demands SAML. This is classic Auth0 territory and it works beautifully.
  2. The internal machine ecosystem. Forty microservices, a legacy mainframe gateway, and three regional warehouse systems all call each other. They need access tokens with a very specific shape: a custom nw_region claim, an act (actor) claim for delegation, audiences that map to internal service IDs, and — critically — a second signing key that Northwind's security team rotates on a hardware HSM they already own for SOC 2 reasons.

For months the team tried to bend Auth0 into shape #2 with Actions and custom claims. It mostly worked, but two requirements never fit cleanly: the HSM-resident signing key (Auth0 manages its own keys) and an internal-only token exchange grant for service-to-service delegation with tight, contract-bound rules that change weekly and must be auditable inside Northwind's own repo.

The architect's decision: keep Auth0 for human authentication (it is unbeatable there), and stand up a Spring Authorization Server for internal token issuance. When a human logs in, the Spring AS redirects them to Auth0, Auth0 proves who they are, and the Spring AS then mints internal tokens signed by the HSM key with exactly the claims the fleet expects. Machines talk only to the Spring AS. Humans never see it — they see Auth0's polished login. An API gateway sits in front, relaying tokens inward and re-validating at every boundary.

This is the architecture we build in this chapter. Notice the discipline: Auth0 is not replaced — it is federated to. Each system does what it is best at.

Note

Northwind's trigger was concrete: an HSM-resident signing key plus proprietary, fast-changing delegation policy. "We want control" is not a trigger. "Our auditors require keys never leave our HSM" is.

4. Real-World Analogy — The Embassy and the Local Visa Office

Imagine you are a citizen of country A travelling to country B.

  • Auth0 is your home country's passport office. It is exceptionally good at one thing: proving who you are. It checks your biometrics, your history, your MFA. Your passport (the Auth0 ID token) is a globally respected proof of identity.
  • Your Spring Authorization Server is country B's local visa office. Country B does not re-run your biometrics — it trusts your passport. But country B does not let you wander around on a passport alone. It inspects your passport, then issues its own document — a visa (your first-party access token) — stamped with country-B-specific rules: which provinces you may enter (audiences), how long you may stay (expiry), what you may do (scopes), signed with country B's seal (your HSM key).
  • The API gateway is the border checkpoint. Inside country B, nobody looks at your home passport again — every internal checkpoint inspects the visa. If your visa is forged or expired, you are stopped, regardless of how valid your passport is.

This is exactly federation. The passport office (Auth0) handles identity. The visa office (Spring AS) handles authorization within your domain. The two are loosely coupled by trust, not merged. And — crucially — once you are inside, the home passport is irrelevant; only the locally issued visa matters. That is why your services validate your JWKS, never Auth0's.

Note

The analogy also explains token relay: as you pass through successive internal checkpoints (gateway → service → another service), each one re-checks the same visa. The visa is "relayed" inward, not re-issued at every door.

5. Internal Working — What Spring Authorization Server Actually Does

Spring Authorization Server (SAS) is a focused implementation of OAuth 2.1 and OpenID Connect Core 1.0, built on Spring Security. It is not a full IdP product — it has no user database, no login UI of its own beyond what you wire up, no admin console. That minimalism is the point: you compose it from filters. Here is what happens inside, endpoint by endpoint.

The endpoints SAS exposes

EndpointPurposeSpec
/.well-known/openid-configurationDiscovery — tells clients where everything isOIDC Discovery
/oauth2/authorizeAuthorization endpoint — starts the code flowOAuth 2.1
/oauth2/tokenToken endpoint — exchanges code for tokensOAuth 2.1
/oauth2/jwksPublishes public keys so resource servers can verify signaturesJWK Set
/oauth2/introspectOpaque-token lookup for resource serversRFC 7662
/oauth2/revokeRevokes a refresh/access tokenRFC 7009
/connect/registerDynamic Client Registration (optional)RFC 7591
/userinfoReturns claims about the authenticated userOIDC Core

The internal request pipeline

Every request flows through a chain of Spring Security filters. SAS contributes its own filters that the OAuth2AuthorizationServerConfigurer installs. Conceptually:

   incoming HTTP
        |
        v
  [SecurityFilterChain #1: Authorization Server endpoints]
        |  OAuth2AuthorizationEndpointFilter  -> handles /oauth2/authorize
        |  OAuth2TokenEndpointFilter          -> handles /oauth2/token
        |  OidcProviderConfigurationEndpoint  -> /.well-known/...
        |  NimbusJwkSetEndpointFilter         -> /oauth2/jwks
        |        |
        |        |  (if no authenticated principal yet)
        |        v
        |   redirect to /login  ----+
        |                            |
        v                            v
  [SecurityFilterChain #2: default/login]
        |  oauth2Login()  -> federates to Auth0 (the RP filters)
        |        OAuth2LoginAuthenticationFilter
        |        OAuth2AuthorizationRequestRedirectFilter
        |        v
        |   establishes the upstream session via Auth0
        +--> back to chain #1, which now mints YOUR tokens

How a token is actually minted

When the token endpoint runs, SAS builds a JwtEncodingContext and asks an OAuth2TokenCustomizer<JwtEncodingContext> bean to add claims. It then signs using the JWKSource<SecurityContext> you provided (an in-memory RSA key in dev, an HSM-backed key in prod). The federated Auth0 identity is available in the security context as an OidcUser, so your customizer can copy or transform Auth0 claims (email, sub, custom claims from Actions) into your first-party token.

Key

The bridge between the two worlds is one bean: the token customizer. It reads the upstream Auth0 identity (an OidcUser) and writes your downstream claims. This is where federation becomes concrete — Auth0's sub becomes a lookup key into your user store, and your custom claims (nw_region, roles, entitlements) get stamped onto the token your services trust.

6.2 Federating to Auth0 — the client (Relying Party) side

This is the configuration that makes our AS log in against Auth0. It is ordinary spring-security-oauth2-client config — the same you'd write for any web app that uses Auth0.

spring:
  security:
    oauth2:
      client:
        registration:
          auth0:                                   # an upstream IdP registration
            client-id: ${AUTH0_CLIENT_ID}
            client-secret: ${AUTH0_CLIENT_SECRET}
            scope: [openid, profile, email]
            authorization-grant-type: authorization_code
            client-name: Auth0
            # where Auth0 sends the user back INTO our AS:
            redirect-uri: "{baseUrl}/login/oauth2/code/auth0"
        provider:
          auth0:
            issuer-uri: https://YOUR_TENANT.eu.auth0.com/   # trailing slash matters
            user-name-attribute: sub
Warn

The issuer-uri must include the trailing slash for Auth0, and must exactly equal the iss claim Auth0 puts in its tokens. A mismatch causes a silent id_token validation failed at step (h). Spring fetches Auth0's discovery document from {issuer-uri}.well-known/openid-configuration at startup, so the AS must be able to reach Auth0 on boot.

6.3 The two security filter chains

@Configuration
public class SecurityConfig {

  // Chain #1: the OAuth2 Authorization Server endpoints (highest priority)
  @Bean
  @Order(1)
  public SecurityFilterChain authorizationServerChain(HttpSecurity http) throws Exception {
    OAuth2AuthorizationServerConfigurer authServer =
        OAuth2AuthorizationServerConfigurer.authorizationServer();

    http
      .securityMatcher(authServer.getEndpointsMatcher())
      .with(authServer, server -> server.oidc(Customizer.withDefaults())) // enable OIDC
      .authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
      // If the user is NOT yet authenticated at the AS, send them to login,
      // which (chain #2) federates to Auth0:
      .exceptionHandling(e -> e.defaultAuthenticationEntryPointFor(
          new LoginUrlAuthenticationEntryPoint("/oauth2/authorization/auth0"),
          new MediaTypeRequestMatcher(MediaType.TEXT_HTML)))
      // Our AS also accepts Auth0's tokens during the federated callback:
      .oauth2ResourceServer(rs -> rs.jwt(Customizer.withDefaults()));

    return http.build();
  }

  // Chain #2: default chain handling federated login to Auth0
  @Bean
  @Order(2)
  public SecurityFilterChain federationChain(HttpSecurity http) throws Exception {
    http
      .authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
      // THIS line makes our AS a client of Auth0:
      .oauth2Login(Customizer.withDefaults());
    return http.build();
  }
}

Notice the elegant trick: the AS's authentication entry point points at /oauth2/authorization/auth0 — the Spring OAuth2 client entry point. So when a portal app hits /oauth2/authorize and there is no AS session, the user is bounced to Auth0, logs in, comes back, an AS session is created, and the original authorize request resumes and mints our token.

6.4 Registering a first-party client (static)

@Bean
public RegisteredClientRepository registeredClientRepository() {
  RegisteredClient portal = RegisteredClient.withId(UUID.randomUUID().toString())
      .clientId("northwind-portal")
      .clientAuthenticationMethod(ClientAuthenticationMethod.NONE) // public SPA -> PKCE
      .authorizationGrantType(AuthorizationGrantType.AUTHORIZATION_CODE)
      .authorizationGrantType(AuthorizationGrantType.REFRESH_TOKEN)
      .redirectUri("https://portal.northwind.com/callback")
      .scope(OidcScopes.OPENID)
      .scope(OidcScopes.PROFILE)
      .scope("shipments:read")
      .clientSettings(ClientSettings.builder()
          .requireProofKey(true)              // enforce PKCE
          .requireAuthorizationConsent(false) // first-party: no consent screen
          .build())
      .tokenSettings(TokenSettings.builder()
          .accessTokenTimeToLive(Duration.ofMinutes(10))
          .accessTokenFormat(OAuth2TokenFormat.SELF_CONTAINED) // JWT
          .build())
      .build();

  return new InMemoryRegisteredClientRepository(portal);
  // In prod: JdbcRegisteredClientRepository backed by Postgres.
}

6.5 The signing key (JWKS)

@Bean
public JWKSource<SecurityContext> jwkSource() {
  // DEV: generate an RSA key in memory.
  // PROD: load from an HSM / KMS via a PKCS#11 KeyStore; the private
  // key never leaves the hardware.
  RSAKey rsaKey = generateRsa();                 // helper using KeyPairGenerator
  JWKSet jwkSet = new JWKSet(rsaKey);
  return new ImmutableJWKSet<>(jwkSet);
}

@Bean
public AuthorizationServerSettings authorizationServerSettings() {
  return AuthorizationServerSettings.builder()
      .issuer("https://as.northwind.internal")   // OUR issuer, not Auth0's
      .build();
}

6.6 The token customizer — where federation becomes real

@Bean
public OAuth2TokenCustomizer<JwtEncodingContext> tokenCustomizer(UserService users) {
  return context -> {
    if (!context.getTokenType().getValue().equals("access_token")) return;

    // The principal here carries the UPSTREAM Auth0 identity:
    Authentication principal = context.getPrincipal();
    String auth0Sub = principal.getName();                  // e.g. "auth0|abc123"

    // Map Auth0's sub to our internal user + entitlements:
    InternalUser u = users.byExternalId(auth0Sub);

    context.getClaims().claims(claims -> {
      claims.put("nw_region", u.region());                  // custom claim
      claims.put("roles", u.roles());                       // first-party RBAC
      claims.put("entitlements", u.entitlements());
      // Keep a link back to the federated identity for audit:
      claims.put("ext_idp", "auth0");
      claims.put("ext_sub", auth0Sub);
    });
  };
}
Tip

This customizer is the seam between the two authorization servers. Auth0 answered "who is this?" and gave you auth0|abc123. Your AS answers "what may they do here?" and stamps roles, nw_region, and entitlements. Keep authorization data in your token, not Auth0's — it changes faster and is your domain's concern.

7. Practical Implementation — Wiring the Gateway and a Resource Server

7.1 A resource server (microservice) trusting YOUR AS

# shipments-service application.yml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://as.northwind.internal   # OUR AS, never Auth0
          audiences: shipments-api
@Configuration
class ResourceServerConfig {
  @Bean
  SecurityFilterChain api(HttpSecurity http) throws Exception {
    http
      .authorizeHttpRequests(a -> a
        .requestMatchers("/shipments/**").hasAuthority("SCOPE_shipments:read")
        .anyRequest().authenticated())
      .oauth2ResourceServer(rs -> rs.jwt(jwt -> jwt
        .jwtAuthenticationConverter(scopeConverter())));
    return http.build();
  }
}

7.2 Token relay through Spring Cloud Gateway

The gateway sits in front of every service. With the TokenRelay filter it forwards the incoming bearer token to downstream services automatically — and, when configured as an OAuth2 client, it can also refresh tokens.

# api-gateway application.yml
spring:
  cloud:
    gateway:
      default-filters:
        - TokenRelay=         # copy Authorization: Bearer to downstream calls
      routes:
        - id: shipments
          uri: lb://shipments-service
          predicates:
            - Path=/api/shipments/**
          filters:
            - StripPrefix=1
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://as.northwind.internal
// Gateway validates the token at the edge, then relays it inward.
@Bean
SecurityWebFilterChain gatewaySecurity(ServerHttpSecurity http) {
  http
    .authorizeExchange(ex -> ex.anyExchange().authenticated())
    .oauth2ResourceServer(rs -> rs.jwt(Customizer.withDefaults()));
  return http.build();
}

Machines that are not acting for a human use the client-credentials grant directly against your Spring AS — no Auth0 involved, because there is no human to authenticate.

Production essentials:

  • State out of the JVM. Use JdbcRegisteredClientRepository, JdbcOAuth2AuthorizationService, and JdbcOAuth2AuthorizationConsentService so any replica can serve any request. In-memory stores only work for a single node and lose all sessions on restart.
  • HSM/KMS-backed keys. The JWKSource reads a non-exportable private key (AWS KMS, Azure Key Vault, or PKCS#11 HSM). Publish multiple keys in JWKS during rotation so in-flight tokens stay verifiable.
  • Key rotation. Add the new key to JWKS, start signing with it, keep the old public key published until the longest-lived token expires, then drop it. Resource servers cache JWKS — set a sane cache TTL (e.g., 5 min) so rotation propagates.
  • High availability of the AS. It is now a single point of failure for token issuance. Run 3+ replicas behind a load balancer; health-check the token endpoint, not just /health.
  • Auth0 dependency. If Auth0 is down, new human logins fail (but existing valid tokens still work until expiry). Cache JWKS and discovery; set generous timeouts; consider a maintenance fallback page.
  • Observability. Emit an audit event per token issued with client_id, ext_sub, scopes, and audience. Correlate gateway request IDs through to services.
Warn

Putting your own AS in the critical path means you now own its uptime. Auth0's 99.99% SLA does not protect a poorly-run self-hosted AS. Budget for on-call, patching, and DR drills before you commit.

9. Security Analysis

Threats specific to the federated, two-AS design

ThreatVectorMitigation

Refresh-token theftLong-lived credential stolenRotate refresh tokens, detect reuse, bind to client; consider DPoP/sender-constraining.

The cardinal rule

Your microservices must validate tokens from exactly one issuer — yours. The whole security benefit of federation collapses if a service also accepts Auth0-issued tokens directly, because then an attacker who can get any Auth0 token (e.g., from a different app on the same tenant) could call your internal APIs. The boundary is intentional and one-directional.

Danger

Never disable signature validation "to make it work in dev." Never use the same RSA key in dev and prod. Never publish the private key in JWKS — JWKS is public keys only. A single leaked private key lets anyone forge tokens for every service that trusts your AS.

10. Performance Considerations

  • JWT validation is cheap and stateless. Resource servers verify the RSA/EC signature locally using cached JWKS — no network call per request. This is the single biggest performance reason to use self-contained JWTs over opaque tokens + introspection.
  • JWKS caching. Spring's NimbusJwtDecoder caches the key set (default ~5 min). Tune the cache so you avoid a JWKS fetch storm on every cold start, but keep it short enough that key rotation propagates promptly.
  • Federation cost is paid once per session, not per request. The expensive multi-redirect dance with Auth0 happens only at login. After that, the user has an AS session and tokens; subsequent API calls never touch Auth0.
  • Token size. Stuffing large entitlements arrays into the access token bloats every request header. If entitlements are big, put a reference (e.g., a version stamp) in the token and resolve details server-side, or use a fine-grained-authz service.
  • Database hot path. With JDBC stores, the authorization-code lookup and refresh-token rotation hit the DB. Index authorization_code_value and refresh-token columns; use connection pooling (HikariCP).
  • Signing throughput. RSA signing is more CPU-heavy than EC. For high token-issuance volume, prefer ES256 (EC P-256) keys — smaller signatures, faster signing — if your resource servers support it.
  • Stateless scaling. Because validation is local, you can scale resource servers horizontally without coordination. The AS itself scales by sharing the JDBC store across replicas.
Tip

Measure the login latency budget separately from the API latency budget. Federation adds 3–5 redirects (hundreds of ms) but only at session start. If interviewers ask "doesn't federation make every call slow?" the correct answer is no — it is a one-time login cost.

11. Common Mistakes

  1. Building an AS when Auth0 already suffices. The #1 mistake. Legitimate triggers: HSM-resident signing keys you must own, proprietary issuance policy that must live in your repo, air-gapped/sovereign deployments, an internal token-exchange grant Auth0 cannot model, or contractual data-residency for token state. "We want control" and "to learn" are not production triggers.
  2. Trailing-slash mismatch on Auth0 issuer-uri. Causes silent id_token validation failure. The configured value must equal Auth0's iss exactly.
  3. Resource servers trusting two issuers. Accepting both Auth0 and your AS tokens defeats the security boundary (see §9).
  4. In-memory stores in production. Sessions and authorizations vanish on restart and don't share across replicas. Use JDBC stores.
  5. Publishing the private key in JWKS. JWKS is public keys only. A horrifying but real mistake when serializing the full JWKSet incorrectly — always use the public-only view.
  6. No PKCE on public clients. SPAs and mobile must use PKCE; never use a client secret in a browser.
  7. Long-lived access tokens. Self-contained JWTs cannot be revoked before expiry. Keep them short (5–15 min) and rely on refresh tokens.
  8. Forgetting the audience. Without per-service aud, any token works at any service — confused-deputy risk.
  9. Copying ALL Auth0 claims into your token blindly. Map deliberately. Your token's authorization claims are your concern, not whatever Auth0 happened to include.
  10. Skipping JWKS reachability at boot. If the AS can't reach Auth0's discovery endpoint on startup, federation config fails. Plan for network egress and timeouts.

12. Best Practices

  • Default to Auth0-only. Add your own AS only against a written requirement. Document the trigger in an ADR.
  • One issuer per token domain. Humans authenticate at Auth0; internal tokens are issued by your AS; services trust your AS alone.
  • PKCE everywhere for public clients; confidential clients use client_secret_basic or, better, private_key_jwt / mTLS.
  • Short access tokens, rotating refresh tokens with reuse detection.
  • Per-service audiences and least-privilege scopes.
  • HSM/KMS keys with documented rotation runbooks; overlap old and new public keys in JWKS during rotation.
  • JDBC-backed stores for clients, authorizations, and consents; back them up.
  • Validate the upstream leg fully: Auth0 iss, aud, nonce, exp, signature, plus PKCE and state.
  • Map federated identity deliberately in the token customizer; keep an audit link (ext_idp, ext_sub).
  • Treat the gateway as a policy edge: validate at the edge, relay inward, re-validate at each service.
  • Use Auth0 for what it is great at — Actions for risk/MFA, Organizations for B2B, connections for social/enterprise — and let those flow through into your federation.

13. Interview Questions (with Model Answers)

Q1. When would you run your own authorization server alongside Auth0?

Model answer: Only against a concrete requirement Auth0 cannot meet: HSM-resident signing keys you must own for compliance; proprietary, fast-changing token-issuance policy that must live in your codebase and audit trail; air-gapped or data-sovereign deployments; a custom grant (e.g., internal token exchange/delegation) Auth0 doesn't model; or contractual control over where token state is stored. Otherwise, Auth0 alone is the right, lower-risk choice. I'd federate to Auth0 for human authentication and mint first-party tokens for internal services.

Q2. What does "federating to Auth0" actually mean technically?

Model answer: My Spring AS acts as an OIDC Relying Party to Auth0: it runs the authorization-code-plus-PKCE flow against Auth0's /authorize and /oauth/token, validates the returned id_token (signature, iss, aud, nonce, exp), and establishes a local session. Then it switches roles to OIDC Provider and issues its own tokens to my clients. Two issuers, two keys, one trust link.

Q3. Why must internal services trust only your AS, not Auth0?

Model answer: To preserve the trust boundary. If a service accepted Auth0-issued tokens, anyone holding any token from that Auth0 tenant could call internal APIs, bypassing my authorization layer and custom claims. The federation is intentionally one-directional: Auth0 → my AS → services.

Q4. How does token relay work and why re-validate at each hop?

Model answer: The gateway forwards the same bearer token downstream (Spring Cloud Gateway's TokenRelay filter). Each service re-validates locally using cached JWKS and checks scopes/audience. Re-validation is defense-in-depth: a compromised gateway or internal mis-route can't grant access without a valid token for that audience.

Q5. Static vs dynamic client registration — when each?

Model answer: Static (RegisteredClientRepository, code or JDBC) for a known set of first-party clients — tighter governance, reviewed in PRs. Dynamic (RFC 7591 /connect/register) when third parties or many tenants must self-register; gate it behind an initial access token and strict policy, because open DCR is an attack surface.

Q6. Doesn't adding an AS make every API call slower?

Model answer: No. The federation redirects happen once per login. After that, tokens are JWTs validated locally by resource servers with cached JWKS — no per-request network calls to either Auth0 or the AS.

Q7. How do you rotate signing keys without breaking live tokens?

Model answer: Add the new key to JWKS, start signing with it, keep the old public key published until all tokens signed with it expire, then remove it. Resource servers cache JWKS with a short TTL so they pick up the new key. Key IDs (kid) in the header let verifiers select the right key.

Q8. Where do custom claims like roles belong — Auth0 or your AS?

Model answer: Authorization claims that are my domain's concern (roles, entitlements, region) belong in my token, added by the token customizer. Auth0 owns authentication facts (verified email, MFA level). Mapping Auth0's sub to my user record in the customizer is the seam.

14. Certification Tips

  • Know the role-switching vocabulary. The exam tests whether you understand that one component can be both an OIDC Provider and an OIDC Relying Party. Auth0 calls upstream-IdP brokering "Connections" / "Enterprise federation"; in OAuth terms your AS is an RP to Auth0.
  • Auth0 connection types. Be able to name database, social, enterprise (SAML, OIDC, WS-Fed), and passwordless connections — and that an upstream OIDC connection is how Auth0 itself federates outward.
  • Issuer + audience validation is a recurring exam theme. Memorize: validate iss, aud, exp, signature, and nonce for ID tokens.
  • PKCE is mandatory for public clients in OAuth 2.1 — exam-favorite fact.
  • Grant types: authorization_code (+PKCE) for users, client_credentials for machines, refresh_token for renewal. Implicit and ROPC are deprecated.
  • JWKS contains public keys only. Expect a trap answer offering "private key endpoint."
  • Self-contained vs reference (opaque) tokens and the trade-off: revocation vs validation cost.

15. Hands-On Exercises

  1. Boot the AS. Create the Spring Boot project with the two starters from §6.1. Add the two filter chains and an in-memory client. Hit http://localhost:9000/.well-known/openid-configuration and confirm your issuer appears.
  2. Federate to Auth0. Create a Regular Web Application in Auth0, set its callback to http://localhost:9000/login/oauth2/code/auth0, and fill in the YAML from §6.2. Trigger an authorize request and verify you are redirected to Auth0's login.
  3. Inspect both tokens. Decode the Auth0 id_token and your AS access token at jwt.io (or locally). Compare iss, aud, kid. Confirm they differ.
  4. Add a custom claim. Implement the token customizer from §6.6 to add nw_region. Re-issue and confirm the claim appears in your token but not Auth0's.
  5. Stand up a resource server (§7.1) and call it with your access token. Then call it with the Auth0 token directly and confirm it is rejected (wrong issuer) — this proves the boundary.
  6. Client credentials. Register the billing daemon (§7.3) and obtain a token with curl using grant_type=client_credentials. No browser, no Auth0.

17. Mini Project — "Delegation Exchange"

Implement an internal token exchange (RFC 8693-style) scenario that justifies your own AS — the kind of thing that pushes teams off Auth0-only.

Scenario: The orders-service, acting on behalf of a logged-in user, must call fulfillment-service but with a narrowed token that carries an act (actor) claim proving "orders-service acting for user X" and a reduced scope. Auth0 can do token exchange, but Northwind needs the actor-chain logic and contract checks in its own repo.

  1. Configure the Spring AS to accept a custom exchange request from orders-service (confidential client) presenting the user's original access token.
  2. In a custom token endpoint / customizer, validate the incoming token, then mint a new downstream token with: reduced scope (fulfillment:write only), audience fulfillment-api, an act claim { "sub": "orders-service" }, and the original user as the primary sub.
  3. Have fulfillment-service log the actor chain for audit and enforce the reduced scope.
  4. Write a short note: why this is cleaner in your own AS than stretching Auth0, and the security checks the exchange must perform (don't widen scope, verify the original token, bind audience).
Note

This mini project is the canonical "we genuinely needed our own AS" story. Delegation with proprietary, evolving actor-chain rules is one of the cleanest legitimate triggers.

19. Cheat Sheet

  ROLES
    Spring AS  ==  OIDC Provider (to your clients)  +  OIDC RP (to Auth0)
    Auth0      ==  upstream IdP (authentication, social/SSO/MFA)
    Gateway    ==  edge validation + TokenRelay
    Services   ==  resource servers, validate YOUR JWKS only

  ISSUERS / KEYS (never mix)
    Auth0 token : iss=https://TENANT.auth0.com/   key=Auth0   aud=app
    Your  token : iss=https://as.northwind.internal key=HSM   aud=service-id

  STARTERS
    spring-boot-starter-oauth2-authorization-server   (be a Provider)
    spring-boot-starter-oauth2-client                  (be an RP to Auth0)
    spring-boot-starter-oauth2-resource-server         (validate tokens)

  KEY BEANS
    RegisteredClientRepository       -> who may request tokens
    JWKSource<SecurityContext>        -> signing keys (HSM in prod)
    AuthorizationServerSettings      -> .issuer(...)
    OAuth2TokenCustomizer            -> map Auth0 sub -> your claims

  ENDPOINTS (Spring AS)
    /.well-known/openid-configuration   /oauth2/authorize
    /oauth2/token   /oauth2/jwks   /oauth2/introspect   /oauth2/revoke
    /userinfo   /connect/register (DCR)

  FEDERATION CALLBACK
    /login/oauth2/code/auth0   (Auth0 sends user back here)

  GRANTS
    authorization_code + PKCE  -> humans (public clients)
    client_credentials         -> machines (no Auth0)
    refresh_token              -> renewal

  GOLDEN RULES
    1. Default to Auth0-only; build an AS only on a written trigger.
    2. Services trust ONE issuer (yours) + check aud.
    3. JWKS = public keys only; rotate via overlap.
    4. PKCE for public; short access tokens; rotate refresh tokens.
    5. Map identity in the token customizer; keep ext_idp/ext_sub for audit.

20. Key Takeaways

  • An AS can be a client of another AS. Federation = your Spring AS logs in against Auth0, then issues its own tokens. Auth0 answers "who?"; your AS answers "what may they do here?".
  • The default is Auth0-only. Running your own AS is justified only by concrete triggers — HSM keys, proprietary issuance/delegation policy, sovereignty, or a custom grant. "Control" alone is not a trigger.
  • Two issuers, two keys, one trust link. Your microservices validate your JWKS exclusively. Mixing issuers destroys the boundary.
  • The token customizer is the seam. It maps Auth0's sub to your user and stamps your authorization claims.
  • Token relay re-validates at every hop. The gateway forwards the bearer token; each service re-checks signature, audience, and scope.
  • Federation cost is per-login, not per-request. JWT validation is local and cheap.
  • Production means ownership. JDBC stores, HSM/KMS keys with rotation runbooks, HA replicas, and the acceptance that you now own token-issuance uptime.
  • Static client registration for first-party governance; dynamic only when self-service is required — and always gated.
Key

If you remember one sentence: federate to Auth0 for identity, issue your own tokens for authorization, and let your services trust only you.
