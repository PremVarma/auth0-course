Chapter 17 — Project 1 — React + Auth0

Everything you have learned about OAuth 2.0, OpenID Connect, PKCE, tokens, and scopes now becomes a real, working application. In this chapter you build a complete React + TypeScript single-page app (SPA) that logs users in through Auth0, protects routes, reads ID-token claims, calls a protected API with an access token, refreshes tokens silently in the background, and renders different UI for different roles. We do it from first principles: every line of configuration has a reason rooted in browser security, and we never wave our hands and say "just trust the SDK."

1. Theory — First Principles of an Auth0 SPA

A Single-Page Application is JavaScript that runs entirely in the user's browser. There is no trusted server-side session you can hide a secret in — every byte of your React bundle is downloadable and readable by anyone. This single fact drives every design decision in this chapter.

Because the browser is a public client (it cannot keep a secret), the SPA must authenticate using the OAuth 2.0 Authorization Code flow with PKCE (Proof Key for Code Exchange). Let us re-derive why from the ground up:

  • Why not put a password field in React? Then your app touches the raw credentials, becomes a phishing target, and must implement MFA, breached-password detection, brute-force protection, and social login itself. Auth0's Universal Login page handles all of that on its own domain.
  • Why not the old Implicit flow? Implicit returned tokens in the URL fragment (#access_token=...), exposing them to browser history, referrer headers, and any script on the page. It is deprecated. PKCE returns a one-time authorization code instead, which is useless without the code verifier your app generated.
  • Why PKCE specifically? A confidential client (a backend) proves its identity with a client secret. A SPA has no secret. PKCE substitutes a dynamically generated secret per login: the app sends a hashed code_challenge up front, then the raw code_verifier when redeeming the code. An attacker who steals the code from the redirect cannot redeem it without the verifier, which never left the browser tab.

Three artifacts come out of a successful login, and you must keep their purposes distinct:

TokenAudiencePurposeYour app should…
ID token (JWT)Your SPA (client_id)Tells the app who the user is (claims: sub, name, email).Read claims for UI. Never send it to an API.
Access tokenYour API (audience)Authorizes calls to your backend. Opaque or JWT.Attach in Authorization: Bearer. Never inspect it for auth decisions in the SPA.
Refresh tokenAuth0 token endpointObtains new access tokens without a full redirect.Let the SDK store/rotate it. Never log it.
Key

The ID token answers "who is logged in?" and is for your front end. The access token answers "what may this request do?" and is for your back end. Confusing the two is the single most common Auth0 mistake — and a guaranteed interview red flag.

The @auth0/auth0-react SDK wraps @auth0/auth0-spa-js, which implements the PKCE dance, token caching, and silent renewal. React only adds an idiomatic layer: a context Provider and a useAuth0() hook so any component can read auth state.

2. Story-Based Explanation

Imagine Maya, a frontend engineer, building "Dashly," an analytics dashboard. On day one she hard-codes a login form and stores the password in localStorage. Two weeks later, security review flags it: an XSS bug would leak every user's password, and there's no MFA. Maya rips it out.

She signs up for Auth0 and registers Dashly as a Single Page Application. Auth0 hands her a domain and a client_id — no secret, because it knows SPAs can't keep one. She installs @auth0/auth0-react, wraps her <App/> in an <Auth0Provider>, and adds a "Log in" button that calls loginWithRedirect().

The first time she clicks it, the browser sails away to dashly.us.auth0.com. She types her credentials on Auth0's page — Dashly never sees them. Auth0 redirects back to http://localhost:3000 with ?code=...&state=... in the URL. The SDK silently swaps that code (plus its secret verifier) for tokens, scrubs the URL clean, and now useAuth0() reports isAuthenticated: true with Maya's profile.

Next, Dashly needs to call its own /api/metrics endpoint. Maya adds an audience to the provider so Auth0 issues an access token for that API. Her data hook calls getAccessTokenSilently(), attaches the token as a Bearer header, and the Express API validates it. When the token expires an hour later, the SDK quietly fetches a new one using the rotating refresh token — Maya never sees a flicker. Finally, she gives admins an extra "Settings" tab by reading a roles claim she added via an Auth0 Action. Same app, two experiences. That is the whole arc of this chapter.

4. Real-World Analogy

Think of a large conference at a hotel.

  • Universal Login = the registration desk in the lobby. You don't prove your identity to each individual session room; you do it once, at a single trusted counter, run by professionals (Auth0).
  • ID token = your name badge. It says who you are — "Maya, Acme Corp." The session rooms (your React components) glance at it to greet you. You would never hand your badge to a bank teller as payment; likewise you never send an ID token to an API.
  • Access token = a drink ticket for the bar (your API). It's scoped ("one beer"), time-limited (expires tonight), and the bartender only checks the ticket — not your whole life story.
  • Refresh token = the wristband that lets you go back to the desk for more drink tickets without re-registering. Rotation means each time you trade it, you get a fresh wristband and the old one is cut off — so a stolen wristband from yesterday is worthless.
  • PKCE code_verifier = a secret handshake you invent at the door. The bouncer (Auth0) only completes your entry if your handshake matches the hash you whispered earlier. An eavesdropper who overheard your entry code still can't get in.

5. Internal Working — What the SDK Actually Does

When you render <Auth0Provider>, the SDK creates an Auth0Client instance and, on mount, runs checkSession(). Here is the machinery underneath the friendly hook:

  1. Bootstrapping on page load. The provider checks the URL for code and state. If present (we just came back from Auth0), it calls handleRedirectCallback(): validates state against what it stored (CSRF protection), POSTs the code + verifier to /oauth/token, validates the ID token's signature and nonce, and caches the tokens.
  2. Token cache. By default tokens live in an in-memory cache, scoped by audience + scope. This is the safest store because a closed tab wipes it and JavaScript on other origins can't read it. Optionally you set cacheLocation="localstorage" to survive refreshes — at the cost of XSS exposure (covered in §9).
  3. Silent authentication. To restore a session after a hard refresh (in-memory cache lost), the SDK can call checkSession(), which opens a hidden iframe to /authorize?prompt=none. If the Auth0 session cookie is still valid, Auth0 returns a code without UI. However, third-party-cookie blocking (Safari ITP, Chrome) breaks iframe silent auth — which is exactly why refresh token rotation is the modern default for SPAs.
  4. Refresh token rotation. When you enable useRefreshTokens and request the offline_access scope, Auth0 issues a refresh token. Each use returns a new refresh token and invalidates the old one. If a stolen token is replayed, Auth0 detects "automatic reuse" and revokes the whole token family — breach containment by design.
  5. React state propagation. The provider holds {isLoading, isAuthenticated, user, error} in React context. Every state change triggers a re-render of consumers via useAuth0(). isLoading is true until the bootstrap finishes — your UI must wait for it before deciding "logged out."
Note

The ID token's nonce ties the token to this login attempt (replay protection), while state ties the redirect to this browser tab (CSRF protection). The SDK generates and verifies both for you — but knowing they exist is a certification favorite.

Warn

A SPA's client_id and domain are not secrets — they ship in the bundle. The security boundary is the Allowed Callback URLs list in the Auth0 dashboard, not hiding the client id. Still keep env vars out of git so you don't mix up dev/prod tenants.

6.2 Strongly-typed config helper

// src/auth/authConfig.ts
export interface AuthConfig {
  domain: string;
  clientId: string;
  audience: string;
  apiBaseUrl: string;
}

function required(name: string, value: string | undefined): string {
  if (!value) throw new Error(`Missing env var: ${name}`);
  return value;
}

export const authConfig: AuthConfig = {
  domain:    required("VITE_AUTH0_DOMAIN",    import.meta.env.VITE_AUTH0_DOMAIN),
  clientId:  required("VITE_AUTH0_CLIENT_ID", import.meta.env.VITE_AUTH0_CLIENT_ID),
  audience:  required("VITE_AUTH0_AUDIENCE",  import.meta.env.VITE_AUTH0_AUDIENCE),
  apiBaseUrl: required("VITE_API_BASE_URL",   import.meta.env.VITE_API_BASE_URL),
};

Why fail loudly? A missing audience silently downgrades your access token to an opaque, non-JWT token your API can't validate. Throwing at startup turns a baffling 401 into an obvious config error.

6.3 The Auth0Provider wrapper

// src/auth/Auth0ProviderWithNavigate.tsx
import { Auth0Provider, AppState } from "@auth0/auth0-react";
import { PropsWithChildren } from "react";
import { useNavigate } from "react-router-dom";
import { authConfig } from "./authConfig";

export function Auth0ProviderWithNavigate({ children }: PropsWithChildren) {
  const navigate = useNavigate();

  // After Auth0 redirects back, restore the route the user was on.
  const onRedirectCallback = (appState?: AppState) => {
    navigate(appState?.returnTo ?? window.location.pathname, { replace: true });
  };

  return (
    <Auth0Provider
      domain={authConfig.domain}
      clientId={authConfig.clientId}
      authorizationParams={{
        redirect_uri: window.location.origin,
        audience: authConfig.audience,
        scope: "openid profile email offline_access",
      }}
      useRefreshTokens={true}
      useRefreshTokensFallback={true}
      cacheLocation="memory"
      onRedirectCallback={onRedirectCallback}
    >
      {children}
    </Auth0Provider>
  );
}

Line by line:

  • redirect_uri: window.location.origin — where Auth0 sends the code back. Must exactly match an entry in Allowed Callback URLs.
  • audience — REQUIRED to get an access token for your API. Omit it and you only get an ID token + a Management-API-shaped token you shouldn't use.
  • scope: "openid profile email" — OIDC scopes that populate ID-token claims. offline_access requests a refresh token.
  • useRefreshTokens — opt into rotating refresh tokens instead of iframe silent auth (resilient to third-party-cookie blocking).
  • useRefreshTokensFallback — if a refresh fails, fall back to a one-time iframe attempt.
  • cacheLocation="memory" — the secure default; tokens never touch localStorage.
  • onRedirectCallback — co-locates Auth0's redirect with React Router so you land back on the page you started from, not always /.

The Provider must sit inside the Router (so useNavigate works) but outside your routes:

// src/main.tsx
import React from "react";
import ReactDOM from "react-dom/client";
import { BrowserRouter } from "react-router-dom";
import { Auth0ProviderWithNavigate } from "./auth/Auth0ProviderWithNavigate";
import App from "./App";

ReactDOM.createRoot(document.getElementById("root")!).render(
  <React.StrictMode>
    <BrowserRouter>
      <Auth0ProviderWithNavigate>
        <App />
      </Auth0ProviderWithNavigate>
    </BrowserRouter>
  </React.StrictMode>
);

7. Practical Implementation

7.1 Login & logout buttons

// src/components/AuthButtons.tsx
import { useAuth0 } from "@auth0/auth0-react";

export function LoginButton() {
  const { loginWithRedirect } = useAuth0();
  return (
    <button
      onClick={() =>
        loginWithRedirect({
          appState: { returnTo: window.location.pathname },
        })
      }
    >
      Log In
    </button>
  );
}

export function LogoutButton() {
  const { logout } = useAuth0();
  return (
    <button
      onClick={() =>
        logout({ logoutParams: { returnTo: window.location.origin } })
      }
    >
      Log Out
    </button>
  );
}

loginWithRedirect sends the browser to Universal Login. logout clears the local token cache and hits Auth0's /v2/logout to end the SSO session, then returns to returnTo (must be in Allowed Logout URLs). Without the round-trip to Auth0, clicking "Log in" again would silently re-authenticate from the lingering session cookie — surprising users who thought they logged out.

7.2 A loading-aware navbar

// src/components/NavBar.tsx
import { useAuth0 } from "@auth0/auth0-react";
import { Link } from "react-router-dom";
import { LoginButton, LogoutButton } from "./AuthButtons";
import { useRoles } from "../auth/useRoles";

export function NavBar() {
  const { isAuthenticated, isLoading } = useAuth0();
  const { hasRole } = useRoles();

  if (isLoading) return <nav>Loading…</nav>;

  return (
    <nav>
      <Link to="/">Home</Link>
      {isAuthenticated && <Link to="/profile">Profile</Link>}
      {isAuthenticated && <Link to="/dashboard">Dashboard</Link>}
      {hasRole("admin") && <Link to="/admin">Admin</Link>}
      {isAuthenticated ? <LogoutButton /> : <LoginButton />}
    </nav>
  );
}

7.3 Protected routes

The SDK ships withAuthenticationRequired, an HOC that redirects to login if the user isn't authenticated. We wrap it so the user returns to the intended page after login:

// src/auth/AuthGuard.tsx
import { withAuthenticationRequired } from "@auth0/auth0-react";
import { ComponentType } from "react";

const Loading = () => <div>Redirecting to login…</div>;

export function protectComponent(Component: ComponentType): ComponentType {
  return withAuthenticationRequired(Component, {
    onRedirecting: () => <Loading />,
    // Preserve the deep link so we come back here post-login.
    returnTo: () => window.location.pathname + window.location.search,
  });
}

// src/App.tsx
import { Routes, Route } from "react-router-dom";
import { NavBar } from "./components/NavBar";
import { Home } from "./pages/Home";
import { Profile } from "./pages/Profile";
import { Dashboard } from "./pages/Dashboard";
import { Admin } from "./pages/Admin";
import { protectComponent } from "./auth/AuthGuard";
import { RoleGuard } from "./auth/RoleGuard";

const ProtectedProfile   = protectComponent(Profile);
const ProtectedDashboard = protectComponent(Dashboard);

export default function App() {
  return (
    <>
      <NavBar />
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/profile"   element={<ProtectedProfile />} />
        <Route path="/dashboard" element={<ProtectedDashboard />} />
        <Route path="/admin"
               element={<RoleGuard role="admin"><Admin /></RoleGuard>} />
      </Routes>

}
Danger

A protected route is UX, not security. Hiding the /admin link or redirecting unauthenticated users does NOT protect data — the bundle and any embedded logic are fully visible. Real authorization happens at the API, which validates the access token and its scopes/permissions on every request. The front-end guard just avoids showing broken pages.

7.4 Reading the user profile / ID-token claims

// src/pages/Profile.tsx
import { useAuth0 } from "@auth0/auth0-react";

export function Profile() {
  const { user, isLoading } = useAuth0();
  if (isLoading) return <p>Loading…</p>;
  if (!user) return null;

  return (
    <section>
      <img src={user.picture} alt={user.name} width={72} />
      <h2>{user.name}</h2>
      <p>Email: {user.email} {user.email_verified ? "✓" : "(unverified)"}</p>
      <p>Subject (sub): <code>{user.sub}</code></p>
      <pre>{JSON.stringify(user, null, 2)}</pre>
    </section>
  );
}

The user object is the decoded ID-token claim set. user.sub (e.g. auth0|abc123) is the stable, unique user identifier — use it as the primary key, never the email (emails change). Custom claims must be namespaced (a full URI) to survive OIDC's reserved-claim rules; we add them with an Action next.

7.5 Adding roles via an Auth0 Action

Roles assigned in Auth0's RBAC aren't in tokens by default. Add a Login / Post-Login Action in the dashboard:

// Auth0 Post-Login Action
exports.onExecutePostLogin = async (event, api) => {
  const namespace = "https://dashly.app";
  const roles = event.authorization?.roles ?? [];
  // Put roles in BOTH tokens: ID token for UI, access token for the API.
  api.idToken.setCustomClaim(`${namespace}/roles`, roles);
  api.accessToken.setCustomClaim(`${namespace}/roles`, roles);
};

7.6 A typed roles hook

// src/auth/useRoles.ts
import { useAuth0, User } from "@auth0/auth0-react";

const ROLES_CLAIM = "https://dashly.app/roles";

interface UserWithRoles extends User {
  [ROLES_CLAIM]?: string[];
}

export function useRoles() {
  const { user } = useAuth0<UserWithRoles>();
  const roles: string[] = user?.[ROLES_CLAIM] ?? [];
  const hasRole = (role: string) => roles.includes(role);
  return { roles, hasRole };
}

7.7 The role guard component

// src/auth/RoleGuard.tsx
import { PropsWithChildren } from "react";
import { useRoles } from "./useRoles";
import { protectComponent } from "./AuthGuard";

function RoleGuardInner({ role, children }: PropsWithChildren<{ role: string }>) {
  const { hasRole } = useRoles();
  if (!hasRole(role)) return <p>403 — You do not have access to this page.</p>;
  return <>{children}</>;
}

// First require authentication, THEN check the role.
export const RoleGuard = protectComponent(RoleGuardInner) as typeof RoleGuardInner;

7.8 Calling a protected API (the access-token hook)

// src/api/useApi.ts
import { useAuth0 } from "@auth0/auth0-react";
import { useCallback } from "react";
import { authConfig } from "../auth/authConfig";

export function useApi() {
  const { getAccessTokenSilently } = useAuth0();

  const callApi = useCallback(
    async <T,>(path: string, init: RequestInit = {}): Promise<T> => {
      // SDK returns cached token if valid, else refreshes silently.
      const token = await getAccessTokenSilently({
        authorizationParams: { audience: authConfig.audience },
      });

      const res = await fetch(`${authConfig.apiBaseUrl}${path}`, {
        ...init,
        headers: {
          ...(init.headers ?? {}),
          Authorization: `Bearer ${token}`,
          "Content-Type": "application/json",
        },
      });

      if (res.status === 401) throw new Error("Unauthorized — token rejected by API");
      if (res.status === 403) throw new Error("Forbidden — missing required scope/permission");
      if (!res.ok) throw new Error(`API error ${res.status}`);
      return (await res.json()) as T;
    },
    [getAccessTokenSilently]
  );

  return { callApi };
}

// src/pages/Dashboard.tsx
import { useEffect, useState } from "react";
import { useApi } from "../api/useApi";

interface Metrics { activeUsers: number; revenue: number; }

export function Dashboard() {
  const { callApi } = useApi();
  const [data, setData]   = useState<Metrics | null>(null);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    let cancelled = false;
    callApi<Metrics>("/api/metrics")
      .then((d) => { if (!cancelled) setData(d); })
      .catch((e) => { if (!cancelled) setError(e.message); });
    return () => { cancelled = true; };
  }, [callApi]);

  if (error) return <p>Error: {error}</p>;
  if (!data) return <p>Loading metrics…</p>;
  return (
    <section>
      <h2>Active users: {data.activeUsers}</h2>
      <h2>Revenue: ${data.revenue.toLocaleString()}</h2>
    </section>
  );
}
Tip

Wrap callApi in useCallback with getAccessTokenSilently as a dependency. Without it, a new function identity each render makes your useEffect fire in a loop — a classic React + data-fetching bug.

8. Production Architecture

                         INTERNET
                            |

              v                          +----------------------+

  • One tenant per environment. Separate dev, staging, and prod Auth0 tenants. Manage them as code with the Auth0 Deploy CLI or Terraform so callback URLs, Actions, and APIs are reproducible.
  • SPA app per origin. Each deploy origin must be listed in Allowed Callback / Logout / Web Origins. Use a custom domain (auth.dashly.app) so Universal Login is first-party — this dodges third-party-cookie issues and looks trustworthy.
  • Immutable, cache-busted bundles. Vite emits hashed filenames; serve index.html with no-cache and assets with long-lived caching.
  • BFF option. For higher security you can adopt a Backend-For-Frontend: a thin server holds tokens in an HttpOnly cookie session and proxies API calls, so no token ever reaches JavaScript. Heavier to operate, but immune to token theft via XSS.

9. Security Analysis

9.1 The threat model of a public client

ThreatMitigation in this app
Authorization code interceptionPKCE (S256) — code is useless without the in-memory verifier.
CSRF on the redirectstate parameter generated & verified by the SDK.
ID-token replaynonce bound to the login attempt; signature + iss/aud/exp checks.
Token theft via XSScacheLocation="memory" (no localStorage); strict CSP; sanitize all rendered HTML.
Stolen refresh token replayedRefresh token rotation + automatic reuse detection revokes the family.
Open redirect / token leakStrict Allowed Callback/Logout/Web Origins allowlists.
Privilege escalationRoles enforced at the API via access-token permissions, not just hidden UI.
Danger

XSS is the apex predator of SPAs. If an attacker can run JS in your origin, they can read in-memory tokens, call getAccessTokenSilently(), and impersonate the user. Memory caching narrows the window (no persistent token to scrape) but does not eliminate it. Defense in depth: a strict Content-Security-Policy, no dangerouslySetInnerHTML with untrusted input, dependency auditing, and short token lifetimes.

9.2 localStorage vs memory caching

Aspectmemory (default)localstorage
XSS exposureLower (token gone on tab close)Higher (persistent, readable by any script)
Survives hard refreshNo (needs silent re-auth)Yes
Recommended forDefault — use with refresh-token rotationOnly if refresh fails & you accept the risk

The modern, recommended combo is cacheLocation="memory" + useRefreshTokens. On refresh, the rotating refresh token (held in memory and, internally, a fallback) silently re-establishes the session without persisting an access token to disk.

10. Performance Considerations

  • Token caching is your friend. getAccessTokenSilently() returns the cached token with zero network cost until it expires. Do not pre-fetch a token on every keystroke; call it lazily in your API layer.
  • Avoid the render-loop trap. Memoize API functions (useCallback) and effect dependencies; an unmemoized token getter triggers infinite refetches.
  • De-duplicate concurrent refreshes. The SDK coalesces simultaneous getAccessTokenSilently() calls into a single token request, so firing five API calls at once won't trigger five refreshes.
  • Lazy-load protected pages. Use React.lazy + Suspense for /admin and /dashboard so unauthenticated visitors never download admin code.
  • First-paint cost of bootstrap. The provider's isLoading phase includes a possible silent-auth round trip. Render a lightweight skeleton, not a blank screen, while isLoading is true.
  • JWKS caching is server-side. Your API caches Auth0's signing keys; it does not refetch them per request. (Mentioned because interviewers probe the full path.)

11. Common Mistakes

  1. Sending the ID token to the API. APIs must reject ID tokens — wrong audience. Always use the access token from getAccessTokenSilently().
  2. Forgetting audience. No audience → no API access token. Symptom: 401 from your API even though login "works."
  3. Treating route guards as security. Hiding UI is not authorization. Enforce on the server.
  4. Ignoring isLoading. Rendering "Please log in" during the loading phase flashes the wrong UI and may trigger redundant redirects.
  5. Putting the Provider outside the Router (or the Router outside the Provider when you need useNavigate in the callback) — breaks onRedirectCallback navigation.
  6. Non-namespaced custom claims. roles is silently dropped; https://dashly.app/roles survives.
  7. Mismatched callback URLs. http://localhost:3000 vs http://localhost:3000/ (trailing slash) → "Callback URL mismatch."
  8. Storing tokens in localStorage by reflex. Prefer memory + refresh rotation.
  9. Calling getAccessTokenSilently in render instead of in an effect/handler — causes loops and unhandled promise warnings.
  10. Logging tokens to the console "to debug." They are bearer credentials; treat them like passwords.

12. Best Practices

  • Use memory cache + refresh-token rotation as the default token strategy.
  • Always set an audience and request only the scopes you need (least privilege).
  • Centralize API calls in a single hook (useApi) so token handling and error mapping live in one place.
  • Use a custom domain for Auth0 to keep login first-party.
  • Manage tenants as code (Deploy CLI / Terraform); never click-configure prod by hand.
  • Add a strict CSP and never render untrusted HTML.
  • Use user.sub as the canonical user key; namespace all custom claims.
  • Show a loading state while isLoading; never assume "logged out" prematurely.
  • Type your claims (useAuth0<UserWithRoles>()) so role checks are compile-checked.
  • Re-verify roles/permissions on the server — the SPA's checks are cosmetic.

13. Interview Questions (with Model Answers)

Q1. Why must a React SPA use Authorization Code + PKCE instead of the Implicit flow?

Model answer: A SPA is a public client with no place to store a secret. Implicit returned tokens directly in the URL fragment, exposing them to history, referrers, and scripts, with no client authentication. Authorization Code + PKCE returns a one-time code that is exchanged for tokens via a back-channel-style POST; the code is bound to a per-request code_verifier that never leaves the browser, so an intercepted code can't be redeemed. Implicit is deprecated; PKCE is the OAuth 2.1 standard for public clients.

Q2. What is the difference between the ID token and the access token, and where does each go?

Model answer: The ID token (audience = your client) authenticates the user to the app; it's for reading profile claims in the front end and must never be sent to an API. The access token (audience = your API) authorizes requests to the API and goes in the Authorization: Bearer header. Conflating them causes either insecure APIs (accepting ID tokens) or broken calls (sending the wrong audience).

Q3. How does silent token renewal work, and why prefer refresh-token rotation over iframe silent auth?

Model answer: getAccessTokenSilently() returns a cached token until expiry, then renews. Historically renewal used a hidden iframe to /authorize?prompt=none, relying on the Auth0 session cookie — but browsers block third-party cookies, breaking it. Refresh-token rotation (with offline_access) instead exchanges a refresh token for a new access token and a new refresh token, invalidating the old one. Reuse detection revokes the whole family if a stolen token is replayed, making it both resilient and breach-resistant.

Q4. Is hiding the admin route in React enough to secure admin features?

Model answer: No. The bundle is public; anyone can read it, forge requests, or bypass the router. Front-end guards are UX only. The API must validate the access token and enforce roles/permissions (scopes) on every request. Defense lives on the server.

Q5. How do roles end up in the token, and where do you enforce them?

Model answer: Assign roles via Auth0 RBAC, then a Post-Login Action sets a namespaced custom claim on the access (and optionally ID) token. The SPA reads the ID-token claim to toggle UI; the API reads the access-token permissions/claim to authorize the actual operation. Enforcement is on the API.

Q6. Where should tokens be stored in a SPA, and why?

Model answer: In memory (the SDK default), combined with refresh-token rotation. Memory avoids persistent XSS-readable storage; rotation lets the session survive refresh without writing an access token to localStorage. For maximum security, a BFF holds tokens in an HttpOnly cookie so JS never sees them at all.

14. Certification Tips

  • Know the flow name: SPAs use Authorization Code Flow with PKCE. Implicit is deprecated — expect a "which flow?" question.
  • Application type matters: register the app as Single Page Application (no secret). Choosing "Regular Web App" is a trap answer.
  • Audience vs scope: audience selects the API; scopes request permissions. Missing audience → no API token.
  • Custom claims must be namespaced with a non-Auth0 URL; otherwise they're stripped.
  • Allowed URLs: Callback (login return), Logout (post-logout return), Web Origins (silent auth / CORS). Map each to its purpose.
  • refresh token rotation + reuse detection is the recommended SPA token strategy — memorize the terms.
  • Universal Login over Embedded Login: better security, MFA, attack protection, and SSO out of the box.
  • The user object from useAuth0() equals the decoded ID token claims, not API data.

20. Key Takeaways

Key

A React SPA is a public client: it authenticates with Authorization Code + PKCE through Auth0's Universal Login and never handles raw credentials or secrets.

Key

The ID token identifies the user to your front end (read claims via useAuth0().user); the access token authorizes calls to your API (Bearer header). Never mix them up.

Key

Wrap your app in <Auth0Provider> (inside the Router), use loginWithRedirect/logout, and protect routes with withAuthenticationRequired — but remember route guards are UX, not security.

Key

Get API tokens via getAccessTokenSilently(), which caches and silently renews using refresh-token rotation. Use cacheLocation="memory" for the best XSS posture.

Key

Roles arrive as namespaced custom claims via a Post-Login Action; render role-based UI in React, but enforce authorization on the API every time.
