You will create a real Auth0 tenant, register three different application types (an SPA, a Regular Web App, and a Machine-to-Machine app), publish a protected API with scopes and permissions, build a full RBAC model with roles, switch on Organizations for B2B multi-tenancy, create users while mastering the critical user_metadata vs app_metadata distinction, and turn on social login, enterprise connections, passwordless and MFA. 1. Theory — First Principles of an Auth0 Tenant

Before you click a single button, you must understand the object model you are about to build. Auth0 is not "a login box." It is a hosted authorization server (per OAuth 2.0 / RFC 6749) plus an identity provider (per OpenID Connect). Everything you configure in the dashboard is just data that changes how that server behaves at token-issuance time.

The root container is the tenant. A tenant is an isolated, namespaced instance of Auth0 with its own:

  • Domain — e.g. your-name.us.auth0.com. This is the OAuth issuer (iss claim) and the host of every endpoint: /authorize, /oauth/token, /.well-known/openid-configuration, /.well-known/jwks.json, /userinfo.
  • Signing keys — an RSA key pair per tenant. The private key signs tokens (RS256); the public key is published at the JWKS endpoint so resource servers can verify signatures without ever contacting Auth0.
  • User store(s) — called connections. A database connection stores username/password identities; social and enterprise connections federate to external IdPs.
  • Applications (clients), APIs (resource servers / audiences), roles & permissions, organizations, Actions, branding and policy.

The first-principles mental model is a chain of trust: a user proves identity to a connection → Auth0 (the authorization server) mints signed tokens → your application (client) carries those tokens → your API (resource server) verifies them against the tenant's public keys. Every dashboard task in this chapter wires up one link in that chain.

Key

A tenant = an isolated OAuth authorization server. An application = an OAuth client (something that requests tokens). An API = an OAuth resource server, identified by an audience (something that consumes tokens). Keep these three nouns straight and the entire dashboard makes sense.

Why one tenant per environment

Because the signing keys, users, and config are tenant-scoped, the canonical pattern is one tenant per environment: acme-dev, acme-staging, acme-prod. This is not optional advice — it is the only way to test a config change (new Action, new connection) without risking production users. The free plan gives you a development tenant; you add more from the tenant switcher.

2. Story-Based Explanation — Maya Launches "CineBook"

Maya is the founding engineer at CineBook, a cinema-booking startup. On day one she has three things that need to talk to each other and a deadline:

  1. A React single-page app where customers browse showtimes and book seats — it runs in the browser, so it can keep no secret.
  2. An admin portal (a server-rendered Express/Next app) where staff manage screenings — it runs on a server, so it can keep a secret.
  3. A nightly batch job that reconciles ticket sales — no human is present, so it logs in as itself, not as a user.

All three need to call the same Booking API. Maya could hand-roll passwords and sessions… or she can model each actor correctly in Auth0. She creates a tenant cinebook-dev, registers the React app as an SPA, the admin portal as a Regular Web App, the batch job as a Machine-to-Machine app, and the Booking API as an API with an audience and scopes like read:bookings and cancel:bookings.

Then marketing asks for "Sign in with Google" (a social connection), the first enterprise customer demands SAML SSO (an enterprise connection), the security team mandates MFA for staff, and a second enterprise customer wants their own isolated user space — so Maya turns on Organizations. Every requirement in this story maps to exactly one dashboard feature you will configure below. We will follow CineBook as the running example throughout the chapter.

5. Internal Working — What the Dashboard Actually Changes

The dashboard is a friendly face over the Auth0 Management API. Every action you take writes to tenant configuration objects. Understanding those objects demystifies everything.

5.1 What "Create Application" really creates

Creating an app creates a client object with a generated client_id and (for confidential apps) a client_secret. The "Application Type" you pick is not cosmetic — it pre-configures security defaults:

Typetoken_endpoint_auth_methodDefault grant typesSecret?
SPAnone (public)authorization_code (+PKCE), refresh_tokenNo
Regular Web Appclient_secret_post/basicauthorization_code, refresh_tokenYes
Machine to Machineclient_secret_post/basicclient_credentialsYes
Nativenone (public)authorization_code (+PKCE), refresh_token, device_codeNo

5.2 What "Create API" really creates

An API is a resource server object. Its Identifier (you set this, e.g. https://api.cinebook.com) becomes the audience. When an app requests a token with audience=https://api.cinebook.com, Auth0 mints a JWT access token whose aud equals that identifier. If you never create an API and request no audience, Auth0 returns an opaque access token usable only at /userinfo — a frequent source of "my JWT won't decode" confusion.

Warn

The API Identifier is permanent and should be a URI you control, but it does NOT have to be reachable. It is a logical name, never an endpoint Auth0 calls. Do not change it after launch — every issued token's aud is tied to it.

5.3 How RBAC injects permissions into the token

RBAC is off by default. When you flip "Enable RBAC" and "Add Permissions in the Access Token" on an API, Auth0's pipeline does this at issuance time:

 token request
   |
   v
 [ resolve user's direct permissions + permissions via assigned roles ]
   |
   v
 [ intersect with the scopes the app requested (scope param) ]
   |
   v
 [ if "Add Permissions in Access Token" = ON ]
   |        --> write array claim:  "permissions": ["read:bookings", ...]
   |        --> AND fold granted scopes into "scope": "read:bookings ..."
   v
 sign (RS256) -> access_token

So scope is "what the app asked for and was granted," while permissions is the explicit RBAC array. Both are derived from the user's roles intersected with the request — Auth0 never grants more than the user actually has.

6. Code Walkthrough — Reading the Tokens You Just Configured

Configuration is meaningless until you see its fingerprint in a token. Here is a decoded access token from a correctly configured tenant (RBAC on, permissions added):

{
  "iss": "https://cinebook-dev.us.auth0.com/",
  "sub": "auth0|66a1f0c2e4b0d9f1a2b3c4d5",
  "aud": [
    "https://api.cinebook.com",
    "https://cinebook-dev.us.auth0.com/userinfo"
  ],
  "iat": 1718800000,
  "exp": 1718886400,
  "scope": "openid profile email read:bookings create:bookings",
  "permissions": ["read:bookings", "create:bookings"],
  "azp": "AbCdEf123SpaClientId",
  "org_id": "org_aCme123"
}
  • iss proves which tenant signed it — note the trailing slash, a classic verification gotcha.
  • aud is an array here because the SPA also requested openid (which adds the userinfo audience). Your API must accept a token whose aud contains its identifier, not equals it.
  • scope vs permissions — exactly the two derivations from §5.3.
  • org_id appears only because the user logged in through an Organization.

And here is the M2M token from the same tenant — notice there is no user (sub is the client), no scope of openid, and no permissions array (RBAC permissions are user-centric; M2M uses scopes granted to the client):

{
  "iss": "https://cinebook-dev.us.auth0.com/",
  "sub": "M2mBatchClientId@clients",
  "aud": "https://api.cinebook.com",
  "gty": "client-credentials",
  "scope": "read:bookings reconcile:sales",
  "azp": "M2mBatchClientId"
}
Tip

sub ending in @clients and a gty of client-credentials are the two unmistakable signs you are looking at a machine token, not a user token.

Now connect actual code to the tenant you configured. Use environment variables — never hard-code IDs or secrets.

8.1 React SPA (public client, PKCE)

// main.jsx — @auth0/auth0-react
import { Auth0Provider } from "@auth0/auth0-react";
import { createRoot } from "react-dom/client";
import App from "./App";

createRoot(document.getElementById("root")).render(
  <Auth0Provider
    domain={import.meta.env.VITE_AUTH0_DOMAIN}            // cinebook-dev.us.auth0.com
    clientId={import.meta.env.VITE_AUTH0_CLIENT_ID}
    authorizationParams={{
      redirect_uri: window.location.origin + "/callback",
      audience: "https://api.cinebook.com",               // ask for an API token!
      scope: "openid profile email read:bookings create:bookings"
    }}
    useRefreshTokens={true}
    cacheLocation="localstorage"
  >
    <App />
  </Auth0Provider>
);
// Calling the Booking API with the access token
import { useAuth0 } from "@auth0/auth0-react";

function BookingsButton() {
  const { getAccessTokenSilently } = useAuth0();
  async function load() {
    const token = await getAccessTokenSilently();
    const res = await fetch("https://localhost:8080/bookings", {
      headers: { Authorization: `Bearer ${token}` }       // access_token, NOT id_token
    });
    console.log(await res.json());
  }
  return <button onClick={load}>Load my bookings</button>;
}

8.3 Spring Boot resource server (verifies the API token)

# application.yml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://cinebook-dev.us.auth0.com/
          audiences: https://api.cinebook.com
// SecurityConfig.java — map the Auth0 "permissions" claim to authorities
@Configuration
@EnableMethodSecurity
public class SecurityConfig {

  @Bean
  SecurityFilterChain api(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a
            .requestMatchers(HttpMethod.GET, "/bookings").hasAuthority("read:bookings")
            .requestMatchers(HttpMethod.DELETE, "/bookings/**").hasAuthority("cancel:bookings")
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(j -> j.jwtAuthenticationConverter(conv())));
    return http.build();
  }

  private JwtAuthenticationConverter conv() {
    JwtGrantedAuthoritiesConverter ga = new JwtGrantedAuthoritiesConverter();
    ga.setAuthoritiesClaimName("permissions");  // Auth0's RBAC claim
    ga.setAuthorityPrefix("");                    // keep "read:bookings" verbatim
    JwtAuthenticationConverter c = new JwtAuthenticationConverter();
    c.setJwtGrantedAuthoritiesConverter(ga);
    return c;
  }
}

8.4 FastAPI resource server

# auth.py — verify RS256 token against tenant JWKS
import jwt                          # PyJWT
from jwt import PyJWKClient
from fastapi import Depends, HTTPException, Security
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

DOMAIN = "cinebook-dev.us.auth0.com"
AUDIENCE = "https://api.cinebook.com"
ISSUER = f"https://{DOMAIN}/"
jwks = PyJWKClient(f"https://{DOMAIN}/.well-known/jwks.json")
bearer = HTTPBearer()

def verify(creds: HTTPAuthorizationCredentials = Security(bearer)):
    token = creds.credentials
    key = jwks.get_signing_key_from_jwt(token).key
    try:
        return jwt.decode(token, key, algorithms=["RS256"],
                          audience=AUDIENCE, issuer=ISSUER)
    except Exception as e:
        raise HTTPException(401, f"invalid token: {e}")

def require(perm: str):
    def dep(claims: dict = Depends(verify)):
        if perm not in claims.get("permissions", []):
            raise HTTPException(403, "insufficient_permissions")
        return claims
    return dep
# main.py
from fastapi import FastAPI, Depends
from auth import require
app = FastAPI()

@app.get("/bookings")
def list_bookings(claims = Depends(require("read:bookings"))):
    return {"sub": claims["sub"], "ok": True}

// reconcile.js — Node fetch, cache the token until it expires
let cache = { token: null, exp: 0 };
async function getToken() {
  if (cache.token && Date.now() < cache.exp - 60_000) return cache.token;
  const r = await fetch("https://cinebook-dev.us.auth0.com/oauth/token", {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({
      grant_type: "client_credentials",
      client_id: process.env.M2M_CLIENT_ID,
      client_secret: process.env.M2M_CLIENT_SECRET,
      audience: "https://api.cinebook.com",
    }),
  });
  const j = await r.json();
  cache = { token: j.access_token, exp: Date.now() + j.expires_in * 1000 };
  return cache.token;
}

9. Security Analysis

  • Public vs confidential clients. SPAs and native apps cannot hold a secret — anything shipped to a browser or device is extractable. That is why they use PKCE instead of a client secret. Never "fix" a CORS error by turning an SPA into a Regular Web App and embedding the secret in JS.
  • Callback URL allowlisting. Exact-match callback/logout URLs prevent attackers from redirecting the authorization response (and thus the code/tokens) to a site they control. Never use wildcards in production; never add http://localhost to a production app.
  • RS256, not HS256. RS256 lets resource servers verify with a public key from JWKS — no shared secret to leak. HS256 forces every API to hold the signing secret, multiplying the blast radius. Keep the API on RS256.
  • Validate aud and iss. A token minted for another API (different aud) must be rejected even if the signature is valid — otherwise a low-privilege API's token could be replayed against a high-privilege one.
  • Least-privilege scopes for M2M. Authorize each M2M client for only the permissions it needs. The batch job gets reconcile:sales, not cancel:bookings.
  • app_metadata is the security boundary. Users can edit their own user_metadata via self-service flows; they can never edit app_metadata. Put authorization-relevant data (plan tier, internal flags, tenant id) in app_metadata only.
  • MFA on privileged roles. Require MFA for Staff/Admin via a policy or an Action that checks the user's roles. Adaptive MFA steps up only on risky logins, balancing security and friction.
Danger

Putting authorization flags in user_metadata (e.g. {"isAdmin": true}) is a critical privilege-escalation bug. Self-service profile endpoints let users write user_metadata — they could make themselves admin. Authorization data lives in roles/permissions or app_metadata, full stop.

10. Performance Considerations

  • Cache the JWKS. Resource servers should fetch /.well-known/jwks.json once and cache the keys (Spring, PyJWKClient and express-jwt do this automatically). Re-fetch only on key rotation / unknown kid. Fetching per request adds a network round-trip to every API call.
  • Cache M2M tokens. Client-credentials tokens live for hours (default 24h). Caching them (as in §8.5) avoids hammering /oauth/token and the per-token M2M billing on paid plans.
  • Keep tokens lean. Every role/permission and custom claim inflates the JWT. Large tokens slow every request (bigger headers) and can exceed proxy header limits (often 8 KB). If a user has hundreds of permissions, prefer coarse roles or fetch fine-grained authz server-side.
  • RBAC adds negligible issuance cost but the permission resolution happens per token — another reason to cache and reuse tokens within their lifetime rather than re-authenticating constantly.
  • Region choice = latency. The /authorize and /oauth/token round-trips go to your tenant's region. Pick the region nearest your user base.

12. Best Practices

  • Name things by environment and type: CineBook Web (React) — dev. Future-you will thank present-you.
  • One tenant per environment, and manage config as code with the Auth0 Deploy CLI or Terraform so dev → staging → prod is reproducible (covered deeply in later chapters).
  • Design scopes by capability (read:bookings, cancel:bookings), not by role. Roles bundle scopes; the API checks scopes/permissions.
  • Enable RBAC + add permissions to the token from day one so your resource servers have a stable authorization signal.
  • Keep secrets in a vault / env vars, rotate them, and never commit .env.
  • Use Organizations for B2B isolation (per-customer branding, connections, membership) rather than overloading metadata.
  • Put display/preference data in user_metadata, authorization/business data in app_metadata.
  • Turn on MFA early (at least for privileged roles) and prefer phishing-resistant factors (WebAuthn/passkeys) plus Adaptive MFA.
  • Prefer enterprise & passwordless connections where they reduce password risk, and always enable the connection on the specific app/org that needs it.

13. Interview Questions (with model answers)

Q1. What is the difference between an Auth0 Application and an Auth0 API?

Model answer: An Application is an OAuth client — it requests tokens (SPA, Regular Web App, M2M). An API is an OAuth resource server identified by an audience — it consumes/verifies access tokens. The app obtains a token whose aud equals the API's identifier, then calls the API with it. They are two sides of the OAuth exchange.

Q2. Why does an SPA use PKCE while a Regular Web App can use a client secret?

Model answer: An SPA is a public client — its code runs in the browser, so any embedded secret is extractable. PKCE binds the authorization code to a dynamically generated verifier known only to that browser session, so an intercepted code is useless. A Regular Web App runs on a server, can safely store a secret, and authenticates the token request with it.

Q3. How do RBAC permissions end up in the access token?

Model answer: You enable "RBAC" and "Add Permissions in the Access Token" on the API. At issuance, Auth0 resolves the user's permissions (direct + via roles), intersects them with the requested scopes, and writes them as a permissions array (and folds granted scopes into scope). The resource server then authorizes on that claim.

Q4. user_metadata vs app_metadata — when do you use each?

Model answer: user_metadata is user-editable, for preferences/display (theme, language). app_metadata is read-only to the user and set by the backend, for authorization/business data (plan, tenant id, internal flags). Putting authz data in user_metadata is a privilege-escalation risk because self-service flows can write it.

Q5. What does the audience parameter do, and what happens if you omit it?

Model answer: audience tells Auth0 which API the token is for; the issued token's aud is set to that identifier and it becomes a verifiable JWT. Omit it and Auth0 returns an opaque access token only valid at /userinfo — your API cannot verify it as a JWT.

Q6. When would you use Organizations instead of separate tenants?

Model answer: Organizations model B2B customers within one tenant — shared infrastructure but isolated membership, per-org connections (e.g. each customer's SSO) and branding. Separate tenants are for environments (dev/staging/prod) or hard data-isolation/compliance boundaries, not per-customer multi-tenancy.

Q7. How does an M2M token differ from a user token?

Model answer: M2M uses the client-credentials grant — no user, no interactive login. The token's sub is the client (...@clients), gty is client-credentials, there is no id_token, and authorization comes from scopes granted to the client, not user roles.

Q8. Why RS256 over HS256 for an API?

Model answer: RS256 is asymmetric: Auth0 signs with a private key, resource servers verify with the public key from JWKS — no shared secret. HS256 is symmetric, forcing every verifier to hold the signing secret, increasing leak risk and coupling. RS256 also supports clean key rotation via kid.

14. Certification Tips

  • Know the four application types cold and the grant/auth-method each defaults to (SPA→PKCE/public, RWA→code+secret, M2M→client_credentials, Native→PKCE/device).
  • The exam loves the audience trap: "Why is the access token opaque?" → no audience requested. "Why 401 calling the API?" → ID token used, or wrong aud.
  • RBAC two-switch rule: permissions appear in the token only when both "Enable RBAC" and "Add Permissions in Access Token" are on.
  • Metadata: remember user_metadata = user-editable preferences; app_metadata = backend-set, security-sensitive, not user-editable.
  • Connections are enabled per application/organization — a connection existing isn't enough; it must be toggled on for the app.
  • Organizations = B2B within a tenant; understand "Business Users", login prompt behaviour, and the org_id claim.
  • Passwordless and MFA are configured under Authentication / Security and must be enabled for the relevant connection/app; know OTP, magic link, SMS, WebAuthn factors.
  • Region and domain are immutable; the domain is the issuer; one tenant per environment is the recommended topology.

19. Cheat Sheet

 OBJECTS
   Tenant  = authorization server   (domain = issuer, has signing keys)
   App     = OAuth client           (requests tokens)
   API     = resource server        (Identifier = audience, verifies tokens)
   Role    = bundle of permissions  (assigned to users)
   Org     = B2B tenancy in a tenant (isolated members/branding/connections)

 APP TYPES
   SPA          -> PKCE, no secret, public client
   Regular Web  -> auth code + client_secret (server-side)
   M2M          -> client_credentials (no user, sub=...@clients)
   Native       -> PKCE + device code, no secret

 MUST-DO TOGGLES
   API: Enable RBAC  +  Add Permissions in Access Token
   Connection: enable per Application/Organization

 TOKEN RULES
   Call APIs with the ACCESS TOKEN (not id_token)
   Always send audience= to get a JWT (else opaque)
   Verify: signature(RS256/JWKS) + iss + aud + exp + scope/permissions

 METADATA
   user_metadata = user-editable preferences (theme, lang)
   app_metadata  = backend-only, authz/business data (plan, tenant, flags)

 KEY ENDPOINTS  (tenant.region.auth0.com)
   /authorize                       start login
   /oauth/token                     exchange code / client_credentials
   /userinfo                        profile (opaque token ok here)
   /.well-known/openid-configuration   discovery
   /.well-known/jwks.json           public keys for verification

 CLI/CURL (M2M)
   POST /oauth/token  grant_type=client_credentials
        client_id + client_secret + audience

20. Key Takeaways

Key

A tenant is an isolated OAuth authorization server; Applications request tokens, APIs (audiences) consume them. Get those three nouns right and the entire dashboard is just wiring them together.

Key

Pick the application type that matches where the code runs: SPA/Native are public clients (PKCE, no secret); Regular Web Apps and M2M are confidential (hold a secret). Never embed a secret in a browser.

Key

To get a verifiable JWT for your API, always request an audience; to get permissions in the token, enable both RBAC switches on the API.

Key

Roles bundle permissions for users; scopes are what the app requests; the resource server authorizes on the resulting permissions/scope claim after verifying signature, iss, aud and exp.

Key

user_metadata = user-editable preferences; app_metadata = backend-only authorization/business data. Never put security flags in user_metadata.

Key

Use Organizations for B2B multi-tenancy, enable connections per app/org, and turn on social, passwordless and MFA deliberately — each is a separate, intentional toggle, not a default.
