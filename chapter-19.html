Chapter 19 — Project 3 — Spring Boot Resource Server

A login page is only half of identity. The other half lives on the server that actually holds your data — the API that must decide, on every single request, "is this caller who they claim to be, and are they allowed to do this?" In this project we build that server: a production-shaped Spring Boot 3 API on Java 21 that trusts nothing except a cryptographically signed Auth0 access token. We will derive, from first principles, why a "resource server" exists at all, how it validates a JWT without ever calling Auth0 on the hot path, why the audience claim is the line between a secure API and a confused-deputy disaster, and how to turn Auth0 permissions into Spring Security authorities you can enforce with SecurityFilterChain and @PreAuthorize. By the end you will have a real, runnable API you can hit with a real access token — and the mental model to defend every design choice in a senior interview.

1. Theory — First Principles of a Resource Server

OAuth 2.0 names four roles. You must be able to recite them and, more importantly, explain why each exists:

RoleWho it is in our projectJob
Resource OwnerThe human userOwns the data; consents to access
ClientThe SPA / mobile / CLI appRequests a token, then calls the API
Authorization ServerAuth0 (your tenant)Authenticates the user, issues tokens
Resource ServerThis Spring Boot appHolds the protected data; validates tokens; enforces access

The resource server is the API that owns the protected resources. Its single defining property is profound: it never sees the user's password and it never runs the login flow. All it ever receives is an HTTP request carrying an Authorization: Bearer <access_token> header. Its entire security posture reduces to one question repeated on every request — "Should I honour this token, and what does it let the caller do?"

Why separate the resource server from the authorization server?

Because authentication is hard and authorization is frequent. Authenticating a human — passwords, MFA, social login, breached-password detection, bot detection — is a specialist, security-critical, constantly-attacked problem. You centralize it once, in Auth0, and never reimplement it. Authorization — "can this token call DELETE /invoices/42?" — happens millions of times a day, on every API, and must be fast and local. Splitting the two lets each scale and evolve independently, and lets ten different microservices all trust the same token without ten copies of login code. This is the architectural payoff of OAuth: one issuer, many resource servers.

The two ways to validate a token

  • Introspection (RFC 7662): the resource server sends the token to the authorization server and asks "is this valid?" Simple, always-fresh, but adds a network round-trip and a hard dependency on Auth0 being up for every request. Used for opaque tokens.
  • Local JWT validation: the token is a self-describing, signed JWT. The resource server verifies the signature with Auth0's public key (no secret needed) and reads the claims directly. No per-request network call. This is what we build, and what Auth0 issues by default.
Key

A resource server is a token consumer, not a token issuer. It holds no passwords, runs no login, and stores no client secret for validation. Its security rests entirely on: (1) verifying the JWT signature against the issuer's public keys, (2) checking the standard claims (iss, exp, aud), and (3) mapping the token's permissions to local authorization decisions.

2. Story-Based Explanation — The Concert Wristband

Imagine you run the backstage operations of a music festival. You have a box office (Auth0) far from the stage. Fans queue at the box office, prove who they are, pay, and walk away with a tamper-proof, holographic wristband (the access token). That wristband encodes — printed right on it — the wearer's tier (General, VIP, Crew) and which festival it is good for.

You, at the backstage gate (the resource server), are not the box office. You cannot check anyone's ID, you do not have the credit-card machine, and you absolutely do not phone the box office for every person who walks up — the line would never move. Instead you do three lightning-fast checks by looking at the wristband:

  1. Is the hologram genuine? You hold a card of authentic hologram patterns (Auth0's public keys / JWKS). If the wristband's hologram matches, the box office really printed it. This is signature verification.
  2. Is it for this festival, and not expired? A genuine wristband from last year's festival, or a genuine wristband for the food court rather than backstage, must be refused. This is checking iss, exp, and — critically — aud.
  3. What tier does it show? "Crew" gets into the equipment area; "VIP" gets the lounge; "General" gets neither. This is mapping permissions to authorities.

The genius of the wristband is that the gate is autonomous. Ten gates around the festival all trust the same holograms with zero coordination. The box office can be closed for the night and the gates still work. And nobody can forge a wristband, because forging the hologram requires the box office's secret press (Auth0's private signing key), which never leaves the box office. Our Spring Boot app is that backstage gate.

4. Real-World Analogy — The Passport and the Border Officer

A passport is the closest everyday object to a JWT, and the analogy is precise enough to reason with:

Passport worldJWT / resource-server world
The passport office issues passportsAuth0 issues access tokens
Tamper-proof printing & hologramsRS256 signature with Auth0's private key
Border officer checks it is genuine without phoning the officeResource server verifies signature with the public key
"Issued by" country on the coveriss claim
Expiry dateexp claim
Visa stamp: valid for this countryaud claim (the API identifier)
Visa type: tourist vs. work permitpermissions / scope

The decisive insight: a passenger could hold a perfectly genuine, unexpired passport and still be turned away — because the visa is for the wrong country. A genuine token signed by Auth0 for the analytics API must not be honoured by the billing API. That "wrong country" check is the aud claim, and skipping it is the most dangerous mistake a resource server can make. We give it its own validator in step 6.

5. Internal Working — What Spring Security Actually Does

When you add spring-boot-starter-oauth2-resource-server and set an issuer-uri, Spring Boot's auto-configuration wires a precise chain of objects. Knowing them by name is what separates "I copied a tutorial" from "I can debug this in production."

  1. BearerTokenAuthenticationFilter sits in the servlet filter chain. It extracts the token from the Authorization: Bearer header (via DefaultBearerTokenResolver) and hands it to the authentication manager.
  2. JwtAuthenticationProvider receives the raw token and delegates decoding to a JwtDecoder.
  3. NimbusJwtDecoder is the workhorse. On first use it calls Auth0's /.well-known/openid-configuration to discover the JWKS URI, then fetches the public keys (JWKS) and caches them in memory. It selects the key by the token header's kid, verifies the RS256 signature, and parses the claims.
  4. OAuth2TokenValidator chain runs after signature verification. By default it includes a timestamp validator (exp/nbf) and, because we used issuer-uri, an issuer validator (iss). This is where we plug in our custom audience validator.
  5. JwtAuthenticationConverter turns the validated Jwt into an AbstractAuthenticationToken whose getAuthorities() Spring uses for access control. By default it reads the scope/scp claim and prefixes each with SCOPE_. We override this to also read Auth0's permissions claim.
  6. The resulting Authentication is placed in the SecurityContextHolder, where SecurityFilterChain rules and @PreAuthorize expressions can read it.

How signature verification works without a shared secret

RS256 is asymmetric. Auth0 signs with a private key that never leaves Auth0. Verification needs only the matching public key, which Auth0 publishes openly at the JWKS endpoint. This is why a resource server stores no secret for validation — and why you should never use the symmetric HS256 algorithm for Auth0 APIs (it would force every resource server to hold the shared secret, multiplying the blast radius of a leak).

Note

The JWKS is cached, but Auth0 can rotate signing keys. Nimbus handles this: if it sees a token with an unknown kid, it re-fetches the JWKS (rate-limited) and tries again. That is why rotation is a non-event for a correctly configured resource server.

6.4 The audience validator — first principles

An OAuth2TokenValidator<Jwt> is a function "given a decoded JWT, return success or a list of errors." We implement one that fails unless the aud claim contains our API identifier. Why this matters: Auth0 may issue a perfectly valid token to a client for a different API. Without this check, that token would be accepted here — a classic "confused deputy," letting a token minted for API-A act on API-B.

package com.helios.api.security;

import org.springframework.security.oauth2.core.OAuth2Error;
import org.springframework.security.oauth2.core.OAuth2TokenValidator;
import org.springframework.security.oauth2.core.OAuth2TokenValidatorResult;
import org.springframework.security.oauth2.jwt.Jwt;

public final class AudienceValidator implements OAuth2TokenValidator<Jwt> {

    private final String requiredAudience;

    public AudienceValidator(String requiredAudience) {
        this.requiredAudience = requiredAudience;
    }

    @Override
    public OAuth2TokenValidatorResult validate(Jwt jwt) {
        // aud is an array in Auth0 tokens; getAudience() returns List<String>.
        if (jwt.getAudience().contains(requiredAudience)) {
            return OAuth2TokenValidatorResult.success();
        }
        OAuth2Error error = new OAuth2Error(
                "invalid_token",
                "The required audience '" + requiredAudience + "' is missing",
                null);
        return OAuth2TokenValidatorResult.failure(error);
    }
}

6.5 Mapping Auth0 permissions to Spring authorities

Spring's default converter only reads the scope claim and prefixes entries with SCOPE_. Auth0, when you enable RBAC with "Add Permissions in the Access Token," also emits a permissions array (e.g. ["read:invoices","delete:invoices"]). We merge both into authorities so we can author rules against either.

package com.helios.api.security;

import org.springframework.core.convert.converter.Converter;
import org.springframework.security.authentication.AbstractAuthenticationToken;
import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.oauth2.jwt.Jwt;
import org.springframework.security.oauth2.server.resource.authentication.*;

import java.util.*;
import java.util.stream.*;

public final class Auth0AuthoritiesConverter
        implements Converter<Jwt, AbstractAuthenticationToken> {

    private final JwtGrantedAuthoritiesConverter scopes =
            new JwtGrantedAuthoritiesConverter(); // emits SCOPE_xxx from "scope"

    @Override
    public AbstractAuthenticationToken convert(Jwt jwt) {
        Collection<GrantedAuthority> authorities = new HashSet<>(scopes.convert(jwt));

        // Auth0 RBAC "permissions" claim -> authorities (no prefix, so we can
        // write hasAuthority('read:invoices') directly).
        List<String> perms = jwt.getClaimAsStringList("permissions");
        if (perms != null) {
            perms.stream()
                 .map(SimpleGrantedAuthority::new)
                 .forEach(authorities::add);
        }
        return new JwtAuthenticationToken(jwt, authorities, jwt.getSubject());
    }
}

6.6 The SecurityConfig — tying it together

package com.helios.api.security;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.*;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.oauth2.core.*;
import org.springframework.security.oauth2.jwt.*;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
@EnableMethodSecurity            // turns on @PreAuthorize / @PostAuthorize
public class SecurityConfig {

    @Value("${spring.security.oauth2.resourceserver.jwt.issuer-uri}")
    private String issuer;

    @Value("${auth0.audience}")
    private String audience;

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            // An API has no browser session and no forms -> stateless, no CSRF.
            .csrf(csrf -> csrf.disable())
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/public/**").permitAll()
                // URL-level rule: GET invoices needs the read scope/permission.
                .requestMatchers(HttpMethod.GET, "/api/invoices/**")
                    .hasAuthority("read:invoices")
                .anyRequest().authenticated())
            .oauth2ResourceServer(oauth2 -> oauth2
                .jwt(jwt -> jwt
                    .decoder(jwtDecoder())
                    .jwtAuthenticationConverter(new Auth0AuthoritiesConverter())));
        return http.build();
    }

    @Bean
    JwtDecoder jwtDecoder() {
        // Builds a NimbusJwtDecoder from the issuer's discovery doc (fetches JWKS).
        NimbusJwtDecoder decoder = JwtDecoders.fromIssuerLocation(issuer);

        OAuth2TokenValidator<Jwt> withIssuer =
                JwtValidators.createDefaultWithIssuer(issuer); // exp + iss
        OAuth2TokenValidator<Jwt> withAudience =
                new DelegatingOAuth2TokenValidator<>(
                        withIssuer, new AudienceValidator(audience));

        decoder.setJwtValidator(withAudience);
        return decoder;
    }
}
Tip

We deliberately build the JwtDecoder as an explicit bean instead of relying purely on auto-config, because we need to attach our custom validator chain. JwtValidators.createDefaultWithIssuer already includes the timestamp + issuer checks, so we only add the audience validator rather than re-implementing the defaults.

7. Practical Implementation — The Controller & Method Security

Two complementary places enforce access: URL-level rules in the filter chain (coarse, fast, declared centrally) and method-level rules with @PreAuthorize (fine-grained, close to the business logic, can reference method arguments and the principal).

package com.helios.api.web;

import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.security.core.annotation.AuthenticationPrincipal;
import org.springframework.security.oauth2.jwt.Jwt;
import org.springframework.web.bind.annotation.*;

import java.util.*;

@RestController
@RequestMapping("/api")
public class InvoiceController {

    // No annotation needed: permitAll in SecurityConfig.
    @GetMapping("/public/health")
    public Map<String, String> health() {
        return Map.of("status", "up");
    }

    // Method-level check; equivalent to the URL rule, shown for teaching.
    @GetMapping("/invoices")
    @PreAuthorize("hasAuthority('read:invoices')")
    public List<String> list(@AuthenticationPrincipal Jwt jwt) {
        // jwt.getSubject() is the Auth0 user id (sub claim).
        return List.of("INV-001 owned-by " + jwt.getSubject(), "INV-002");
    }

    // Requires the delete permission AND demonstrates SpEL on arguments.
    @DeleteMapping("/invoices/{id}")
    @PreAuthorize("hasAuthority('delete:invoices')")
    public Map<String, Object> delete(@PathVariable String id,
                                      @AuthenticationPrincipal Jwt jwt) {
        return Map.of("deleted", id, "by", jwt.getSubject());
    }

    // Combine permission + business rule: a manager OR the resource owner.
    @GetMapping("/invoices/{id}")
    @PreAuthorize("hasAuthority('read:invoices') and " +
                  "(hasAuthority('manage:all') or #ownerSub == authentication.name)")
    public Map<String, String> getOne(@PathVariable String id,
                                      @RequestParam String ownerSub) {
        return Map.of("id", id, "owner", ownerSub);
    }
}

To run it against Auth0, perform these dashboard steps once:

  1. APIs → Create API. Set the Identifier to https://api.helios.com (this becomes the token's aud) and signing algorithm RS256.
  2. On the API, toggle Enable RBAC and Add Permissions in the Access Token so the permissions claim is emitted.
  3. Define permissions read:invoices, delete:invoices, manage:all and assign them to roles/users.

Because each pod validates tokens locally, the resource servers are stateless — any pod can serve any request, so horizontal scaling is trivial and there is no session store to share. Auth0 is touched only on cold start and key rotation, not per request, so it is not in the critical latency path. Put TLS, rate limiting, and a WAF at the edge; never expose the resource server directly. The same token works across all microservices that share the issuer, which is the whole point of a centralized authorization server.

Note

For multiple APIs behind the gateway, each Spring service validates its own audience. A token minted for api.billing is rejected by api.analytics — the audience validator is what enforces that isolation between services.

The single most common production vulnerability in Spring resource servers is configuring issuer-uri and assuming you are done. You are not — without the audience validator, any valid Auth0 token from your tenant (including one minted for a totally different, lower-trust API) is accepted. Always validate aud.

10. Performance Considerations

  • Local validation is the win. JWT signature verification is a single RSA public-key operation — microseconds — with no network call on the hot path. This is why local JWT validation scales far better than per-request introspection.
  • JWKS caching. Nimbus caches keys in memory with a refresh window. The cost of fetching JWKS is paid once per pod, plus on rare key rotation, not per request.
  • Cold start. The first request after boot triggers JWKS discovery. Mitigate with a readiness probe that warms the decoder, or accept a tiny first-request penalty.
  • Token size. Large permissions arrays bloat every request header. Prefer coarse scopes for routing and reserve fine permissions for sensitive operations; or resolve detailed permissions from your DB keyed by sub when the list is large.
  • Clock skew. The timestamp validator allows ~60s skew by default. Keep server clocks NTP-synced to avoid spurious exp/nbf failures.
  • Avoid blocking on Auth0. Never call the Auth0 Management API synchronously inside a request to "enrich" the token — that re-introduces the network dependency you eliminated. Cache or use token claims.

11. Common Mistakes

  1. Skipping the audience validator. The flagship mistake. See step 9.
  2. Issuer-uri mismatch. Auth0's iss ends with a trailing slash (https://tenant.auth0.com/). Omit it and validation fails with a confusing "issuer mismatch."
  3. Expecting permissions without enabling RBAC. If RBAC + "Add Permissions in the Access Token" are off in the dashboard, the claim is absent and every hasAuthority('read:invoices') returns 403.
  4. Confusing SCOPE_ prefix vs raw permissions. hasAuthority('SCOPE_read:invoices') matches the scope claim; hasAuthority('read:invoices') matches our mapped permissions. Mixing them silently denies access.
  5. Leaving CSRF on for a stateless API. A bearer-token API has no cookies/session; CSRF protection just breaks non-GET requests. Disable it (and keep it stateless).
  6. Forgetting @EnableMethodSecurity. Without it, @PreAuthorize is silently ignored — endpoints you think are protected are wide open.
  7. Validating the ID token instead of the access token. ID tokens are for the client to learn about the user; resource servers must validate the access token, whose aud is the API.
  8. Using HS256. Forces sharing a secret with every resource server. Use RS256.

12. Best Practices

  • Validate all four: signature, iss, exp, and aud. Treat audience validation as non-negotiable.
  • Deny by default: end the chain with anyRequest().authenticated(), never permitAll().
  • Keep the API stateless and disable CSRF; let the gateway handle TLS, rate limiting, and WAF.
  • Externalize issuer-uri and audience to config/secrets, not hard-coded constants — they differ per environment.
  • Use fine-grained, verb:noun permissions (read:invoices) and enforce them as close to the data as possible with @PreAuthorize.
  • Customize the AccessDeniedHandler/AuthenticationEntryPoint to return clean RFC 6750 WWW-Authenticate error responses (401 vs 403 distinction).
  • Never log tokens; redact the Authorization header in access logs.
  • Write integration tests with jwt() request post-processors so security is part of CI, not an afterthought.

13. Interview Questions (with Model Answers)

Q1. What is a resource server and how does it differ from the authorization server?

Model answer: The authorization server (Auth0) authenticates users and issues tokens; it owns credentials and login flows. The resource server is the API that holds protected data and only consumes tokens — it validates the access token on each request and enforces authorization, but never sees passwords or runs login. Separating them lets one issuer serve many APIs and keeps authentication centralized while authorization stays fast and local.

Q2. Walk me through validating an Auth0 JWT in Spring Boot.

Model answer: Add spring-boot-starter-oauth2-resource-server, set issuer-uri. On first request, NimbusJwtDecoder discovers the JWKS and caches the public keys. For each token it selects the key by kid, verifies the RS256 signature, then runs a validator chain: timestamp (exp/nbf), issuer (iss), and a custom audience validator. A converter then maps claims to authorities and stores the Authentication in the security context.

Q3. Why must you validate the audience claim?

Model answer: Because a token genuinely signed by your tenant might have been issued for a different API. If you only check signature and issuer, that token would be accepted — a confused-deputy attack where a token scoped for API-A is replayed against API-B. The aud claim is the boundary between services; validating it ensures the token was minted specifically for this API.

Q4. Difference between scopes and permissions in Auth0?

Model answer: Scopes (scope claim) are what the client requested and the user consented to; they describe delegated access. Permissions (permissions claim, emitted when RBAC is enabled) are granted to the user via roles, independent of what was requested. In Spring, default conversion prefixes scopes with SCOPE_; we add a converter to map permissions to bare authorities for hasAuthority.

Q5. URL-level vs method-level security — when to use each?

Model answer: URL rules in the filter chain are coarse, central, and run before the controller — great for broad gating and performance. @PreAuthorize is fine-grained, lives next to business logic, and can reference method arguments and the principal via SpEL — great for ownership and contextual rules. Production systems use both: coarse gate at the edge, precise checks at the method.

Q6. How does key rotation not break your API?

Model answer: The decoder caches JWKS but keys carry a kid. When Auth0 rotates and a token arrives with an unknown kid, Nimbus re-fetches the JWKS (rate-limited) and finds the new key. No deploy or restart required.

Q7. Why is local JWT validation preferred over introspection?

Model answer: Local validation needs no per-request network call — just an in-memory RSA verification — so it is faster and removes a runtime dependency on Auth0 in the hot path. Introspection is fresher (handles revocation immediately) but costs a round-trip per request. Most systems pick local validation with short token lifetimes to bound the revocation window.

14. Certification Tips

  • Know the four OAuth roles cold and which one a Spring API plays (resource server). The exam loves role-mapping questions.
  • Memorize that access tokens (not ID tokens) are sent to APIs, and that the API Identifier you set in Auth0 becomes the token aud.
  • Remember the validation quartet: signature, iss, exp, aud. Auth0's own quickstarts add the audience validator manually — expect a question on why.
  • RS256 vs HS256: RS256 (asymmetric) is the Auth0 default for APIs; HS256 requires a shared secret and is discouraged.
  • RBAC settings: "Enable RBAC" + "Add Permissions in the Access Token" control the permissions claim.
  • JWKS endpoint location: /.well-known/jwks.json; discovery at /.well-known/openid-configuration.

20. Key Takeaways

Key

A resource server consumes tokens; it never issues them, holds no passwords, and runs no login. Its job is validate-then-authorize, on every request, locally.

Key

Security rests on the validation quartet: signature, iss, exp, and aud. Spring's issuer-uri gives you the first three for free — you must add the audience validator yourself.

Key

RS256 + JWKS means validation is local and secret-free: Auth0 signs with a private key, you verify with the public key. No per-request call to Auth0, so resource servers stay stateless and scale horizontally.

Key

Map Auth0 permissions to bare Spring authorities, then enforce with coarse URL rules and fine-grained @PreAuthorize (remember @EnableMethodSecurity). Deny by default; 401 = bad token, 403 = insufficient permission.

Test

Prove it end-to-end with a real access token from the Auth0 dashboard's API Test tab — decode it at jwt.io, confirm aud/iss/permissions, then watch a wrong-audience token correctly fail with 401.
