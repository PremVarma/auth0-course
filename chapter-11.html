Chapter 11 — Auth0 Fundamentals: Architecture and Core Concepts

For the last ten chapters you built the theory: identity, OAuth 2.0, OpenID Connect, and the anatomy of a JWT. Now we put a real product behind that theory. This chapter is the map of Auth0 — the mental model that makes every later chapter click into place. We will define, from first principles, what Auth0 actually is, why a company would rent identity instead of building it, and how the nine or ten core nouns of the platform — tenant, region, application, connection, organization, API, scope, Universal Login, the two APIs, and the SDKs — fit together into one request flow. By the end you will be able to draw the entire Auth0 architecture from memory and explain every arrow on the diagram.

1. Theory — Auth0 from First Principles

Every application that has users faces the same unglamorous problem: how do I know who is calling me, and what am I allowed to let them do? That problem splits into two halves you already know by name:

  • Authentication (AuthN) — proving an identity. "You are Alice."
  • Authorization (AuthZ) — deciding permissions for that identity. "Alice may read invoices but not delete them."

Historically each app solved this itself: a users table, a password column, a bcrypt hash, a session cookie. That works for one app with email/password. It collapses the moment the business says: "add Google login," "let enterprise customers use their own SSO," "support passwordless," "add MFA," "be SOC 2 compliant," "rotate signing keys," "block credential-stuffing bots." Each of those is a deep, security-critical subsystem. Building them in-house means you are now an identity company that happens to sell something else.

Auth0 is Identity-as-a-Service (IDaaS): a hosted authorization server and identity platform that implements OAuth 2.0 and OpenID Connect correctly, runs the login UI, stores or federates user identities, issues and signs tokens, and exposes everything through APIs and SDKs. You delegate the hard, dangerous parts of identity to a specialist and keep your codebase focused on your product.

The key first principle: Auth0 is, at its core, an OpenID Connect Provider (OP) and OAuth 2.0 Authorization Server. Everything else — the dashboard, connections, organizations, Actions — is configuration and value-added tooling around that standards-compliant core. Because it speaks the standards you learned in Chapters 4–10, you already understand 70% of it. This chapter teaches the Auth0-specific vocabulary that wraps those standards.

Key

Auth0 does not replace the OAuth/OIDC concepts you learned — it implements them as a product. A "client" becomes an Application, an "authorization server" becomes your tenant, a "resource server" becomes an API, and an "identity provider" becomes a connection.

2. Story-Based Explanation — The Cinema Startup

Meet Maya, founder of CineSpot, a movie-booking startup (we will build exactly this in the Chapter 26 capstone). Week one, she ships a React app with email/password login backed by her own Postgres table. It works.

Week three, marketing wants "Sign in with Google." Maya spends two days wrestling Google's OAuth console, redirect URIs, and token exchange. Week five, a big corporate client says: "Our 4,000 employees must log in with our Okta — we will not create new passwords." That is SAML/enterprise SSO; Maya has no idea where to start. Week six, an attacker runs a credential-stuffing script against her login endpoint and locks out real users. Week seven, the company pursuing SOC 2 asks Maya for her password-rotation, MFA, and breach-detection policies. She has none.

Maya is now spending more time on identity than on movie booking. She signs up for Auth0. She creates a tenant (her private identity universe), registers her React app as an Application, flips on a Google social connection (the corporate Okta becomes an enterprise connection she configures once), turns on MFA and brute-force protection with two toggles, and points her API at an Auth0 API definition with read:bookings and book:tickets scopes. Login now happens on Auth0's Universal Login page. Maya deleted her password table. Her code shrank. She went back to building movie booking.

Every Auth0 noun in bold above is something we define in this chapter. Keep CineSpot in mind — it is the running example.

5. Internal Working — What Each Concept Really Is

5.1 Tenants and Regions

A tenant is a logically isolated instance of Auth0 dedicated to you. It is the top-level container for every other object — applications, APIs, connections, users, keys, logs, and settings. Crucially, the tenant is your authorization server: it owns a unique domain (e.g. cinespot-dev.us.auth0.com) which becomes the issuer (iss) claim in every token and the base of every endpoint. Tenants are hard-isolated from one another: users, connections, and keys never leak across tenants.

You typically run at least three tenants — dev, staging, and prod — because there is no "environments" concept inside a single tenant. Configuration is promoted between tenants with the Deploy CLI / Terraform (covered later).

A region is the geographic home of your tenant's data and compute: US, EU, AU (Australia), or JP (Japan), plus private-cloud options. You pick the region at tenant creation and cannot move it later without a migration. Region choice is driven by two forces: data residency / compliance (GDPR may require EU; some customers require data stay in-country) and latency (put the tenant near your users). The region is encoded in the domain: ...us.auth0.com, ...eu.auth0.com. (Tenants created before regional domains existed may have a bare name.auth0.com — a custom domain is the durable fix.)

5.2 Applications (Clients)

An Application in Auth0 is an OAuth 2.0 client — a piece of software that requests tokens. Each Application has a client_id (public) and, for confidential clients, a client_secret (private). The application type you choose is not cosmetic: it sets safe defaults for which OAuth flows and grant types are allowed, because the security model differs fundamentally depending on whether the client can keep a secret.

TypeExampleCan keep a secret?Flow it uses
Single Page App (SPA)React, Angular, Vue in the browserNo (code is public)Authorization Code + PKCE
Regular Web AppNext.js (server), Spring MVC, Express SSRYes (server-side)Authorization Code (+ secret)
NativeiOS, Android, desktop, mobileNoAuthorization Code + PKCE (system browser)
Machine to Machine (M2M)Cron job, backend service, daemonYesClient Credentials (no user)

Public clients (SPA, Native) cannot hold a secret — anyone can read the JS bundle or decompile the app — so they must use PKCE to protect the code exchange. Confidential clients (Regular Web, M2M) run on a server and can authenticate with a secret. M2M is special: there is no user, so there is no id_token — only an access_token representing the application itself.

5.3 Connections

A connection is a configured source of identities — the bridge between Auth0 and wherever users actually live. Four families:

  • Database connections — Auth0 stores the username/password (Argon2/bcrypt hashed). The default is Username-Password-Authentication. You can also point at your own legacy DB via custom DB scripts.
  • Social connections — federate to Google, Apple, GitHub, Facebook, Microsoft, etc. via OAuth. Auth0 brokers the OAuth dance with the provider for you.
  • Enterprise connections — corporate IdPs via SAML, OIDC, WS-Fed, Azure AD / Entra ID, Okta, ADFS, Google Workspace, LDAP/AD (via connector). This is how Maya's corporate client logs in with their own Okta.
  • Passwordless connections — no password at all: email magic link / OTP or SMS OTP.

A connection is enabled per-application: an app can offer database + Google, while a B2B org offers only its enterprise connection. The same human can have multiple connection identities (Google and database) which can be account-linked into one user.

5.4 Organizations

Organizations are Auth0's first-class B2B feature: logical groupings of users that represent your business customers inside a single tenant. Each organization can have its own enabled connections (Acme uses Acme's Okta; Globex uses Google), its own branding on the login page, its own membership and roles, and its own invitations. A user can belong to several organizations. The org context is carried in the org_id token claim, so your API can enforce tenant isolation ("this token is for Acme's data only"). Use organizations when you sell to companies; you do not need them for a pure consumer (B2C) app.

5.5 Universal Login vs Embedded Login

Universal Login means the login UI is hosted by Auth0 on your tenant domain. Your app redirects the browser to /authorize; Auth0 renders the page, collects credentials, runs MFA, and redirects back with a code. Embedded login means you build your own login form and POST credentials through the Authentication API from your app.

Auth0 strongly recommends Universal Login, and so does every security-minded engineer, for reasons we detail in §9: credentials are never typed into your origin (phishing-resistant), you get SSO and MFA "for free," and new features (passkeys, bot detection) light up without code changes. We cover the why in depth in the Security Analysis section.

5.6 Authentication API vs Management API

Auth0 exposes two completely different APIs, and confusing them is the #1 beginner mistake:

  • Authentication API (https://YOUR_DOMAIN/...) — the OAuth/OIDC runtime: /authorize, /oauth/token, /userinfo, /.well-known/openid-configuration, /.well-known/jwks.json, logout. This is what end-users and your app touch to log in and get tokens. Public-facing.
  • Management API (https://YOUR_DOMAIN/api/v2/...) — the admin/CRUD API for the tenant: create users, assign roles, list connections, configure clients programmatically. It is itself an Auth0 API with audience https://YOUR_DOMAIN/api/v2/; you call it with an M2M access token. Backend-only — never from a browser.

5.7 APIs, Audiences, and Scopes/Permissions

In Auth0 an API is a resource server registration. Its most important field is the identifier, a URL-shaped string (it need not be reachable) that becomes the audience (aud) of access tokens minted for it — e.g. https://api.cinespot.com. When a client asks for a token, it sets audience=https://api.cinespot.com; Auth0 then issues a JWT access token aimed at that API (without an audience for a custom API, you get an opaque token only good for /userinfo).

Scopes are the permissions an API defines: read:bookings, book:tickets, manage:screenings. A client requests scopes; the issued token's scope (or permissions) claim lists what was granted. With RBAC enabled on the API, you define permissions, group them into roles, assign roles to users, and Auth0 puts the user's effective permissions in the token. Your API then checks "does this token carry book:tickets?" before letting the call through.

6.2 React SPA — Universal Login with the React SDK

Note the audience: without it you get an id_token but no API-ready access token. The SDK does PKCE for you.

// main.jsx
import { Auth0Provider } from "@auth0/auth0-react";

<Auth0Provider
  domain="cinespot-dev.us.auth0.com"
  clientId="SPA_CLIENT_ID"
  authorizationParams={{
    redirect_uri: window.location.origin,
    audience: "https://api.cinespot.com",        // ask for an API token
    scope: "openid profile email read:bookings"  // request permissions
  }}>
  <App />
</Auth0Provider>
// App.jsx — login, read user, call the API
import { useAuth0 } from "@auth0/auth0-react";

function App() {
  const { loginWithRedirect, logout, user, isAuthenticated,
          getAccessTokenSilently } = useAuth0();

  if (!isAuthenticated)
    return <button onClick={() => loginWithRedirect()}>Log in</button>;

  const callApi = async () => {
    const token = await getAccessTokenSilently();          // access_token
    const res = await fetch("https://api.cinespot.com/bookings", {
      headers: { Authorization: `Bearer ${token}` }        // gate scan
    });
    console.log(await res.json());
  };

  return (
    <>
      <p>Hello {user.name}</p>
      <button onClick={callApi}>Load bookings</button>
      <button onClick={() => logout()}>Log out</button>
    </>
  );
}

6.3 Spring Boot — validating the access token (resource server)

The API never calls Auth0 per request; it fetches the JWKS once, caches the public keys, and verifies signatures locally. This is the "gate agent" in our analogy.

# application.yml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://cinespot-dev.us.auth0.com/
          audiences: https://api.cinespot.com   # reject tokens for other APIs
// SecurityConfig.java
@Configuration
@EnableMethodSecurity
public class SecurityConfig {
  @Bean
  SecurityFilterChain api(HttpSecurity http) throws Exception {
    http
      .authorizeHttpRequests(reg -> reg
        .requestMatchers(HttpMethod.GET, "/bookings")
          .hasAuthority("SCOPE_read:bookings")   // require the scope
        .anyRequest().authenticated())
      .oauth2ResourceServer(o -> o.jwt(org.springframework.security.config.Customizer.withDefaults()));
    return http.build();
  }
}

6.4 FastAPI — validate a JWT against Auth0 JWKS

# deps.py
import jwt
from jwt import PyJWKClient
from fastapi import Depends, HTTPException, Security
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

ISSUER   = "https://cinespot-dev.us.auth0.com/"
AUDIENCE = "https://api.cinespot.com"
jwks = PyJWKClient(f"{ISSUER}.well-known/jwks.json")   # cached

def verify(creds: HTTPAuthorizationCredentials = Security(HTTPBearer())):
    token = creds.credentials
    key = jwks.get_signing_key_from_jwt(token).key
    try:
        return jwt.decode(token, key, algorithms=["RS256"],
                          audience=AUDIENCE, issuer=ISSUER)
    except jwt.PyJWTError:
        raise HTTPException(status_code=401, detail="invalid token")
# main.py
from fastapi import FastAPI, Depends
app = FastAPI()

@app.get("/bookings")
def bookings(claims: dict = Depends(verify)):
    if "read:bookings" not in claims.get("scope", "").split():
        raise HTTPException(403, "insufficient scope")
    return {"sub": claims["sub"], "bookings": []}

7. Practical Implementation — Stand Up a Tenant in 10 Steps

  1. Sign up at auth0.com; pick a region (match your users/compliance). Your first tenant is created — name it yourco-dev.
  2. Dashboard → Applications → create one of type Single Page Application. Copy its client_id.
  3. In the app settings, add Allowed Callback URLs (http://localhost:3000), Allowed Logout URLs, and Allowed Web Origins.
  4. Dashboard → APIs → create one; set the Identifier to https://api.cinespot.com. Add scopes/permissions.
  5. On the API, enable RBAC and "Add Permissions in the Access Token" if you want permissions in the JWT.
  6. Dashboard → Authentication → Database: keep Username-Password-Authentication; enable it for your app.
  7. Dashboard → Authentication → Social: add Google; enable for your app. (Use your own Google client ID in prod — the dev keys are shared and rate-limited.)
  8. Dashboard → Security → Attack Protection: turn on Brute-force and Suspicious IP Throttling. Security → Multi-factor: enable MFA.
  9. Wire the SDK (the React code above). Log in via Universal Login; inspect the tokens at jwt.io.
  10. Create a separate yourco-prod tenant; never test in prod. Promote config via the Deploy CLI / Terraform.
Tip

Set up a custom domain (auth.cinespot.com) early. It keeps cookies first-party, looks professional, and decouples you from the regional *.auth0.com hostname so you can migrate without breaking the issuer in clients.

8. Production Architecture

A real CineSpot deployment separates concerns by application type and keeps tokens flowing the right way:

                         ┌───────────────────────────────────────────┐
                         │   AUTH0 TENANT (prod, EU region)            │
                         │   custom domain: auth.cinespot.com          │
   ┌─────────┐  redirect │   Universal Login · Connections · Actions   │
   │ React   │──────────>│   APIs: https://api.cinespot.com            │
   │ SPA     │<──tokens── │   M2M client for jobs + Management API      │
   └────┬────┘           └───────────────┬─────────────────────────────┘
        │ Bearer access_token            │ JWKS (public keys, cached)
        v                                v
   ┌─────────────┐   internal    ┌──────────────┐   ┌──────────────┐
   │ Next.js BFF │──────────────>│ Spring Boot  │   │ FastAPI      │
   │ (Reg.WebApp)│   service mesh │ Booking API  │   │ Pricing API  │
   └─────────────┘               └──────┬───────┘   └──────┬───────┘

        │ session cookie (httpOnly)      └── audience+scope ─┘

                                  └────────────────────────────┘
  • SPA uses PKCE, stores tokens in memory, calls APIs directly with bearer tokens.
  • Next.js BFF (Backend-for-Frontend, a Regular Web App) holds an httpOnly session cookie — the most secure pattern for browser apps because no tokens touch JS.
  • APIs are independent resource servers; each validates the JWT against the cached JWKS — zero per-request calls to Auth0.
  • M2M jobs use Client Credentials; rotate secrets via a vault.
  • Three tenants (dev/staging/prod), config as code (Terraform/Deploy CLI), prod in the compliance-required region.

9. Security Analysis

Why Universal Login over embedded login (the deepest reason): with embedded login your app's origin handles raw passwords, which means (a) any XSS on your origin can keylog credentials, (b) you become the phishing target, (c) cross-origin credential POSTs invite CSRF and CORS pain, and (d) you re-implement MFA, bot detection, and breach-password checks yourself. Universal Login moves credential entry to Auth0's hardened, isolated origin: your app never sees the password, attackers cannot phish what your origin never collects, and security upgrades (passkeys, bot detection) deploy without touching your code. This is the same principle as "never type your bank password into a third-party site."

Audience is a security boundary, not a formality. A token minted for https://api.cinespot.com must be rejected by any other API. If your resource server skips the aud check, a token leaked from a low-value service can be replayed against a high-value one (the "confused deputy" / token-reuse attack). Always validate issuer and audience and signature.

Public clients must use PKCE. SPAs and native apps cannot keep a secret; PKCE binds the authorization code to the client that started the flow, defeating code interception. Never use the legacy Implicit flow, and never ship a "client_secret" inside a SPA.

Tenant isolation & least privilege. Keep dev/staging/prod as separate tenants. Give each M2M client only the scopes it needs on the Management API — a sync job does not need delete:users. Treat the Management API token like a root credential: backend-only, short-lived, scoped.

Danger

Never call the Management API from a browser or mobile app, and never embed its M2M secret in client code. A leaked Management token can read every user, reset passwords, and reconfigure the tenant.

10. Performance Considerations

  • Validate JWTs locally. RS256 verification uses the public keys from JWKS, fetched and cached by your SDK. Do not hit Auth0 per request. This makes token validation a sub-millisecond CPU op and lets your API scale horizontally without depending on Auth0's uptime per call.
  • Cache JWKS, but respect rotation. SDKs cache keys and re-fetch on an unknown kid. Don't hardcode a public key — Auth0 rotates signing keys; hardcoding breaks logins on rotation.
  • Prefer JWT access tokens over /userinfo. Calling /userinfo on every request adds a network round-trip to Auth0. Put the claims you need in the token (via Actions) and read them locally.
  • Right-size token lifetimes. Short access tokens (e.g. 15–60 min) + refresh tokens balance security and the cost of re-authenticating. Avoid silent-auth storms by using refresh token rotation.
  • Region/latency. Put the tenant near your users; use a custom domain on a CDN-backed edge. Login latency is dominated by redirect round-trips, not token validation.
  • Rate limits. The Management API is rate-limited. Don't use it on the hot path — cache results, batch, and treat it as an admin tool, not a runtime dependency.

11. Common Mistakes

  • Forgetting audience → you get an opaque access token (or only an id_token) and your API rejects it. The id_token is for the client, not the API.
  • Sending the id_token to your API. The id_token authenticates the user to the client; APIs must consume the access_token.
  • Confusing the two APIs — calling /api/v2/users with a user's login token (it has the wrong audience), or trying to log users in via the Management API.
  • Embedding login / shipping a client_secret in a SPA. Public clients have no secret; use PKCE + Universal Login.
  • Skipping issuer/audience validation on the resource server — accepting any signed token.
  • One tenant for all environments. Testing in prod corrupts real users and logs.
  • Wrong application type (e.g. "Regular Web App" for a React SPA) → wrong default grants and a secret you can't protect.
  • Hardcoding the JWKS key → logins break on key rotation.
  • Picking the wrong region at creation and discovering a compliance problem later — you cannot move it in place.

12. Best Practices

  • Use Universal Login everywhere; treat embedded login as a last resort.
  • One API per resource server with a clear, URL-shaped identifier; always send the matching audience.
  • Choose the correct application type; let it set safe default grants.
  • Separate tenants per environment; manage config as code (Terraform / Deploy CLI) and promote dev → staging → prod.
  • Set up a custom domain for first-party cookies and durable issuer URLs.
  • Enable MFA and Attack Protection from day one.
  • Use RBAC + roles for permissions; keep scopes granular (read:bookings, not admin).
  • Validate signature + issuer + audience + expiry on every API.
  • Keep M2M secrets in a vault; grant least-privilege Management scopes.
  • Use the SDKs rather than hand-rolling flows; they handle PKCE, storage, and validation correctly.

13. Interview Questions (with model answers)

Q1. What is Auth0 at its core, and what problem does it solve?

A. Auth0 is Identity-as-a-Service — a hosted OAuth 2.0 authorization server and OpenID Connect provider. It solves the problem that authentication/authorization is a deep, security-critical subsystem (social login, enterprise SSO, MFA, breach detection, key rotation, compliance) that every app needs but few should build. You delegate it and keep your codebase focused on your product.

Q2. Explain tenants and why you'd use more than one.

A. A tenant is an isolated Auth0 instance and your authorization server; its domain is the token issuer. There is no environments concept inside a tenant, so you run separate dev/staging/prod tenants and promote config as code, avoiding any chance of testing against real users.

Q3. What's the difference between the four application types?

A. It's about whether the client can keep a secret. SPA and Native are public clients (no secret) and must use Authorization Code + PKCE. Regular Web App is confidential (server-side, uses a secret). M2M has no user and uses Client Credentials, receiving only an access token.

Q4. id_token vs access_token — which goes where?

A. The id_token authenticates the user to the client (the app reads who the user is). The access_token authorizes calls to an API and is audience-scoped; the resource server validates and consumes it. Sending the id_token to an API is a classic bug.

Q5. Authentication API vs Management API?

A. The Authentication API is the runtime OIDC/OAuth surface (/authorize, /oauth/token, /userinfo) used to log users in and mint tokens. The Management API (/api/v2/*) is the admin CRUD API for the tenant, called from a backend with an M2M token — never from a browser.

Q6. What is an audience and why does it matter for security?

A. The audience is the API the token is intended for (the aud claim). Validating it prevents a token issued for one API from being replayed against another (confused-deputy/token-reuse). It's a hard security boundary, not metadata.

Q7. Why is Universal Login preferred over embedded login?

A. Credentials are entered on Auth0's isolated origin, so your app never handles passwords — phishing- and XSS-resistant — and you get SSO, MFA, bot detection, and passkeys without writing security code. Embedded login makes your origin the attack surface.

Q8. How does an API validate a token at scale without calling Auth0 each time?

A. It fetches the tenant's JWKS once, caches the RS256 public keys, and verifies the signature locally, also checking issuer, audience, and expiry. This is O(1) CPU and removes Auth0 from the per-request path.

Q9. What are Organizations and when do you use them?

A. Organizations model your B2B customers inside one tenant — each with its own connections, branding, members, and roles, surfaced via the org_id claim. Use them for multi-tenant SaaS; you don't need them for pure consumer apps.

Q10. Name the connection types and give an example of each.

A. Database (Auth0-stored username/password), Social (Google/Apple via OAuth), Enterprise (corporate Okta/Entra via SAML/OIDC), Passwordless (email magic link or SMS OTP).

14. Certification Tips

Exam focus

The Auth0/Okta certification (and the "Identity Fundamentals"/CIAM tracks) lean heavily on the vocabulary in this chapter.

  • Memorize the mapping: Application = client, API = resource server, tenant = authorization server, connection = identity provider.
  • Know which flow each application type uses by default (SPA/Native → Code+PKCE; Regular Web → Code+secret; M2M → Client Credentials).
  • Be crystal clear on Authentication API vs Management API and their audiences (YOUR_DOMAIN vs YOUR_DOMAIN/api/v2/).
  • Know that id_token = AuthN for the client, access_token = AuthZ for the API, and that custom-API access tokens are JWTs while no-audience tokens are opaque.
  • Remember Universal Login is recommended; embedded login is the exception.
  • Understand regions (data residency, can't move in place) and that the tenant domain is the issuer.
  • Recognize the four connection types and the role of Organizations for B2B.
  • Know that APIs validate tokens via JWKS with RS256 and must check iss/aud/exp/sig.

19. Cheat Sheet

  MENTAL MAP (standards -> Auth0)
    client            = Application      (SPA | Regular Web | Native | M2M)
    authorization srv = Tenant           (domain = issuer; lives in a Region)
    resource server   = API              (Identifier = audience)
    identity provider = Connection       (database | social | enterprise | passwordless)
    B2B grouping      = Organization     (org_id claim)

  TOKENS
    id_token      -> CLIENT  (who the user is)        | AuthN
    access_token  -> API     (what they may do, aud)  | AuthZ
    refresh_token -> renew access tokens

  TWO APIs
    Authentication API : /authorize /oauth/token /userinfo   (login + tokens)
    Management API     : /api/v2/*  aud=YOUR_DOMAIN/api/v2/  (admin, backend only)

  FLOWS BY APP TYPE
    SPA / Native  -> Authorization Code + PKCE
    Regular Web   -> Authorization Code + client_secret
    M2M           -> Client Credentials (no user, no id_token)

  ALWAYS SEND audience=<your API id> to get a JWT access token.
  ALWAYS VALIDATE sig + iss + aud + exp on the API (via JWKS / RS256).
  PREFER Universal Login. SEPARATE tenants per environment.

  KEY ENDPOINTS
    https://YOUR_DOMAIN/.well-known/openid-configuration
    https://YOUR_DOMAIN/.well-known/jwks.json

20. Key Takeaways

Key

Auth0 is a hosted OAuth 2.0 / OpenID Connect provider — it implements the standards you already learned as a product, so the vocabulary is just a renaming: client → Application, auth server → Tenant, resource server → API, IdP → Connection.

Key

The tenant is your isolated authorization server; its domain is the token issuer; its region (fixed at creation) governs data residency and latency. Run separate tenants per environment.

Key

Application type = "can it keep a secret?" Public (SPA/Native) → PKCE; confidential (Regular Web) → secret; M2M → Client Credentials with no user and no id_token.

Key

id_token authenticates the user to the client; access_token authorizes the API and is audience-scoped. Always send audience to get a JWT; always validate sig + iss + aud + exp on the API via cached JWKS.

Key

Two distinct APIs: the Authentication API (runtime login/tokens) and the Management API (backend-only admin CRUD). Never confuse them; never call Management from a browser.

Key

Prefer Universal Login (credentials never touch your origin), use Connections for identity sources, Organizations for B2B, and the official SDKs so PKCE, storage, and validation are correct by default.
