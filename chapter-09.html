Chapter 9 — JWT Deep Dive: Structure and Algorithms

Every time Auth0 logs a user in, it hands your application a small, dense string of characters — a JSON Web Token. That string is the beating heart of modern identity: it is how your backend knows who is calling without a database lookup, how a mobile app proves it is allowed to hit your API, and how a microservice trusts a request that travelled through five other services first. In this chapter we crack the JWT wide open. We will read it byte by byte, learn exactly why it is encoded the way it is, master the cryptography that makes it tamper-proof, and write real code in Node.js, Java, Python, and the browser that decodes and verifies one correctly. By the end you will never again copy-paste a token into a website to "see what's inside" — you will know precisely what is inside, and more importantly, whether you should believe it.

1. Theory — First Principles: What a JWT Actually Is

Start with the problem, not the solution. HTTP is stateless: every request arrives as if the server has never seen the client before. Yet we need the server to know "this request is from Alice, and Alice is an admin." There are two broad ways to solve this:

  1. Stateful sessions: the server stores a random opaque session ID in memory or a database. The client sends the ID; the server looks it up to find who the ID belongs to. The truth lives on the server.
  2. Stateless tokens: the server hands the client a self-describing token that contains the identity claims, cryptographically sealed so it cannot be forged. The client sends the token; the server verifies the seal and reads the claims directly. The truth travels with the request.

A JWT (JSON Web Token, RFC 7519) is the second approach. It is a compact, URL-safe container for a set of claims (statements about an entity, usually a user) that is digitally signed so any party with the right key can confirm two things: the claims have not been altered, and they were issued by who they say they were.

The word "token" is generic; the precision comes from the layers. A JWT is the payload format. The signing/encryption rules come from JOSE (Javascript Object Signing and Encryption), which splits into:

  • JWS — JSON Web Signature (RFC 7515): a token that is signed. Anyone can read it; only the holder of the key can have created it. This is what Auth0 issues by default (an ID token and access token are signed JWTs).
  • JWE — JSON Web Encryption (RFC 7516): a token that is encrypted. Only the holder of the decryption key can read it. Rarer; used when claims are sensitive.
Key

A signed JWT is not secret. Anyone who intercepts it can read every claim. The signature guarantees integrity and authenticity (it wasn't changed, it came from the real issuer), not confidentiality. Never put a password, a credit card number, or any secret in a JWT payload.

The defining property is self-verification: given only the token and a public key (or shared secret), a resource server thousands of miles from Auth0, with no network call back to Auth0, can decide whether to trust the token. That property is what makes JWTs the lingua franca of distributed systems.

2. Story-Based Explanation — The Sealed Festival Wristband

Imagine a three-day music festival. At the gate you show your ticket and ID. The staff don't want to check your ID every time you walk between stages, food trucks, and the VIP lounge — that would create huge queues. So they give you a wristband.

On the wristband, written in plain ink, is some information: your name, your ticket tier (General / VIP / Artist), and an expiry stamp ("valid until Sunday 23:59"). Anyone can read it — it's right there on your wrist. But the wristband also has a special holographic seal that only the festival's machine at the gate can produce. Bouncers at each stage carry a small UV light. They don't re-check your ID; they just shine the light on the seal. If the hologram is genuine and the expiry hasn't passed, you're waved through.

Now map the story:

  • The festival gate machine is Auth0's authorization server — only it can mint genuine wristbands.
  • The ink-written info (name, tier, expiry) is the JWT payload / claims — readable by anyone.
  • The holographic seal is the signature.
  • The bouncer's UV light is your API verifying the signature with the public key.
  • A forged wristband drawn with a marker has no real hologram — the UV light reveals it instantly. That's a tampered JWT failing signature verification.

One subtlety the story teaches: the bouncer never phones the front gate. The whole point of the seal is that verification is local. That is exactly why a JWT lets ten microservices trust a token without any of them calling Auth0 on every request.

5. Internal Working — Base64url, Claims, and the Signature Math

5.1 Base64url encoding — what and why

Each of the three parts is text encoded with Base64url. Base64 takes arbitrary bytes and represents them using 64 printable characters (A–Z, a–z, 0–9, plus two more), turning every 3 bytes into 4 characters. Standard Base64 uses +, /, and = padding. Those characters are problematic in URLs and HTTP headers: + means space in query strings, / is a path separator, and = needs escaping.

Base64url (RFC 4648 §5) fixes this with two substitutions and one removal:

Standard Base64Base64url
+ (plus)- (hyphen)
/ (slash)_ (underscore)
= paddingremoved entirely
Warn

Base64url is encoding, not encryption. It scrambles nothing — it is fully reversible by anyone with no key. The header and payload of every signed JWT are wide open. Decoding them is trivial (we'll do it in code). Encoding exists only to make arbitrary JSON safe to transport in a URL or header.

Let's decode a real header by hand. The string eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9 is Base64url. Decoded, it is the ASCII text:

{"alg":"RS256","typ":"JWT"}

5.2 The header

The header is JSON describing how the token was signed. Common fields:

FieldMeaning
algSigning algorithm, e.g. RS256, HS256, ES256. Required.
typType, usually JWT. For access tokens Auth0 may use at+jwt (RFC 9068).
kidKey ID — tells the verifier which public key in the JWKS to use. Essential for rotation.

5.3 The payload and the signature math

The payload is JSON containing the claims (next section). The signature is where cryptography enters. Define:

 signingInput = base64url(header) + "." + base64url(payload)

 HS256:  signature = HMAC-SHA256( signingInput, secret )
         verify: recompute HMAC with same secret, compare to S

 RS256:  signature = RSA-PKCS1v1.5-SHA256-SIGN( signingInput, privateKey )
         verify: RSA-VERIFY( signingInput, S, publicKey )

 ES256:  signature = ECDSA-P256-SHA256-SIGN( signingInput, privateKey )
         verify: ECDSA-VERIFY( signingInput, S, publicKey )

Notice the asymmetry of trust. With HMAC (HS256) the same secret both creates and checks the signature — symmetric. With RSA/ECDSA the private key creates and the public key only checks — asymmetric. That single difference drives nearly every architectural decision later in this chapter.

6. Code Walkthrough — Building and Reading a JWT from Scratch

To truly understand a JWT, build one without a library first. This Node.js script signs and verifies an HS256 token using only the built-in crypto module — no dependencies. Read every line; the comments explain the why.

// build-jwt.js  — run with: node build-jwt.js
import crypto from "node:crypto";

// Base64url helpers: encode bytes/JSON to base64url, and back.
const b64url = (buf) =>
  Buffer.from(buf)
    .toString("base64")
    .replace(/\+/g, "-")   // + -> -
    .replace(/\//g, "_")   // / -> _
    .replace(/=+$/g, "");  // strip padding

const fromB64url = (str) =>
  Buffer.from(str.replace(/-/g, "+").replace(/_/g, "/"), "base64");

const secret = "super-secret-shared-key-keep-this-safe";

// 1. Header: declare the algorithm.
const header  = { alg: "HS256", typ: "JWT" };

// 2. Payload: the claims. iat/exp are UNIX seconds (NOT milliseconds).
const now = Math.floor(Date.now() / 1000);
const payload = {
  sub: "user_42",
  name: "Alice",
  roles: ["admin"],
  iat: now,
  exp: now + 3600,            // expires in 1 hour
  iss: "https://my-app.example.com/",
  aud: "https://api.my-app.example.com",
};

// 3. Encode header and payload, join with a dot = the signing input.
const encHeader  = b64url(JSON.stringify(header));
const encPayload = b64url(JSON.stringify(payload));
const signingInput = `${encHeader}.${encPayload}`;

// 4. Sign: HMAC-SHA256 over the signing input, keyed by the secret.
const signature = b64url(
  crypto.createHmac("sha256", secret).update(signingInput).digest()
);

const token = `${signingInput}.${signature}`;
console.log("TOKEN:\n", token);

// ---- VERIFY (what a resource server does) ----
function verify(token, secret) {
  const [h, p, s] = token.split(".");
  if (!h || !p || !s) throw new Error("Malformed token");

  // Recompute the signature over the received header.payload.
  const expected = b64url(
    crypto.createHmac("sha256", secret).update(`${h}.${p}`).digest()
  );

  // Constant-time compare to avoid timing attacks.
  const ok = crypto.timingSafeEqual(Buffer.from(s), Buffer.from(expected));
  if (!ok) throw new Error("Invalid signature — token was tampered with!");

  const claims = JSON.parse(fromB64url(p).toString("utf8"));

  // Claim checks — the signature being valid is NOT enough.
  const nowSec = Math.floor(Date.now() / 1000);
  if (claims.exp && nowSec >= claims.exp) throw new Error("Token expired");
  if (claims.iss !== "https://my-app.example.com/") throw new Error("Bad issuer");
  if (claims.aud !== "https://api.my-app.example.com") throw new Error("Bad audience");

  return claims;
}

console.log("VERIFIED CLAIMS:\n", verify(token, secret));
Tip

Note the two-stage validation: first the signature (is this token genuine and unaltered?), then the claims (exp, iss, aud — is it for me, right now?). A token can have a perfect signature and still be wrong for your API. Real libraries do both for you, but you must configure the claim checks.

7. Practical Implementation — Verifying Auth0 Tokens with Real Libraries

You will almost never hand-roll JWT code in production. Auth0 issues RS256 tokens, so your API fetches Auth0's public keys from its JWKS endpoint and verifies with them. Here are correct, runnable examples per stack.

7.1 Node.js / Express — express-oauth2-jwt-bearer

// npm i express express-oauth2-jwt-bearer
import express from "express";
import { auth } from "express-oauth2-jwt-bearer";

const app = express();

// This middleware fetches Auth0's JWKS, caches keys, picks by `kid`,
// verifies the RS256 signature, and checks iss/aud/exp automatically.
const checkJwt = auth({
  audience: "https://api.my-app.example.com",          // must equal token `aud`
  issuerBaseURL: "https://YOUR_TENANT.us.auth0.com/",  // builds iss + JWKS url
  tokenSigningAlg: "RS256",                            // pin the algorithm!
});

app.get("/api/private", checkJwt, (req, res) => {
  // req.auth.payload now holds the verified claims.
  res.json({ message: "Verified!", sub: req.auth.payload.sub });
});

app.listen(3000, () => console.log("API on :3000"));

7.2 Node.js — manual verification with jose + remote JWKS

// npm i jose
import { jwtVerify, createRemoteJWKSet } from "jose";

const JWKS = createRemoteJWKSet(
  new URL("https://YOUR_TENANT.us.auth0.com/.well-known/jwks.json")
);

export async function verifyAccessToken(token) {
  const { payload, protectedHeader } = await jwtVerify(token, JWKS, {
    issuer: "https://YOUR_TENANT.us.auth0.com/",
    audience: "https://api.my-app.example.com",
    algorithms: ["RS256"],   // never trust alg from the header alone
  });
  return payload; // exp/nbf checked automatically by jwtVerify
}

7.3 Java Spring Boot — resource server (Spring Security)

// build.gradle: org.springframework.boot:spring-boot-starter-oauth2-resource-server
// application.yml configures issuer + audience; Spring builds the JWKS pipeline.

7.4 Python FastAPI — verify with PyJWT + JWKS

# pip install fastapi "pyjwt[crypto]" requests uvicorn
import jwt
from jwt import PyJWKClient
from fastapi import FastAPI, Depends, HTTPException
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

ISSUER   = "https://YOUR_TENANT.us.auth0.com/"
AUDIENCE = "https://api.my-app.example.com"
jwks_client = PyJWKClient(f"{ISSUER}.well-known/jwks.json")

app = FastAPI()
bearer = HTTPBearer()

def verify(creds: HTTPAuthorizationCredentials = Depends(bearer)):
    token = creds.credentials
    try:
        # Pick the right public key using the token's `kid`.
        signing_key = jwks_client.get_signing_key_from_jwt(token).key
        claims = jwt.decode(
            token, signing_key,
            algorithms=["RS256"],          # pin algorithm
            audience=AUDIENCE,             # checks `aud`
            issuer=ISSUER,                 # checks `iss`
        )                                  # checks exp/nbf automatically
        return claims
    except jwt.PyJWTError as e:
        raise HTTPException(status_code=401, detail=str(e))

@app.get("/api/private")
def private(claims=Depends(verify)):
    return {"sub": claims["sub"]}

8. Production Architecture — Issuer, JWKS, and Distributed Verification

In production, signing and verifying live in different places, connected only by the public key distributed through JWKS. Here is the canonical picture.

                         AUTH0 TENANT (issuer)
                  +--------------------------------+
                  |  Authorization Server          |
   user login --> |  - holds PRIVATE signing keys  |
                  |  - signs RS256 tokens          |
                  |  - publishes PUBLIC keys at:   |
                  |    /.well-known/jwks.json      |
                  +----------------+---------------+
                                   |
            access token (JWT)     |   JWKS (public keys, by kid)
            handed to client       |   fetched + cached by APIs
                                   |
        +--------------+-----------+-----------+--------------+
        v              v                       v              v
  +-----------+  +-----------+           +-----------+  +-----------+
  | Orders    |  | Payments  |   . . .   | Inventory |  | Reporting |
  | API       |  | API       |           | API       |  | API       |
  | verify    |  | verify    |           | verify    |  | verify    |
  | locally   |  | locally   |           | locally   |  | locally   |
  +-----------+  +-----------+           +-----------+  +-----------+
   each service verifies the SAME token with the SAME public key,
   independently, with NO call back to Auth0 per request.

The JWKS document is just JSON listing one or more public keys, each tagged with a kid:

{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "kid": "NEC1...currentKey",
      "n":   "0vx7agoebGc...very-long-modulus...",
      "e":   "AQAB",
      "alg": "RS256"
    },
    {
      "kty": "RSA", "use": "sig", "kid": "PRE2...nextKey",
      "n": "...", "e": "AQAB", "alg": "RS256"
    }
  ]
}

Key rotation works like this: Auth0 starts signing with a new key while still publishing the old public key in JWKS. Tokens already in the wild carry the old kid and still verify; new tokens carry the new kid. Your library matches by kid and "just works" across the rollover, because it fetches the current JWKS. This is why you must look up the key by kid and cache JWKS with a sensible TTL, rather than hardcoding a public key.

Key

The architectural superpower of RS256 + JWKS: a brand-new microservice can verify Auth0 tokens with zero shared secrets and zero coordination — it just fetches the public JWKS. With HS256 you would have to securely distribute the same secret to every service, and any one of them could mint tokens. That is why Auth0 defaults to and recommends RS256.

9.2 The "alg: none" attack

The original JWT spec allowed "alg":"none" — an unsigned token. Naive verifiers that "trusted" the header's algorithm would accept a token with an empty signature, letting an attacker craft {"sub":"admin"} with no signature at all. Defense: never let the token's header decide the algorithm. Always pass an explicit allow-list (algorithms: ["RS256"]) to your verify call. Every example in this chapter does this.

9.3 The RS256 → HS256 confusion attack

If a server is configured to "verify with the public key" but lets the header pick the algorithm, an attacker can take the well-known RSA public key, switch the header to HS256, and HMAC-sign the token using the public key as the HMAC secret. A buggy verifier would then HMAC-verify with that same public key — and accept the forgery. Defense, again: pin algorithms: ["RS256"] so an HS256 token is rejected outright.

Danger

The two deadliest JWT mistakes are (1) trusting alg from the token header, and (2) skipping aud/iss/exp validation. Either one alone can turn "verified" into "owned." A valid signature only proves the token wasn't altered — it says nothing about whether the token was meant for your API or whether it is still in date.

9.4 Other essentials

  • Confidentiality: signed JWTs are readable. Don't store secrets in claims; serve everything over HTTPS so tokens aren't sniffed.
  • Revocation: a signed JWT is valid until exp regardless of logout. Keep access-token lifetimes short (minutes), use refresh tokens for renewal, and use Auth0 features (token revocation, sender-constraining) for high-risk cases.
  • Storage in browsers: prefer in-memory or secure, HttpOnly cookies over localStorage to reduce XSS theft risk.
  • Clock skew: allow a small leeway (e.g. 60s) on exp/nbf so minor clock differences don't reject valid tokens.

10. Performance Considerations

  • Verification is local and cheap. RS256 signature verification is on the order of microseconds-to-low-milliseconds — vastly faster than a network round-trip to a session store. This is the headline performance win of JWTs.
  • Cache the JWKS. Never fetch /.well-known/jwks.json on every request. Libraries cache it; tune the TTL (commonly 10 minutes to a few hours). On a kid miss, refetch once — that gracefully handles rotation.
  • HS256 verify is fastest (a single HMAC), RS256 verify is fast (public-exponent is small, so RSA verify is cheap even though RSA sign is slow), ES256 verify is fast and produces much smaller tokens.
  • Token size matters on the wire. Every API call carries the whole token in the header. Bloated custom claims inflate every request and can blow past header size limits (often ~8 KB). Keep payloads lean; fetch large profile data from an endpoint, don't stuff it into the token.
  • Avoid double work. Verify once per request at the edge/gateway, then pass the decoded claims downstream rather than re-verifying in every service if they share a trust boundary.
  Stateful session lookup        Stateless JWT verify
  ----------------------         --------------------
  request --> cache/db  (network) request --> CPU verify (local)
          ~1-10 ms per hit                ~0.01-1 ms, no network
  scales with shared store        scales horizontally, no shared store

11. Common Mistakes

  • Thinking a JWT is encrypted. It is signed, not secret. Putting a password or PII you don't want exposed in the payload leaks it to anyone who sees the token.
  • Letting the header choose the algorithm. Opens alg:none and RS256→HS256 confusion attacks. Always pin an allow-list.
  • Verifying the signature but not the claims. Forgetting aud means a token issued for a different API of the same tenant will be accepted by yours.
  • Confusing seconds and milliseconds. exp, iat, nbf are UNIX time in seconds. Passing JavaScript's Date.now() (milliseconds) makes tokens "expire" in the year 50000+.
  • Hardcoding a single public key. Breaks the moment Auth0 rotates keys. Always resolve by kid from JWKS.
  • Decoding ≠ verifying. Calling jwt.decode() without a key (or with verification disabled) just reads claims — it provides zero security. Use verify.
  • Treating namespaced custom claims as registered. Auth0 requires custom claims to be namespaced (a URI prefix). Reading them under the wrong key returns undefined.
  • Non-constant-time comparison of HS256 signatures. Use a timing-safe compare to avoid leaking the secret via timing.
  • Long-lived access tokens. Because JWTs can't be easily revoked, a 30-day access token is a 30-day liability. Keep them short.

12. Best Practices

  • Use RS256 (or ES256) for APIs so verifiers only need the public key; reserve HS256 for tightly-coupled, single-trust-boundary cases.
  • Always validate iss, aud, and exp (and nbf if present) on top of the signature, with a small clock-skew leeway.
  • Pin the algorithm via an explicit allow-list on every verify call.
  • Resolve keys by kid from a cached JWKS; refetch on miss to handle rotation transparently.
  • Keep access tokens short-lived (minutes); use refresh tokens (rotating) for longevity.
  • Keep payloads minimal; namespace all custom claims; never store secrets in claims.
  • Use battle-tested libraries (jose, PyJWT, Spring Security, express-oauth2-jwt-bearer) instead of hand-rolling crypto.
  • Always transport over HTTPS; protect tokens at rest in the client (HttpOnly cookies / in-memory, not localStorage).

13. Interview Questions (with Model Answers)

Q1. What are the three parts of a JWT and what does each do?

A. Header, payload, signature, joined by dots and Base64url-encoded. The header declares the signing algorithm (alg) and often a key id (kid) and type (typ). The payload holds the claims — statements about the subject plus metadata like exp. The signature is a cryptographic seal over header.payload that proves integrity and authenticity.

Q2. Is a JWT encrypted? Can I put a password in it?

A. A standard (JWS) JWT is signed, not encrypted — the payload is plainly readable by anyone via Base64url decode. Never put secrets in it. If you need confidentiality you use JWE (encryption), which is far less common for identity claims.

Q3. Explain HS256 vs RS256 and when you'd choose each.

A. HS256 is symmetric HMAC: one shared secret both signs and verifies, so every verifier could also forge tokens. RS256 is asymmetric RSA: a private key signs, a public key verifies, so verifiers can confirm authenticity without the power to mint tokens. Choose RS256 when many independent services must verify (the Auth0 default) because you distribute only the public key via JWKS. Choose HS256 only when one party both issues and consumes within a single trust boundary and you want maximum speed/simplicity.

Q4. What is the JWKS endpoint and what is kid for?

A. JWKS (/.well-known/jwks.json) publishes the issuer's public keys as JSON. Each key has a kid (key id). A token's header carries the kid of the key that signed it; the verifier reads it, finds the matching public key in the cached JWKS, and verifies. This makes key rotation seamless.

Q5. How does key rotation work without breaking live tokens?

A. The issuer publishes both old and new public keys in JWKS during the transition, signs new tokens with the new key (new kid), and lets old tokens (old kid) keep verifying until they expire. Verifiers select by kid and refresh JWKS on a cache-miss, so they pick up new keys automatically.

Q6. What is the alg:none attack and how do you prevent it?

A. An attacker sets the header algorithm to none and removes the signature; a naive verifier that trusts the header accepts the unsigned token. Prevent it by never letting the header pick the algorithm — pass an explicit allow-list (e.g. ["RS256"]) to the verify function.

Q7. A token has a valid signature. Is the request safe to trust?

A. Not yet. A valid signature only means the token wasn't altered and came from the expected key. You still must check exp (not expired), iss (right issuer), and aud (this token was meant for my API). Only then trust the claims.

Q8. How do you revoke a JWT before it expires?

A. You can't cheaply, by design — that's the trade-off for statelessness. Mitigations: keep access tokens short-lived; use rotating refresh tokens; maintain a small denylist of revoked token ids (jti) checked at the gateway for high-risk scenarios; or use Auth0's revocation and sender-constraining features.

Q9. Why namespaced custom claims?

A. To avoid collisions with registered claims and to comply with the OIDC rule that non-standard claims in ID tokens be collision-resistant. Auth0 enforces a URI namespace, e.g. https://myapp.com/roles, so your custom data can't clash with reserved names.

Q10. Why is RS256 verification fast even though RSA is "slow"?

A. RSA signing uses the large private exponent (slow), but verification uses the tiny public exponent (commonly 65537), which makes the modular exponentiation cheap. So verify — the operation your APIs do constantly — is fast.

14. Certification Tips

Exam focus

For the Auth0 / Okta certification, anchor these facts:

  • Auth0 signs API access tokens and ID tokens with RS256 by default; you can switch a client to HS256 but it's discouraged for APIs.
  • The ID token is for the client (proves who logged in, OIDC); the access token is for the API (authorizes a call). Don't send an ID token to an API.
  • JWKS lives at https://YOUR_TENANT/.well-known/jwks.json; OIDC metadata at /.well-known/openid-configuration.
  • Validate iss, aud, exp, signature, and (for ID tokens) nonce/azp where applicable.
  • Custom claims in Auth0 must be namespaced and are added via Actions (post-login flow) — know that Actions are the modern mechanism (Rules/Hooks are legacy).
  • Know at+jwt as the access-token type per RFC 9068 and that access tokens may be opaque if no API audience is requested.
  • Remember the difference: authentication = who you are (ID token); authorization = what you may do (access token + scopes/permissions).

17. Mini Project — A JWT Inspector Web Tool

Build a small React component that lets a user paste a JWT, then displays the decoded header and payload and verifies the signature against a JWKS URL. This cements the decode-vs-verify distinction.

// JwtInspector.jsx — npm i jose
import { useState } from "react";
import { jwtVerify, createRemoteJWKSet, decodeJwt, decodeProtectedHeader } from "jose";

export default function JwtInspector() {
  const [token, setToken] = useState("");
  const [jwksUrl, setJwksUrl] = useState(
    "https://YOUR_TENANT.us.auth0.com/.well-known/jwks.json"
  );
  const [out, setOut] = useState(null);

  async function inspect() {
    try {
      // 1. DECODE (no key) — read-only, NOT trustworthy yet.
      const header = decodeProtectedHeader(token);
      const payload = decodeJwt(token);

      // 2. VERIFY against the live JWKS — this is what establishes trust.
      const JWKS = createRemoteJWKSet(new URL(jwksUrl));
      let verified = false, reason = "";
      try {
        await jwtVerify(token, JWKS, { algorithms: ["RS256"] });
        verified = true;
      } catch (e) { reason = e.message; }

      setOut({ header, payload, verified, reason });
    } catch (e) {
      setOut({ error: "Malformed token: " + e.message });
    }
  }

  return (
    <div>
      <textarea value={token} onChange={(e) => setToken(e.target.value)}
                placeholder="Paste JWT here" rows={4} />
      <input value={jwksUrl} onChange={(e) => setJwksUrl(e.target.value)} />
      <button onClick={inspect}>Inspect</button>
      {out && <pre>{JSON.stringify(out, null, 2)}</pre>}
    </div>
  );
}

Stretch goals: show a green/red badge for verification; highlight expired tokens by comparing exp to Date.now()/1000; pretty-print namespaced custom claims separately from registered ones; warn loudly if the header alg is anything other than RS256.

Warn

This is a learning tool. Never paste production tokens into any third-party online JWT decoder — the token is a live credential. Decode locally.

19. Cheat Sheet

 STRUCTURE   header.payload.signature   (3 base64url parts, dot-joined)
 HEADER      { "alg":"RS256", "typ":"JWT", "kid":"..." }
 SIGN INPUT  base64url(header) + "." + base64url(payload)
 SIGNATURE   sign(signInput, key, alg)

 REGISTERED CLAIMS
   iss  issuer        sub  subject (user id)   aud  audience (the API)
   exp  expiry (sec)  iat  issued-at (sec)     nbf  not-before (sec)
   jti  unique token id

 ALGORITHMS
   HS256  HMAC-SHA256   symmetric    same secret signs+verifies
   RS256  RSA-SHA256    asymmetric   private signs / public verifies  (Auth0 default)
   ES256  ECDSA-SHA256  asymmetric   small keys+tokens, fast

 VERIFY CHECKLIST  (do ALL)
   [ ] signature valid (key by kid from JWKS)
   [ ] alg pinned to an allow-list  (defeats alg:none / RS256->HS256)
   [ ] exp not passed (+small leeway)   [ ] nbf reached
   [ ] iss == expected issuer           [ ] aud == my API

 ENDPOINTS
   JWKS:   https://TENANT/.well-known/jwks.json
   OIDC:   https://TENANT/.well-known/openid-configuration
   HEADER: Authorization: Bearer <token>

 GOLDEN RULES
   * signed != secret      * decode != verify
   * times are SECONDS     * never trust header alg
   * RS256 for APIs        * keep access tokens short-lived

20. Key Takeaways

Key

A JWT is three Base64url segments — header.payload.signature — that together form a self-describing, tamper-evident container for identity claims.

Key

Base64url is encoding, not encryption. A signed JWT's contents are readable by anyone; the signature provides integrity and authenticity, never confidentiality. Never store secrets in claims.

Key

The registered claims iss, sub, aud, exp, nbf, iat, jti carry the who/what/when of a token. Validating iss, aud, and exp is as essential as checking the signature.

Key

HS256 is symmetric (one shared secret). RS256/ES256 are asymmetric (private signs, public verifies). Asymmetric signing + JWKS is what lets countless services verify Auth0 tokens locally with no shared secrets — the reason RS256 is the default.

Key

JWKS + kid make key rotation seamless: publish old and new public keys, select by kid, refresh on miss. Custom claims must be namespaced.

Key

Always pin the algorithm to an allow-list (defeats alg:none and RS256→HS256), and remember: a valid signature alone is necessary but not sufficient — you must still validate the claims before you trust the request.
