Chapter 10 — JWT Security: Attacks and Best Practices

A JWT is only as trustworthy as the code that validates it. In the last chapters you learned how JWTs are built, signed, and decoded. Now we flip the table and think like an attacker: we will forge tokens with alg=none, trick a server into verifying an RS256 token with the public key as an HMAC secret, replay stolen tokens, brute-force weak secrets, and slip past servers that forget to check aud, iss, and exp. For every attack you will see exactly why it works at the byte level, then the precise defense — culminating in the RFC 8725 best-practices checklist that every senior engineer is expected to know cold. By the end you will be able to audit any JWT-based system and explain, from first principles, whether it is safe.

1. Theory — First Principles of JWT Trust

A JSON Web Token (JWT) is a self-contained, cryptographically signed claim set. Three Base64URL parts joined by dots: header.payload.signature. The header and payload are not encrypted — they are merely encoded, so anyone can read them. The signature is the only thing standing between an honest token and a forged one.

To reason about JWT security you must hold one idea above all others:

Key

A JWT is trustworthy only if the receiver independently re-computes and verifies the signature using a key it controls, with an algorithm it dictates. The token must never be allowed to choose its own algorithm or key. The moment the attacker influences how you verify, the signature is meaningless.

Every JWT attack in this chapter exploits a violation of that one principle. Let us derive the trust model from scratch.

The two signature families

  • HMAC (HS256/384/512) — symmetric. The same secret key both signs and verifies. Whoever can verify can also forge. Used when one party owns both ends (e.g., a monolith signing its own session tokens).
  • RSA / ECDSA (RS256, ES256, PS256) — asymmetric. A private key signs; a public key verifies. The public key is safe to publish (Auth0 exposes it at /.well-known/jwks.json). Verifiers never hold the signing key. This is what every OIDC provider, including Auth0, uses for ID tokens and access tokens.

Why does Auth0 default to RS256? Because in a distributed system you have many verifiers (your API, your gateway, your microservices) but exactly one signer (Auth0). With HMAC, every verifier would need the shared secret — and any one of them, if compromised, could mint tokens. With RS256 the private key never leaves Auth0; verifiers only ever see the public key, which cannot forge anything. Asymmetric crypto separates the power to verify from the power to forge. That separation is the whole point.

Confidentiality vs. integrity

JWTs (the JWS variety, which is 99% of what you meet) provide integrity and authenticity, not confidentiality. Anyone with the token can read every claim. So rule one: never put secrets — passwords, SSNs, full credit-card numbers — inside a JWT. If you genuinely need an encrypted token, that is a JWE (JSON Web Encryption), a separate and rarer construct.

2. Story — The Night the Admin Panel Fell

Picture a startup, "Ledgerly", shipping fast. Their Node API checks JWTs like this: it Base64-decodes the token, reads the alg field from the header, and verifies accordingly. Convenient — the library "just figures out" the algorithm.

One evening a security researcher named Mara intercepts her own token in the browser. She decodes the header: {"alg":"RS256","typ":"JWT"}. She edits it to {"alg":"none","typ":"JWT"}, changes the payload's "role":"user" to "role":"admin", deletes the signature entirely (leaving the trailing dot), and replays the request.

The server reads alg:none, concludes "this token says it isn't signed, so there's nothing to verify," and accepts it. Mara is now an admin. No private key, no brute force — she simply asked the server not to check, and it obliged.

The next morning Ledgerly's engineers patch it by hard-coding the expected algorithm and rejecting none. But Mara isn't done. She notices the API now uses a verify call that "auto-selects" between RS256 and HS256. She takes the public RSA key (published openly at the JWKS endpoint), and signs a forged token using HS256 with that public key as the HMAC secret. She sets alg:HS256. The server, trusting the token's chosen algorithm, loads its RSA public key and runs HMAC verification with it — and the signatures match, because Mara used the very same public string. Admin again.

Danger

Both break-ins share one root cause: the server let the token dictate the verification algorithm. The fix is identical for both — pin the algorithm on the server side and never trust the header's alg.

This story is not hypothetical. The alg=none and RS256→HS256 confusion bugs were real CVEs across multiple popular JWT libraries (2015–2017), and variants still surface today in hand-rolled validators. We will reproduce both, then bulletproof against them.

4. Real-World Analogy — The Wax-Seal Letter

Imagine medieval messengers carrying letters sealed with the king's wax signet. The seal proves the letter is authentic. Now map the attacks:

  • alg=none is a guard who accepts a letter that says, at the top, "This letter requires no seal." A competent guard checks the seal regardless of what the letter claims about itself.
  • RS256→HS256 confusion is subtler. The king's signet (private key) makes the seal; everyone owns a cast copy of the seal's imprint (public key) to compare against — but you can only compare, you cannot stamp with a mere imprint. The confusion attack tricks the guard into using that public imprint as if it were the secret stamp itself, so the attacker — who also has the public imprint — can produce matching seals.
  • Replay is stealing a genuine sealed letter and delivering it yourself. The seal is real, so it passes — which is why royal letters carry an expiry date and name the intended recipient.
  • Weak HMAC secret is a kingdom whose "secret" stamp is the word "password" — any blacksmith can replicate it overnight.
  • Missing aud/iss checks is a guard who accepts any sealed letter without reading who it was addressed to (aud) or which king sent it (iss) — so a letter meant for a neighboring castle is honored at yours.

5. Internal Working — Bytes, Signing, and Why the Confusion Works

The signing input is the ASCII string BASE64URL(header) + "." + BASE64URL(payload). Call it the signing input M.

HS256:  signature = HMAC_SHA256(key=secret,  message=M)
        verify    : recompute HMAC and compare (constant time)

RS256:  signature = RSA_SIGN(privateKey, SHA256(M))
        verify    : RSA_VERIFY(publicKey, SHA256(M), signature)

Here is the crux of the confusion attack, made concrete. A vulnerable verify function looks like:

// VULNERABLE pseudo-implementation inside a naive library
function verify(token, key) {
  const { header, payload, signature } = split(token);
  const M = base64url(header) + "." + base64url(payload);

  if (header.alg === "HS256") {
    return hmacSha256(M, key) === signature;   // key treated as HMAC SECRET
  }
  if (header.alg === "RS256") {
    return rsaVerify(M, signature, key);        // key treated as RSA PUBLIC key
  }
}

The single variable key is overloaded. The server intends it to be an RSA public key. But the attacker sets header.alg = "HS256", so the function takes the first branch and feeds that same public-key string into hmacSha256 as the secret. Because the RSA public key is public, the attacker computed the very same HMAC_SHA256(publicKeyPEM, M) offline. The two HMACs match. Forgery complete — no private key ever needed.

Note

The byte-level subtlety: tiny formatting differences in how the public key is serialized (PEM with or without trailing newline, headers like -----BEGIN PUBLIC KEY----- included or stripped) change the HMAC. Real exploits try several common serializations. The point stands: the defense is not "format the key carefully" — it is "never let one branch decide between symmetric and asymmetric based on the token."

Why exp/iss/aud exist at the protocol level

A valid signature only proves "Auth0 issued this exact claim set." It says nothing about when, for whom, or whether it is still meant to be used. The registered claims close those gaps:

  • exp (expiration) — after this Unix timestamp the token is invalid. Bounds the blast radius of theft.
  • iss (issuer) — who minted it (e.g., https://your-tenant.us.auth0.com/). Stops tokens from a different/attacker IdP being honored.
  • aud (audience) — the intended recipient (your API identifier). Stops a token meant for API A being replayed against API B (the "confused deputy" within a tenant).
  • nbf (not before), iat (issued at) — timing windows.
  • kid (in the header) — which key signed it, so you fetch the right public key from JWKS.

6.1 Crafting an alg=none token by hand (curl)

# header {"alg":"none","typ":"JWT"}  and  payload {"sub":"123","role":"admin"}
# base64url-encode each (note: '=' padding stripped, +/ -> -_)
H=$(printf '%s' '{"alg":"none","typ":"JWT"}'   | basenc --base64url | tr -d '=')
P=$(printf '%s' '{"sub":"123","role":"admin"}' | basenc --base64url | tr -d '=')

# alg=none means NO signature -> token ends with a trailing dot, empty 3rd part
TOKEN="$H.$P."
echo "$TOKEN"

curl -i https://lab.example.com/admin \
  -H "Authorization: Bearer $TOKEN"
# A vulnerable server returns 200. A correct server returns 401.

6.2 Forging an RS256→HS256 confusion token (Node lab script)

import crypto from "node:crypto";
import fs from "node:fs";

// The attacker downloads the server's PUBLIC key (it's published, that's fine).
const publicKeyPem = fs.readFileSync("server_public.pem", "utf8");

const b64url = (buf) =>
  Buffer.from(buf).toString("base64")
    .replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/g, "");

const header  = b64url(JSON.stringify({ alg: "HS256", typ: "JWT" }));
const payload = b64url(JSON.stringify({ sub: "123", role: "admin",

const signingInput = `${header}.${payload}`;

// Sign with HMAC, using the PUBLIC KEY string as the "secret".

                  .update(signingInput).digest("base64")
                  .replace(/\+/g,"-").replace(/\//g,"_").replace(/=+$/g,"");

6.3 The correct, safe verification (Node, jose)

import { createRemoteJWKSet, jwtVerify } from "jose";

const JWKS = createRemoteJWKSet(
  new URL("https://your-tenant.us.auth0.com/.well-known/jwks.json"));

export async function verifyAccessToken(token) {
  const { payload } = await jwtVerify(token, JWKS, {
    algorithms: ["RS256"],                       // PIN the algorithm. No "none", no HS256.
    issuer:   "https://your-tenant.us.auth0.com/", // check iss
    audience: "https://api.ledgerly.com",          // check aud
    clockTolerance: "5s",                          // small skew only; exp/nbf enforced
  });
  return payload; // safe to trust now
}

Walk through every guard: algorithms:["RS256"] defeats both alg=none and HS256 confusion because the library refuses any other algorithm before selecting a verification path. createRemoteJWKSet guarantees we verify with Auth0's public key fetched by kid — never a secret, never the token's choice. issuer and audience close the redirect/confused-deputy gaps. jwtVerify enforces exp/nbf automatically; clockTolerance keeps that strict.

7. Practical Implementation — Hardened Validators Across Stacks

7.1 Java Spring Boot (Spring Security Resource Server)

// application.yml — issuer-uri makes Spring fetch JWKS and pin RS256 automatically
// spring.security.oauth2.resourceserver.jwt.issuer-uri=https://your-tenant.us.auth0.com/

@Configuration
@EnableWebSecurity
public class SecurityConfig {

  @Value("${spring.security.oauth2.resourceserver.jwt.issuer-uri}")
  String issuer;

  @Bean
  JwtDecoder jwtDecoder() {
    // Loads JWKS, restricts to RS256 (the JWKS key type), validates signature.
    NimbusJwtDecoder decoder =
        JwtDecoders.fromIssuerLocation(issuer);

    OAuth2TokenValidator<Jwt> withIssuer =
        JwtValidators.createDefaultWithIssuer(issuer); // checks iss + exp
    OAuth2TokenValidator<Jwt> audience = new AudienceValidator("https://api.ledgerly.com");
    decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(withIssuer, audience));
    return decoder;
  }

  @Bean
  SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
    return http.build();
  }
}

// Custom audience validator — Spring does NOT check aud by default!
class AudienceValidator implements OAuth2TokenValidator<Jwt> {
  private final String audience;
  AudienceValidator(String audience) { this.audience = audience; }
  public OAuth2TokenValidatorResult validate(Jwt jwt) {
    if (jwt.getAudience().contains(audience))
      return OAuth2TokenValidatorResult.success();
    return OAuth2TokenValidatorResult.failure(
      new OAuth2Error("invalid_token", "Required audience missing", null));
  }
}
Warn

Spring Security validates iss, exp, and the signature out of the box, but it does not validate aud unless you add a validator. Forgetting this is one of the most common production gaps — your API will happily accept a token minted for a different API in the same tenant.

7.2 FastAPI (Python)

import jwt                       # PyJWT
from jwt import PyJWKClient
from fastapi import Depends, FastAPI, HTTPException, Header

ISSUER   = "https://your-tenant.us.auth0.com/"
AUDIENCE = "https://api.ledgerly.com"
jwks = PyJWKClient(f"{ISSUER}.well-known/jwks.json")

def verify(authorization: str = Header(...)) -> dict:
    if not authorization.startswith("Bearer "):
        raise HTTPException(401, "Missing bearer token")
    token = authorization.split(" ", 1)[1]
    try:
        signing_key = jwks.get_signing_key_from_jwt(token).key
        return jwt.decode(
            token, signing_key,
            algorithms=["RS256"],          # PIN — blocks none + HS256 confusion
            audience=AUDIENCE,             # checks aud
            issuer=ISSUER,                 # checks iss
            options={"require": ["exp", "iat", "iss", "aud"]},  # demand they exist
        )
    except jwt.InvalidTokenError as e:
        raise HTTPException(401, f"Invalid token: {e}")

app = FastAPI()

@app.get("/admin")
def admin(claims: dict = Depends(verify)):
    if "admin" not in claims.get("permissions", []):
        raise HTTPException(403, "Forbidden")
    return {"ok": True, "sub": claims["sub"]}

8. Production Architecture — Defense in Depth

                       +-------------------+
                       |      Auth0        |  (single SIGNER, holds private key)
                       |  RS256, JWKS, kid |
                       +---------+---------+
                                 | publishes PUBLIC keys
                                 v
   Browser/SPA          /.well-known/jwks.json   (cached by verifiers)
   token in MEMORY              |        |        |
   refresh in cookie           v        v        v
        |             +--------+   +--------+   +--------+
        | Bearer      | API GW |   | Svc A  |   | Svc B  |   <- many VERIFIERS
        |------------>| pin    |   | pin    |   | pin    |      (public key only)
        |             | RS256  |   | RS256  |   | RS256  |
        |             | iss/aud|   | aud=A  |   | aud=B  |
        |             | exp    |   | exp    |   | exp    |
        |             +---+----+   +--------+   +--------+
        |                 |
        |   short TTL (5-15m) access tokens; revocation via:
        |   - refresh-token rotation + reuse detection (Auth0)
        |   - deny-list of jti for emergency revoke (Redis, TTL=exp)
        |   - sender-constrained tokens (DPoP / mTLS) for high value
        v
    HTTPS everywhere; HSTS; no tokens in URLs/logs

Architectural principles, justified:

  • One signer, many verifiers, asymmetric keys. The private key lives only in Auth0. Every service verifies with the public JWKS. A compromised microservice cannot mint tokens.
  • Per-API audience. Each service pins its own aud. A token for Service A is rejected by Service B even though both trust the same issuer — containing lateral movement.
  • Short access-token TTL (5–15 min) bounds replay. Long-lived refresh tokens, kept server-side or in httpOnly cookies, are exchanged for new access tokens and are rotated on every use with reuse detection.
  • Emergency revocation: a Redis deny-list keyed by jti with TTL set to the token's exp, checked by the gateway. Stateless JWTs cannot be revoked natively, so this is the standard escape hatch.

10. Performance Considerations

  • JWKS caching. Fetching the public key on every request adds an HTTP round trip and lets the JWKS endpoint become a bottleneck or DoS target. Cache keys by kid (Auth0 keys rotate rarely). Honor Cache-Control; refresh on an unknown kid (signals rotation), but rate-limit that refresh so an attacker can't force a JWKS fetch storm with random kid values.
  • RS256 verify vs HS256. RSA verification is slower than HMAC but still sub-millisecond and trivially parallel — and it's a public-key op (cheap side), not signing. The security win (no shared secret) dwarfs the cost. Don't choose HS256 "for speed."
  • Stateless = no DB hit. The reason JWTs scale is that verification needs no central session store — purely local CPU plus a cached key. Adding a revocation deny-list reintroduces a lookup; keep it in a fast in-memory store (Redis) and only consult it where the risk justifies the latency.
  • Token size. Big tokens (many claims/roles) inflate every request header. Keep payloads lean; reference large authorization data by ID rather than embedding it.
  • Constant-time compares. Signature/secret comparison must be constant-time (libraries do this) to avoid timing side channels — relevant mainly to HMAC.

11. Common Mistakes

  • Decoding instead of verifying. Calling jwt.decode() (or splitting + Base64) without checking the signature. Decoding is not verification — it trusts attacker-controlled data.
  • Trusting header.alg. Letting the token pick the algorithm. Always pin an allow-list.
  • Verifying aud nowhere. Especially in Spring Boot, where it's off by default.
  • Hard-coding HS256 with a weak secret like "secret" or "changeme" in a config file checked into git.
  • Storing access tokens in localStorage. One XSS flaw = full token theft. Prefer in-memory + httpOnly refresh.
  • No expiry, or huge expiry. 24-hour access tokens turn any leak into a day-long breach.
  • Logging tokens. Tokens in access logs, error traces, or URLs (query strings) leak via log aggregation, browser history, and Referer headers.
  • Treating ID tokens as access tokens. ID tokens are for the client to learn who the user is; they are not for authorizing API calls. Send the access token to APIs.
  • Skipping exp with a giant clock tolerance ("just set 1 hour skew") — that silently defeats expiry.

12. Best Practices — RFC 8725 ("JWT Best Current Practices")

RFC 8725 is the IETF's distilled guidance after years of real-world JWT breaks. Memorize these — they are interview and certification gold.

Key — RFC 8725 Checklist

✅ Always validate the signature before using any claim.
✅ Use an algorithm allow-list; the verifier dictates the algorithm, not the token.
✅ Reject alg=none (and any algorithm not on your list).
✅ Bind key to algorithm: a key is for exactly one alg; never use a public key for HMAC.
✅ Use strong keys: HMAC secrets ≥256 bits of entropy; prefer asymmetric (RS256/ES256) for distributed verification.
✅ Validate all critical claims: iss, aud, exp (and nbf/iat as relevant).
✅ Use the typ header / explicit typing to prevent cross-token confusion (e.g. at+jwt for access tokens).
✅ Don't trust jku/x5u/kid to choose key locations; pin the JWKS source.
✅ Keep tokens short-lived; use rotation + revocation for the rest.
✅ Never put secrets in the payload — JWS is signed, not encrypted.

Beyond the RFC: serve everything over TLS/HSTS; store access tokens in memory (SPA) or httpOnly+SameSite cookies (web); rotate refresh tokens with reuse detection; for high-value APIs add sender-constrained tokens (DPoP or mutual TLS) so a stolen bearer token is useless without the holder's key.

13. Interview Questions (with Model Answers)

Q1. Explain the alg=none attack and the fix.

A. The header declares alg:none, meaning "unsecured JWT" with an empty signature. A verifier that trusts the token's algorithm concludes there is nothing to verify and accepts a fully attacker-controlled payload. Fix: pin a server-side algorithm allow-list (e.g. ["RS256"]) so any token whose alg isn't allowed — including none — is rejected before verification logic runs.

Q2. Why is RS256 safer than HS256 in a microservices system?

A. RS256 is asymmetric: only Auth0 holds the private signing key; services verify with the public key. So the power to verify is separated from the power to forge, and no shared secret is distributed across services. HS256 shares one secret for sign and verify, so any verifier (or a leak of the secret) can mint tokens.

Q3. Walk me through the RS256→HS256 confusion attack.

A. The attacker takes the public key (published at JWKS), HMAC-signs a forged payload using that public key string as the HMAC secret, and sets alg:HS256. A verifier that auto-selects based on the header runs HMAC with the same public key as the secret, the signatures match, and the forged token is accepted — no private key needed. Defense: pin RS256; never let one code path switch between symmetric and asymmetric based on the token.

Q4. A token's signature is valid but you still reject it. Why might that be?

A. A valid signature only proves authenticity of the claims. It can still fail exp (expired), nbf, iss (wrong issuer), aud (meant for another API), or appear on a revocation deny-list. All of those are independent of signature validity.

Q5. Where should a SPA store the access token, and why?

A. In memory (JS variable / SDK cache). localStorage and sessionStorage are readable by any script, so a single XSS exfiltrates the token. Memory is wiped on reload, and the Auth0 SDK silently re-obtains tokens via rotating refresh tokens. For server-rendered apps, keep tokens in an encrypted httpOnly+SameSite cookie so page JS can't read them at all.

Q6. JWTs are stateless — how do you revoke one before it expires?

A. Natively you can't; you compensate. Keep access-token TTL short (5–15 min) so revocation is "eventually" automatic. For immediate revocation, maintain a deny-list of jti (with TTL = token's exp) checked at the gateway, and revoke the user's refresh tokens so no new access tokens are issued. Refresh-token rotation with reuse detection invalidates a whole token family if a stolen refresh token is replayed.

Q7. What stops a token issued for API A from working against API B?

A. The aud claim. Each API validates that aud equals its own identifier, so a token minted for A (aud=A) is rejected by B even though both trust the same issuer.

Q8. How would you make a stolen bearer token useless?

A. Sender-constrain it. With DPoP or mutual-TLS, the token is cryptographically bound to a key held by the legitimate client; the resource server checks a proof of possession, so a replayed token without the matching private key fails. Short TTL and TLS reduce exposure further.

14. Certification Tips

  • Know Auth0's defaults: APIs default to RS256; signing keys are at /.well-known/jwks.json, selected by kid. The exam loves "which algorithm / where is the public key."
  • ID token vs access token: ID token = authentication info for the client (audience = client_id); access token = authorization for an API (audience = API identifier). Don't send ID tokens to APIs.
  • Validation order: signature → iss → aud → exp/nbf. Expect a question on which claim prevents which attack.
  • Refresh token rotation and reuse detection are heavily featured — know that reusing a rotated refresh token revokes the entire family.
  • Token storage: Auth0 SDKs default to in-memory; cacheLocation: "localstorage" exists but is flagged as an XSS risk — know the trade-off.
  • RFC 8725 by name: algorithm allow-list, reject none, validate claims, don't trust header-chosen keys.

19. Cheat Sheet

JWT SECURITY — QUICK REFERENCE
==============================================================
VERIFY, DON'T DECODE.  Token never chooses alg or key.

ALWAYS, server-side:
  algorithms = ["RS256"]      # pin -> kills alg=none + HS256 confusion
  issuer     = exact tenant URL          (iss)
  audience   = this API's identifier     (aud)
  enforce exp / nbf, small clock skew (<=5s)
  JWKS URL hard-coded; ignore jku / x5u / token-chosen key

KEYS:
  RS256 (asymmetric) -> distributed: 1 signer, many verifiers
  HS256 (symmetric)  -> only if one party owns both ends
  HMAC secret >= 256 bits random; never a public key as secret

STORAGE:
  SPA   -> access token in MEMORY (not localStorage)
  SSR   -> httpOnly + SameSite cookie
  refresh token -> rotate + reuse detection

LIFETIME / REVOCATION:
  access TTL 5-15 min; refresh rotated
  emergency revoke: jti deny-list (TTL = exp) at gateway
  high value: DPoP / mTLS sender-constrained tokens

NEVER:
  trust header.alg | accept "none" | put secrets in payload
  log tokens / put them in URLs | use ID token to call APIs
==============================================================

20. Key Takeaways

Key

1. A JWT is trustworthy only when the receiver controls the algorithm and the key — never the token.
2. Pinning an algorithm allow-list (["RS256"]) defeats both alg=none and the RS256→HS256 confusion attack in one move.
3. A valid signature is necessary but not sufficient — always validate iss, aud, and exp.
4. Prefer RS256: one signer, many verifiers, no shared secret to leak. Use strong HMAC secrets only when symmetric is truly appropriate.
5. Store access tokens in memory or httpOnly cookies, never localStorage; keep them short-lived, rotate refresh tokens, and keep a revocation path.
6. Bearer tokens are stealable — sender-constrain high-value tokens with DPoP/mTLS, and never log them or put them in URLs.
7. RFC 8725 is the canonical checklist: validate signature, allow-list algorithms, reject none, validate claims, don't trust header-chosen keys.
