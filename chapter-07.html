Chapter 7 — OpenID Connect Core

OAuth 2.0 answered the question "may this app access that resource?" — it is an authorization framework and, by design, says nothing about who the user is. OpenID Connect (OIDC) is the thin, standardized identity layer bolted on top of OAuth 2.0 that finally answers "who just logged in, and how do I trust that answer?" In this chapter you will learn OIDC from first principles: the ID token, the discovery document, JWKS key rotation, the nonce replay defense, the userinfo endpoint, the standard scopes and claims, and the full Authorization Code flow end-to-end — with runnable code in Node, Spring Boot, FastAPI, React/Next.js, plus curl and Postman. By the end you will be able to implement, secure, debug, and explain OIDC at a senior level.

1. Theory — First Principles

Start with the gap. OAuth 2.0 (Chapter 5–6) is a delegated authorization protocol. A client obtains an access token — an opaque or JWT credential that grants access to an API (a "resource server"). Crucially, the access token is for the API, not for the client. It is not designed to tell the client application anything reliable about the end user. The access token's audience is the resource server; reading user identity out of it is, at best, an implementation accident and, at worst, a security hole.

People nonetheless tried to do authentication with raw OAuth 2.0 ("log in with X"). They invented ad-hoc tricks: hit a proprietary /me endpoint with the access token, trust whatever comes back. This produced incompatible, insecure pseudo-standards (the infamous "OAuth login" confusion). Two failure modes dominated:

  • Access token as proof of identity — an access token leaked from one app could be replayed at another app's "login with this token" endpoint (the confused deputy / token substitution attack).
  • No standard identity contract — every provider returned user data in a different shape, with no signed, verifiable assertion the client could validate offline.

OpenID Connect 1.0 (finalized 2014, still current in 2026) fixes this by defining:

  1. A new artifact, the ID token — a signed JWT whose audience is the client and whose purpose is to assert "this user authenticated, here is who they are, here is when and how."
  2. A reserved scope, openid, that turns an OAuth request into an OIDC request. No openid scope → no ID token → it is plain OAuth.
  3. Standard claims (name, email, sub, etc.) and a userinfo endpoint to fetch them.
  4. Self-describing metadata: the discovery document and the JWKS key endpoint, so a client can configure itself and verify signatures automatically.
  5. Replay defenses: nonce (binds the ID token to a specific browser request) on top of OAuth's state (CSRF defense).
Key

One-sentence mental model: OAuth 2.0 gets you an access token to call an API; OpenID Connect additionally gets you an ID token that proves who logged in. OIDC = OAuth 2.0 + identity contract. It reuses every OAuth endpoint and adds the ID token, the openid scope, userinfo, and discovery.

Why a JWT for the ID token? Because the client must verify it without calling the server. A signed JWT carries its own proof: the issuer signs it with a private key; the client validates it with the matching public key (from JWKS). That makes login stateless and tamper-evident. We will dissect every validation step in §5 and §9.

2. Story-Based Explanation

Imagine Maya, a developer building "PhotoVault," a web app that lets users back up photos. She wants two things: (1) let users sign in with their existing identity, and (2) later call a "Cloud Drive" API on their behalf.

Act I — the OAuth-only mistake. Maya first wires plain OAuth 2.0. PhotoVault redirects the user to the identity provider, gets an access token back, and calls Cloud Drive's /me. It works in the demo. But a security researcher, Theo, shows her an exploit: he builds a malicious app, tricks a victim into authorizing it, captures the victim's access token, and pastes it into PhotoVault's "log in with token" endpoint. PhotoVault calls /me, sees the victim's profile, and logs Theo in as the victim. The access token had no notion of "which client am I for" that PhotoVault checked. Identity by access token is broken.

Act II — the OIDC fix. Maya adds scope=openid profile email and a random nonce. Now the provider returns an ID token alongside the access token. The ID token is a signed JWT that says: iss = the provider, aud = PhotoVault's exact client_id, sub = the user's stable ID, nonce = the value Maya generated, plus iat/exp. PhotoVault verifies the signature against the provider's published public key, checks aud equals its own client_id, and checks nonce matches what it sent. Theo's stolen token is useless: even if he steals an ID token, its aud is some other app, and he cannot forge a new signature.

Act III — separation of concerns. Maya now uses the ID token to establish the login session (who the user is) and the access token to call Cloud Drive (what the app may do). Two tokens, two jobs. When she needs the access token to outlive its short life, she adds offline_access to get a refresh token. Three tokens, three jobs — and she never confuses them again.

Note

The moral of Maya's story is the single most-tested OIDC fact: never use an access token to identify a user, and never send an ID token to an API to authorize access. ID token = identity, for the client. Access token = authorization, for the API.

4. Real-World Analogy

Think of an international airport.

  • Passport = ID token. Issued by a trusted government (the issuer), it asserts who you are. It has your photo (claims), an issue date and expiry (iat/exp), and a holographic seal that border control can verify without phoning the issuing country (the signature, verified via public keys). The passport is about you and is presented to identify you. It is not a ticket.
  • Boarding pass = access token. It does not prove who you are in general; it grants a specific permission: board flight BA117, seat 14C. The gate agent (resource server / API) checks the boarding pass, not your life story. It is scoped (this flight, this seat = OAuth scopes) and short-lived.
  • Frequent-flyer membership = refresh token. Long-lived; you present it to get new boarding passes without re-proving your identity each time.
  • The passport's seal registry = JWKS. Border control trusts the seal because the issuing authority publishes its sealing standards/keys. When a country rotates its security feature (key rotation), the registry is updated and old + new are honored during transition.
  • Tamper-evident hologram bound to this entry = nonce. Imagine the passport stamp encoded a one-time code you whispered at the desk; a photocopy presented later wouldn't match, foiling replay.
Tip

If you ever catch yourself "showing the passport to the gate agent to board" (sending an ID token to an API) or "using the boarding pass to prove citizenship" (using an access token to identify the user), stop — you have swapped the artifacts. That swap is the root cause of a huge fraction of real OIDC bugs.

5. Internal Working

5.1 Anatomy of an ID token

An ID token is a JWT: three Base64URL parts separated by dots — header.payload.signature. Header and payload are JSON; the signature is a JWS over header + "." + payload.

// HEADER (decoded)
{
  "alg": "RS256",          // signing algorithm (asymmetric -> client verifies with public key)
  "typ": "JWT",
  "kid": "NkJDQ0Q0..."     // which JWKS key was used; client looks this up
}

// PAYLOAD (decoded) — the CLAIMS
{
  "iss": "https://your-tenant.us.auth0.com/",  // issuer (must match exactly)
  "sub": "auth0|6512ab...",                     // STABLE unique user id (your primary key)
  "aud": "aBcD1234ClientId",                    // audience = THIS client's client_id
  "iat": 1718800000,                            // issued-at (epoch seconds)
  "exp": 1718803600,                            // expiry  (epoch seconds)
  "nonce": "n-0S6_WzA2Mj",                      // must equal the nonce the client sent
  "auth_time": 1718800000,                      // when the user actually authenticated
  "name": "Maya Singh",
  "email": "maya@example.com",
  "email_verified": true
}
Warn

The only stable user identifier is sub (subject). Email can change and can be reassigned; never key your user table on email. Identity is iss + sub together (the same sub can recur across different issuers).

5.2 The seven mandatory ID token validation steps

This is the heart of OIDC security. A relying party (your client) MUST, per the spec:

  1. Signature. Fetch the key whose kid matches the token header from jwks_uri; verify the JWS. Reject alg: none. Pin asymmetric algs (RS256/ES256); never let the token's header dictate that a symmetric secret is used (the alg-confusion attack).
  2. Issuer. iss must exactly equal your configured issuer (including trailing slash). String compare, not "contains."
  3. Audience. aud must contain your client_id. If aud is an array and an azp (authorized party) is present, azp must equal your client_id.
  4. Expiry. exp must be in the future; reject if past (allow small clock skew, e.g. 60s).
  5. Issued-at. iat should be sane (not far in the future). Optionally enforce a max token age.
  6. Nonce. nonce must equal the value you generated and stored for this request (replay defense — §9.1).
  7. auth_time / acr (conditional). If you requested max_age or specific authentication context (e.g. MFA), verify auth_time and acr/amr satisfy your policy.

5.3 How signature verification actually works (RS256)

  Issuer (Auth0)                              Client (Relying Party)
  --------------                              ----------------------
  has PRIVATE key  -- sign -->  id_token  -- send -->  has PUBLIC key (from JWKS)
                                                       |
   signature = RSA_sign(SHA256(h"."p), privKey)        |
                                                       v
                          RSA_verify(SHA256(h"."p), sig, pubKey) == true ?
                          yes -> token is authentic & untampered
                          no  -> REJECT
  Asymmetric => the client never holds a secret capable of MINTING tokens.

Contrast with HS256 (symmetric): the same secret signs and verifies, so every verifier could forge tokens. For ID tokens validated by public clients (SPAs, mobile), RS256 is the correct default; Auth0 uses RS256 by default.

6. Code Walkthrough — verifying an ID token by hand

Before reaching for a library, see what a library does for you. Here is manual RS256 verification in Node using the standard jose library's primitives, so every step is visible.

// verify-id-token.js  (Node 20+, "type":"module")
import { createRemoteJWKSet, jwtVerify, decodeProtectedHeader } from 'jose';

const ISSUER   = 'https://your-tenant.us.auth0.com/';   // note trailing slash
const AUDIENCE = 'aBcD1234ClientId';                    // your client_id
const JWKS     = createRemoteJWKSet(new URL(ISSUER + '.well-known/jwks.json'));

export async function verifyIdToken(idToken, expectedNonce) {
  // 1. Reject 'none' / unexpected algs BEFORE verifying.
  const { alg } = decodeProtectedHeader(idToken);
  if (alg !== 'RS256') throw new Error(`unexpected alg: ${alg}`);

  // 2-5. jwtVerify resolves the kid against JWKS, checks signature, iss, aud, exp, nbf.
  const { payload } = await jwtVerify(idToken, JWKS, {
    issuer:   ISSUER,
    audience: AUDIENCE,
    algorithms: ['RS256'],
    clockTolerance: '60s',
  });

  // 6. Nonce — the library does NOT know your stored nonce; you must check it.
  if (payload.nonce !== expectedNonce) throw new Error('nonce mismatch (replay?)');

  // 7. (optional) max_age enforcement
  // if (Date.now()/1000 - payload.auth_time > 3600) throw new Error('reauth required');

  return payload; // trusted claims: payload.sub, payload.email, ...
}
Note

What jwtVerify did for you: parsed the header, picked the key by kid from the cached JWKS (refetching if unknown), verified the RSA signature, and checked iss, aud, exp, nbf with clock tolerance. It deliberately leaves nonce to you because only your app knows the value it generated. This is exactly the seven-step checklist from §5.2.

6.1 Decode (NOT verify) — to inspect during debugging

// Decoding != verifying. NEVER trust decoded claims you haven't verified.
function unsafeDecode(jwt) {
  const [, payload] = jwt.split('.');
  return JSON.parse(Buffer.from(payload, 'base64url').toString('utf8'));
}
console.log(unsafeDecode(idToken)); // debugging only
Danger

Decoding a JWT is trivial and unauthenticated — anyone can read the payload (it is only Base64, not encryption). Treat decoded values as attacker-controlled until the signature and claims are verified. Never put secrets in an ID token.

7. Practical Implementation

7.1 curl — drive the flow manually

# Step A: discovery — let the server tell you every endpoint
curl -s https://your-tenant.us.auth0.com/.well-known/openid-configuration | jq

# Step B: build the /authorize URL (open in a browser).
#   PKCE: code_verifier is random; code_challenge = BASE64URL(SHA256(verifier))
VERIFIER=$(openssl rand -base64 60 | tr -d '\n=+/' | cut -c1-64)
CHALLENGE=$(printf '%s' "$VERIFIER" | openssl dgst -binary -sha256 | openssl base64 | tr '+/' '-_' | tr -d '=')
echo "https://your-tenant.us.auth0.com/authorize?\
response_type=code&client_id=aBcD1234ClientId&\
redirect_uri=http://localhost:3000/callback&\
scope=openid%20profile%20email%20offline_access&\
audience=https://api.photovault.example&\
state=xyzCSRF&nonce=n-0S6_WzA2Mj&\
code_challenge=$CHALLENGE&code_challenge_method=S256"

# Step C: after browser redirect gives you ?code=AUTH_CODE, exchange it:
curl -s -X POST https://your-tenant.us.auth0.com/oauth/token \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d grant_type=authorization_code \
  -d client_id=aBcD1234ClientId \
  -d client_secret=YOUR_CLIENT_SECRET \
  -d code=AUTH_CODE \
  -d code_verifier="$VERIFIER" \
  -d redirect_uri=http://localhost:3000/callback | jq
# -> { "access_token": "...", "id_token": "ey...", "refresh_token": "...",
#      "expires_in": 86400, "token_type": "Bearer", "scope": "openid profile ..." }

# Step D: call userinfo with the ACCESS token (not the id_token!)
curl -s https://your-tenant.us.auth0.com/userinfo \
  -H "Authorization: Bearer ACCESS_TOKEN" | jq

7.3 Node / Express — the right way (use a certified library)

// app.js — express-openid-connect does discovery, PKCE, state, nonce & validation for you
import express from 'express';
import { auth } from 'express-openid-connect';

const app = express();
app.use(auth({
  authRequired: false,
  auth0Logout: true,
  baseURL: 'http://localhost:3000',
  clientID: process.env.CLIENT_ID,
  clientSecret: process.env.CLIENT_SECRET,
  secret: process.env.SESSION_SECRET,        // encrypts the session cookie
  issuerBaseURL: 'https://your-tenant.us.auth0.com',
  authorizationParams: {
    response_type: 'code',                    // Authorization Code flow
    scope: 'openid profile email offline_access',
    audience: 'https://api.photovault.example',
  },
}));

app.get('/', (req, res) =>
  res.send(req.oidc.isAuthenticated()
    ? `Hi ${req.oidc.user.name} (sub=${req.oidc.user.sub})`
    : '<a href="/login">Log in</a>'));

app.listen(3000);

// SecurityConfig.java — Spring Security validates the ID token automatically
@Configuration
@EnableWebSecurity
public class SecurityConfig {
  @Bean
  SecurityFilterChain chain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .oauth2Login(Customizer.withDefaults()); // discovery + JWKS + ID token validation
    return http.build();
  }

  @GetMapping("/me")  // inject the verified OIDC user
  public Map<String,Object> me(@AuthenticationPrincipal OidcUser user) {
    return Map.of("sub", user.getSubject(), "email", user.getEmail());
  }
}

7.5 FastAPI — verifying the ID token with cached JWKS

# auth.py
import time, httpx
from jose import jwt                       # python-jose
from fastapi import Depends, HTTPException, Request

ISSUER   = "https://your-tenant.us.auth0.com/"
AUDIENCE = "aBcD1234ClientId"
_jwks, _jwks_at = None, 0

async def jwks():
    global _jwks, _jwks_at
    if not _jwks or time.time() - _jwks_at > 3600:   # cache 1h, respect rotation
        async with httpx.AsyncClient() as c:
            _jwks = (await c.get(ISSUER + ".well-known/jwks.json")).json()
            _jwks_at = time.time()
    return _jwks

async def current_user(request: Request):
    token = request.cookies.get("id_token") or ""
    keys = await jwks()
    try:
        claims = jwt.decode(token, keys, algorithms=["RS256"],
                            audience=AUDIENCE, issuer=ISSUER)
    except Exception as e:
        raise HTTPException(401, f"invalid id token: {e}")
    # nonce check happens at callback time against the stored value
    return claims

8. Production Architecture

Where does OIDC live in a real system? The dominant secure pattern in 2026 is the Backend-for-Frontend (BFF): the OIDC flow and tokens stay server-side; the browser holds only an encrypted, httpOnly session cookie. This avoids exposing tokens to JavaScript (XSS theft) entirely.

  Browser (no tokens in JS)            BFF / Web Server                Auth0
  ------------------------             ----------------                -----
  httpOnly SameSite cookie  <--session-->  runs Auth Code+PKCE  <--OIDC--> /authorize
       |                                   stores tokens server-side       /token
       |  /api/* (cookie)                  validates id_token              /jwks.json
       v                                   |                               (cached)
  +-----------+    proxy + attach          v
  |   BFF     | --- access_token ----> Resource API (verifies access_token via JWKS)
  +-----------+    refresh when expiring

Decision guide for token placement:

App typeFlowToken storageWhy
Server-rendered web (Spring, Next.js, Express)Auth Code + PKCEEncrypted httpOnly cookie / server sessionNo tokens in browser JS; XSS can't exfiltrate
SPA with its own APIBFF (Auth Code + PKCE server-side)Cookie to BFF; tokens on BFFBest security; avoids browser token storage
Pure SPA (no backend)Auth Code + PKCE (in browser)In-memory; refresh via rotating refresh tokensPKCE replaces the secret; never use Implicit
Native / mobileAuth Code + PKCE (system browser)OS secure storage / keychainPKCE mandatory; public client
Key

JWKS caching is an architecture concern: cache keys (respect Cache-Control / TTL ~10–60 min), and on encountering an unknown kid, refetch once (to pick up a rotated key) before rejecting. This makes key rotation seamless and prevents a thundering herd against jwks_uri.

9.1 Why state AND nonce (they are different)

  state  -> protects the CALLBACK (CSRF):   "did *I* start this login?"
            random value sent to /authorize, returned as ?state=, compared.

  nonce  -> protects the ID TOKEN (replay):  "is this id_token for *this* request?"
            random value sent to /authorize, embedded in id_token.nonce, compared.

  state lives in the URL round-trip; nonce lives INSIDE the signed token.
  You need both: state can't protect a token's contents; nonce can't stop CSRF.
Danger

The Implicit flow (response_type=token id_token) is deprecated — it returned tokens in the URL fragment, exposing them to history, logs, and referrers. As of OAuth 2.1 / 2026 best practice, always use Authorization Code + PKCE, even for SPAs. Do not use Implicit in new systems.

10. Performance Considerations

  • Verify ID tokens locally. Signature verification with a cached JWKS key is microseconds of CPU and zero network — far cheaper than introspection. Don't call the network on every request to validate identity.
  • Cache the discovery document and JWKS. Fetch discovery once at startup (or with a long TTL); cache JWKS for minutes and refetch only on unknown kid or TTL expiry. Uncached, you add a round-trip per login and risk rate limits.
  • Prefer the ID token over userinfo for basic profile. If profile/email claims are in the ID token, you already have them — calling /userinfo is an extra network hop. Use userinfo when you need fresh or omitted claims.
  • Keep ID tokens lean. Large custom claims bloat every request that carries the token/session. Put bulk data behind userinfo or your own API, not in the token.
  • RS256 verify vs HS256: RS256 verification is asymmetric and slightly heavier than HMAC, but still sub-millisecond and the right trade for public clients. Don't "optimize" to HS256 and break the security model.
  • Connection reuse: use a keep-alive HTTP client for JWKS/discovery fetches; share a singleton createRemoteJWKSet rather than constructing one per request.

11. Common Mistakes

Danger

Using the access token to identify the user. Access tokens are for APIs; their format may be opaque and their claims are not an identity contract. Use the ID token.

Danger

Sending the ID token to your API as the bearer credential. APIs must validate access tokens (correct aud = the API). An ID token's aud is the client; accepting it at the API is an audience-confusion bug.

  • Forgetting the openid scope. No openid → no ID token → it's plain OAuth and login breaks silently.
  • Not validating the signature (only decoding). Decoding is not verifying; unverified claims are attacker-controlled.
  • Loose issuer/audience checks (substring match, ignoring trailing slash, skipping aud).
  • Allowing alg: none or symmetric algs by trusting the token header — always pin RS256.
  • Skipping nonce (or generating it but never comparing it on return).
  • Keying users on email instead of iss+sub.
  • Treating email_verified=false as verified — and account-linking on unverified email (account-takeover risk).
  • Hardcoding endpoints instead of reading the discovery document → breaks on tenant/region change or rotation.
  • Storing tokens in localStorage → XSS exfiltration. Use httpOnly cookies / BFF.
  • Requesting offline_access you don't need → unnecessary long-lived refresh tokens to protect.

12. Best Practices

  • Always Authorization Code + PKCE; never Implicit. PKCE even for confidential clients.
  • Use a certified OIDC library/SDK (express-openid-connect, Spring Security, @auth0/nextjs-auth0, @auth0/auth0-react, authlib). Don't hand-roll the flow.
  • Drive config from the discovery document; never hardcode endpoints.
  • Validate all seven: signature (RS256, pinned), iss (exact), aud, exp (with small skew), iat, nonce, and conditionally auth_time/acr.
  • Generate state and nonce with a CSPRNG, store them bound to the browser session, and compare on return.
  • Request the least scopes needed; add offline_access only when you truly need refresh tokens; pass audience only to get an API access token.
  • Keep tokens out of the browser where possible (BFF + httpOnly, SameSite=Lax/Strict cookies).
  • Use the ID token to start a session, then rely on your own session — don't re-present the ID token on every request.
  • Trust email only when email_verified === true; key users on sub.
  • Cache JWKS/discovery with sane TTLs and a refetch-on-unknown-kid strategy.

13. Interview Questions (with model answers)

Q1. What does OpenID Connect add to OAuth 2.0?

A. OIDC is an identity layer on top of OAuth 2.0. OAuth only delegates authorization (access tokens for APIs). OIDC adds: the ID token (a signed JWT asserting who authenticated, audience = the client), the reserved openid scope that triggers it, standard claims and the userinfo endpoint, the discovery document and JWKS for self-configuration and signature verification, and the nonce replay defense. It reuses OAuth's endpoints and grants.

Q2. Difference between an ID token and an access token?

A. ID token: identity assertion, audience = client, always a JWT, validated by the client to establish login. Access token: authorization credential, audience = the API/resource server, JWT or opaque, validated by the API. They have different audiences and different consumers; swapping them is an audience-confusion vulnerability.

Q3. Why nonce if we already have state?

A. state defends the callback against CSRF (it's a URL round-trip value proving the client initiated the flow). nonce defends the ID token against replay/injection: it is embedded inside the signed token, so a stolen/replayed token from another request won't match the nonce this client generated. State protects the transaction; nonce protects the token's binding to that transaction.

Q4. Walk me through ID token validation.

A. (1) Verify the JWS signature using the JWKS key matching the header kid, pinning RS256 and rejecting none. (2) iss exactly matches configured issuer. (3) aud contains our client_id (check azp if multiple). (4) exp not past (small skew allowed). (5) iat sane. (6) nonce matches the stored value. (7) If max_age/MFA requested, check auth_time/acr/amr.

Q5. What is the discovery document and why use it?

A. A JSON metadata document at /.well-known/openid-configuration listing the issuer, authorization/token/userinfo endpoints, jwks_uri, supported scopes/claims/response types and algorithms. Clients read it to self-configure and to locate signing keys, so endpoints aren't hardcoded and rotation/region changes don't break them.

Q6. How does JWKS enable key rotation?

A. JWKS publishes the issuer's current public keys, each tagged with a kid. The ID token header names the kid used. To rotate, the issuer publishes the new key (both old and new appear during overlap) and starts signing with it. Clients select keys by kid and refetch JWKS on an unknown kid, so rotation is transparent and never requires client redeploys.

Q7. What is the Hybrid flow and when is it used?

A. Hybrid uses combined response_type values like code id_token: the front channel returns an ID token immediately and a code to exchange at the token endpoint. It lets the client validate identity early (e.g., to bind/sanity-check the request) before the back-channel exchange. Modern guidance favors plain Authorization Code + PKCE; Hybrid is mostly seen in legacy/financial-grade setups and is largely superseded.

Q8. Why prefer RS256 over HS256 for ID tokens?

A. RS256 is asymmetric: the issuer signs with a private key, clients verify with a public key from JWKS. No verifier can forge tokens, and rotation is easy. HS256 shares one secret between issuer and verifier — every verifier could mint tokens, and distributing the secret to public clients (SPAs) is impossible to keep secret. RS256 is correct for OIDC.

Q9. Should an SPA store the ID/access token in localStorage?

A. No. localStorage is readable by any JS, so XSS exfiltrates it. Prefer a BFF that keeps tokens server-side and issues an httpOnly, SameSite cookie; if a pure SPA is required, keep tokens in memory and use Authorization Code + PKCE with rotating refresh tokens.

Q10. When do you call userinfo vs read claims from the ID token?

A. If the needed claims are already in the verified ID token, use them — no network call. Call /userinfo (with the access token) when you need claims not included in the ID token or want the freshest profile. userinfo is the authoritative source for the user's current standard claims.

14. Certification Tips

Tip

For the Auth0 / OIDC certification, memorize the artifact→consumer→audience triangle: ID token → client → aud=client_id; access token → API → aud=API identifier; refresh token → /token endpoint.

  • Exams love the trap "use the access token to log the user in." The answer is always the ID token.
  • Know that openid is the scope that makes a request OIDC and triggers the ID token.
  • Map scopes to claims: profile → name/picture/locale/etc., email → email + email_verified, offline_access → refresh token.
  • Know the discovery path exactly: /.well-known/openid-configuration, and that it contains jwks_uri.
  • Remember Auth0 defaults to RS256 and that Implicit is deprecated in favor of Auth Code + PKCE.
  • Distinguish state (CSRF, URL) vs nonce (replay, inside ID token).
  • Know sub is the stable user identifier and identity = iss + sub.
  • Recognize response_type values: code (Auth Code), code id_token/code token (Hybrid), id_token token (Implicit, avoid).

17. Mini Project — "AuthLens" ID-token verifier service

Create a small service that accepts an issuer URL and an ID token and returns a structured verification report. It must:

  • Fetch and cache the discovery document and JWKS for the given issuer.
  • Run each of the seven validation steps independently and report pass/fail with the offending claim value.
  • Detect and flag dangerous conditions: alg: none, non-RS256 alg, missing nonce, expired token, audience mismatch, unknown kid.
// authlens.js (sketch) — POST {issuer, idToken, expectedAud, expectedNonce}
import express from 'express';
import { createRemoteJWKSet, jwtVerify, decodeProtectedHeader } from 'jose';

const app = express(); app.use(express.json());
const jwksCache = new Map();
const jwksFor = (iss) => jwksCache.get(iss)
  ?? jwksCache.set(iss, createRemoteJWKSet(new URL(iss + '.well-known/jwks.json'))).get(iss);

app.post('/verify', async (req, res) => {
  const { issuer, idToken, expectedAud, expectedNonce } = req.body;
  const report = { steps: [] };
  const add = (name, ok, detail) => report.steps.push({ name, ok, detail });
  try {
    const hdr = decodeProtectedHeader(idToken);
    add('alg', hdr.alg === 'RS256', `alg=${hdr.alg}`);
    const { payload } = await jwtVerify(idToken, jwksFor(issuer), {
      issuer, audience: expectedAud, algorithms: ['RS256'], clockTolerance: '60s',
    });
    add('signature+iss+aud+exp', true, `sub=${payload.sub}`);
    add('nonce', payload.nonce === expectedNonce, `nonce=${payload.nonce}`);
    report.valid = report.steps.every(s => s.ok);
  } catch (e) { add('verify', false, e.message); report.valid = false; }
  res.json(report);
});
app.listen(4000);

Extend it: add a UI that color-codes each step, and a "diff against userinfo" panel.

19. Cheat Sheet

 OIDC = OAuth 2.0 + identity layer (ID token, openid scope, userinfo, discovery, nonce)

 TOKENS        aud           consumer       format      job
 ----------    -----------   -----------    --------    --------------------
 id_token      client_id     the CLIENT     JWT         "who logged in" (session)
 access_token  API id        the API        JWT/opaque  "what app may do"
 refresh_token auth server   /token         opaque      get new tokens

 SCOPES   openid (REQUIRED) | profile | email | offline_access(=refresh)

 ENDPOINTS  /.well-known/openid-configuration  -> discovery
            jwks_uri                           -> public keys (by kid)
            /authorize  /oauth/token  /userinfo

 VALIDATE id_token (7):
   1 signature (JWKS, RS256, reject none)   5 iat sane

   3 aud contains client_id (+azp)          7 auth_time/acr (if max_age/MFA)
   4 exp not past (±skew)

           RS256 always      never Implicit           tokens out of JS (BFF)

 KEY CLAIMS  sub(stable id)  iss  aud  exp  iat  nonce  email+email_verified

 GOLDEN RULE  id_token => identify (client).  access_token => authorize (API).

20. Key Takeaways

Key

OIDC is the identity layer on OAuth 2.0. It reuses every OAuth endpoint and adds the ID token, the openid scope, userinfo, discovery, and nonce. OAuth authorizes; OIDC authenticates.

Key

Three tokens, three jobs. ID token (identity, aud=client), access token (authorization, aud=API), refresh token (renewal, for /token). Never confuse or swap them — swapping is an audience-confusion vulnerability.

Key

Validate ID tokens in seven steps: signature (RS256 via JWKS, reject none), iss, aud, exp, iat, nonce, and conditionally auth_time/acr. Decoding is not verifying.

Key

Discovery + JWKS make clients self-configuring and rotation-safe. Read /.well-known/openid-configuration; cache JWKS; select keys by kid; refetch on unknown kid.

Key

Use Authorization Code + PKCE everywhere (never Implicit), keep tokens out of browser JS (BFF + httpOnly cookies), pin RS256, and use both state (CSRF) and nonce (replay). Key users on iss+sub.
