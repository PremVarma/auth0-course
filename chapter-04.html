Phase 2 · OAuth 2.0 Masterclass

Chapter 4 — OAuth 2.0 Foundations

Almost every "Log in with Google", "Connect your GitHub", and "Allow this app to read your calendar" button on the internet runs on one protocol: OAuth 2.0. Auth0 itself is, at its core, a hosted, hardened OAuth 2.0 / OpenID Connect server. If OAuth is fuzzy, every later chapter — flows, tokens, rules, APIs, fine-grained authorization — will feel like memorization. This chapter builds OAuth from absolute first principles: the problem it solves, the four roles, the two endpoints, the two channels, the two token types, scopes and consent, and the single most misunderstood fact in the whole field — OAuth 2.0 is an authorization framework, not an authentication protocol. By the end you will be able to draw the entire dance from memory and explain every arrow.

1. Theory — First Principles

Before OAuth, there was a genuinely terrible pattern called the password anti-pattern. Imagine a printing service called PrintMyPics wants to grab the photos in your Google account so it can mail you a calendar. In ~2006 the only way to do this was for PrintMyPics to ask you for your Google username and password, then log in as you and scrape your photos.

Stop and feel how bad that is. You handed a third party your master credential. With it they can read your email, change your password, delete your account, impersonate you everywhere Google reaches. There is no way to give them "just photos". There is no way to revoke only PrintMyPics without changing your password and breaking every other app. There is no expiry. There is no audit trail of who did what. The credential is reusable forever and grants unlimited power.

OAuth 2.0 (RFC 6749, 2012) exists to solve exactly one problem, and the name tells you what it is:

Key

Delegated authorization. OAuth lets a user (the resource owner) grant a third-party application (the client) limited, revocable, scoped access to resources held on another service — without ever sharing the user's password with that application.

Every design decision in OAuth flows from breaking down the password anti-pattern into requirements:

Problem with sharing passwordsOAuth requirementOAuth mechanism
App gets unlimited powerAccess must be scopedscope parameter + consent screen
App keeps access foreverAccess must expireShort-lived access tokens
Can't revoke one appAccess must be revocable per appToken revocation; per-client grants
App can do everything you canApp acts with its own identity, not yoursclient_id / client_secret
Password leaks = total compromiseThe high-value secret must never touch the clientRedirect to the authorization server

The genius move is indirection: instead of the user giving the password to the app, the user authenticates directly at the service that holds the resources, and that service hands the app a token — a narrow, time-boxed, app-specific "valet key". The password never leaves the service. The token is all the app ever sees.

2. Story-Based Explanation

Meet Maya. She uses a cloud photo service, PixVault, where all her photos live. She discovers FrameIt, an app that prints physical photo books. FrameIt needs to read Maya's photos.

The bad old way: FrameIt shows a form: "Enter your PixVault email and password." Maya types them in. FrameIt now is Maya at PixVault. It could delete her albums or read her private ones. Maya is uneasy, and rightly so.

The OAuth way: Maya clicks "Connect PixVault". FrameIt does not ask for her password. Instead it redirects her browser to PixVault itself. On a real PixVault page (Maya checks the URL bar — it really is pixvault.com), she logs in to PixVault, with PixVault. PixVault then shows a consent screen:

"FrameIt wants to: View your photos (read-only). It will NOT be able to delete photos or see your account settings. [Allow] [Deny]"

Maya clicks Allow. PixVault sends her browser back to FrameIt with a one-time authorization code. FrameIt's server quietly swaps that code (plus its own secret) for an access token at PixVault's token endpoint. From now on, FrameIt calls PixVault's API with that token: GET /photos with header Authorization: Bearer abc123…. PixVault sees a token that says "read photos only, expires in 1 hour, issued to FrameIt for Maya" and returns exactly that.

Three weeks later Maya is done. She goes to PixVault → Settings → Connected Apps → FrameIt → Revoke. FrameIt is cut off instantly. Maya never changed her password. She never gave it away. That is delegated authorization.

Note

Notice who talked to whom. Maya ↔ PixVault for the password. FrameIt ↔ PixVault for the token. FrameIt never learned Maya's password. The trust boundaries stayed clean. This separation is the entire point.

4. Real-World Analogy — The Hotel & the Valet

You drive a luxury car to a hotel. Two kinds of keys exist:

  • Your master key fob opens everything: ignition, trunk, glovebox, and it programs new keys. This is your password. You never hand it to a stranger.
  • The valet key starts the engine and opens the door — but not the trunk or glovebox, and it stops working after the valet shift ends. This is an access token: scoped (drive, not trunk), and time-boxed.

Map it to OAuth:

Hotel worldOAuth world
You (the car owner)Resource owner
The valetClient application
The valet desk that issues keysAuthorization server
The car (and its locks)Resource server / API
Master fobPassword (never shared)
Valet key (limited, expiring)Access token (scoped, short-lived)
"Drive + door, no trunk"Scopes
"Get me a fresh key tomorrow"Refresh token
Telling the desk "cancel that valet's key"Token revocation

Crucially, the valet desk — not the valet — decides what the key can do. In OAuth, the authorization server, not the client, decides what's in the token. The client just presents what it was given.

5. Internal Working — What Each Piece Actually Does

The four roles, precisely

RoleDefinition (RFC 6749)Concrete example
Resource OwnerThe entity that can grant access to a protected resource. Usually the end user.Maya, the human
ClientThe application requesting access on behalf of the resource owner.FrameIt (web/mobile/SPA)
Authorization Server (AS)Authenticates the resource owner and issues access tokens after getting authorization.Auth0 (your-tenant.auth0.com)
Resource Server (RS)The API hosting protected resources; accepts and validates access tokens.Your /api/photos backend
Note

In Auth0 terms: the Authorization Server is your Auth0 tenant. The Resource Server is an Auth0 API (identified by an audience). The Client is an Auth0 Application (with a client_id). Memorize this mapping — it appears in every dashboard screen.

The two endpoints

An OAuth authorization server exposes (among others) two core HTTP endpoints. Knowing which is which is fundamental:

Authorization EndpointToken Endpoint
Path (Auth0)/authorize/oauth/token
ChannelFront channel (browser redirect)Back channel (server POST)
Who interactsThe user (via browser)The client (server-to-server)
HTTP methodGET (redirect)POST (form-encoded)
PurposeAuthenticate user, get consent, return a codeExchange code (or refresh token) for tokens

Front channel vs back channel

The front channel is any communication that passes through the user's browser — typically via HTTP redirects, with parameters in the URL query string. It is observable: the user can see it, browser history records it, and a malicious browser extension could read it. Therefore nothing irreversible or high-value travels in the front channel — only a short-lived, one-time authorization code.

The back channel is a direct, server-to-server HTTPS call. The browser is not involved and cannot see it. This is where the client_secret is presented and where actual tokens are returned. Confidential clients can keep a secret precisely because they have a back channel a browser can't snoop.

What's inside a token

An access token can be one of two physical formats:

  • Opaque token — a random, meaningless string (e.g. 2YotnFZFEjr1zCsicMWpAA). The resource server can't read it; it must call the AS's introspection endpoint to learn what it means. Easy to revoke (just delete the server-side record), but adds a network hop on every API call.
  • JWT (JSON Web Token) — a self-describing, cryptographically signed token whose payload (claims) the resource server can validate locally using the AS's public key — no network call needed. Fast and stateless, but harder to revoke before expiry.

Auth0 issues JWT access tokens when you request an API audience, and opaque access tokens when you only request /userinfo (i.e. no audience). This distinction trips up nearly every beginner — we'll return to it.

6. Code Walkthrough — Reading the Wire

Let's read every byte of a real Authorization Code flow against Auth0. Start with the front-channel redirect the client builds:

GET https://YOUR_TENANT.auth0.com/authorize?
    response_type=code
  &client_id=AbC123ClientId
  &redirect_uri=https%3A%2F%2Fframeit.example.com%2Fcallback
  &scope=openid%20profile%20read%3Aphotos
  &audience=https%3A%2F%2Fapi.pixvault.com
  &state=xyz789-random-csrf-token
  &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  &code_challenge_method=S256

Line by line:

  • response_type=code — "I want an authorization code" (Authorization Code grant).
  • client_id — public identifier of the FrameIt application. Not secret.
  • redirect_uri — where to send the browser back. Must exactly match a pre-registered URL (prevents code theft).
  • scope — the permissions requested. openid opts into OIDC; read:photos is a custom API scope.
  • audience — Auth0-specific: which API (resource server) the access token is for. This is what makes Auth0 mint a JWT access token.
  • state — opaque anti-CSRF value the client generates and later verifies. Non-negotiable.
  • code_challenge / method — PKCE (RFC 7636). Binds the code to this client instance; covered fully in Chapter 5.

After login + consent, the AS redirects the browser back:

HTTP/1.1 302 Found
Location: https://frameit.example.com/callback?code=SplxlOBeZQQYbYS6WxSbIA&state=xyz789-random-csrf-token

The client verifies state matches, then exchanges the code on the back channel:

curl --request POST \
  --url 'https://YOUR_TENANT.auth0.com/oauth/token' \
  --header 'content-type: application/x-www-form-urlencoded' \
  --data grant_type=authorization_code \
  --data 'client_id=AbC123ClientId' \
  --data 'client_secret=THE_SUPER_SECRET_VALUE' \
  --data code=SplxlOBeZQQYbYS6WxSbIA \
  --data 'redirect_uri=https://frameit.example.com/callback' \
  --data code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

The token endpoint responds:

{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6Ii4uLiJ9.eyJpc3MiOiJodHRwczovL1lPVVJfVEVOQU5ULmF1dGgwLmNvbS8iLCJzdWIiOiJhdXRoMHwxMjMiLCJhdWQiOiJodHRwczovL2FwaS5waXh2YXVsdC5jb20iLCJzY29wZSI6InJlYWQ6cGhvdG9zIn0...",
  "refresh_token": "v1.MnD8s...opaque...Qk",
  "id_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "scope": "openid profile read:photos",
  "expires_in": 86400,
  "token_type": "Bearer"
}

Decode the access_token payload (the middle segment, base64url) and you'd see:

{
  "iss": "https://YOUR_TENANT.auth0.com/",
  "sub": "auth0|123",
  "aud": "https://api.pixvault.com",
  "iat": 1718755200,
  "exp": 1718841600,
  "scope": "read:photos",
  "azp": "AbC123ClientId"
}
Warn

See three tokens? access_token is for calling the API (audience api.pixvault.com). id_token is for the client to learn who the user is (that's OIDC, Chapter 6) — never send it to an API. refresh_token is for getting new access tokens later. Mixing these up is the #1 beginner mistake.

7. Practical Implementation

Here are minimal, runnable implementations of the same flow across stacks. They all do the same thing: redirect to /authorize, handle the callback, exchange the code, call the API.

Node.js (Express) — confidential client, manual flow

import express from "express";
import crypto from "crypto";

const app = express();
const AS = "https://YOUR_TENANT.auth0.com";
const CLIENT_ID = process.env.CLIENT_ID;
const CLIENT_SECRET = process.env.CLIENT_SECRET;   // back channel only
const REDIRECT_URI = "http://localhost:3000/callback";
const AUDIENCE = "https://api.pixvault.com";
const sessions = {};

// 1) Kick off: build the front-channel redirect
app.get("/login", (req, res) => {
  const state = crypto.randomBytes(16).toString("hex");
  sessions[state] = true;                            // remember it to verify later
  const url = new URL(`${AS}/authorize`);
  url.search = new URLSearchParams({
    response_type: "code",
    client_id: CLIENT_ID,
    redirect_uri: REDIRECT_URI,
    scope: "openid profile read:photos",
    audience: AUDIENCE,
    state,
  }).toString();
  res.redirect(url.toString());
});

// 2) Callback: verify state, exchange code on the BACK channel
app.get("/callback", async (req, res) => {
  const { code, state } = req.query;
  if (!sessions[state]) return res.status(403).send("Invalid state (possible CSRF)");
  delete sessions[state];

  const tokenRes = await fetch(`${AS}/oauth/token`, {
    method: "POST",
    headers: { "content-type": "application/x-www-form-urlencoded" },
    body: new URLSearchParams({
      grant_type: "authorization_code",
      client_id: CLIENT_ID,
      client_secret: CLIENT_SECRET,
      code,
      redirect_uri: REDIRECT_URI,
    }),
  });
  const tokens = await tokenRes.json();

  // 3) Use the access token to call the resource server
  const api = await fetch(`${AUDIENCE}/photos`, {
    headers: { Authorization: `Bearer ${tokens.access_token}` },
  });
  res.json(await api.json());
});

app.listen(3000, () => console.log("http://localhost:3000/login"));

FastAPI (Python) — resource server validating a JWT access token

from fastapi import FastAPI, Depends, HTTPException
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
import jwt                       # pip install pyjwt[crypto]
from jwt import PyJWKClient

app = FastAPI()
DOMAIN = "YOUR_TENANT.auth0.com"
AUDIENCE = "https://api.pixvault.com"
ISSUER = f"https://{DOMAIN}/"
jwks = PyJWKClient(f"https://{DOMAIN}/.well-known/jwks.json")
bearer = HTTPBearer()

def require_scope(scope: str):
    def checker(cred: HTTPAuthorizationCredentials = Depends(bearer)):
        token = cred.credentials
        key = jwks.get_signing_key_from_jwt(token).key
        try:
            claims = jwt.decode(
                token, key, algorithms=["RS256"],
                audience=AUDIENCE, issuer=ISSUER,   # validate aud + iss
            )
        except jwt.PyJWTError as e:
            raise HTTPException(401, f"Invalid token: {e}")
        if scope not in claims.get("scope", "").split():
            raise HTTPException(403, "Insufficient scope")
        return claims
    return checker

@app.get("/photos")
def list_photos(claims=Depends(require_scope("read:photos"))):
    return {"owner": claims["sub"], "photos": ["a.jpg", "b.jpg"]}

React (SPA) — public client, never holds a secret

// npm i @auth0/auth0-react   — the SDK uses Authorization Code + PKCE under the hood
import { Auth0Provider, useAuth0 } from "@auth0/auth0-react";

function Photos() {
  const { loginWithRedirect, getAccessTokenSilently, isAuthenticated } = useAuth0();
  async function load() {
    const token = await getAccessTokenSilently();   // SDK handles code+PKCE+refresh
    const r = await fetch("https://api.pixvault.com/photos", {
      headers: { Authorization: `Bearer ${token}` },
    });
    console.log(await r.json());
  }
  return isAuthenticated
    ? <button onClick={load}>Load my photos</button>
    : <button onClick={() => loginWithRedirect()}>Connect PixVault</button>;
}

export default function App() {
  return (
    <Auth0Provider
      domain="YOUR_TENANT.auth0.com"
      clientId="PUBLIC_SPA_CLIENT_ID"
      authorizationParams={{
        redirect_uri: window.location.origin,
        audience: "https://api.pixvault.com",
        scope: "openid profile read:photos",
      }}>
      <Photos />
    </Auth0Provider>
  );
}

Spring Boot — resource server with one config block

// application.yml
// spring.security.oauth2.resourceserver.jwt.issuer-uri: https://YOUR_TENANT.auth0.com/
@Configuration
@EnableWebSecurity
public class SecurityConfig {
  @Bean
  SecurityFilterChain filter(HttpSecurity http) throws Exception {
    http
      .authorizeHttpRequests(a -> a
        .requestMatchers("/photos").hasAuthority("SCOPE_read:photos")
        .anyRequest().authenticated())
      .oauth2ResourceServer(o -> o.jwt(jwt -> {}));  // validates RS256 via JWKS
    return http.build();
  }
}

@RestController
class PhotoController {
  @GetMapping("/photos")
  List<String> photos(@AuthenticationPrincipal Jwt jwt) {
    return List.of("a.jpg", "b.jpg"); // jwt.getSubject() == the user
  }
}

8. Production Architecture

A real OAuth deployment separates concerns cleanly. Here is a typical production topology with Auth0 as the AS:

                         ┌──────────────────────────────────────┐
   ┌──────────┐  HTTPS   │            AUTH0 (managed AS)         │
   │ Browser  │◀────────▶│  /authorize  /oauth/token  /jwks.json│
   │  (SPA)   │  redirect│  Universal Login · MFA · Rules        │
   └────┬─────┘          └───────────────┬──────────────────────┘
        │ Bearer JWT                     │ signs tokens with private key
        │ (access token)                 │ publishes PUBLIC key at JWKS
        ▼                                ▼  (cached by every RS)
   ┌──────────────┐      ┌───────────────────────────────────────────────┐
   │  API Gateway │─────▶│   Resource Servers (your microservices)        │
   │ (rate limit, │      │  ┌──────────┐  ┌──────────┐  ┌──────────┐     │
   │  WAF, mTLS)  │      │  │ photos   │  │ billing  │  │ orders   │ ... │
   └──────────────┘      │  │ aud:..api│  │ aud:..api│  │ aud:..api│     │
                         │  validate JWT locally via cached JWKS public key│
                         └───────────────────────────────────────────────┘

Key architectural decisions:

  • Stateless validation. Each service validates JWTs locally using the AS's public key (fetched once from /.well-known/jwks.json and cached). No per-request call to Auth0 — that's what makes JWT scale to millions of req/s.
  • One audience per logical API. Tokens minted for billing shouldn't be accepted by photos. The aud claim enforces this — a token is bound to one resource server.
  • Refresh tokens in the back end (BFF pattern). For SPAs, the safest production pattern is a Backend-for-Frontend that holds tokens in a secure, http-only cookie session rather than browser storage. Covered in later chapters.
  • Key rotation. Auth0 rotates signing keys; because clients fetch JWKS dynamically and keys are identified by kid, rotation is seamless. Never hard-code a public key.

9. Security Analysis

Public vs confidential clients — the central security distinction

Confidential clientPublic client
Can it keep a secret?Yes — runs on a server you controlNo — code ships to the user (browser/mobile)

Danger

Never embed a client_secret in a SPA, mobile app, or any code distributed to users. It is trivially extractable. Public clients use PKCE (Proof Key for Code Exchange) instead — a per-request, dynamically generated proof that replaces the static secret. If a tutorial tells you to put a secret in a React app, close it.

What the threats are, and how OAuth answers them

ThreatMitigation in OAuth 2.0

Warn

The legacy Implicit grant (response_type=token) returned the access token directly in the URL fragment via the front channel. It is now deprecated (OAuth 2.1) because tokens leaked into browser history, logs, and referrers. Always use Authorization Code + PKCE — even for SPAs.

10. Performance Considerations

  • JWT vs opaque — the latency trade-off. A JWT is validated locally (a signature check, microseconds). An opaque token requires a network round-trip to the AS's /introspect endpoint on every API call. For high-traffic APIs, JWTs win decisively; reserve opaque + introspection for cases where instant revocation outweighs latency.
  • Cache the JWKS. Fetch /.well-known/jwks.json once and cache it (respecting cache headers, typically hours). Re-fetch only when you see an unknown kid. Fetching JWKS per request would add a network call back in and defeat the point.
  • Right-size token lifetimes. Short access-token TTL (e.g. 15–60 min) limits replay window but increases refresh traffic. Long TTL reduces refresh load but widens the blast radius of a leak. Tune per sensitivity.
  • Keep tokens small. Every byte of a JWT rides on every request header. Stuffing large arrays of permissions or profile data into a token bloats requests and can hit header-size limits (8 KB on many servers). Put coarse scopes in the token; fetch fine-grained data from a service.
  • Refresh-token rotation has a cost. Rotation issues a new refresh token each use — more writes at the AS, but vastly better security. The trade-off almost always favors rotation.

11. Common Mistakes

Danger

Treating OAuth as authentication. "I got an access token, so the user is logged in." No — an access token says nothing reliable about who the user is. Use an ID token (OIDC) for identity. This deserves its own section (#20-ish below) — and the next chapter.

  • Putting client_secret in front-end code. Already covered, but it's so common it bears repeating. Public clients use PKCE, full stop.
  • Skipping the state parameter. Without it your callback is open to CSRF. Always generate, store, and verify it.
  • Sending the id_token to your API as the bearer credential. APIs must consume access tokens (with aud = your API). ID tokens have aud = your client and may be rejected — or worse, naively accepted.
  • Not validating aud and iss on the resource server. A signature check alone is insufficient: a valid token for a different API or tenant would pass. Validate issuer, audience, expiry, and signature.
  • Forgetting the audience param with Auth0 and then wondering why the access token is opaque and your API can't decode it. No audience → /userinfo-only opaque token.
  • Requesting more scopes than needed. Over-scoping scares users at consent and widens damage if leaked. Request least privilege.
  • Storing access tokens in localStorage where any XSS can steal them. Prefer in-memory + http-only cookie (BFF) patterns.

12. Best Practices

Tip

Memorize this as your default OAuth posture for 2026.

  • Use Authorization Code + PKCE for everything interactive (web, SPA, mobile). It is the OAuth 2.1 baseline.
  • Use Client Credentials grant for machine-to-machine (no user present) — covered in Chapter 5.
  • Always send and verify state (CSRF) and, for OIDC, nonce (replay).
  • Pre-register exact redirect_uri values; no wildcards.
  • Request the minimum scopes needed; request more later via incremental authorization.
  • Validate tokens fully on the RS: signature, iss, aud, exp, nbf, and required scopes.
  • Keep secrets in a vault / secret manager, never in code or front-end bundles.
  • Prefer short access tokens + rotating refresh tokens.
  • Always use HTTPS everywhere; OAuth's security assumes TLS.
  • Use the SDK (Auth0 libraries) rather than hand-rolling the flow in production — they get PKCE, state, nonce, and refresh right.

13. Interview Questions (with model answers)

Q1. What problem does OAuth 2.0 solve?

Model answer: Delegated authorization. It lets a user grant a third-party app limited, revocable, scoped access to their resources on another service without sharing their password. It replaces the password anti-pattern by issuing scoped, expiring tokens instead.

Q2. Name the four OAuth roles.

Model answer: Resource owner (user), client (the app), authorization server (issues tokens, e.g. Auth0), resource server (the API holding protected data).

Q3. Front channel vs back channel — why does it matter?

Model answer: The front channel passes through the browser via redirects (URL-visible, snoopable), so only a one-time authorization code travels there. The back channel is direct server-to-server HTTPS where the client_secret and actual tokens are exchanged, invisible to the browser. The separation keeps high-value secrets off the channel an attacker can observe.

Q4. Why is OAuth 2.0 not authentication?

Model answer: An access token proves the app was authorized to access a resource; it doesn't reliably prove who the user is. The token's audience is the API, not the client. Using token possession as "logged in" leads to the confused-deputy / "OAuth login" pitfall. Authentication needs OIDC's ID token, which is explicitly about identity, audience-bound to the client, and contains a verified sub.

Q5. Public vs confidential client?

Model answer: A confidential client runs on a server and can safely keep a client_secret; a public client (SPA/mobile) ships to users and cannot, so it uses PKCE instead of a secret.

Q6. Opaque vs JWT access tokens — trade-offs?

Model answer: JWTs are self-contained and validated locally (fast, stateless, scales) but hard to revoke before expiry. Opaque tokens are meaningless strings requiring introspection (network hop per call) but are trivially revocable server-side. Choose JWT for performance, opaque when instant revocation is essential.

Q7. What's the state parameter for?

Model answer: CSRF protection on the redirect. The client generates a random value, sends it on /authorize, and verifies it matches on the callback — ensuring the response corresponds to a request this client actually initiated.

Q8. Why was the Implicit grant deprecated?

Model answer: It returned the access token directly in the URL fragment through the front channel, exposing it to browser history, logs, and referrer leakage, with no client authentication. Authorization Code + PKCE supersedes it for all client types.

Q9. In Auth0, why might your access token be opaque instead of a JWT?

Model answer: Because no audience (API identifier) was requested. Without an audience, Auth0 issues an opaque token usable only against /userinfo. Add the audience param to get a JWT for your API.

Q10. How does a resource server validate a JWT without calling the AS?

Model answer: It fetches the AS's public signing keys once from /.well-known/jwks.json (cached), selects the key by kid, verifies the RS256 signature, then checks iss, aud, exp, and required scopes — all locally.

14. Certification Tips

Note

The Auth0 Certified Developer / Professional exams lean heavily on these foundations. High-yield facts:

  • Know the four roles and the Auth0 mapping: tenant = AS, Application = client, API = resource server.
  • Know the two endpoints: /authorize (front, GET, code) and /oauth/token (back, POST, tokens).
  • Know which grant to pick: interactive → Authorization Code + PKCE; M2M → Client Credentials; never Implicit / ROPC.
  • Remember: access token → API, ID token → client, refresh token → get new tokens. Audiences differ.
  • Remember the audience ⇒ JWT, no audience ⇒ opaque rule — Auth0 loves to test this.
  • OAuth = authorization; OIDC = authentication layer on top. The exam will phrase a question to tempt you into calling OAuth "login".
  • PKCE is required for public clients and recommended for all in OAuth 2.1.
  • Exact-match redirect URIs; state for CSRF; HTTPS mandatory.

20. Key Takeaways

Key

OAuth 2.0 solves delegated authorization: scoped, revocable, expiring access to your data by a third party — without sharing your password.

Key

Four roles, two endpoints, two channels. Owner / client / AS / RS. /authorize (front, code) and /oauth/token (back, tokens). Secrets and tokens live only on the back channel.

Key

Three tokens, three jobs. Access token → call the API. ID token → tell the client who the user is. Refresh token → get new access tokens. Never confuse their audiences.

Key

Public vs confidential is about secrets. Server-side apps keep a client_secret; browser/mobile apps can't, so they use PKCE. Never ship a secret to users.

Key

JWT vs opaque is a trade-off. JWT = local, fast, stateless, harder to revoke. Opaque = introspection, slower, instantly revocable. With Auth0, an audience gives you a JWT.

Danger

OAuth 2.0 is NOT authentication. An access token proves authorization, not identity. To know who the user is, you need OpenID Connect's ID token — which is exactly where Chapter 6 goes. First, Chapter 5 takes you through every OAuth grant type and PKCE in depth.
