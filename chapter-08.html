Chapter 8 — OIDC Tokens: Validation, Introspection and Revocation

In Chapter 7 you learned how OpenID Connect mints an ID token and how the login dance produces it. But a token you do not verify is just a string an attacker can forge. This chapter is the rigorous, first-principles guide to what happens after a token lands in your hands: how to validate an ID token claim-by-claim, how to check a cryptographic signature using JWKS and the kid, how a resource server validates an access token, when to call the introspection endpoint (RFC 7662) instead of validating locally, how to revoke tokens (RFC 7009), how to handle expiry and refresh without locking users out, and how to log a user out everywhere. Get this right and you have built the trust boundary your entire system depends on; get it wrong and every other security control is decoration.

1. Theory — First Principles of Token Trust

A token is a bearer credential: whoever holds it is treated as the subject it describes. That single fact drives everything in this chapter. If a token can be presented by anyone who possesses it, then the only thing standing between your system and an impostor is your ability to answer one question with certainty: "Is this token genuine, intended for me, and still valid right now?"

To answer that question we decompose it into three independent properties, each of which must hold:

  • Authenticity / Integrity — Was this token issued by the authority I trust (Auth0), and has a single byte been changed since? This is answered by verifying the digital signature.
  • Intended audience — Was this token minted for me, or for some other application? A token valid for App A must be rejected by App B. This is the aud (and for ID tokens, the relationship between aud and your client ID) check.
  • Freshness / Liveness — Is the token within its valid time window (exp, iat, nbf), and has it not been revoked since issuance?

There are two fundamentally different validation strategies, and choosing between them is one of the most important architectural decisions in OIDC:

StrategyHow it worksNetwork costRevocation awareness
Local / stateless validationVerify the JWT signature with the issuer's public key, then check the claims. No call to the issuer per request.Zero (keys cached)None until the token expires
Introspection (RFC 7662)POST the token to the authorization server's /introspect endpoint; it returns active: true/false plus claims.One round-trip per requestImmediate — the server is the source of truth
Key

JWT access tokens are validated locally (fast, scalable, but blind to revocation until expiry). Opaque tokens must be introspected (a network call, but always authoritative). This trade-off — speed vs. immediacy — is the central tension of token validation, and you will meet it again in performance, security, and architecture.

The reason we can validate locally at all is asymmetric cryptography. Auth0 signs tokens with a private key (RS256 by default) that never leaves Auth0. It publishes the matching public key at a well-known URL. Anyone can verify a signature with the public key, but only Auth0 can produce one with the private key. That asymmetry is what lets thousands of API instances verify tokens without ever talking to Auth0 and without sharing any secret.

2. Story-Based Explanation — The Forged Wristband

Imagine a three-day music festival. At the gate you show your ticket once and receive a tamper-evident wristband. For the rest of the festival, the wristband is your authorization — staff at the beer tent, the VIP area, and the backstage gate never re-check your ticket; they glance at the wristband.

Now consider how a wristband fails — and how each failure maps exactly to a token claim:

  • A counterfeit wristband — printed by a scalper. Staff defeat this by checking the hologram only the festival's printer can produce. That hologram is the signature. No hologram, no entry.
  • Yesterday's wristband — last year's color, or a Day-1 band on Day-2. That is expiry (exp).
  • A general-admission band at the backstage gate — genuine, in-date, but not minted for that area. That is wrong audience (aud) and missing scope.
  • A band cut off an ejected troublemaker — genuine and in-date, but the holder was thrown out an hour ago. The hologram still checks out; only a radio call to security HQ reveals it is void. That radio call is introspection, and cutting the band is revocation.

The festival deliberately uses cheap, local hologram checks at most gates (fast, no radio needed) and reserves the slow radio-to-HQ check for the highest-value backstage gate. That is exactly the JWT-vs-introspection trade-off. And the reason a cut wristband can still pass a hologram check is the same reason a revoked-but-unexpired JWT still passes local validation: the local check has no knowledge of events that happened after the band was issued.

Note

Hold this analogy in your head for the whole chapter. Every algorithm below is just "checking the hologram, the color/date, the zone, and — when it matters enough — radioing HQ."

4. Real-World Analogy — Passport vs. Visa vs. Border Phone Call

Think of crossing an international border.

  • An ID token is your passport: it proves who you are and is checked once at immigration to let you into the country (your app establishes a session). You do not show your passport to buy a coffee inside the country — its job ends at the door.
  • An access token is a visa stamped for specific activities: it says what you may do (scopes/permissions) and at which destination (the aud = the specific API). The coffee shop (your API) checks the visa, not the passport.
  • Local validation is the border officer recognizing the security features of the passport — watermarks, the chip, the issuing-country seal — without phoning the issuing government. Fast, and trustworthy because the document is tamper-evident.
  • Introspection is the officer actually phoning the issuing authority to ask "is passport #X still valid?" — slower, but it catches a passport that was reported stolen after it was printed.
  • Revocation is the issuing government cancelling a passport in its central database. The physical document still looks perfect; only a phone call (introspection) reveals it is void.
Tip

The analogy explains the single most counter-intuitive fact in this chapter: revoking a JWT access token does not stop it from passing local validation. The cancelled passport still has valid watermarks. Only introspection — or waiting for expiry — closes that window. This is why you keep JWT access-token lifetimes short.

5. Internal Working — Signatures, JWKS, and the kid

5.1 How an RS256 signature is produced and verified

A JWT is base64url(header) + "." + base64url(payload) + "." + base64url(signature). With RS256:

  1. Auth0 computes signing_input = base64url(header) + "." + base64url(payload).
  2. It hashes the signing input with SHA-256, then encrypts that hash with its RSA private key. The result is the signature.
  3. Your code re-computes the SHA-256 hash of the signing input, then uses Auth0's RSA public key to verify that the signature decrypts to the same hash.

Because only the holder of the private key can produce a signature that verifies against the public key, a valid signature simultaneously proves authenticity (it came from Auth0) and integrity (the payload was not altered — any change flips the hash).

5.2 JWKS — the public key directory

Auth0 publishes its public keys as a JWKS (JSON Web Key Set) document at https://YOUR_TENANT/.well-known/jwks.json. Each entry is a JWK:

{
  "keys": [
    {
      "kty": "RSA",          // key type
      "use": "sig",          // used for signatures
      "kid": "abc123KEYID",  // KEY ID — matches the JWT header's "kid"
      "n":   "0vx7agoeb...",  // RSA modulus  (base64url)
      "e":   "AQAB",          // RSA exponent (base64url)
      "alg": "RS256",
      "x5c": ["MIID...certificate..."]
    }
  ]
}

5.3 Why kid exists: key rotation

Auth0 periodically rotates signing keys (and you can force a rotation). During rotation, tokens signed with the old key are still in the wild while new tokens use the new key. So the JWKS often contains multiple keys at once. The JWT header's kid tells you exactly which public key to use, eliminating guesswork:

   JWT header: { "alg":"RS256", "kid":"NEW_KEY_2" }
                                        |
                                        v   match by kid
   JWKS: [ {kid:"OLD_KEY_1", ...},  {kid:"NEW_KEY_2", ...} ]
                                          ^^^^^^^^^^^^^ use this one
Warn

Never hard-code a single public key or pin one kid. When Auth0 rotates keys, hard-coded validation breaks for all users at once. Always resolve the key dynamically from JWKS by kid, and cache the JWKS (do not fetch it on every request — see §10).

5.4 The OIDC discovery document

You should not hard-code the JWKS URL either. Every OIDC provider publishes a discovery document at /.well-known/openid-configuration that links to the JWKS, the token, authorization, introspection, revocation, and end-session endpoints. Libraries fetch this automatically. See §20's OIDC metadata reference.

6. Code Walkthrough — Validation by Hand, Then by Library

6.1 Node.js — manual ID-token validation (to see every step)

This is intentionally explicit so you understand what libraries do for you. In production use a library (§7), but read this once.

import jwt from 'jsonwebtoken';
import { JwksClient } from 'jwks-rsa';

const ISSUER   = 'https://YOUR_TENANT.us.auth0.com/';
const AUDIENCE = 'YOUR_CLIENT_ID';            // ID token aud = client_id

const jwks = new JwksClient({
  jwksUri: `${ISSUER}.well-known/jwks.json`,
  cache: true, cacheMaxEntries: 5, cacheMaxAge: 600000, // 10 min cache
  rateLimit: true, jwksRequestsPerMinute: 10
});

// (1) resolve the signing key by the header's kid
function getKey(header, callback) {
  jwks.getSigningKey(header.kid, (err, key) => {
    if (err) return callback(err);
    callback(null, key.getPublicKey());
  });
}

export function validateIdToken(idToken, expectedNonce) {
  return new Promise((resolve, reject) => {
    jwt.verify(idToken, getKey, {
      algorithms: ['RS256'],          // (2) PIN the algorithm — reject "none"
      issuer:   ISSUER,               // (3) iss must match exactly
      audience: AUDIENCE,             // (4) aud must contain my client_id
      clockTolerance: 60              // (5) 60s leeway for clock skew on exp/iat
    }, (err, claims) => {
      if (err) return reject(err);            // signature/iss/aud/exp failures
      if (claims.nonce !== expectedNonce)     // (6) replay protection
        return reject(new Error('nonce mismatch'));
      resolve(claims);                        // (7) trusted user profile
    });
  });
}
Danger

The single most dangerous mistake is omitting algorithms: ['RS256']. Without it, some libraries will honor an attacker-supplied "alg":"none" token (no signature) or an HS256 token signed with your public key as if it were a shared secret. Always pin the algorithm to RS256 (or your configured asymmetric alg).

7. Practical Implementation — Production Validators per Stack

7.1 Java Spring Boot — resource server (access-token validation)

Spring Security validates JWTs, resolves JWKS by kid, and caches keys for you. You configure the issuer and a custom audience validator.

# application.yml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://YOUR_TENANT.us.auth0.com/
          # issuer-uri triggers auto-discovery of jwks_uri from
          # /.well-known/openid-configuration

app:
  auth0:
    audience: https://api.cinema.example.com   # your API Identifier
@Configuration
@EnableMethodSecurity
public class SecurityConfig {

  @Value("${app.auth0.audience}") String audience;
  @Value("${spring.security.oauth2.resourceserver.jwt.issuer-uri}") String issuer;

  @Bean
  SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a
          .requestMatchers("/public/**").permitAll()
          .requestMatchers("/admin/**").hasAuthority("SCOPE_read:admin")
          .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(j -> j.decoder(jwtDecoder())));
    return http.build();
  }

  @Bean
  JwtDecoder jwtDecoder() {
    // NimbusJwtDecoder fetches JWKS, selects key by kid, verifies RS256,
    // and caches keys (default 5 min) automatically.
    NimbusJwtDecoder decoder = JwtDecoders.fromIssuerLocation(issuer);

    OAuth2TokenValidator<Jwt> withAudience =
        new DelegatingOAuth2TokenValidator<>(
            JwtValidators.createDefaultWithIssuer(issuer), // iss + exp
            audienceValidator());                          // aud
    decoder.setJwtValidator(withAudience);
    return decoder;
  }

  private OAuth2TokenValidator<Jwt> audienceValidator() {
    return jwt -> jwt.getAudience().contains(audience)
        ? OAuth2TokenValidatorResult.success()
        : OAuth2TokenValidatorResult.failure(
            new OAuth2Error("invalid_token", "Missing required audience", null));
  }
}

7.2 FastAPI — dependency that validates the access token

import jwt                       # pip install "pyjwt[crypto]"
from jwt import PyJWKClient
from fastapi import Depends, HTTPException, Security
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

ISSUER   = "https://YOUR_TENANT.us.auth0.com/"
AUDIENCE = "https://api.cinema.example.com"
JWKS_URL = f"{ISSUER}.well-known/jwks.json"

jwks_client = PyJWKClient(JWKS_URL, cache_keys=True, lifespan=600)  # cache 10m
bearer = HTTPBearer()

def verify_token(cred: HTTPAuthorizationCredentials = Security(bearer)) -> dict:
    token = cred.credentials
    try:
        signing_key = jwks_client.get_signing_key_from_jwt(token)  # by kid
        claims = jwt.decode(
            token, signing_key.key,
            algorithms=["RS256"],          # pin algorithm
            audience=AUDIENCE,             # aud check
            issuer=ISSUER,                 # iss check
            leeway=60,                     # clock skew tolerance
        )                                  # exp/iat enforced automatically
        return claims
    except jwt.PyJWTError as e:
        raise HTTPException(status_code=401, detail=f"Invalid token: {e}")

def require_scope(scope: str):
    def checker(claims: dict = Depends(verify_token)):
        if scope not in claims.get("scope", "").split():
            raise HTTPException(status_code=403, detail="Insufficient scope")
        return claims
    return checker

# usage:
# @app.get("/bookings")
# def list_bookings(claims = Depends(require_scope("read:bookings"))): ...

7.3 React (SPA) — let the SDK manage tokens, you consume them

In an SPA you do not validate the access token (your API does). You let @auth0/auth0-react store and refresh tokens, and you attach the access token to API calls.

import { useAuth0 } from '@auth0/auth0-react';

function useApi() {
  const { getAccessTokenSilently } = useAuth0();
  return async function call(path) {
    // getAccessTokenSilently transparently uses the refresh token /
    // silent-auth iframe to obtain a fresh access token when needed.
    const token = await getAccessTokenSilently({
      authorizationParams: { audience: 'https://api.cinema.example.com',
                             scope: 'read:bookings' }
    });
    const res = await fetch(`https://api.cinema.example.com${path}`, {
      headers: { Authorization: `Bearer ${token}` }
    });
    if (res.status === 401) throw new Error('token rejected');
    return res.json();
  };
}

8. Production Architecture — Where Validation Lives

In a real system, token validation is not a single line in one service. It is a layered defense distributed across the edge, the gateway, and each service. Here is a reference layout for a microservices platform behind Auth0:

                     Internet
                        |
        +---------------v----------------+
        |        CDN / WAF (edge)         |  rate limit, block obvious junk
        +---------------+----------------+
                        |
        +---------------v----------------+
        |     API GATEWAY  (Kong/Envoy)   |  FIRST validation:
        |  - verify RS256 sig via JWKS    |  signature + iss + exp
        |  - JWKS cached (shared)         |  reject 80% of bad tokens here
        |  - strips/normalizes headers    |
        +---------------+----------------+
                        | (validated, with claims forwarded)
        +-----------+---+----+-----------+
        |           |        |           |
   +----v---+  +----v---+  +-v------+  +-v------+
   | orders |  |payments|  |catalog |  | users  |   each service:
   | svc    |  | svc    |  | svc    |  | svc    |   - re-checks aud(=its API)
   +--------+  +--------+  +--------+  +--------+   - checks scope/permissions
        |                                          (defense in depth)
   payments svc, being high-value, ALSO introspects
   the token (RFC 7662) for immediate revocation awareness.
Key

Validate at the gateway, re-authorize at the service. The gateway proves the token is genuine and unexpired (cheap, centralized). Each service still checks that the token's audience matches that service's API identifier and that the required scope/permission is present — because a token valid for the catalog API must not be accepted by the payments API.

8.1 Hybrid validation pattern

The pragmatic production pattern combines both strategies:

  • Default: local JWT validation everywhere with short access-token TTL (e.g. 10–15 min). This gives you scale.
  • High-value or sensitive operations introspect (payments, account deletion, admin). This gives those paths immediate revocation awareness.
  • Optional revocation cache: maintain a short-TTL deny-list (e.g. in Redis) of jti values revoked since issuance, populated by an Auth0 Log Stream / webhook. Services consult it during local validation to get near-immediate revocation without per-request introspection.

9. Security Analysis — Attacks and Defenses

AttackWhat the attacker doesDefense
alg: noneStrips the signature, sets alg to none, hoping you skip verification.Pin algorithms: ['RS256']. Never accept none.
Algorithm confusion (RS256→HS256)Signs an HS256 token using your public key as the HMAC secret; a naive verifier that trusts the header's alg accepts it.Pin the expected algorithm; never let the token's header choose the verification algorithm.
Audience confusionReplays a token issued for API-A against API-B.Validate aud equals this API's identifier on every service.
Token replay (ID token)Reuses a captured ID token from a previous login.nonce binding: the ID token's nonce must equal the one you generated for that login attempt.
Expired-token acceptanceUses a token after exp.Enforce exp with small leeway; keep TTL short.
JWKS spoofing / SSRFTricks the verifier into fetching keys from an attacker URL (e.g. via a header-controlled jku).Hard-pin the issuer; derive jwks_uri only from the trusted discovery doc; use TLS; never trust a key URL from the token header.
Refresh-token theftSteals a long-lived refresh token from storage.Refresh token rotation + automatic reuse detection: reusing a rotated RT revokes the whole family.
Revocation blindnessKeeps using a JWT after the user was disabled/logged out.Short TTL + introspection (or a revocation deny-list) on sensitive paths.
Danger

Never store tokens in localStorage for sensitive apps. It is readable by any XSS payload. Prefer httpOnly, Secure, SameSite cookies managed by a backend (the BFF pattern) so JavaScript can never read the token. An access token in localStorage is one XSS away from full account takeover, and it cannot be revoked fast enough to matter.

9.1 Refresh token rotation & reuse detection

With rotation, every refresh returns a new refresh token and invalidates the old one. If an attacker who stole an RT uses it after the legitimate client has already rotated, Auth0 sees a used token being replayed and revokes the entire token family — logging the victim out and locking out the thief. This converts silent theft into a detectable event.

10. Performance Considerations

  • Cache the JWKS. Fetching jwks.json on every request adds a network round-trip to Auth0 and can trip rate limits. Cache it (5–10 min is typical) and refresh only on a kid miss. Libraries (Nimbus, jwks-rsa, PyJWKClient) do this for you — make sure caching is enabled.
  • Local validation is essentially free. An RS256 verify is a few hundred microseconds of CPU. This is why JWTs scale: 10,000 API instances can each verify independently with no shared state and no per-request call to Auth0.
  • Introspection costs a round-trip per request. Reserve it for high-value paths, or cache introspection results for a few seconds keyed by token hash to amortize cost (accepting a small revocation-latency window).
  • Handle the kid-miss path gracefully. On a key you do not have (post-rotation), refresh the JWKS once and retry — but rate-limit those refreshes so a flood of bad kids cannot become a self-inflicted DoS against Auth0.
  • Right-size token lifetimes. Shorter access tokens = better revocation latency but more refreshes (more load on Auth0). Longer = fewer refreshes but a bigger revocation window. 10–15 min access / rotating refresh is a common balance.
Tip

Measure validation latency. If token validation shows up in your p99, the cause is almost always an un-cached JWKS fetch or per-request introspection — not the crypto.

11. Common Mistakes

  • Not validating the signature at all — decoding the JWT and trusting the claims. Decoding ≠ verifying. Anyone can craft a payload.
  • Forgetting to pin the algorithm — opening the door to alg:none and RS256→HS256 confusion.
  • Skipping the aud check — accepting any valid-from-Auth0 token, letting a token for one API work on another.
  • Validating an access token like an ID token (or vice versa) — ID token aud = client_id; access token aud = API identifier. They are different.
  • Reading user data from the access token — access tokens are for authorization, may be opaque, and their format is not contractually stable. Get profile data from the ID token or /userinfo.
  • Hard-coding a public key or kid — breaks on rotation.
  • Fetching JWKS on every request — latency and rate-limit problems.
  • No clock-skew leeway — tokens randomly rejected when server clocks drift a few seconds.
  • Treating logout as "delete the cookie" — the Auth0 (IdP) session survives, so the next login is silent and the user is "still logged in." You must call the end-session endpoint.
  • Revoking the access token and assuming it stops working — RFC 7009 revocation primarily targets refresh tokens; a JWT access token keeps validating locally until exp.

12. Best Practices

  • Always verify the signature against JWKS, resolving the key by kid; cache JWKS.
  • Always pin algorithms to your asymmetric alg (RS256). Reject none and symmetric algs.
  • Always check iss, aud, and exp (and nonce for ID tokens, azp for multi-audience).
  • Use a battle-tested library; do not hand-roll JWT verification in production.
  • Keep access tokens short-lived; use refresh-token rotation with reuse detection.
  • Store tokens securely: httpOnly/Secure cookies or a backend session (BFF), never localStorage for sensitive apps.
  • Introspect (or use a revocation deny-list) on high-value operations to close the revocation gap.
  • Implement full OIDC logout: clear the local session and call the end-session endpoint, then revoke the refresh token.
  • Allow small clock leeway (30–60s). Use NTP-synced servers.
  • Get user profile data from the ID token / /userinfo, not the access token.

13. Interview Questions (with model answers)

Q1. Walk me through validating an ID token end-to-end.

Model answer: Split the JWT into header/payload/signature. Read alg and kid from the header. Fetch the issuer's JWKS (cached), select the JWK whose kid matches, and verify the RS256 signature over header.payload using that public key — pinning the algorithm to RS256 to prevent alg:none/confusion attacks. Then check claims: iss equals the exact issuer, aud contains my client_id, exp is in the future (with leeway), iat/nbf are sane, and nonce matches the value I generated for this login. If all pass, establish a session.

Q2. Why use JWTs if you can't revoke them instantly?

Model answer: JWTs trade instant revocation for stateless scalability — any service can verify them with cached public keys and no call to the IdP, which is essential at scale. You mitigate the revocation gap with short lifetimes, refresh-token rotation, and introspection or a revocation deny-list on sensitive paths. It's a deliberate trade-off, not a flaw.

Q3. When would you choose introspection over local validation?

Model answer: When tokens are opaque (no JWT to verify), when you need immediate revocation awareness (payments, admin actions, account deletion), or when the authorization server must be the single source of truth. The cost is a network round-trip per request, so I reserve it for high-value paths and rely on local validation elsewhere.

Q4. What's the difference between an ID token and an access token, and how does validation differ?

Model answer: The ID token is for the client — it proves authentication and carries the user's identity; its aud is the client_id and it should never be sent to APIs. The access token is for the resource server — it authorizes API calls; its aud is the API identifier and it carries scopes/permissions. Validation differs mainly in the audience: ID token aud = client_id and includes a nonce check; access token aud = API identifier with scope checks.

Q5. How does kid support key rotation?

Model answer: During rotation the JWKS holds both old and new keys. The token header's kid identifies which public key signed it, so the verifier picks the right one without guessing. This lets the provider rotate keys without invalidating tokens already issued under the previous key.

Q6. A user reports they're "still logged in" after logout. Diagnose.

Model answer: Logout only cleared the local app session/cookie but didn't call Auth0's end-session (/v2/logout) endpoint, so the IdP session cookie persists and the next /authorize silently re-authenticates. Fix: implement RP-initiated logout that redirects to the end-session endpoint, and revoke the refresh token so it can't mint new access tokens.

Q7. How would you implement near-instant revocation for JWTs?

Model answer: Combine short TTLs with a revocation deny-list keyed by jti/sub in a fast store like Redis, populated by Auth0 Log Streams/webhooks on logout/disable events; local validators consult it. For the strongest guarantee, introspect on sensitive endpoints so the authorization server is authoritative.

14. Certification Tips

  • Know the exact validation checklist for ID tokens: signature, iss, aud, exp, iat, nonce (and azp when multiple audiences). Exam questions love asking "which check prevents replay?" → nonce.
  • RFC numbers: Introspection = RFC 7662; Revocation = RFC 7009; PKCE = RFC 7636; Bearer usage = RFC 6750. Memorize these.
  • Endpoints: discovery /.well-known/openid-configuration, keys /.well-known/jwks.json, introspect /oauth/token/introspect (Auth0), revoke /oauth/revoke, logout /v2/logout (or /oidc/logout for OIDC-spec end_session).
  • Audience rule: ID token aud = client_id; access token aud = API identifier. This is a classic distractor.
  • Revocation reality: revoking primarily affects refresh tokens; JWT access tokens validate locally until expiry. Expect a "what actually happens" question.
  • Default signing alg in Auth0 is RS256 (asymmetric). HS256 is symmetric and unsuitable when many parties validate.
  • Refresh token rotation + reuse detection is the recommended pattern for SPAs/native apps — know why (mitigates theft of long-lived tokens).

# Introspect (RFC 7662) — Auth0 (M2M client credentials)
curl -X POST https://YOUR_TENANT/oauth/token/introspect \
  -u "CLIENT_ID:CLIENT_SECRET" \
  -d "token=ACCESS_OR_REFRESH_TOKEN" \
  -d "token_type_hint=access_token"
# -> { "active": true, "scope": "...", "exp": ..., "sub": "..." }

# Revoke (RFC 7009) — refresh token
curl -X POST https://YOUR_TENANT/oauth/revoke \
  -H "Content-Type: application/json" \
  -d '{ "client_id":"CLIENT_ID",
        "client_secret":"CLIENT_SECRET",
        "token":"REFRESH_TOKEN" }'
# -> 200 OK (empty body) whether or not the token existed

20. Key Takeaways

Key

A token is a bearer credential; validation is the entire trust boundary. Validation answers three questions: is it authentic (signature), is it for me (aud), and is it fresh (exp/not revoked).

Key

Verify signatures with the issuer's public key from JWKS, selected by kid, and cache the JWKS. Always pin the algorithm to RS256 to defeat alg:none and RS256→HS256 confusion.

Key

ID token aud = client_id; access token aud = API identifier. ID tokens establish sessions and need a nonce check; access tokens authorize API calls and need scope checks.

Key

Local validation is fast and stateless but blind to revocation until expiry; introspection (RFC 7662) is authoritative but costs a round-trip. Use local everywhere, introspect on high-value paths.

Key

Revocation (RFC 7009) primarily kills refresh tokens; JWT access tokens keep validating until exp. Close the gap with short TTLs, refresh-token rotation with reuse detection, and a deny-list or introspection.

Key

Real logout = clear local session + call the end-session endpoint + revoke the refresh token. Deleting a cookie alone leaves the Auth0 session alive and re-logs the user in silently.
