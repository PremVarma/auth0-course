Chapter 21 — Project 5 — Node.js Express API

Every front-end you have built so far — the SPA, the regular web app, the mobile client — eventually needs to call a backend. That backend must answer one question on every single request: "Who is calling me, and are they allowed to do this?" In this chapter you will build a production-grade Express API that answers that question by validating Auth0-issued JWT access tokens, enforcing scopes and fine-grained permissions, and returning the correct HTTP status (401 for "I don't know who you are" versus 403 for "I know who you are, but you may not do that"). We start from first principles — what a token actually is, why the API must verify a cryptographic signature rather than "ask Auth0," and how a single library, express-oauth2-jwt-bearer, turns that theory into three lines of middleware — then go all the way to curl/Postman testing, threat analysis, and a runnable mini-project.

1. Theory — First Principles of Protecting an API

An API (Application Programming Interface) is a server that exposes operations — GET /api/orders, POST /api/orders, DELETE /api/orders/42 — to programs rather than to humans clicking buttons. Because there is no human session, the API cannot rely on a browser cookie set after a login form. Instead, the caller must present a bearer token on every request, and the API must decide, statelessly, whether to honor it.

To reason about this we need three precise terms from OAuth 2.0 / OpenID Connect (formalized in chapters 4–9):

  • Authentication (AuthN) — proving who you are. The result is an id_token, consumed by the client, never sent to the API.
  • Authorization (AuthZ) — proving what you may do. The result is an access_token, sent to the API in the Authorization: Bearer <token> header.
  • Resource Server — the OAuth name for your API. It is the thing the access token grants access to.

The access token Auth0 issues is a JWT (JSON Web Token, RFC 7519): three Base64URL segments — header.payload.signature — joined by dots. The header names the signing algorithm and key id; the payload carries claims (issuer, audience, expiry, subject, scopes, permissions); the signature is an RSA signature over header.payload produced with Auth0's private key.

The single most important first-principle of this entire chapter: the API never contacts Auth0 to validate a request. Auth0 signs tokens with a private key it never shares; it publishes the matching public key at a well-known URL (the JWKS endpoint). Your API downloads that public key once, caches it, and verifies the signature locally on every request. This is asymmetric cryptography (RS256): only the holder of the private key can create a valid signature, but anyone with the public key can verify one. That is why a JWT can be trusted without a database lookup or a network round-trip per request.

Key

Validating a JWT means checking four things, in order: (1) the signature is valid for Auth0's published public key; (2) the token has not expired (exp); (3) the issuer (iss) is exactly your Auth0 tenant; (4) the audience (aud) is exactly your API's identifier. Skip any one of these and you have a vulnerability, not an API.

Why issuer and audience matter so much deserves a sentence each. The issuer check stops a token minted by a different Auth0 tenant (or a malicious IdP) from being accepted — a valid signature alone is not enough if it was signed by the wrong party. The audience check stops a "confused deputy": a token your user legitimately obtained for API A must not be replayable against API B. The audience pins each token to exactly one resource server.

2. Story-Based Explanation — The Nightclub, the Bouncer, and the Wristband

Picture an exclusive nightclub, Club Resource Server. There are two doors and two staff members.

At the front door stands Auth0, the box office. You show ID (you log in), pay (consent), and the box office issues you a holographic wristband (the access token). Crucially, the box office does not phone the inner rooms to announce you — it simply gives you a wristband that is impossible to forge because of its hologram (the cryptographic signature).

At the inner door stands the bouncer — that is your Express middleware. The bouncer never calls the box office. Instead, the club received, that morning, a single laminated card showing exactly what a genuine hologram looks like under UV light (the JWKS public key). The bouncer holds your wristband under the light:

  • No wristband at all? "You can't come in" → 401 Unauthorized.
  • Wristband, but the hologram is fake or the date has passed? Still 401 — you have not proven you are a legitimate guest.
  • Genuine wristband, but it is a "general admission" band and you are trying to enter the VIP lounge? "I know exactly who you are — and you may not enter here" → 403 Forbidden.

The wristband also has tiny printed icons — bar access, coat check, VIP. Those are the scopes and permissions. The VIP-lounge bouncer checks for the VIP icon specifically; the bartender checks for the bar icon. One wristband, many doors, each door enforcing only the icon it cares about. That is exactly how the auth() middleware (our checkJwt guard) answers "is this a real guest at all" and a scope/permission check (requiredScopes / claimCheck) answers "may this specific guest do this specific thing."

Note

A naming caution: in the API world (this chapter) the "is this a real guest?" guard is auth() from express-oauth2-jwt-bearer. Do not confuse it with requiresAuth(), which is the equivalent guard in the different express-openid-connect SDK used for server-rendered web apps (Chapter 19). Same job — "must be logged in" — but two distinct libraries: tokens-for-an-API here, session-cookies-for-a-web-app there.

Note

The whole magic is that the bouncer is offline-capable. Even if the box office burns down for ten minutes, the bouncer keeps admitting valid wristbands because verification is local. That resilience is the business reason behind stateless JWT validation.

4. Real-World Analogy — The Passport and the Visa

Think of international travel. Your passport is the id_token: it proves who you are to your own country (the client). You never hand your passport to a foreign shop — it is not for them.

To enter another country you obtain a visa stamped specifically for that country — that is the access_token, and the country name on the visa is the audience. A visa for France (API A) does not work at the German border (API B), even though both are genuine. The issuing embassy printed on the visa is the issuer; a border officer who sees a visa "issued" by an embassy that does not exist rejects it instantly.

The border officer (your middleware) does not phone the embassy on every traveler. The embassy long ago distributed the security features of genuine visas (the JWKS public key) to all border posts. The officer checks the hologram locally. Inside the visa, endorsements like "work permitted" or "study permitted" are your scopes/permissions — and the labor inspector inside the country checks the "work" endorsement specifically, just as your checkScopes('write:orders') guard checks one capability.

Tip

The analogy also explains expiry: a visa has a validity window (exp). After it lapses you are not a criminal — you simply need to renew (the client uses a refresh token to get a fresh access token). The border officer rejecting an expired visa returns the equivalent of a 401, not a 403.

5. Internal Working — What Happens Microsecond by Microsecond

When express-oauth2-jwt-bearer sees a request, it performs a precise sequence. Understanding it lets you debug any "why was I rejected?" question.

  1. Extract the token. It reads the Authorization header, confirms the Bearer prefix, and strips it. No header → it throws an UnauthorizedError (401). Per RFC 6750 the scheme is case-insensitive and there is exactly one space.
  2. Decode the header. Base64URL-decode the first segment to read alg (must be RS256) and kid (the key id). If alg is none or HS256 when RS256 is expected, it rejects — this defeats the classic "alg=none" and "algorithm confusion" attacks.
  3. Fetch the public key. Using kid, it looks up the matching key in the JWKS document downloaded from https://YOUR_DOMAIN/.well-known/jwks.json. The JWKS is cached (with rate-limiting and an LRU cache) so it is fetched roughly once, not per request. If the kid is unknown, it refetches once (Auth0 rotates keys), then fails if still unknown.
  4. Verify the signature. It recomputes the RSA-SHA256 signature over header.payload using the public key and compares. A single flipped bit anywhere in the token fails this step.
  5. Validate registered claims. exp (not in the past, allowing a small clock-skew leeway), nbf (not before), iss === your configured issuerBaseURL + trailing slash, and aud includes your configured audience.
  6. Attach the result. On success it sets req.auth = { header, payload, token } and calls next(). Downstream guards read req.auth.payload.scope or req.auth.payload.permissions.

The scope claim is a single space-delimited string (e.g. "read:orders write:orders"), an OAuth convention from RFC 6749. Permissions are different: when you enable RBAC and "Add Permissions in the Access Token" in your Auth0 API settings, Auth0 adds a permissions claim that is a JSON array (e.g. ["read:orders","write:orders"]). Knowing which one your token carries is the most common source of "my scope check fails even though it shouldn't."

Note

The library is a thin, security-hardened wrapper over the proven jose / express-jwt + jwks-rsa stack. It exists so you do not hand-roll caching, clock-skew, key rotation, and algorithm pinning — each a place where a naive implementation introduces a CVE.

6. Code Walkthrough — Reading Every Line

Let us build the middleware piece by piece before assembling the full server. First, configuration via environment variables — never hard-code these.

# .env  (never commit this file — add it to .gitignore)
AUTH0_ISSUER_BASE_URL=https://your-tenant.us.auth0.com/
AUTH0_AUDIENCE=https://orders.example.com/api
PORT=3000

Now the core authentication middleware. auth() returns an Express middleware that performs every check from Section 5.

// src/middleware/auth.js
const { auth } = require('express-oauth2-jwt-bearer');

// checkJwt = "is this a real, valid token for THIS api?"
const checkJwt = auth({
  // The trailing slash MUST match your tenant's iss claim exactly.
  issuerBaseURL: process.env.AUTH0_ISSUER_BASE_URL,
  // The unique identifier you set when you created the API in Auth0.
  audience: process.env.AUTH0_AUDIENCE,
  // Pin the algorithm. Auth0 APIs use RS256 by default. Never allow HS256
  // for an externally-issued token, and never allow "none".
  tokenSigningAlg: 'RS256',
});

module.exports = { checkJwt };

Next, the authorization guards. The library ships two helpers; we wrap them with friendly names.

// src/middleware/authz.js
const {
  requiredScopes,   // checks the space-delimited `scope` claim
  claimCheck,       // generic predicate over the whole payload
} = require('express-oauth2-jwt-bearer');

// 1) Scope-based guard (works with the OAuth `scope` string claim)
//    Usage: router.post('/', checkJwt, requireScope('write:orders'), handler)
const requireScope = (scope) => requiredScopes(scope);

// 2) Permission-based guard (works with the RBAC `permissions` ARRAY claim).
//    requiredScopes only reads `scope`, so for permissions we use claimCheck.
const requirePermission = (permission) =>
  claimCheck((payload) => {
    const perms = payload.permissions || [];
    const ok = Array.isArray(perms) && perms.includes(permission);
    if (!ok) {
      // Throwing here yields a 403 with error=insufficient_scope
      throw new Error(`Missing required permission: ${permission}`);
    }
    return true;
  });

module.exports = { requireScope, requirePermission };
Warn

requiredScopes('a b') means the token needs scope a AND scope b. If you want OR-logic ("read OR write"), do not pass a space-separated string — write a custom claimCheck that tests membership yourself. Misreading this is a classic source of unexpected 403s.

Finally, the error handler. The library throws typed errors; we translate them into clean JSON and the correct status code.

// src/middleware/errorHandler.js
// Express recognizes error middleware by its 4 arguments: (err, req, res, next)
function errorHandler(err, req, res, next) {
  // The library sets err.status (401 or 403) and err.headers (WWW-Authenticate)
  if (err.name === 'UnauthorizedError' || err.status === 401) {
    return res.status(401).json({
      error: 'unauthorized',
      message: 'Authentication required: missing, malformed, or invalid token.',
    });
  }
  if (err.status === 403) {
    return res.status(403).json({
      error: 'insufficient_scope',
      message: 'You are authenticated but lack the required permission.',
    });
  }
  // Fallback for anything unexpected — never leak stack traces in prod.
  console.error(err);
  return res.status(500).json({ error: 'internal_error' });
}

module.exports = { errorHandler };

7. Practical Implementation — The Complete server.js

Here is the full, runnable server wiring everything together. Public and protected routes coexist so you can see the contrast.

// server.js
require('dotenv').config();
const express = require('express');
const helmet = require('helmet');
const cors = require('cors');
const morgan = require('morgan');

const { checkJwt } = require('./src/middleware/auth');
const { requireScope, requirePermission } = require('./src/middleware/authz');
const { errorHandler } = require('./src/middleware/errorHandler');

const app = express();

// ---- Baseline hardening (order matters) ----
app.use(helmet());                 // secure HTTP headers
app.use(cors({ origin: true }));   // tighten origin in production
app.use(express.json());           // parse JSON bodies
app.use(morgan('tiny'));           // request logging

// ---- PUBLIC route: no token required ----
app.get('/api/public', (req, res) => {
  res.json({ message: 'Anyone can read this. No token needed.' });
});

// ---- PROTECTED route: any valid token ----
// checkJwt enforces signature + exp + iss + aud.
app.get('/api/orders', checkJwt, (req, res) => {
  res.json({
    message: 'You are authenticated.',
    subject: req.auth.payload.sub,
    scopes: req.auth.payload.scope,
  });
});

// ---- SCOPE-protected route: valid token AND scope 'write:orders' ----
app.post('/api/orders', checkJwt, requireScope('write:orders'), (req, res) => {
  res.status(201).json({ message: 'Order created.', order: req.body });
});

// ---- PERMISSION-protected route: valid token AND permission 'delete:orders' ----
app.delete('/api/orders/:id', checkJwt, requirePermission('delete:orders'), (req, res) => {
  res.json({ message: `Order ${req.params.id} deleted.` });
});

// ---- Error handler MUST be registered LAST ----
app.use(errorHandler);

const port = process.env.PORT || 3000;
app.listen(port, () => console.log(`API listening on http://localhost:${port}`));

module.exports = app; // exported for tests

8. Production Architecture — Where This Fits in a Real System

A single Express process is fine for learning. In production the API sits inside a larger topology. The token-validation logic stays identical, but several layers wrap it.

                          Internet
                              |
                    +---------v---------+
                    |   CDN / WAF       |  (DDoS, rate-limit, TLS termination)
                    +---------+---------+
                              |
                    +---------v---------+
                    |  API Gateway /    |  (routing, coarse rate-limit;
                    |  Load Balancer    |   MAY pre-validate JWT)
                    +----+--------+-----+
                         |        |
              +----------v-+    +-v----------+
              | Express    |    | Express    |   N stateless replicas.
              | API pod 1  |    | API pod 2  |   Each validates JWT locally
              | checkJwt   |    | checkJwt   |   -> horizontal scale is trivial
              +-----+------+    +-----+------+
                    |                 |
                    +--------+--------+
                             |
                    +--------v--------+        +------------------+
                    |  Database /     |        |  Auth0 JWKS      |
                    |  downstream svc |        |  (cached per pod)|
                    +-----------------+        +------------------+

Why stateless validation is an architectural superpower: because each replica verifies tokens locally against a cached public key, you can run 2 pods or 200 pods with zero shared session store. There is no "sticky session," no Redis for auth, no single point of failure tied to login. Scaling the API is a pure CPU/replica problem.

Defense in depth. An API gateway may also validate the JWT to reject junk early, but the Express service must still validate independently — never trust that something upstream did it. The principle is "validate at the trust boundary you own."

Machine-to-machine. When another backend service (not a user) calls this API, it uses the Client Credentials grant: it exchanges its client id/secret for an access token whose aud is this API. The middleware is identical — it does not care whether a human or a service obtained the token, only that the token is valid for this audience and carries the required scope.

Note

Twelve-factor configuration: domain, audience, port, and log level all come from environment variables / a secrets manager (AWS Secrets Manager, Vault). The same image is promoted dev → staging → prod with only the env changing.

Danger

Never use a JWT library's decode() result for authorization without verify(). decode() only Base64-parses the payload — it performs zero signature checks. Warn

Always serve the API over HTTPS/TLS in production. A bearer token is exactly that — bearer — so anyone who captures it over plaintext HTTP can impersonate the user until it expires. TLS is non-negotiable.

10. Performance Considerations

Stateless JWT validation is fast, but "fast" deserves precision.

  • JWKS caching. The public key is fetched once and cached (default ~10 minutes, with an LRU of recent keys and request rate-limiting). So 99.99% of requests do zero network calls. Only a cold start or a key rotation triggers a fetch. Do not disable the cache.
  • Signature verification cost. RS256 verification is an RSA public-key operation — on the order of tens of microseconds per request on modern hardware. It is CPU-bound but negligible compared to a typical DB query. There is no per-request crypto handshake.
  • No DB lookup for auth. Because authorization data (scopes/permissions) rides inside the token, the API needs no user-table query to authorize. This is the single biggest latency win over session/DB-backed auth.
  • Token size trade-off. Stuffing many permissions or large custom claims into the token grows every request header. Keep tokens lean; if a user has hundreds of permissions, prefer coarse scopes plus an in-API authorization model. Headers above ~8 KB can hit proxy limits.
  • Clock skew leeway. A small leeway (a few seconds) prevents spurious 401s when the API and Auth0 clocks differ slightly. Keep servers NTP-synced so the leeway stays tiny.
  • Connection reuse to JWKS. On cold start the first request pays the JWKS fetch. To avoid a slow first request, warm the cache at boot by making a throwaway verification, or accept a one-time ~100 ms penalty.
Tip

Benchmark with the cache warm. If you load-test from a cold process you will measure the one-time JWKS fetch as if it happened per request — a classic false alarm.

11. Common Mistakes

  1. Trailing-slash mismatch on the issuer. Auth0's iss is https://tenant.us.auth0.com/ with a trailing slash. If your issuerBaseURL omits it, every token is rejected with a confusing error. Match it exactly.
  2. Wrong audience. Requesting a token without the audience parameter yields an opaque token (not a JWT) intended for the /userinfo endpoint — your API cannot validate it. Always request a token for your API's identifier.
  3. Confusing scope with permissions. requiredScopes reads the space-delimited scope string only. If your tenant emits RBAC permissions (an array), requiredScopes will not see them — use claimCheck as shown.
  4. Registering the error handler too early. Express runs middleware in order. The 4-arg error handler must be the last app.use, or your 401/403 errors fall through to a generic 500.
  5. Returning 403 when you mean 401 (and vice-versa). Missing/invalid token = 401. Valid token, missing right = 403. Mixing them up confuses clients and breaks retry logic.
  6. Putting checkJwt on the public route. Apply auth per-route (or per-router), not globally, unless every route truly requires a token.
  7. Hard-coding the domain/audience. Secrets and environment-specific values belong in env vars, never in source.
  8. Logging the token. A debug console.log(req.headers) can leak live credentials into your log aggregator.
Warn

The "opaque token" trap (mistake #2) is the number-one beginner failure. Symptom: your token has only one or two dots when decoded, or jwt.io says "invalid." Fix: ensure the client requests the token with audience=<your API identifier>.

12. Best Practices

  • Default deny. Protect by default; explicitly mark the few public routes. It is safer to forget to open a route than to forget to lock one.
  • Least privilege scopes. Define narrow, verb:resource scopes (read:orders, write:orders, delete:orders) rather than one mega-scope. Grant the minimum each client needs.
  • Enforce authorization at the API, not just the UI. The front-end hiding a button is UX, not security. The API guard is the real boundary.
  • Short access-token lifetimes + refresh tokens. Minimizes the blast radius of a leaked token.
  • Pin the algorithm to RS256 and never accept symmetric algorithms for externally issued tokens.
  • Centralize error handling so every protected route returns consistent, non-leaky 401/403 JSON.
  • Use RBAC + permissions in the access token for fine-grained control; reserve scopes for coarse, client-level consent.
  • Validate independently at each trust boundary — do not assume the gateway already checked.
  • Version your API (/v1/...) so you can evolve scopes/permissions without breaking callers.
  • Write integration tests that assert 401 (no token), 403 (wrong scope), and 200 (correct token) for every protected route.

13. Interview Questions (with Model Answers)

Q1. Why does an API validate a JWT locally instead of calling Auth0 on every request?

Model answer: Auth0 signs tokens with a private key and publishes the matching public key at the JWKS endpoint. The API caches that public key and verifies the RS256 signature locally, so it needs no network call per request. This makes validation fast, stateless, horizontally scalable, and resilient — the API keeps working even if Auth0 is briefly unreachable, because verification depends only on the cached public key, not on an availability call.

Q2. Explain the difference between 401 and 403 with concrete examples.

Model answer: 401 Unauthorized means authentication failed — no token, malformed token, bad signature, expired, or wrong issuer/audience. The client should (re-)authenticate. 403 Forbidden means authentication succeeded but the caller lacks the required permission/scope — e.g. a user with read:orders hitting DELETE /orders/42 which needs delete:orders. Retrying with the same token will not help; the user needs additional grants.

Q3. What stops a token issued for another API from being accepted by mine?

Model answer: The aud (audience) claim. Each token is minted for a specific API identifier, and the middleware rejects any token whose audience does not include this API. This prevents the confused-deputy / cross-API replay attack. The iss claim provides a parallel guarantee against tokens from a different tenant.

Q4. Scope vs permission — when do you use each?

Model answer: Scopes are an OAuth concept representing what a client was granted, delivered as a space-delimited scope string; they express coarse, consent-style capability. Permissions come from Auth0 RBAC, are assigned to users/roles, and (when enabled) appear as a permissions array claim for fine-grained, per-user authorization. Scopes gate "this app may attempt order writes"; permissions gate "this particular user may delete orders."

Q5. How would you defend against the alg=none and RS256→HS256 confusion attacks?

Model answer: Explicitly pin the accepted algorithm to RS256 (tokenSigningAlg: 'RS256') and never accept none or symmetric algorithms for externally issued tokens. A correct library refuses to verify an RSA token using the public key as an HMAC secret. Always verify the signature; never authorize from a decoded-but-unverified payload.

Q6. Where does the error middleware go and why?

Model answer: Last. Express identifies error-handling middleware by its four parameters and invokes it only after a thrown error or next(err). Registering it after all routes ensures the library's 401/403 errors are translated into clean JSON instead of falling through to a default 500.

Q7. How does a backend service (no user) call this protected API?

Model answer: Via the Client Credentials grant: the service authenticates with its own client id/secret to Auth0 and receives an access token whose audience is this API. The API's validation is identical — it only cares that the token is valid for this audience and carries the needed scope, not whether a human or machine obtained it.

Q8. Your token validates on jwt.io but your API returns 401. Name three likely causes.

Model answer: (1) Issuer mismatch — missing trailing slash in issuerBaseURL. (2) Audience mismatch — token was requested without (or with a different) audience, so its aud does not include your API. (3) Expiry — the token is past exp by the time the API checks it (or clock skew between servers).

14. Certification Tips

Key

The Auth0 certification loves the distinction between access token (for the API, carries aud/scope/permissions) and ID token (for the client, identity claims). Memorize: never send an ID token to an API; never use an access token to read user profile in your front-end.

  • Audience is mandatory to get a JWT access token. No audience ⇒ opaque token ⇒ not API-validatable. Exam questions test this exact trap.
  • RBAC settings: remember the two toggles — "Enable RBAC" and "Add Permissions in the Access Token." Only the second puts the permissions claim in the token.
  • RS256 vs HS256: RS256 (asymmetric) is the default and recommended; HS256 (symmetric) shares a secret and does not scale to many resource servers. Know why RS256 is preferred (public-key distribution, no shared secret).
  • JWKS endpoint: know it lives at /.well-known/jwks.json and that the kid in the JWT header selects the key.
  • Token lifetime & refresh: access tokens are short-lived; refresh tokens obtain new ones. APIs do not handle refresh — clients do.
  • 401 vs 403 mapping appears repeatedly. Lock it in.

17. Mini Project — "Orders API" with an Automated Test Suite

Ship the Orders API from Section 7 with a Node built-in test runner suite that does not even need Auth0 online for the negative path (the 401-no-token case requires no network), plus a guarded helper for the positive paths.

// test/api.test.js  (run with: node --test)
const test = require('node:test');
const assert = require('node:assert');
const app = require('../server');
const http = require('node:http');

// minimal request helper
function req(method, path, headers = {}, body) {
  return new Promise((resolve) => {
    const server = app.listen(0, () => {
      const { port } = server.address();
      const r = http.request({ port, method, path, headers }, (res) => {
        let data = '';
        res.on('data', (c) => (data += c));
        res.on('end', () => { server.close(); resolve({ status: res.statusCode, body: data }); });
      });
      if (body) r.write(JSON.stringify(body));
      r.end();
    });
  });
}

test('public route returns 200 without a token', async () => {
  const res = await req('GET', '/api/public');
  assert.strictEqual(res.status, 200);
});

test('protected route returns 401 without a token', async () => {
  const res = await req('GET', '/api/orders');
  assert.strictEqual(res.status, 401);
});

test('protected route returns 401 with a garbage token', async () => {
  const res = await req('GET', '/api/orders', { Authorization: 'Bearer not.a.jwt' });
  assert.strictEqual(res.status, 401);
});

// Positive-path test: set TEST_TOKEN env to a real token to exercise 200/201.
test('protected route returns 200 with a valid token', async (t) => {
  if (!process.env.TEST_TOKEN) return t.skip('set TEST_TOKEN to run');
  const res = await req('GET', '/api/orders', { Authorization: `Bearer ${process.env.TEST_TOKEN}` });
  assert.strictEqual(res.status, 200);
});

20. Key Takeaways

Key

An API protects itself by validating a JWT access token locally on every request — checking signature, expiry, issuer, and audience — using Auth0's cached public key. No per-request call to Auth0 is needed; that is what makes it fast, stateless, and scalable.

  • Three lines of middleware (auth({ issuerBaseURL, audience, tokenSigningAlg })) deliver signature + exp + iss + aud validation. That is the entire authentication boundary.
  • Authentication ≠ authorization. checkJwt answers "is this a real, valid token?" (401 if not); requiredScopes/claimCheck answer "may this caller do this?" (403 if not).
  • 401 vs 403 is the contract with your clients: 401 = (re)authenticate; 403 = you lack the right, do not bother retrying.
  • Audience pins each token to one API; issuer pins it to your tenant. Together they stop replay and impersonation across APIs.
  • Scope (string) vs permissions (array). Know which your token carries — it is the #1 cause of unexpected 403s.
  • Pin RS256, never trust a decoded payload, always use TLS. Security comes from the verified signature, not the readable contents.
  • Register the error handler last and keep its messages generic — clean 401/403 JSON, no stack traces.

You can now take any Express service and turn it into a hardened Auth0-protected resource server — the same pattern you will reuse for every backend in the rest of this course and in production.
