Chapter 3 — Networking Foundations for Auth0

Auth0 does not run inside your app. It is a separate website living at a separate domain, and the entire login experience is a carefully choreographed dance of HTTP redirects, cookies, headers, and cryptographic handshakes that hop between browsers, your servers, and Auth0's servers. If you don't understand the wire — how a request is shaped, why HTTPS matters, what a 302 redirect really does, how cookies are scoped, and why CORS blocks your fetch — then every Auth0 error message will feel like magic gone wrong. This chapter builds the networking bedrock under all of OAuth, OIDC, and Auth0 from first principles, so that by Chapter 4 the "login dance" reads like sheet music instead of noise.

1. Theory — First Principles of the Wire

Everything Auth0 does travels over HTTP (HyperText Transfer Protocol) — a request/response, stateless, text-based protocol. Let's unpack each of those three words because each one shapes how authentication must work.

Request/response: a client (a browser, a mobile app, a backend) sends one request; the server sends back exactly one response. The server cannot spontaneously call the client. This is why login uses redirects — the only way a server can make the browser go somewhere is to answer "go here instead."

Stateless: HTTP itself remembers nothing between requests. Request #2 has no built-in knowledge that request #1 ever happened. The server cannot tell "logged-in Alice" from "anonymous stranger" unless the client re-presents proof on every single request. That proof is a cookie or a token in a header. Statelessness is the entire reason sessions, cookies, and bearer tokens exist.

Text-based: a request is human-readable text: a start line, headers (key: value pairs), a blank line, and an optional body. Because it's plain text, anyone on the path can read it — which is precisely why we wrap it in TLS to get HTTPS.

An HTTP request has four parts:

  1. Method — the verb: GET, POST, PUT, PATCH, DELETE, OPTIONS, HEAD.
  2. Target (path + query) — e.g. /authorize?client_id=abc&scope=openid.
  3. Headers — metadata like Host, Authorization, Cookie, Content-Type.
  4. Body — optional payload (form data, JSON), used by POST/PUT/PATCH.

An HTTP response has three parts: a status line (e.g. HTTP/1.1 302 Found), headers (Location, Set-Cookie, Content-Type), and an optional body.

Status codes are grouped by first digit, and you will read them constantly when debugging Auth0:

ClassMeaningAuth-relevant examples
1xxInformational101 Switching Protocols (WebSocket upgrade)
2xxSuccess200 OK (token endpoint returns JSON), 204 No Content
3xxRedirect302 Found / 303 See Other — the heart of the login dance
4xxClient error400 bad request, 401 unauthenticated, 403 forbidden, 404 not found
5xxServer error500 internal, 502/504 proxy/upstream failures
Key

Memorize the difference: 401 Unauthorized means "I don't know who you are — authenticate." 403 Forbidden means "I know who you are, but you may not do this." Auth0 protects the first; your authorization logic enforces the second.

2. Story-Based Explanation — The Nightclub at the End of the Street

Imagine you (the browser) want into an exclusive members club called MyApp. At the door, the bouncer (your application backend) checks his clipboard for your name. You're not on it, so instead of turning you away, he hands you a printed note: "Go down the street to the Identity Office (Auth0), prove who you are, and come back with a stamped slip. Here's a one-time ticket number written on the note so I know it's really you returning."

That note is an HTTP 302 redirect. The street address of the Identity Office is a domain (your-tenant.auth0.com). The one-time ticket number is the state parameter. You walk down the street, the Identity Office verifies your face (your password, your MFA), stamps a slip (an authorization code), and sends you back with another note telling you to return to the club's redirect URI.

Back at the club door, the bouncer takes your stamped slip and — out of your sight, through a back phone line (a server-to-server HTTPS call) — calls the Identity Office to confirm the slip is genuine and to trade it for a membership card (the tokens). The reason he uses the private phone line and not your hands is that you (the browser) cannot be fully trusted to carry the card safely. Finally he writes your name in a wristband (a session cookie) so that for the rest of the night you walk straight in without repeating the whole trip.

The entire rest of this chapter is just the engineering of that walk down the street: how the addresses work (DNS, origin), why the street is monitored against eavesdroppers (TLS), why the wristband can't be copied (Secure/HttpOnly/SameSite cookies), and how rival clubs try to forge your wristband (CSRF) or pickpocket it (XSS).

4. Real-World Analogy — Postcards, Sealed Envelopes & Passports

  • Plain HTTP is a postcard: every postal worker (router, ISP, coffee-shop Wi-Fi) along the way can read it and even rewrite it. Never send a password on a postcard.
  • HTTPS / TLS is a tamper-evident sealed envelope whose recipient's identity is vouched for by a notary (the Certificate Authority). Anyone can see an envelope went to auth0.com, but not what's inside, and they can't swap the contents undetected.
  • A redirect (302) is a "we've moved — please go to this new address" sign taped on the door. The browser obediently walks to the new address.
  • The state parameter is the coat-check ticket: you keep the stub, and only the matching stub gets your coat back — proving the person returning is the same one who left.
  • The nonce is a tamper-proof serial number printed on a one-time concert ticket: it stops someone from photocopying an old ticket and reusing it.
  • A cookie is a hand stamp at the venue: re-show it and you walk back in without re-queuing. HttpOnly means the stamp is under UV light only the bouncer can read (JavaScript can't); Secure means it only works inside the building (HTTPS); SameSite means a rival venue down the street can't make you flash your stamp on their behalf.

5. Internal Working — DNS, TLS, Origins, and Cookies Under the Hood

5.1 DNS, domains, subdomains, and origin

A domain name like tenant.eu.auth0.com is human-friendly; computers route by IP address. DNS (Domain Name System) is the distributed phonebook that translates the name to an IP. Reading right to left: com is the top-level domain, auth0 is the registered domain, and tenant and eu are subdomains. Each label can point to a different server.

   browser asks ──► OS resolver ──► recursive resolver (ISP / 8.8.8.8)
        │                                  │
        │                                  ├─► root server  (.)
        │                                  ├─► TLD server   (.com)
        │                                  └─► authoritative (auth0.com)
        ▼                                  returns A/AAAA record (IP)
   "tenant.auth0.com = 104.18.x.x"  ◄──────┘   (cached per TTL)

An origin is the security boundary the browser cares about: scheme + host + port. https://app.com and https://app.com:8443 are different origins (different port). https://app.com and http://app.com are different (scheme). https://app.com and https://api.app.com are different (host). The browser's Same-Origin Policy isolates one origin's scripts, cookies, and storage from another's — this is the foundation that CORS later relaxes deliberately.

5.2 The TLS handshake (and what a certificate proves)

TLS gives three guarantees: confidentiality (encryption), integrity (tamper detection), and authentication of the server (you really are talking to auth0.com). The last one is the part beginners miss — encryption to an impostor is worthless, so the certificate is what makes encryption meaningful.

   CLIENT                                          SERVER (auth0.com)
     │  ClientHello (TLS ver, cipher list,           │
     │              random, SNI=tenant.auth0.com) ──►│
     │  ◄── ServerHello (chosen cipher, random)      │
     │  ◄── Certificate (chain to a trusted CA)      │
     │  ◄── server key share (ECDHE)                 │
     │  -- verify cert: signed by trusted CA?        │
     │     name matches host? not expired/revoked? --│
     │  client key share ──►                         │
     │  == both derive same session keys (ECDHE) ==  │
     │  Finished (encrypted) ⇄ Finished (encrypted)  │
     │  ===== application data flows encrypted =====  │

The certificate is an X.509 document binding a public key to a hostname, signed by a Certificate Authority (CA). Your OS/browser ships with a list of trusted root CAs. This chain of trust — root CA → intermediate CA → leaf cert — is PKI (Public Key Infrastructure). TLS 1.3 (the 2018 standard, ubiquitous in 2026) uses ephemeral Diffie-Hellman (ECDHE) so each session has unique keys; even if the server's long-term key leaks later, past traffic stays secret (forward secrecy).

5.3 How a cookie travels

   Server sets it once:        Browser re-sends automatically:
   Set-Cookie: sid=abc;        Cookie: sid=abc
     Domain=app.com;           (sent on EVERY matching request to
     Path=/; Secure;            app.com over https, until expiry —
     HttpOnly; SameSite=Lax     this automatic re-sending is exactly
     Max-Age=3600               what CSRF abuses)
Note

Cookies are scoped by domain + path, NOT by origin. A cookie set without Secure on http can leak to https and vice versa, and a cookie on app.com is sent to app.com and its subdomains if Domain=app.com is specified. This mismatch between "origin" (script isolation) and "cookie scope" (domain/path) is the source of many auth bugs.

6. Code Walkthrough — Reading the Raw Wire

6.1 The redirect to Auth0 (what your server emits)

HTTP/1.1 302 Found
Location: https://tenant.auth0.com/authorize?
  response_type=code&
  client_id=AbC123&
  redirect_uri=https%3A%2F%2Fapp.com%2Fcallback&
  scope=openid%20profile%20email&
  state=8f3kd9s2&
  nonce=z1x2c3v4&
  code_challenge=E9Melhoa...&
  code_challenge_method=S256
Set-Cookie: oauth_state=8f3kd9s2; Path=/; HttpOnly; Secure; SameSite=Lax
Content-Length: 0

Notice three things: the redirect_uri is URL-encoded (%3A%2F%2F is ://); state is stored both in the URL and in a cookie so we can compare them on return; and the response body is empty — the browser acts purely on the Location header.

6.2 The callback & back-channel token exchange (server-side, Node.js)

// Express callback handler — runs on YOUR server, not the browser
app.get('/callback', async (req, res) => {
  const { code, state } = req.query;

  // 1. CSRF defense: the state from Auth0 must equal the one we stored
  if (!state || state !== req.cookies.oauth_state) {
    return res.status(400).send('Invalid state — possible CSRF');
  }

  // 2. Back-channel exchange: code -> tokens. client_secret NEVER
  //    touches the browser; this fetch is server-to-server over TLS.
  const tokenRes = await fetch('https://tenant.auth0.com/oauth/token', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      grant_type: 'authorization_code',
      client_id: process.env.AUTH0_CLIENT_ID,
      client_secret: process.env.AUTH0_CLIENT_SECRET, // secret stays server-side
      code,
      redirect_uri: 'https://app.com/callback',
      code_verifier: req.session.codeVerifier        // PKCE proof
    })
  });
  const tokens = await tokenRes.json(); // { id_token, access_token, ... }

  // 3. Establish a session cookie. Hardened flags explained in §12.
  res.cookie('sid', createSession(tokens), {
    httpOnly: true, secure: true, sameSite: 'lax', maxAge: 3600_000
  });
  res.redirect('/dashboard');
});

// Spring Security handles the redirect dance, state, nonce, PKCE,

// React component using the Auth0 SDK; getAccessTokenSilently returns a JWT.
import { useAuth0 } from '@auth0/auth0-react';

function Profile() {
  const { getAccessTokenSilently } = useAuth0();

  async function loadProfile() {
    const token = await getAccessTokenSilently();   // access token (JWT)
    const res = await fetch('https://api.app.com/me', {
      headers: { Authorization: `Bearer ${token}` } // bearer scheme
    });
    if (res.status === 401) throw new Error('token rejected');
    return res.json();
  }
  // ...render
}

7.4 Next.js — keeping tokens off the browser entirely

// Next.js App Router route handler (server-side). The token never
// reaches client JS; the browser only ever holds an HttpOnly cookie.
import { getAccessToken } from '@auth0/nextjs-auth0';

export async function GET() {
  const { accessToken } = await getAccessToken();      // server only
  const r = await fetch('https://api.app.com/orders', {
    headers: { Authorization: `Bearer ${accessToken}` }
  });
  return Response.json(await r.json());
}

8. Production Architecture — Proxies, Load Balancers & CDNs

In production your app sits behind layers that terminate TLS, spread load, and cache content. Each layer can break auth if misconfigured.

                       ┌──────────── Internet ───────────┐
   Browser ──TLS──► CDN/Edge ──TLS──► Load Balancer ──► Reverse Proxy ──► App
                    (cache,           (spreads traffic,   (TLS termination, (your
                     WAF, DDoS)        health checks)      routing, headers) server)
                         │                  │                   │
                         └── adds/forwards: X-Forwarded-Proto: https
                                            X-Forwarded-For: <client ip>
                                            X-Forwarded-Host: app.com
  • Reverse proxy (nginx, Envoy): sits in front of your app, terminates TLS, and forwards. It often speaks plain http to your app internally, so your app sees http unless it trusts X-Forwarded-Proto. If it doesn't, your app builds redirect_uri=http://... and Auth0 rejects the callback as an invalid/insecure URL.
  • Load balancer: distributes requests across instances. If your session lives in server memory, request #2 may hit a different instance that never saw the login. Fix: sticky sessions or, better, a shared session store (Redis) or stateless JWT sessions.
  • CDN: caches static assets at the edge. Danger: never let a CDN cache a response that contains Set-Cookie or per-user data — one user's session could be served to another. Mark authenticated responses Cache-Control: private, no-store.
# nginx reverse proxy: forward the original scheme/host so the app
# can build correct HTTPS redirect_uris for Auth0.
location / {
    proxy_pass         http://app_upstream;
    proxy_set_header   Host              $host;
    proxy_set_header   X-Forwarded-Proto $scheme;   # https
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Host  $host;
}
# Spring Boot: trust the proxy headers so generated URLs use https
server.forward-headers-strategy=framework
Warn

Only trust X-Forwarded-* headers from proxies you control. A naked, internet-facing app that blindly trusts X-Forwarded-For can be lied to about the client IP — attackers spoof these headers to bypass IP allowlists and rate limits.

9. Security Analysis — CSRF, XSS & the state/nonce Defenses

9.1 CSRF (Cross-Site Request Forgery)

CSRF exploits the browser's habit of automatically attaching cookies to every request to a domain. An attacker's page silently makes your browser POST to bank.com/transfer; because your bank.com session cookie rides along automatically, the bank thinks you asked. The attacker never sees the cookie — they just trigger its use.

   evil.com page ──auto-submits hidden form──► bank.com/transfer
                  browser attaches bank.com cookie automatically
                  bank.com sees a valid session → executes transfer
   Defenses: SameSite cookies  +  anti-CSRF token  +  check Origin

In OAuth, the login dance itself is CSRF-vulnerable: an attacker could trick your browser into completing their login (session fixation) or replay a callback. The state parameter defends this: you generate a random value, stash it (cookie/session), send it on /authorize, and verify the value returned on /callback matches. A forged or replayed callback won't carry your secret state.

9.2 XSS (Cross-Site Scripting)

XSS injects attacker JavaScript into your page, so it runs with your origin's privileges. It can read anything JS can read — including tokens in localStorage and any non-HttpOnly cookie. XSS is strictly more powerful than CSRF: a CSRF defense doesn't stop XSS, because the attacker's script is your page.

   user input "<script>steal(document.cookie)</script>"
        │ stored or reflected unescaped into the page
        ▼
   victim loads page → attacker JS runs as YOUR origin
        → exfiltrates localStorage tokens / non-HttpOnly cookies
   Defenses: output-encode/escape, CSP, HttpOnly cookies, trusted-types

9.3 The nonce — replay defense for the ID token

OIDC adds a nonce: a random value you send on /authorize that Auth0 embeds inside the signed ID token. On return you check the token's nonce claim equals what you sent. This stops an attacker from injecting a previously captured ID token (token replay), because it won't carry your fresh nonce. state binds the request/response round-trip; nonce binds the issued token to your session.

ParameterDefends againstWhere checked
stateCSRF / cross-site request forgery on the callbackYour app compares URL value vs stored value
nonceID-token replay / injectionInside the signed JWT's nonce claim
PKCE code_verifierAuthorization-code interceptionToken endpoint verifies the hash
Danger

Never store long-lived tokens in localStorage if you can avoid it — a single XSS flaw drains them all. Prefer HttpOnly, Secure, SameSite cookies managed by a backend (the BFF — Backend For Frontend — pattern), so JavaScript can never read the credential.

10. Performance Considerations

  • TLS handshake cost: a full handshake adds a round trip. Mitigate with keep-alive (reuse the TCP+TLS connection), HTTP/2 multiplexing, TLS 1.3 (1-RTT, or 0-RTT resumption), and session resumption. Auth0's CDN-fronted endpoints already do this; your job is to reuse connections from your backend (a pooled HTTP client) rather than opening a new TLS session per token call.
  • DNS latency: the first lookup costs time; results are cached for the record's TTL. Long-lived backends benefit from OS/JVM DNS caching — but beware over-caching when Auth0's IPs rotate; respect TTLs rather than caching forever.
  • Redirect chains: each 302 is a full round trip. The login dance is inherently several hops; don't add gratuitous extra redirects (e.g. http→https then www→apex) in front of it. Use HSTS so the browser skips the http→https hop entirely.
  • CORS preflights: every "non-simple" cross-origin request triggers an extra OPTIONS round trip. Raise Access-Control-Max-Age to cache the preflight, and keep requests "simple" where possible to skip it.
  • JWKS / token validation: validating a JWT means fetching Auth0's public signing keys (JWKS). Cache the JWKS in memory (refresh on key rotation / kid miss) so you don't hit the network on every request — covered in depth in the JWT chapters.
  • Cookie size: cookies ride on every request to the domain. A bloated session cookie wastes bandwidth on each call; keep an opaque session id pointing to a server store rather than stuffing data into the cookie.

11. Common Mistakes

Danger

Putting the client_secret in the browser. SPAs and mobile apps are "public clients" — anyone can read the bundle. Secrets belong only on a backend. Use PKCE for public clients instead.

  • Forgetting X-Forwarded-Proto behind a proxy, so the app generates http:// redirect URIs and Auth0 rejects them.
  • redirect_uri mismatch: the value sent must exactly match an entry in Auth0's Allowed Callback URLs — trailing slash, scheme, and port all count.
  • Using Access-Control-Allow-Origin: * with credentials. Browsers forbid the wildcard when allow-credentials is true; you must echo the specific origin.
  • Storing tokens in localStorage and assuming they're safe — they are fully exposed to any XSS.
  • Skipping state/nonce validation "because it works in the demo." It works right up until you're attacked.
  • Caching authenticated responses at the CDN, leaking one user's data to another.
  • SameSite=Strict on the session cookie of a redirect-login app, which can drop the cookie on the cross-site return from Auth0 and produce a confusing "logged in but appears logged out" loop. Lax is the usual sweet spot.
  • Mixed content: an HTTPS page loading an HTTP script/endpoint is blocked by the browser, silently breaking login.

12. Best Practices

  • HTTPS everywhere, end to end, including internal hops where feasible. Enable HSTS with a long max-age and includeSubDomains.
  • Harden cookies: Secure + HttpOnly + SameSite=Lax (or Strict for pure same-site APIs). Scope Path and Domain as narrowly as possible.
  • Always validate state and nonce; let your SDK/framework do it and never disable it.
  • Use PKCE for every authorization-code flow, even confidential clients.
  • Keep tokens off the browser with a BFF where you can; if a SPA must hold an access token, keep it in memory, not localStorage.
  • Lock down CORS to explicit origins, methods, and headers; never wildcard with credentials.
  • Set a strict Content-Security-Policy to neutralize XSS, plus output-encoding on all user-controlled data.
  • Configure the proxy to forward X-Forwarded-* and configure the app to trust only your proxies.
  • Mark authenticated responses Cache-Control: private, no-store so CDNs/proxies never share them.
  • Pin exact redirect URIs in Auth0; avoid open redirects in your own app.
Tip

A quick production sanity script: hit your login URL with curl -I and confirm you see 302 to your Auth0 domain over https, a Set-Cookie with Secure; HttpOnly, and a Strict-Transport-Security header. If any are missing, fix before you ship.

13. Interview Questions (with model answers)

Q1. Why does Auth0 login rely on redirects instead of a normal API call?

A. Because the user must authenticate at the Identity Provider's own origin, so their credentials are never exposed to the relying app, and because HTTP is request/response — the only way a server can move the browser to the IdP and back is via 302 redirects. This also lets the IdP set its own session cookie and centralize MFA/SSO.

Q2. Explain the difference between the front channel and back channel.

A. The front channel goes through the browser (URLs, redirects) and is assumed observable — it carries the state, nonce, and authorization code. The back channel is a direct server-to-server TLS call carrying the client_secret and the actual tokens. Secrets and tokens stay off the browser by being confined to the back channel.

Q3. What exactly does an HTTPS certificate prove, and why is encryption alone insufficient?

A. The certificate, signed by a trusted CA, proves you've established the encrypted channel with the legitimate holder of that hostname — it provides server authentication. Encryption alone could be to a man-in-the-middle impostor; the certificate is what guarantees the other end is really auth0.com, making the encryption meaningful. TLS gives confidentiality, integrity, and authentication together.

Q4. state vs nonce — what does each defend?

A. state is a CSRF/round-trip binding: a random value echoed back on the callback that your app compares to a stored copy, preventing forged or cross-site callbacks. nonce is embedded inside the signed ID token and checked there, preventing ID-token replay/injection. One protects the request flow; the other protects the issued token.

Q5. Why can't you set Access-Control-Allow-Origin: * when sending cookies?

A. The CORS spec forbids combining the wildcard origin with Access-Control-Allow-Credentials: true, because that would let any site make credentialed cross-origin requests. You must echo the specific requesting origin and set Allow-Credentials: true.

Q6. A user logs in successfully but the app shows them as logged out on return. Name two likely networking causes.

A. (1) SameSite=Strict on the session cookie dropping it on the cross-site return from Auth0 — switch to Lax. (2) The app is behind a proxy and didn't trust X-Forwarded-Proto, so it built an http redirect URI / set a non-Secure cookie that mismatched. Also possible: a load balancer without sticky sessions / shared store losing the in-progress login state.

Q7. Why is storing JWTs in localStorage risky, and what's the alternative?

A. localStorage is readable by any JavaScript on the origin, so one XSS exfiltrates every token. The hardened alternative is an HttpOnly, Secure, SameSite cookie managed by a backend (BFF), invisible to JS; if a SPA must hold a token, keep it in memory only and rely on short lifetimes plus silent renewal.

Q8. What is a CORS preflight and when does the browser send one?

A. A preflight is an automatic OPTIONS request the browser sends before a "non-simple" cross-origin request (custom headers like Authorization, methods beyond GET/POST/HEAD, or non-form content types) to ask the server's permission. The server answers with Access-Control-Allow-* headers; only then does the real request go out.

14. Certification Tips

  • The Auth0 exam assumes fluency with the redirect flow: be able to order the steps /authorize → login → /callback → /oauth/token → session from memory.
  • Know that Allowed Callback URLs, Allowed Logout URLs, Allowed Web Origins, and Allowed Origins (CORS) are four distinct tenant settings — exam questions love mixing them up. Callback = where Auth0 may redirect after login; Web Origins = origins allowed to use silent auth/refresh; CORS = origins allowed to call Auth0 endpoints via XHR.
  • Expect questions distinguishing public vs confidential clients and which can hold a secret (only confidential).
  • Be precise on front channel vs back channel and what data each carries.
  • Remember that state is for CSRF and nonce is for replay — a classic single-best-answer trap.
  • Custom Domains exist partly so cookies/first-party context align with your brand domain — understand why a custom domain improves cookie behavior and silent auth.

17. Mini Project — A "Login Dance Inspector"

Build a tiny Node.js/Express app that implements the authorization-code flow against a free Auth0 tenant and logs every wire detail, so you can see the networking you just learned.

import express from 'express';
import crypto from 'node:crypto';
const app = express();

// Generate state + nonce, store them, redirect to Auth0 (front channel)
app.get('/login', (req, res) => {
  const state = crypto.randomBytes(16).toString('hex');
  const nonce = crypto.randomBytes(16).toString('hex');
  res.cookie('oauth_state', state, { httpOnly: true, secure: true, sameSite: 'lax' });
  res.cookie('oauth_nonce', nonce, { httpOnly: true, secure: true, sameSite: 'lax' });

  const url = new URL('https://YOUR_TENANT.auth0.com/authorize');
  url.search = new URLSearchParams({
    response_type: 'code',
    client_id: process.env.CLIENT_ID,
    redirect_uri: 'https://localhost:3000/callback',
    scope: 'openid profile email',
    state, nonce
  }).toString();

  console.log('[FRONT-CHANNEL 302] →', url.toString());
  res.redirect(url.toString());
});

// Verify state, exchange code (back channel), inspect tokens
app.get('/callback', async (req, res) => {
  const { code, state } = req.query;
  console.log('[CALLBACK] code=%s state=%s', code, state);
  if (state !== req.cookies.oauth_state) return res.status(400).send('state mismatch');

  const r = await fetch('https://YOUR_TENANT.auth0.com/oauth/token', {
    method: 'POST', headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      grant_type: 'authorization_code', code,
      client_id: process.env.CLIENT_ID, client_secret: process.env.CLIENT_SECRET,
      redirect_uri: 'https://localhost:3000/callback'
    })
  });
  const tokens = await r.json();
  console.log('[BACK-CHANNEL 200] tokens received:', Object.keys(tokens));
  res.json({ flow: 'complete', received: Object.keys(tokens) });
});

app.listen(3000, () => console.log('Inspector on https://localhost:3000/login'));

Deliverables: (1) the console log showing the front-channel 302 and the back-channel 200; (2) a screenshot of DevTools showing the cookies with their flags; (3) a short write-up mapping each log line to a hop in the §3.2 diagram. Stretch: add PKCE (code_challenge/code_verifier) and decode the ID token to confirm its nonce claim matches your cookie.

19. Cheat Sheet

  STATUS CODES        302 redirect · 200 token JSON · 401 authn · 403 authz
  LOGIN ORDER         /authorize → login+MFA → /callback?code&state
                      → POST /oauth/token (back channel) → Set-Cookie session
  CHANNELS            front = browser/URL (state,nonce,code)
                      back  = server↔server TLS (secret,tokens)
  ORIGIN              scheme + host + port   (cookies scoped by domain+path)
  TLS                 confidentiality + integrity + server auth (CA-signed cert)
  COOKIE FLAGS        Secure (https only) · HttpOnly (no JS) · SameSite=Lax
  state               random, echoed on callback → blocks CSRF
  nonce               random, inside signed ID token → blocks replay
  PKCE                code_verifier/challenge → blocks code interception
  CORS                preflight OPTIONS; no "*" with credentials; cache via Max-Age
  CSRF defense        SameSite + anti-CSRF token + Origin check
  XSS defense         output-encode + CSP + HttpOnly cookies
  PROXY HEADERS       X-Forwarded-Proto / -For / -Host (trust only your proxy)
  HARDEN HEADERS      Strict-Transport-Security · Content-Security-Policy
  SESSIONS@SCALE      shared store (Redis) or stateless JWT, not in-memory
  CDN RULE            never cache authenticated responses (Cache-Control: private,no-store)

20. Key Takeaways

Key

HTTP is stateless and request/response; that single fact forces cookies, tokens, and the redirect-based login dance into existence.

Key

The login flow splits across a front channel (browser, observable, carries code + state + nonce) and a back channel (server-to-server TLS, carries the secret and tokens). Secrets never touch the browser.

Key

HTTPS gives confidentiality, integrity, and server authentication via a CA-signed certificate — encryption to an unverified peer is worthless.

Key

state stops CSRF on the callback; nonce stops ID-token replay; PKCE stops code interception. Always keep all three on.

Key

Cookies are your friends when hardened (Secure + HttpOnly + SameSite) and your enemy when not. Keep tokens off localStorage; defend against XSS with CSP and encoding, and against CSRF with SameSite + tokens.

Key

Proxies, load balancers, and CDNs silently break auth unless you forward X-Forwarded-*, share session state, and never cache authenticated responses. With this wire-level model in hand, Chapter 4's OAuth 2.0 flows will read as straightforward applications of these primitives.
